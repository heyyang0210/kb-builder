##   [1. Overview（概述）](#1-overview概述)  

透明压缩是以BLOCK为单位进行压缩，然后利用Hole Punching能力释放压缩的磁盘空间，从而达到节省空间的目的。

与页面编码等压缩方式不同，透明压缩和解压在write/read block时发生，对上层透明。

##   [2. Features（功能特性）](#2-features功能特性)  

可以创建透明压缩的的表空间，此表空间上的所有对象在持久化时，会进行压缩，比非压缩状态更加节省磁盘空间。

##   [3. Interfaces（接口）](#3-interfaces接口)  

####   [3.1 使用透明压缩](#31-使用透明压缩)  

create tablespace 新增compress语法，用于指定此表空间的压缩属性(默认使用lz4压缩算法)：

```
create tablespace tbs datafile 'tbs' size 10M compress [zstd | lz4];

```

##   [4.Limitations（功能限制）](#4limitations功能限制)  

- windows版本暂不支持
- 支持的文件系统：XFS，ext4， Btrfs， tmpfs， gfs2
- 表空间创建完成之后，透明压缩的属性不能再被修改
- 如果文件系统不支持punch hole或者文件系统的的页大小不为512、1024、2048或4096，不支持透明压缩


##   [5. Detail Design（详细设计）](#5-detail-design详细设计)  

透明压缩是在数据块持久化时，通过压缩算法将原始的block进行压缩，并将压节省的空间通过文件系统的Hole Punching能力释放其占用的实际磁盘空间，使用的时候再将压缩后的block解压为原始的block加载到内存中来。整个过程可以总结为以下流程：

```
             压缩                  刷盘/打洞                 读取                 解压
【原始BLOCK】-------&gt; 【压缩BLOCK】-------------&gt;【磁盘BLOCK】-------&gt;【压缩BLOCK】 --------&gt; 【原始block】
                                  

```

block是否被压缩需要记录在block head上，用于后续的解压，压缩后的数据大小以及压缩算法等需要持久化。

```
typedef struct StBlockHead {
    CodUint32    checkSum;
    CodUint32    changeNum;
    CodUint64    lsn;
    SpaceBlockId id;
    CodUint8     type;
    union {
        CodUint8 encInfo;
        struct {
            CodUint8     encAlgo : 3;
            CodUint8     kVer : 5;
        };
    };
    CodUint8     compress : 1;  // 表示是否压缩
    CodUint8     unused : 7;
    CodUint8     reserved[1];
} BlockHead;

typedef struct StBlockCompressInfo {
    CodUint16 size;     // Compressed data size
    CodUint16 type : 3; // Compressed type
    CodUint16 align : 13;
    CodUint32 reserved;
} BlockCompressInfo;

```

###   [5.1 数据块压缩](#51-数据块压缩)  

data buffer中的block是原始的block，当需要被刷盘时，block会首先拷贝到dbwr的flush buffer中。此时如果block所在的表空间指定了透明压缩，首先通过LZ4对原始block进行压缩，压缩之后有以下几种情况：

1. 压缩失败或压缩之后的size大于等于block size：不压缩，写入原始的block
1. 压缩释放的空间不足一个文件系统的页大小：不压缩，写入原始的block
1. 压缩释放的空间大于等于一个文件系统的页大小：将释放的空间按照文件系统的页向下取整，写入压缩后的block，并将释放的空间进行打洞

1. 进行打洞释放空间。


###   [5.2 文件打洞](#52-文件打洞)  

当压缩释放的空间至少为一个文件系统的页大小时，可以通过fallocate接口进行打洞，释放占用的物理空间。

```
#define _GNU_SOURCE             /* See feature_test_macros(7) */
#include &lt;fcntl.h&gt;

int fallocate(int fd, int mode, off_t offset, off_t len);

Deallocating file space
    Specifying the FALLOC_FL_PUNCH_HOLE flag in the byte range starting at offset and continuing for len bytes.
    Within the specified range, partial filesystem blocks are zeroed, and whole filesystem blocks are removed from the file.     	 
    After a successful call, subsequent reads from this range will return zeros.

```

###   [5.3 数据块解压](#53-数据块解压)  

当block从磁盘读取到data buffer时，完成block的解压。由于打洞的文件位置可以正常读取(返回0)，因此可以按照原来的block size来读取，而不用管压缩之后的block size。

将block读取到data buffer中之后，需要根据block head上的压缩信息判断是否需要解压此block。如果需要解压，将其解压到handler的buffer中，然后再重新拷贝回data buffer。

整个过程可以总结为以下流程：

```
【读取页面】-------&gt; 【checksum校验】-------&gt;【解压】-------&gt;【校验原始block的checksum】 -------&gt;【解压数据拷贝到dataBuf】 -------&gt; 【页面校验(头未校验、checksum校验等)】

```

###   [5.4 持久化](#54-持久化)  

创建压缩表空间，表空间和数据文件都需要记录压缩信息，并持久化（ctrl和redo）。

存在两个问题：

1. 是否需要支持指定压缩算法？
1. 视图是否需要显示压缩后的文件大小？


####   [5.4.1 压缩算法持久化](#541-压缩算法持久化)  

```
typedef struct StRecCreateSpace {
    CodChar   name[COD_NAME_BUFFER_SIZE];  
    CodUint32 id;
    CodUint32 extentBlocks;
    CodUint16 flags;
    CodUint8  type;
    CodUint8  encAlgo : 3;
    CodUint8  keyVersion : 5;
} RecCreateSpace;

```

TablespaceCtrl以及datafileCtrl、datafile record中有预留空间可以持久化压缩算法。    
  目前createSpace的record没有多余的空间可以使用，只可以通过flags来标记是否压缩，不可以记录压缩算法，（需要三位的空间）。

解决方案：    
  1. spaceId 只需要CodUint16 的空间即可，可以将RecCreateSpace中的id改为CodUint16（<font color='red'> 已选用该方案 </font>）    
  2. 新增表空间压缩的日志类型

####   [5.4.2 数据文件压缩大小持久化](#542-数据文件压缩大小持久化)  

支持视图查询数据文件压缩后的大小，需要每次打洞之后统计数据文件的大小，并且持久化。

```
typedef struct StDataFileCtrl {
    DeviceCtrl base;
    CodUint8   used;
    CodUint8   compressType;
    CodUint16  flags;
    CodUint32  nextBlocks;
    CodUint32  maxBlocks;
    CodUint32  pageCount；  // Number of file system pages
    CodUint32  reserved;
} DataFileCtrl;

```

1、数据统计可能不准确，数据文件打洞之后，该值没有持久化，数据库挂掉，会没有更新成功，视图显示的信息会不准确。    
  2、代码调试过程中发现，打洞之后，部分不会释放空间，所以会出现统计的大小与du查询的大小不一致。（测试数据，(4M,2M+12K)、(8M,4M+20K)、(16M,8M+40K)、(32M,16M+72K)、(64M,32M+136K)、(128M,64M+264K)、(256M,128M+524K)）

可以通过lstat接口来计算磁盘的占用大小。（<font color='red'> 已选用该方案 </font>）

###   [5.5 异常处理](#55-异常处理)  

####   [5.5.1 文件系统不支持打洞](#551-文件系统不支持打洞)  

1. 创建压缩表空间，如果文件系统不支持，需要报错。
1. 如果系统的页面大小不是512、1024、2048或4096，需要报错，不支持表空间压缩。
1. windows系统不支持表空间压缩，需要报错。


####   [5.5.2 dbwr写失败](#552-dbwr写失败)  

1. 对文件打洞意味着从数据库角度看空间已经被申请，但是有可能文件系统中对应的空间已被使用，当dbwr写入的时候有可能会因为磁盘物理空间不足而报错。对于这种情况，按照现有的故障处理机制，dbwr进入循环尝试，并上报告警，等待磁盘空间释放。
1. 页面处于压缩表空间，但是文件系统不支持打洞，dbwr打洞会失败不报错。


####   [5.5.3 备份压缩表空间](#553-备份压缩表空间)  

如果备份集所在的文件系统支持文件打洞，可以考虑压缩表空间的备份集也打洞，减少备份集的空间大小。    
  如果备份集所在的文件系统不支持打洞，备份不能失败，压缩表空间的备份集按原始大小备份(不解压直接备份或者解压后再备份)。

####   [5.5.4 restore压缩表空间](#554-restore压缩表空间)  

如果数据库所在文件系统支持文件打洞，restore恢复压缩表空间时，需要进行打洞。    
  如果数据库所在文件系统不支持打洞，restore恢复时失败？

1. 期望恢复成功，restore恢复时需要解压数据页面(压缩没有意义)，持久化信息不更改，dbwr 写页面时需要容错。
1. 期望失败


####   [5.5.5 HA](#555-ha)  

主机支持表空间压缩，备机不支持表空间压缩？

会出现以下2种情况

1. 备机build失败，无法新增备机。
1. 备机回放失败，need repair， 该备机无法修复。


方案：（持久化的数据不更改）

1. 备机正常回放，备机不压缩表空间，不执行文件打洞。
1. build成功，如果是restore是build，备机解压数据页面再写入磁盘，该备机不压缩表空间，也不执行文件打洞。

1. yasminer
1. 健康检查
1. dump


####   [5.6.7 压缩页面的范围](#567-压缩页面的范围)  

有以下两种方案：

1. 所有的页面都需要压缩，创建表空间或者是新增数据文件时，需要对初始化的页面进行压缩打洞。
1. 初始化的页面不压缩，只压缩dbwr刷盘的页面。


优缺点比较：    
  方案一：创建表空间和新增数据文件的速度较慢。省空间。不用尝试打洞验证文件系统。    
  方案二：创建表空间的速度快，没有业务时，该表空间的大小跟原来一致。占用空间。，创建时需要尝试打洞来验证文件系统。

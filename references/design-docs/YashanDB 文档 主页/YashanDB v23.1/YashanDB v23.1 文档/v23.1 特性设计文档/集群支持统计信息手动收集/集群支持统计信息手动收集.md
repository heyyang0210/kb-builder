#   [YDBRD-15403 : 集群支持统计信息手动收集](#ydbrd-15403--集群支持统计信息手动收集)  

  [https://jira.yasdb.com/browse/YDBRD-15403](https://jira.yasdb.com/browse/YDBRD-15403)  

##   [1. Overview（概述）](#1-overview概述)  

1. 单机下对于统计信息的收集主要集中在两个基础函数：ankGatherTableStats、ankGatherIndexStats。无论是搜集全量还是部分统计信息，底层都是调用这两个函数，ankGatherTableStats包含了table、part table、column、part column的收集，ankGatherIndexStats包含了index、part index的收集
1. 收集流程大致为，初始化StatsManager、divide segment、根据并行度初始化若干个worker线程收集统计信息、合并workers上的统计信息、upadte系统表、update dc内存
1. 在集群下，仍然走单机的统计信息流程，由于涉及到系统表和dc的更新，因此需要广播同步到其他实例。由于统计信息上的是表的S lock，因此需要同步的去update dc，而不能直接失效dc。update dc的方式主要根据执行实例广播过来的type、oid、idxId、columns信息、pnum信息去加载相应的系统表，在dc上申请相应的内存，update dc。广播过程中需要考虑并发、失败重试、可重入。


##   [2. Features（功能特性）](#2-features功能特性)  

1. 单机统计信息手动收集集群化，某个实例执行完统计信息手动收集完成后，其他实例能感知到此次收集的结果
1. 支持多实例并发收集同一个表/不同表统计信息收集

##   [4. Specification And Constraints（规格与约束）](#4-specification-and-constraints规格与约束)

##   [5. Detail Design（详细设计）](#5-detail-design详细设计)  

###   [5.1 Data Structures & Flow（数据结构与流程）](#51-data-structures--flow数据结构与流程)  

```
typedef struct StRecGatherStats {
    CodUint64 tabId;      // table oid
    CodUint64 idxId;      // index id
    CodUint64 pnum;       // part number
    CodUint32 columnCnt;
    CodUint8  type;       // STATS_BTREE/STATS_COLINDEX or other
    CodUint8  unused[3];
    CodUint32 columnId[0];
} RecGatherStats;

```

###   [5.2 方案实现](#52-方案实现)  

1.按照单机逻辑执行ankGatherTableStats或ankGatherIndexStats，由于广播层是statsSingleGather中的statsSet中执行，因此广播层只会处理某个table/某个index/某个table part/某个index part/某个table的若干列/某个part table的若干列

2.在本地doSetStats设置完成后，调用AXC_CB->axcBcstGatherStats进行广播，广播内容为BcstGatherStats结构体中的内容

3.被广播到消息的实例根据BcstGatherStats中的内容读取系统表，若是在dc中已有内存，则直接覆盖，否则则申请内存置为NULL，随后set。根据type和pnum，有以下几种处理场景：

1. 若type = STATS_BTREE/STATS_COLINDEX且pnum = COD_INVALID_UINT64。根据idxId获取index，随后根据index->desc.id读取SYSINDEXES，table->statsSet.idxStats[index->desc.indexSlot]若为NULL则mctxAlloc申请内存，随后将系统表上读取出来的内容set到对应位置。
1. 若type = STATS_BTREE/STATS_COLINDEX且pnum != COD_INVALID_UINT64。根据idxId获取到index，然后根据pnum和index获取到IdxPartDict，最后根据IdxPartDict->desc.id读取SYS_INDEX_PART系统表获取对应信息。将table->statsSet.idxStats->count到index->desc.indexSlot的槽位全部申请出来并置NULL，table->statsSet.idxStats[index->desc.indexSlot]若为NULL则mctxAlloc申请内存，若IndexStatsSet->partStats为NULL则mctxAlloc申请内存，并将partStats->count到pnum的所有槽位都申请出来并置NULL，最后单独获取pnum的槽位，若为NULL则mctxAlloc申请内存。最后将系统表上读取出来的内容set到对应位置

1. 若type != STATS_BTREE/STATS_COLINDEX且pnum != COD_INVALID_UINT64且为表的处理。根据oid获取dc，随后根据pnum和dc获取TabPartDict，根据TabPartDict->desc.id读取SYS_TABLE_PART。将table->statsSet.partStats->count到pnum的槽位全部申请出来并置NULL，最后单独获取pnum的槽位，若为NULL则mctxAlloc申请内存。最后将系统表上读取出来的内容set到对应位置
1. 若type != STATS_BTREE/STATS_COLINDEX且pnum = COD_INVALID_UINT64且为列的处理。根据columnCnt构建循环，在循环中去读取columnId[]数组中具体的column id，最后根据oid和column id读取SYS_HIST_HEAD，将table->statsSet.colStats->count到column id的所有槽位都申请出来并置NULL，最后单独获取column id槽位若为NULL则mctxAlloc申请内存，最后将系统表上读取出来的内容set到对应位置。列这边还需要额外处理直方图的更新，需要根据oid和column id读取SYS_HISTOGRAM，同样也是将信息更新到colStats相同的位置的不同字段
1. 若type != STATS_BTREE/STATS_COLINDEX且pnum != COD_INVALID_UINT64且为列的处理。根据columnCnt构建循环，在循环中去读取columnId[]数组中具体的column id，根据dc和pnum获取TabPartDict，最后根据TabPartDict->desc.id和column id读取SYS_HIST_HEAD。由于分区表和分区列都是通过table->statsSet.partStats管理，因此需要先将table->statsSet.partStats->count到pnum的槽位全部申请出来并置NULL，最后单独获取pnum的槽位，若为NULL则mctxAlloc申请内存，随后创建table->statsSet.partStats[pnum]->colStats内存。将这段内存分配完成后，将table->statsSet.partStats[pnum]->colStats.count到column id的所有槽位申请出来并置NULL，最后单独获取pnum槽位，若为NULL则mctxAlloc申请内存。最后将系统表上读取出来的内容set到对应位置。针对分区列同样也需要处理直方图更新。


###   [5.3 并发问题梳理](#53-并发问题梳理)  

1. 多实例并发同一张表的统计信息收集：目前只支持gather并发，并没有set和delete和gather并发，后续如果有这种并发，广播的时候可能从系统表上读不出信息，需要做容错，gather之间的并发只需要处理消息层的并发即可，在广播的过程中，系统表的信息可能会被同步更改，导致广播同步的dc信息可能一半旧一半新，但到最终所有广播完成后，dc上的统计信息会走到一致的状态。
1. 单实例多线程并发同一张表的统计信息收集：同多实例并发一致。
1. 消息层处理的可重入性、并发控制：通过dc->memLatch控制并发。
1. 消息层处理时失败的错误分支处理方式：一是读取系统表失败，此时dc内存没有改动，不影响任何结果，等待重试即可；二是分配内存失败，由于dc的申请内存是不可逆的，只能随着dc淘汰被回收，但一旦objArrayAdd成功后，下一次不会重复add，因此没有问题，但如果多次失败，这种不可逆的内存浪费会被进一步放大。

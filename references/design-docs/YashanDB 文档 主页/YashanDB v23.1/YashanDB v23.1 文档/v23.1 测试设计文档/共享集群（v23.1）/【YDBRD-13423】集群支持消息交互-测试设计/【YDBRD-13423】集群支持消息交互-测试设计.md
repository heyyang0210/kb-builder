# **1.概述**

开发设计文档：    [集群消息交互设计](/pages/createpage.action?spaceKey=YAS&title=%E9%9B%86%E7%BE%A4%E6%B6%88%E6%81%AF%E4%BA%A4%E4%BA%92%E8%AE%BE%E8%AE%A1)  

IR链接：    [YDBRD-12145](https://jira.yasdb.com/browse/YDBRD-12145?src=confmacro)    -  ICS支持集群消息交互  完成     SR链接：    [YDBRD-13423](https://jira.yasdb.com/browse/YDBRD-13423?src=confmacro)    -  【共享集群】集群支持消息交互  完成

集群消息交互，是在统一网络框架ICS（Internal Communication Service 内部通讯服务软件）的基础上，增加适配，包括集群通信的协议适配、消息处理、内存管理、后台处理消息线程分组等等

# **2.需求分析**

ics适配主要实现如下功能：

|功能|设计表现|设计说明|
|:---|:---|:---|
|消息分组|上层在定义通信消息的同时，可以将消息划分到某个组|提供消息分组功能|
|内存管理|上层发送接收消息时，不需要关注内存|提供内存管理，包括分配与释放等|
|集群节点管理|上层可通过接口增加、启停节点|提供节点加入启动ics，节点停止离开ics|
|消息读取回调函数|适配ICS底层消息读取|接收线程可通过该回调读取剩余消息|
|后台处理线程|后台异步线程进行分组，处理依赖关系不大的消息|提供异步消息处理能力|
|消息发送与接收|上层调用发送和接收不需要传入太多的参数|提供同异步发送、接收接口, 包括消息广播|


涉及的任务类型（消息类型）：

|task|description|
|:---|:---|
|async task|处理页面相关消息|
|batch task|处理批量消息，如pastcopy 的正反向清理|
|bsct task|同步 scn 消息|
|complex task|处理一致性读页面相关消息|
|gls task|处理DDL 和 锁相关消息|
|reform task|处理reform 消息|


# **3.规格/范围**

1、部署形态：集群

2、集群支持的实例个数：实例个数不超过4节点

3、ics底层协议通讯的安全性：对于底层的ics协议本身集群并未做修改，使用分布式原有的ics协议，所以对于协议本身的安全性当前不做测试

# **4.约束限制**

**4.1. 当前的约束限制**

1、当前"INTERCONNECT_RECEIVE_TIMEOUT"参数只能设置为0，因为上层还没处理超时的情况，后面有消息异常处理的需求，参数设置层面可以设置，只是业务层面未处理。

2、不支持不连续内存的发送与接收，这一点在测试层面不需要关注，这个点后续会实现

3、task 不支持自动负载均衡，这一点在测试层面不需要关注，后续会实现

4、内存管理不支持自动伸缩，后续会实现

5、故障场景当前不做测试，故障当前未转测

6、INTERCONNECT_MESSAGE_POOL值设置为最小值，这种场景当前不做校验，后续迭代3涉及到机制更改，迭代3再测

**4.2. 实现机制本身的规则**

1、该参数设置为“ON”时，DB的runlog必须设置为debug才会有消息日志的打印

# **5.动态视图/配置参数**

|参数|参数说明|默认值|取值范围|生效方式|参数类型|备注|
|:---|---|---|---|---|---|:---|
|INTERCONNECT_RECEIVE_TIMEOUT|用于控制recv msg的超时时间|0|【0，3600】|重启生效|非隐藏参数|单位为s，技术项目已有参数 ，当前该参数只能设置为0，因为上层还没处理超时的情况，后面有消息异常处理的需求。|
|INTERCONNECT_MESSAGE_POOL|用于控制msg pool的大小|8:64;8:8800;8:16800;8:32800|count:【1，1024】,size:【32，65536】|重启生效|非隐藏参数|技术项目已有参数 ，格式：count:size;count:size;count:size;count:size,INTERCONNECT_MESSAGE_POOL当前不支持自动扩展，迭代3会有需求涉及到该参数的自动扩展,count：消息池能够存储的消息的上限,size：消息缓存单元的大小（msg pool的大小是"count*size"）,从业务层面，构造"消息池被耗尽"的场景（GLS_TASK_COUNT参数值设置较小时，多实例并发下业务，这个时候，msg接收会很快，原则上可以构造这种场景，场景构造成功时，日志中会有" msgpool is exhausted, try ics alloc msg"信息打印，在INFO及以上级别即可打印）|
|INTERCONNECT_LINKS|每个实例的连接数|2|【1，16】|重启生效|非隐藏参数|技术项目已有参数,这个参数是ics底层会用到的一个参数，对于测试而言不可见，保证参数可以设置成功，能传给ics底层即可,多实例之间该参数值需一致|
|GLS_TASK_COUNT|用于控制gls task的线程数|2|【2，64】|重启生效|非隐藏参数|这个值较小时，可能会比较慢；值较大时，相对会比较快；对性能有一定影响|
|GCS_TASK_COUNT|用于控制async和complex的线程数|3|【2，64】|重启生效|非隐藏参数|同上|
|_CLUSTER_MESSAGE_LOG_ENABLED|用于控制集群消息日志的打印|OFF|可选项：【OFF，ON】|立即生效|隐藏参数|该参数设置为“ON”时，DB的runlog必须设置为debug及其以上的级别才会有消息日志的打印,日志中会有"AXC MSG"相关的打印信息|

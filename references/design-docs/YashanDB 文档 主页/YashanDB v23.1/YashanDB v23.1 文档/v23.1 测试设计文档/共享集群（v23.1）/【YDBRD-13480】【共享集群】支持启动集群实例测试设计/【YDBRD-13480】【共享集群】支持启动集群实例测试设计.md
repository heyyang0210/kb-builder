# **1.概述**

集群部署形态下，数据库实例启停时需要与其他组件交互，不再是进程独立运行。数据库实例启动需要注册到YCS组件，关闭需要通知YCS组件。实例在运行期间，通过YCS组件感知其他数据库实例状态变化。数据库实例需要与其他实例交互，通过消息交互保证集群数据库的一致性使用。

# **2.需求分析**

**测试 范围分析**

## 1、数据库实例需要与其他实例交互，通过消息交互保证集群数据库的一致性使用。

     ** 1.1 DB关闭时**  ：该实例与其他数据库实例解除联系，支持退出过程其他数据库处理在线业务

     ** 1.2 DB启动时**  ：该实例与其他数据库实例互联，支持启动过程其他数据库处理在线业务

## 2、实例间db资源的并发加入、退出

  


**涉及操作命令**  ：ycsctl start resource   ycsctl stop resource ycsctl status ycsctl start ycs ycsctl stop ycs

  


#### 启动分析：

1、（nomount）DB实例启动时，将本地ics_addr注册到YCS，YCS将此实例加入到集群后，返回集群的拓扑信息到当前实例。同时YCS广播最新的实例状态到集群他实例。

2、（mount）实例发起加入请求

    主实例(第一个启动的实例)，无需执行此步骤

    非主实例，向master实例发起加入请求

3、

a、将新启动的实例加入到本地拓扑关系中，ICS服务自动将对应实例的连接通道建立起来

b. 当前主实例发起reform，对所有在线实例的GRC加锁，进而锁住全局资源访问（  全局缓存服务  GCS，  全局锁服务  GLS）。  --此时业务会卡住重试  --是否有不被卡住的情况

c.资源重分布(remaster)

    针对所有在线的实例执行remaster，根据新的实例分布完成资源的重分布，各实例根据新的dht信息，将数据进行迁移到对应的实例。

d. 释放全局资源

    实例加入集群模式下，完成资源重分布即可释放全局GRC锁，使得当前在线的实例可以处理业务，此阶段新的实例拓扑关系原则上已经生效。

e.撤销事务托管

master实例检查最新实例拓扑关系，关闭加入实例的托管事务回滚，  将托管事务内存释放掉  。此阶段对托管事务的并发访问会路由到正在启动的实例，通过判断数据库状态进行拦截和重试。  

f.完成reform和实例启动

当前面几步都完成后，正在启动的实例收到完成finish reform的应答，进入后续的启动流程，完成实例启动。

#### 停止分析：

1.   实例注销

实例注销退出同样由主实例发起reform，将退出实例相关的资源信息重分布到其他在线实例中。实例退出根据退出的角色不同分为：

 - 非master实例退出，将其持有的资源信息转移到其他在线实例，由master实例托管此实例事务。

    - master实例退出，将其持有的资源信息转移到其他在线实例，释放当前被托管的事务，通知ycs做switchover切换db master，由new master实例托管所有未启动实例事务。   

 - master实例退出，当前实例是最后一个实例，此阶段直接退出，不需要进行reform。

2.   退出YCS 

DB实例退出时，同样需要回调YCS提供的接口，通过YCS通知所有在线实例刷新实例拓扑关系，关闭ICS连接等，实例退出的拓扑关系维护是reform最后阶段刷新的。

3.   主实例退出reform

 1.释放本地资源 实例退出要先关闭本地会话连接，释放所有本地资源，然后再通知YCS，此阶段后不会再产生新的本地资源访问。

 2. 锁定全局资源 锁定全局资源后，所有跨实例的请求都会被阻塞在本地，此阶段除了事务请求/DDL广播外，不会再有新的请求过来，且后台请求会逐步被处理完成。

 4. 释放全局资源 实例注销退出集群时，完成资源重分布即可释放全局GRC锁，使得其他实例可以处理业务，此阶段新的实例拓扑关系原则上已经生效。

 5. 主实例托管事务 主实例进行事务托管加载，此阶段不会产生托管事务回滚。

 6. 完成reform 各在线实例关闭相应的网络连接，退出实例继续完成后续的停止流程处理，残留的消息直接丢弃由请求者重试。

###   [GRC迁移](https://conf.yasdb.com/pages/viewpage.action?pageId=109585476#grc%E8%BF%81%E7%A7%BB)  

GRC管理的资源状态信息数据分布在所有节点上，就需要路由策略供访问时使用，当前GRC采用一致性hash算法，在一致性hash环上每个实例负责若干区间的数据，相关元数据称为DHT rule。在集群节点成员变动时，每个实例负责的区间发生变化，生成新版本的DHT rule，并按照新的规则在节点间重 新分布被管理的资源数据。

### **规格**

- 部署形态：集群
- 节点数量：最大4节点（测试时以3节点为测试场景）
- 部署模式：单主机磁阵+多主机磁阵


### **约束限制**     

 1、nomount拉起三个节点。n0 节点为master，在非master节点n1节点建库。此场景不支持    
   2、某节点nomount状态下，其他实例异常，该节点升主，由于是nomount状态，会自己退出。

  


    A.启动YCS，单独启停DB并发                            --可测，ycsctl start resource，ycsctl stop resource

    B.并发执行YCS启停  时同时启动DB                     --不可测，【YDBRD-13464 支持启停YCS节点特性】 合入后可测

    C.YCS启停时同时启动DB + 启停DB  并发       --有ycs并发不可测，db并发可测。

# **三.测试设计方法**

该需求的测试场景和观察点主要涉及2个方面：

1、DB的串行启停，覆盖已转测的业务类型           --业务不阻塞（报错或成功），保证数据一致性

2、实例间不同DB、实例内同一DB的并发启停

     --启动模式的组合（mount nomount open）

     --实例间不同DB启动和停止组合，进行并发

     --不同的部署方式（一节点，两节点，三节点，四节点），测试以三节点为主

     --多节点下，实例内同一DB启动和停止并发

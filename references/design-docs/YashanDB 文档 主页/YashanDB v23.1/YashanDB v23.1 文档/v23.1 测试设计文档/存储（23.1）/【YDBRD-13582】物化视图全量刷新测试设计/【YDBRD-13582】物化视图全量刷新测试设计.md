# **1. 概述**

物化视图创建时可以指定多种不同的刷新模式，在创建后将使用这些刷新模式进行手动、或者定时、或自动拉取数据，以保证物化视图能够同步数据。

# **2. 需求分析**

SR:     [YDBRD-13582](https://jira.yasdb.com/browse/YDBRD-13582?src=confmacro)    -  物化视图支持全量刷新  完成

开发设计：    [物化视图全量刷新设计文档](https://conf.yasdb.com/pages/viewpage.action?pageId=122074149)  

本次特性范围仅支持物化视图全量，其他功能后续演进； 其中，将支持以下几种全量刷新模式：

- 创建时指定build immediate，创建完成后即刷新数据
- 创建时指定on demand，将利用高级包功能进行手动刷新
- 创建时指定定时参数，物化视图将内置job功能定时刷新
- 创建时指定on commit，物化视图将在基表相关事务提交时刷新


**部署模式限制：**

- 特性支持的部署形态为 主备(单机) （其他部署形态视后续演进支持）
- 单机行执行 （列执行后续演进支持）


  


**手动刷新使用高级包刷新**

exec dbms_mview.refresh(); 参数列表：

|参数|数据类型|说明|
|:---|:---|:---|
|TAB|VARCHAR|物化视图名字|
|METHOD|VARCHAR|物化视图名字，默认是C（全量刷新），可留空，指定时仅C有效，其他模式暂不支持|
|REFRESH_AFTER_ERRORS|BOOL|兼容参数，仅列表兼容|
|PURGE_OPTION|INTEGER|兼容参数，仅列表兼容|
|PARALLELISM|INTEGER|并行度兼容参数，仅列表兼容|
|ATOMIC_REFRESH|BOOL|指定TRUE时，刷新行为是delete全表+insert into select；指定为FALSE时，刷新行为是truncate全表+insert into select|
|NESTED|BOOL|嵌套刷新，暂不支持。兼容参数，仅列表兼容|
|OUT_OF_PLACE|BOOL|兼容参数，仅列表兼容|


  


MATERIALIZED_VIEW$系统表新增一个字段MV_JOB_ID，用以关联定时刷新任务与物化视图记录

|字段|数据类型|说明|
|---|---|---|
|MV_JOB_ID|BIGINT|物化视图定时任务创建的JOB的OID|


  


跟刷新相关的参数说明：

-  build分支语法功能支持
    - build immediate：指创建时即完成一次全量数据刷新，填充数据并持久化
    - build deferred： 指创建时仅完成定义创建，不刷新数据
- create mv refresh子句
    - 刷新类型选项
        - fast：快速刷新【仅语法支持，无快速刷新功能，即使指定了快速刷新，实际刷新也是全量刷新】
        - complete：全量刷新
        - force：优先快速，如快速刷新不可用则切换为全量刷新【目前仅支持全量刷新】
    - 刷新模式选项
        - on demand：根据手动命令或高级包刷新【目前支持使用高级包刷新】
        - on commit：事务提交时刷新相关联物化视图
        - on statement【因SE要求这个语法选项已经删去】
    - 定时刷新选项【功能支持】
        - start with date：指定第一次刷新定时时间
        - next date：指定刷新间隔时间
    - 指定不刷新：never refresh【指定后无法刷新】


# **3. 测试设计方法**  ** **

**测试设计方法：**

- 针对高级包的各个参数，采用等价类划分的方式，对参数的有效等价类做组合覆盖，无效等价类单独覆盖
- 针对高级包刷新功能验证，主要采用场景法和错误分析法，从用户的角度出发，列出来可能存在的场景来进行覆盖
- 针对定时刷新，采用场景法和正交组合的方式，列出start和next所有存在的正常的时间值，并start和next的存在的正常的时间间隔做组合覆盖（异常场景已经在create、alter需求中覆盖）
- 针对on commit刷新，采用场景法，列出所有基表可能的dml和ddl场景，对基表进行修改，查看物化视图是否对应修改


  


**测试范围：**

- master table表结构：heap、tac、lsc
- 部署形态：单机、HA、集群和分布式不支持需要拦截
- 基表：1个、多个
- 子查询：走全表扫描、索引扫描、索引回表的方式扫描
- 刷新场景：基表空表刷新、小数据量刷新、大数据量刷新
- 刷新方式：创建刷新、手动刷新、定时刷新、commit刷新、从不刷新 几种方式进行交互组合刷新
- 刷新前后数据对比:
-           本次刷新和上次刷新无数据变化
-           本次刷新和上次刷新之间有DML操作导致数据的变更
-           上次刷新空表，本次刷新有新增数据
-            上次刷新表中有数据，本地刷新后为空表


  


**测试关注点：**

- 刷新的数据正确，刷新的时机正确
- 失败刷新场景报错信息正确
- 无卡住、死锁、core问题
- 刷新后走重写的方式查询数据正确、执行计划正确
- MATERIALIZED_VIEW$：
-       MATERIALIZED_VIEW$中新增MV_JOB_ID，各种刷新方式都需要观测该字段是否正确
-       在指定定时刷新时结合MATERIALIZED_VIEW$中的MV_JOB_ID，在DBA_JOBS、DBA_SCHEDULER_JOBS中观察信息是否正确


  


**所有刷新方式公共的基表结构变化的场景有：**

1、drop +create 重建

- drop后创建一个同名的表，且表的结构相同
- drop 后创建一个同名的表，物化视图查询的列类型相同，未引用的列结构不同
- drop 后创建一个同名的表， 物化视图引用的列不存在
- drop 后创建一个同名的表， 物化视图引用的列数据类型不相同


2、truncate：truncate基表后做刷新

3、drop column

- drop column 在add 一个相同的列
- drop 一些column后再add column ，物化视图查询的列类型相同，未引用的列结构不同
- drop 一个物化视图引用的列
- drop 一个物化视图引用的列后再add 同名的列， 物化视图引用的列数据类型不相同


4、add column

5、alter table rename

6、alter table shrink table

7、alter table modify datatype

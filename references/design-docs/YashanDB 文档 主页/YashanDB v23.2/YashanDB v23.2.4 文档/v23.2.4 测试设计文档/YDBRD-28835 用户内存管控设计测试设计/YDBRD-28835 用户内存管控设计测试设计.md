# 1. 概述

在嘉实POC时，客户明确要求有资源隔离的能力，即单个查询不能影响整个引擎。客户的痛点问题是，他们当前系统因为资源隔离功能不合理，一些app写的SQL不合理占用了大量系统资源，导致频繁需要人工干预处理，甚至因此受到他们的客户的投诉。

从资源隔离能力看，涉及CPU、内存、IO、磁盘空间等维度。IO、磁盘空间的资源隔离能力，客户并没有提及，暂时不在考虑范围内。CPU资源隔离能力Yashan已经支持，也给客户做过演示，得到客户的认可。内存资源隔离则是客户关注的重点，在交流过程中也明确需要这个能力。

内存管理

1、公共内存及特殊内存通过推荐配置等管理策略来管理，不属于本 SR 的管理范畴。

2、用户内存通过  资源管理体系RESOURCE MANAGER进行配置管理。用户申请的内存，需要以用户标识（例如用户ID或资源使用组ID）进行标记和跟踪，可以通过专门的视图按用户（或资源使用组）进行查看。

用户内存配置项、COLUMNAR_VM_BUFFER_SIZE 预占及根据 stage 数进行切分、本 SR 实现的内存管控的关联关系

在没有内存管控的情况下，所有用户的所有并发同时可用的总内存由 COLUMNAR_VM_BUFFER_SIZE 配置决定，超过使用量以前的版本会对用户报错，当前版本已实现了 COLUMNAR_VM_BUFFER_SIZE 根据 stage 数进行切分及预占，可以避免因内存不足导致的查询 SQL 报错；本 SR 实现的内存管控，用户(资源组)/用户 session 在预占内存时会对申请的内存进行校验是否超过 limit 限制，如果超过则无限次重试，直到预占成功后执行 SQL 。根据 limit 设置的大小，用户能感知到性能可能会受影响，不会对用户报错。对 CPU 及 parallel worker 的资源管控以前的 SR 已实现，不在本 SR 的测试范围内，本 SR 只关注内存资源管控的相关场景。

用户使用资源管控步骤：

1、创建资源组(CREATE_CONSUMER_GROUP)

2、创建资源计划(CREATE_PLAN)

3、创建资源指令(CREATE_PLAN_DIRECTIVE)

4、资源使用者映射到资源使用组(SET_CONSUMER_GROUP_MAPPING)

  


## 2.2 应用场景

本 SR 解决的核心问题是内存资源的隔离能力，即在配置了内存资源管控的情况下，2 个用户执行的业务相互影响在用户层面可控，用户及 session 执行业务可用的内存由用户根据业务特点自己控制；

1、不同用户执行不同的查询，每个用户执行的业务能使用的内存由用户所属资源组的配置来控制，不应超过配置值；

2、不同 session 执行不同的查询，session 执行的业务能使用的内存在 session 所属资源组来控制，不应超过配置值；

用户通过高级包 DBMS_RESOURCE_MANAGER 的方法来创建资源组---创建计划—创建资源计划指令，对内存资源进行管理；

1、通过资源组关联数据库用户，来对数据库用户使用用户内存进行资源管控，用户的所有 session 实际使用的内存之和不超过资源组内存 limit；

2、通过资源组内配置该资源组内所属用户连接的 session 的内存 limit ，来对用户 session 使用用户内存进行资源管控；单个 session 上的内存使用不超过 session 的内存 limit

3、同时配置资源组内存 limit 及session 的内存 limit；用户组的所有 session 实际使用的内存之和不超过资源组内存 limit，同时单个 session 上的内存使用不超过 session 的内存 limit，任意一个超过限制都会触发资源管控

由于使用内存上限由用户配置，存在不超配、超配 2 种情况，测试场景也应覆盖这两种场景；

资源组配置好内存上限百分比之后，CN、DN、MN 根据各自节点上用户内存的配置之和进行上限计算；

用户也可能在配置好资源组后，将资源组进行切换；

默认是没有资源管控的，如果没有设置，默认行为为单用户、单 session 可使用的内存上限为 100%；

在进行资源管控配置时，用户是否会校验是否存在？是否会校验资源组是否存在？如果不校验，没有创建资源组指令的资源组默认行为是什么？--- SET_CONSUMER_GROUP_MAPPING 的时候会去验证用户名和 group id ，可以不考虑这个测试点；

另外一种情况是扩容 CN、DN 组或者节点时，应该将资源管控同步到新扩容的节点上，保证设置在所有节点上生效，缩容也不影响剩余节点上的资源管控；

## 2.3 规格约束

|规格或约束|描述|技术原理|备注|
|---|---|---|---|
|规格|支持按资源使用组级别内存管控|使用内存前，需要向资源组申请内存配额|Oracle只有会话级，不过Oracle支持了最大活跃会话数，间接控制住了资源使用组的内存|
|规格|支持按会话级别内存管控|使用内存前，需要向会话申请内存配额|OceanBase只有租户级内存管控，会话级没有划分|
|规格|内存配额最终还受实际内存资源限制|即使配额足够，内存资源使用完了同样无法申请到内存|  
|
|规格|内存配额允许超过系统配置内存值|由实际内存资源限制兜底|是否需要开关控制？OceanBase有这个配置resource_hard_limit，主要避免OOM，Yashan通过参数推荐控制了总内存|
|规格|只有用户内存资源才进行管控|公共内存使用不受资源使用组管控|  
|
|规格|动态调小内存管控上限，可能会延时生效|已经分配出去的配额要等会话释放了才能回收|  
|
|规格|cn在执行之前占有的内存，不纳入重试机制，如果不足则报错|

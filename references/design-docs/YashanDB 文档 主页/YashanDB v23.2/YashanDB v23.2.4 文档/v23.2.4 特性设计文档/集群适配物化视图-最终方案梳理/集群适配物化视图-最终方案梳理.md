## 刷新流程

|适配分析|具体方案|备注|
|---|---|---|
|高级包刷新|跨实例也是走的高级包流程，天然支持|  
|
| on commit刷新流程：,需要让其他实例上基表的dc能感知到有物化视图,（基表dc不失效，需要发消息让基表加载物化视图）|创建物化视图时发消息同步,重建基表同名表同步|  
|
|物化视图的刷新属性变化：,物化视图的dc会失效，但基表dc不失效；,对于其他实例已经打开的基表dc，需要同步dc上物化视图的变化    
  在刷新过程中发现物化视图dc失效，重新加载物化视图dc即可，理论上天然适配|每次刷新都重新打开物化视图dc；,天然适配|  
|
|【并发】,刷新时的并发控制,  
|在集群下使用一个全局mutex，锁的粒度是物化视图，保证多实例也可以串行刷新|  
|


##   
  查询重写的失效机制

|适配分析|具体方案|细节|
|---|---|---|
|查询重写的跨实例失效，需要消息承载集群化，否则可能会core或在不同实例查出错误数据。,场景：,一个基表变化了，物化视图的dc不失效，仅把刷新的valid标志修改；如基表名字变了、列类型变了等等触发,  
,此时需要在集群将这个valid修改同步过去，以达到目的：,该物化视图的列定义已经和基表的列元数据不同， 不能再用于查询改写，但从文本匹配无法识别，必须将valid标志同步过去，否则可能会core|tabInvalidMViewStatus 这个机制需集群化,改造涉及的DDL二阶段MSG,  
|改造了ddl info，引入一个hasMView标志,这个标志代表着本次alter的对象上有关联物化视图。,如果alter的广播消息过去，会尝试打开该对象上的物化视图，并将valid标志刷新|


  


## 执行计划失效机制

|适配分析|具体方案|实现细节|
|---|---|---|
|场景：物化视图的查询改写属性变更,（即原来不可以重写，现在可以用物化视图重写）,需要将基表已经生成的计划失效。 单机的变更是修改基表的版本号，这个需要做集群化,  
,单机行为：基表dc不失效；,通过版本号变更，触发含基表的plan失效,  
,达到目的：若之前物化视图不允许改写，现在改成允许；,基表在其他实例已经生成的plan失效，重parse之后，改用物化视图重写、,或之前允许改写，现在改成不允许，也要失效plan|mViewUpdateMasterTabVer 这个机制需集群化,/* update master table version to invalidate plan cache */,  
  消息同步期间，瞬时在部分实例上允许重写，部分实例不允许，可能涉及数据新鲜度的问题，但影响不大,可接受|在ddl info上引入一个updateMasterTabs标志；,意味着需要刷新基表的version，让这些基表已经生成的执行计划能够失效|

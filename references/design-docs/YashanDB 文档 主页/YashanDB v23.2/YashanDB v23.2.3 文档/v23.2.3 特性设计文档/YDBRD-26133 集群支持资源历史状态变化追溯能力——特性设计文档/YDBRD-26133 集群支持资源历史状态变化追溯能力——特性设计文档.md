*IR链接：*    [YASHAN-979 集群支持资源历史状态变化追溯能力](https://pingcode.yasdb.com/ship/ideas/660b7443009f91eb87f2b323)

##   [1. 总述](#1-总述)  

###   [1.1 需求来源](#11-需求来源)  

在开发过程中，可能会存在实现上的问题使数据库在运行的过程中出现故障，如果涉及到全局资源（当前包含：GCS/GLS），我们通常需要依赖于DEBUG日志来确认GCS/GLS资源的变化过程（何时请求了block，以什么权限等等）。然而，在实际的生产环境中，出于性能考虑，客户通常会选择将日志级别设置到INFO或者更低的级别，如此一来则无法通过DEBUG日志来确认全局资源的变化——倘若客户现场因全局资源直接或间接发生问题，DEBUG日志的缺少将使得问题的定位与解决变得困难。

因此，本需求旨在提供一种能力，可以不依赖于DEBUG日志，将全局资源的近期变化记录下来，并提供在适当的时机进行导出分析的能力。

###   [1.2 调研文档](#12-调研文档)  

  [特性调研文档](https://conf.yasdb.com/pages/viewpage.action?pageId=152995780)    中尝试分析了Oracle的类似能力，但是由于资料缺失、信息过少，难以分析其具体能力、推测其实现。

###   [1.3 需求分析](#13-需求分析)  

从需求来源来说，本需求需要对数据库本身性能不要产生影响，而且能够具备一定的可供研发人员定位问题的能力。

出于性能、内存使用考虑，主要记录GCS/GLS资源的某一时刻最近的若干固定数量的历史动作，比如仅为    `block 1-0-1024`    记录最近的最多16次动作记录。对于超过数量的历史动作记录，总是选择淘汰时间最早的记录，保留最新的记录。

|属性|场景名称|方案设计|关键技术点|特性是否涉及|
|---|---|---|---|---|
|功能|资源master记录经过master的GCS/GLS资源动作|master在GRC resource上记录资源的历史变化|否|是|
||用户dump GCS资源动作历史|通过提供SQL语法使用客户端进行dump|否|是|
||黑匣子dump GCS/GLS资源动作历史|在已注册的信号处理函数内主动dump现有资源|否|是|

##   [3. 规格与约束](#3-规格与约束)  

- 仅在集群部署形态有效
- 最多记录到当前时刻最邻近的16条历史
- GCS资源历史mount后可dump
- GLS资源历史mount后可dump


##   [4. 特性](#4-特性)  

在对资源动作的记录上，我们需要区分是否是发生在master上，发生在master上的动作可以记录在GRC上；而非资源master实例上可能也会涉及到一些动作（它们不经过master），不过由于其可能会频繁复用，所以暂不考虑记录了。

同时，我们要考虑尽可能占用少的内存。

经过平衡存储大小和信息重要程度后，整理出所需要记录的信息：

```
typedef struct StGrcHistory {
    union {
        CodUint8 history;
        struct {
            CodUint8 status : 2;
            CodUint8 role : 1;  // reserved for grc role
            CodUint8 type : 5;
        };
    };
    union {
        CodUint8 byte1;
        struct {
            CodBool  unused : 2;
            CodUint8 peerInst : 6;
        };
    };
} GrcHistory;

```

|字段|名称|说明|作用|
|---|---|---|---|
|type|动作|经重新编码的消息类型（很多请求的使用的消息是类似的，为了节省内存使用并预留给未来的消息使用，将相似消息进行了重新编码）|最关键的知晓资源流转的类型|
|status|资源状态|经重新编码的资源状态（GCS/GLS中请求的资源状态比较相似，进行了编码）|最关键的知晓资源流转时涉及的资源状态|
|role|角色|为    [YDBRD-26195 集群GCS支持资源角色](https://pingcode.yasdb.com/pjm/items/6618f16dfd997db58ad84cd1)    预留的字段||
|peerInst|对端实例|资源历史动作的对端实例（相对于master自身来说）|最关键的知晓资源变化的请求者|


GrcResource上记录近期16条，共占用32字节（原始GrcResource占用144字节，增加32字节属于可接受范围）。

###   [4.1 资源master记录经过master的GCS/GLS资源动作](#41-资源master记录经过master的gcsgls资源动作)  

仅在消息闭环时，由master记录原始请求信息到GRC resource上：

||消息类型|编码动作|编码权限|说明|
|---|---|---|---|---|
|GCS|MSG_REQ_MASTER_BLOCK|REQ_RES|S/X|requester向master请求block|
||MSG_REQ_RA_BLOCK|REQ_RA|X(请求RA后owner被登记为X)|requester向master请求预读block，可能涉及到多个block|
||MSG_REQ_MASTER_CR_BLOCK|REQ_RES|NONE|requester向master请求CR block（有的情况不会主动闭环，这种不会记录）|
||MSG_REQ_MASTER_UPGRADE_BLOCK|REQ_RES|UPGRADE|requester在持有block的S权限时，向master请求X权限（即升级）|
|GLS|MSG_REQ_MASTER_LOCK|REQ_RES|S/X/UPGRADE|requester向master请求gls lock|
||MSG_REQ_RELEASE_LOCK|REQ_RES|NONE|requester向master登记释放gls lock|


由于对内存使用的严格要求，对实际存储在内存的编码方式进行了调整，动作可能不具备唯一的编号，具体说明参见上面的描述。

###   [4.2 用户dump GCS资源动作历史](#42-用户dump-gcs资源动作历史)  

用户通过提供的语法可以主动dump GCS的资源动作历史，并在trace文件中进行查看。本能力主要是在    [YDBRD-25891 集群支持全局block资源dump](https://pingcode.yasdb.com/pjm/items/6611a8eb579a3edb84d861c9)    的基础上进行扩展。

在dump的实例上，从master获取GrcResource将历史信息一起dump出去。

###   [4.3 黑匣子dump GCS/GLS资源动作历史](#43-黑匣子dump-gcsgls资源动作历史)  

当数据库触发段错误等其他错误，进而触发信号处理函数时，需要主动将已有的GCS/GLS资源动作历史导出，可以用于辅助分析问题：dump遍历GrcResource，有信息的打印，没有跳过。

###   [5.4 黑匣子生成耗时评估](#54-黑匣子生成耗时评估)  

在集群四实例部署，且各自DB配置为：

```
DATA_BUFFER_SIZE=512M
REDO_BUFFER_SIZE=32M
REDO_BUFFER_PARTS=8
SHARE_POOL_SIZE=1G
SQL_POOL_PARTS=8
HA_ELECTION_TIMEOUT=18
HA_HEARTBEAT_INTERVAL=6
CONTROL_FILES=('+DG0/dbfiles/ctrlfile0', '+DG0/dbfiles/ctrlfile1', '+DG0/dbfiles/ctrlfile2')
CLUSTER_DATABASE=TRUE
RECYCLEBIN_ENABLED=OFF
INTERCONNECT_MESSAGE_POOL=1024:64;512:8800;128:16800;64:32800
#TRANSACTION_LOCK_TIMEOUT=180
RUN_LOG_LEVEL=debug
RUN_LOG_FILE_COUNT=200

```

这种情况下，使用    `kill -11`    干掉db模拟生成黑匣子，大约生成了GCS相关的信息8249条，GLS信息567条，文件大小为507KB，耗时50毫秒。

估算的话相当于有    `8249 * 8KB = 64MB`    的block，根据这个数据将dump的过程重复1560次（    `GrcResource = 8249 GCS + 567 GLS, 8000 * 8K = 64M, 100G / 64M = 1560`    ），以便模拟100GB data buffer的情况，仅dump grc大约耗时22秒（也就是GCS信息约    `8249 * 1560 = 12868440`    条，GLS信息约    `567 * 1560 = 884520`    条），文件大小为652MB。

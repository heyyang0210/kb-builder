# 1. 需求概述

**IR描述：**

描述

需求来源： 研发 

场 景： 集群下资源历史状态变化追溯能力，提供问题定位效率（增加全局资源历史转移信息，解除DEBUG日志依赖） 

需求描述： 集群下资源历史状态变化追溯能力 

需求规格：

部署形态：集群

#   
  2. 功能点

1、用户dump gcs资源动作历史：使用已有sql语法"  alter system dump datafile  "

2、黑匣子dump gcs/gls资源动作历史：开发实现，测试不感知，测试需要测试

# 3. 规格约束

从研发概要设计中获取

1、部署形态：集群

2、对于资源的操作：最多记录16条历史记录-------考虑大于16时的表现

3、GCS/GLS资源mount后即可dump-----考虑对于非mount状态的拦截，gcs资源已有拦截用例，gls资源需要新增拦截用例

# 4. 主要应用场景

**需求本身的主要应用场景**

1、数据库日志为INFO级别，且数据库出现bug时，进行分析定位，重点测试，测试dump信息的正确性和完备性

2、数据库业务正常进行的过程中，dump能力对数据库的影响程度

**需求与其他特性的关联场景**

1、与故障的交互：故障产生后，黑匣子的dump能力

2、与并发业务的交互：业务过程中dump，对业务的影响，要考虑性能

# 5. 概要测试设计

## 5.1 功能测试设计

### 1.说明测试设计的整体思路，明确测试范围，规格限制。可以使用流程图、逻辑覆盖等方法体现测试思路。

**说明：**

该特性属于研发自己保证质量的需求，测试只做轻量级测试，投入人力为2人/天左右，保证基本功能和稳定性，不影响功能，不影响性能

**整体测试思路：**

1、测试dump的基本能力，验证功能正确性。

- 这部分测试中，主要覆盖gcs和gls的典型消息流场景即可，不用做全量级覆盖，涉及的业务类型使用普通表即可，dump时单实例串行和多实例并行dump交叉测试
- 这部分测试很明确，直接使用场景法即可


2、测试dump操作对业务的影响，这部分需要业务和dump同时进行

- 这部分测试中，需要在dump的过程中，并行下发业务，检查dump对业务的影响，这里gcs和gls分别覆盖1-2个场景即可，数据量放大，涉及的业务类型使用普通表/分区表/临时表/索引，混合测试即可
- 在tpcc业务运行过程中，进行资源的dump操作，检查dump对性能的影响
- 导入导出过程中进行dump操作，会不会影响导入导出的性能，需要进行测试摸底一下，可以放在sit进行，视测试进展决定是否测试


3、测试黑匣子dump能力/故障场景

- 手动模拟构造故障场景，检查故障场景下，黑匣子dump出来的信息的完备性和正确性，这里覆盖两种场景即可，gcs业务过程中故障和gls业务过程中故障
- 在机器资源（内存）比较小的前提下，并发dump较多的资源，测试这种场景下会不会core，优先级不高，建议放在sit阶段进行测试


4、其它规格约束相关测试

- 对于资源的操作：最多记录16条历史记录-------考虑大于/小于16时的表现：小于16时：全部记录；大于16时：新记录覆盖旧记录
- GCS/GLS资源mount后即可dump-----考虑对于非mount状态的拦截，gcs资源已有拦截用例，gls资源需要新增拦截用例

# 3. 规格约束

**需求范围**

故障范围包括（磁盘故障、网络故障、网络拥塞、进程退出服、服务器宕机）

1 网络故障是否指所有类型网络故障（包括网卡down/网络交换机故障/网线故障、网络延迟、双链路场景下down掉其中一条网络链路）

（1）网络丢包支持

2 服务器宕机场景中是否包含reboot场景-----包括

3 进程退出是否包括所有形式（kill -9、kill -19、kill -18、kill   ~~15）~~   ---包括

  


**需求规格**

1、部署形态：集群

2、节点个数：4

3、支持4节点在线故障恢复

4、DB层面：支持多点故障，支持连续故障

（1） 多点故障是指什么场景？------多个节点同时故障

（2） 连续故障是指什么场景？------1个节点故障之后，故障恢复的过程中，另一个节点继续故障

（3）支持范围是：4个节点中任意一个节点故障，还是可以支持到4个节点中任意多个节点故障？------可以支持到4个节点中任意多个节点故障

（4）高可用是否支持集群HA-------不支持

（5）约束中明确指出的不支持能力直接不测还是代码中会做拦截处理------------不会做拦截

5、YCS层面故障范围是相同的（下面这几种都是支持的）

（1）叠加故障：同时产生两种不同类型的故障（比如：同时产生网络故障和磁盘故障）

（2）多点故障：多个节点同时故障（比如：正常4节点场景下，节点1和节点2都故障了）

（3）连续故障：在1个节点故障后，整个集群层面故障还没有处理完成，这个时候另一个节点又故障了（比如：4节点场景下，节点1故障了，集群ycs层面还在处理故障，这个时候节点2又故障了）

  


**需求约束**

1、YCS层面有无规格约束限制？----开发同步，暂时无，后续需要持续关注

2、YCS层面新增配置参数是否会支持在线修改？新增配置参数时涉及到的线程数可以动态扩缩吗？实际使用的线程数有没有可测视图可以观测？------开发同步：当前不支持动态参数修改，后续也不会有相应修改计划；新增配置参数时涉及到的线程数是否可扩缩待会上确认；开发DFX层面需要提供可测视图

3、和竞品设计实现上的差异性（来自开发概要设计文档）

-  触发节点重启的机制不同，崖山是节点通过读主节点磁盘中的信息来判断是否需要重启， ORACLE 中是读取  kill     block  中的有毒信息去重启。 
-  集群发生重组集群的触发机制不同，崖山是当发现集群中主节点的磁盘心跳异常或者网络异常时，会通过自有的选举算法选出新的集群主节点。  ORACLE  通过守护进程中的网络心跳分析线程，以及磁盘心跳中对VF的可见性通过集群管理节点（RM）来进行集群重配置。


# 4. 主要应用场景

## 4.1 需求本身的主要应用场景

集群本身的高可用只要在产生故障时都会涉及，所以主要应用场景就是故障场景：在故障产生时，集群可以正常处理故障，保证整个集群的可用性。

## 4.2 需求与其他特性的关联场景

1、该需求涉及到整个集群的各个服务组件，各个服务组件之间的交互，主要涉及YCS\YFS\DB

2、在故障过程中必然要有业务才有测试的意义，该特性涉及到的关联业务较多，从对象的角度划分，主要有如下对象：

# 5. 概要测试设计

## 5.1 功能测试设计

### **1.测试设计整体思路**

**4节点高可用的实现和2节点高可用的实现在整体方案上无较大变更，但是与2节点高可用相比，场景更加复杂。整体测试设计思路沿用23.1"2节点高可用"需求的测试方案，但是需要在2节点高可用测试设计的基础上做相应的补充。**

#### （1）2节点高可用的大概测试思路

1）从不同组件的层面去做测试：YCS/YFS/DB/3者之间的交互

2）不同业务类型下的故障

3）覆盖不同的故障类型

4）从代码分支和内部实现机制的角度，做打点测试

#### （2）4节点高可用和2节点高可用在测试场景层面的区别

1）2节点场景下，不管对于ycs还是db，都不会出现多个非master角色，但是4节点场景下有这种情况

2）2节点场景下的故障，不管对于ycs还是db，不会出现多个节点同时故障的场景，但是4节点场景下有这种情况

3）2节点场景下，从DB内核global memory的角度考虑，RMO模型中必然有2个角色是在同一个节点上的，但是4节点场景下会有3个角色在不同节点上的场景

4）2节点场景下，从ycs的角度来考虑，因为经历了23.1补丁版本noscsi的大改造，所以在机制内部实现上是有差异性的，但是从测试角度而言，我们重点关注外部的业务表现，外部业务表现无大差异

5）2节点场景下的大部分打点已失效，对于ycs而言，需要在重构之后，针对性的新增打点能力，对于db而言，无法构造的场景需要新增打点能力，尤其是global memory消息流中的故障场景

#### （3）4节点高可用整体测试思路

1）复用2节点高可用的用例，根据测试点新增用例和修改用例（修改用例主要指已有的2节点用例；新增主要是指针对2节点和4节点有差异的地方进行用例新增），主要涉及HA用例+testkill KT用例+一致性 KT用例

2）针对上述第2点所列的区别点做用例设计和新增

#### （4）其它测试点

1）ycs层面新增workPool机制，用于解决"ycs/yfs的业务逻辑与ics的消息接收线程耦合导致在某些特定场景下ics底层节点启停并发因而挂起"的问题，需要针对该场景做针对性测试

2）需要考虑ycs 3+节点的并发启停和该需求的先后依赖关系，若并发启停先转，需要考虑并发启停过程中出现故障的场景；否则，在ycs3+节点的并发启停需求中考虑该场景

### 2.关键数据、测试场景的构造方法，用例自动化方法，可能涉及的测试框架说明。

#### （1）测试场景构造方法

1）对于故障构造方式，进程退出类统一采用kill方式；网络故障类统一采用混沌测试工具模拟；宕机/掉电类统一采用ibmc/交互机端下发掉电类模拟

2）对于测试过程中涉及的业务数据，数据量可以不用很大，各种ddl操作和dml操作覆盖全即可

#### （2）用例自动化方法

1）对于指定场景类的用例，使用HA框架进行自动化，需要识别是否需要做框架适配和接口新增，在用例自动化的过程中进行识别

2）对于随机kill场景，使用testkill框架和一致性框架进行自动化，需要识别是否需要做框架适配和接口新增，在用例自动化的过程中进行识别

3）对于打点场景的用例，使用guider框架的fp接口，需要识别是否需要做框架适配和接口新增，在用例自动化的过程中进行识别，需要提前根据开发设计文档进行打点识别

4）对于网络故障的场景，使用dfx框架进行自动化，需要识别是否进行业务背景的新增，以及框架的适配

5）长稳过程中的故障，需要识别是否进行业务背景的新增，以及框架的适配

6）RTO的测试，需要在对应的维护用例中做框架适配和维护

## 5.2 DFX测试设计

DFX部分的测试点和2节点场景下无差异，主要测试点如下：

### **5.1 性能层面测试：**

（1）正常tpcc场景测试，测试该需求对性能指标的影响

（2）tpcc业务过程中kill主/备，检查DB层面集群能否正常恢复

### **5.2 RTO层面测试：**

（1）2节点场景下，tpcc业务过程中kill主/备，集群自动恢复，测试这个过程中的RTO，测试对2节点RTO结果的影响

（2）4节点场景下，tpcc业务过程中kill主/备，集群自动恢复，测试这个过程中的RTO，进行RTO值摸底

（2）4节点场景下，tpcc业务过程中主/备 断网，集群自动恢复，测试这个过程中的RTO，进行RTO值摸底

（3）4节点场景下，tpcc业务过程中主/备 断电，集群自动恢复，测试这个过程中的RTO，进行RTO值摸底

1、RTO测试需要确认在哪个阶段进行，迭代阶段还是SIT阶段，还是跟着SR走，取决于这个需求和RTO需求的转测前后关系，这个需求必然是会影响RTO的------------RTO测试集中放在RTO专项中进行测试

2、RTO的时间建议各个组件以视图的形式展示，可提高可测性和效率，涉及YCS/YFS/DB-------DB层面已提诉求，在DB支持多节点高可用的需求中转测，在视图中进行展示；YCS在日志中增加RTO的关键标志符；YFS层面基本不涉及，当前未对其做规范性要求和新增

### **5.3 数据一致性KT层面测试：**

（1）基础串行业务场景中异常恢复后的一致性校验------功能场景中已覆盖

（2）大并发过程中异常恢复后的一致性校验和持久性校验------框架适配，适配后测试

（3）性能过程中异常恢复后的一致性校验

（4）YCS层面的IOFENCE场景下的一致性校验需要考虑

### **5.4 长稳层面测试：----王伟跟踪**

（1）已有长稳基础业务中增加部分故障场景（涉及主/备分别故障或者主备同时故障），检查DB层面集群能否正常恢复

（2）已有长稳模型中增加故障场景，检查DB层面集群能否正常恢复

（3）这里重点针对DB层面，YCS层面并不涉及，因为YCS层面主要在有业务的情况下触发了iofence会涉及到这部分交互，但是这属于基础功能层面的验证，没必要在长稳层面进行验证。

# 1. 需求概述

YCR盘支持导入、导出（升级、备份恢复依赖）

# 2. 功能点

1）原yascs.ini拆分为全局配置和本地配置

2）以下配置项放到全局配置中

VOTING_DISK

NETWORK_HB_TIMEOUT

DISK_HB_KEEP_ALIVE

3）导入时从全局文件导入到ycr

4）导出时，从ycr导出到文件

# 3. 规格约束

**需求范围**

1、导出export的能力为根据YCR的参数导出一套ycsctl命令集合（.sh），  是能够实现原有集群配置部署的全量命令脚本。

2、导入  import  的能力为通过这个导出的命令集合进行备份恢复和升级回退。用旧工具执行导入，即可一键回退。

3、首次部署时，不可使用导入能力。新增ycsctl set ycr_config key value的能力，key为voting_disk和network_hb_timeout以及disk_hb_keep_alive。这部分从yascs.ini挪出来。

**需求规格**

1、部署形态：集群

2、节点个数：2   — 原则  上  与节点数目无关，可以尝试多配置节点，少启动  – 四节点可测，两节点为主测试

3、启动时YCS带DB

4、对文件格式、编码格式和文件大小是否有要求？ –-  不做文件大小、文件一致性、文件格式的校验

**需求约束**

1、YCR目前只能静态修改，即YCR必须再没有启动的情况下导入。

2、新增入口是否支持并发？ – ycr导入与单条ycr命令并发，最终结果不保证是一个原子操作

3、  导出的文本，如果用户改了其中命令的顺序、语法等原来能校验的错误，会导致部分成功，不保证原子性和回滚到最初状态，也就是说在配置前不校验

4、  扩缩容或者修改参数值的场景，不和升级一起进行，是同版本ycsctl下单独进行修改。这部分的修改需要提前导出备份，以免操作失败无法回退

# 4. 主要应用场景

## 4.1 需求本身的主要应用场景

在共享集群的环境下，客户可使用全局的配置文件直接可以导入YCR配置，也可以直接从YCR之中导出这个全局的配置文件，避免繁琐的命令行操作：

1、客户备份恢复的场景。

2、升级回退场景。

## 4.2 需求与其他特性的关联场景

1、  涉及已有ycsctl工具的扩展，考虑与已有命令的影响，比如并发控制、对YCSC的依赖、help信息的变化、资料的变更等。

2、涉及到本地配置项的变更，需要考虑参数的配置、删除、参数呈现的方式以及资料等部分的变化。

3、涉及到YCS的故障场景？？--- 是否能保证导入导出的原子性？命令的重入性？

## 4.3 友商实现机制调研

- ocr是动态数据，dcr是静态数据，前者支持备份恢复，后者不支持
- ocr和dcr都支持导入导出以及健康检查功能
- dcr的init功能，提供了对升级的支持
- dcr的init功能支持鉴权，ocr不支持
- ycr暂时不支持动态修改


# 5. 概要测试设计

## 5.1 功能测试设计

### **1.测试设计整体思路**

本需求属于对已有功能的增量开发提供更友好的用户使用体验，因此需要从新增功能的重点应用场景、客户体验感等各方面出发考虑测试，同时需要考虑现有功能的变更和影响。整体测试思路如下：

1、新增入口层面的测试，包括命令输入正常的使用、输入异常的合理报错及拦截等。

2、对导入导出功能的基本功能测试，新增重点内容，需重点测试。

     1）对于导入文件，需要从粗细粒度去考虑文件本身、文件内容的限制约束：

           a）粗粒度角度，包括对导入文件的路径、文件存在与否、超大文件是否兼容等角度进行测试；

           b)  细粒度角度，包括文件内部参数的校验，包括关键命令/关键字的输入输出异常、重复设置的校验、关键字缺省是否允许、文件多余空行空格等问题，是否能在启动阶段拦截。

     2）对于导出功能，对于文件的校验也需要从粗细粒度上去考量：

           a) 粗粒度角度，导出路径的校验（是否为指定路径）、文件格式等；

           b) 细粒度角度，关键字数值是否与现有系统一致等。

 3、对于全局参数的设置，主要是将已有yasdb.ini中的参数值挪到YCR盘中进行全局管理，这部分是对已有功能的变更，需要考虑对已有功能的影响，新增设置方式的实用性、可执行性各方面进行考虑。

4、考虑新增YCR命令的并发是否符合已有YCR的约束。

5、是否涉及故障，例如导入导出过程发生中断，能否保持系统一致性。 

6、需要考虑整个特性的可维可测性，观察手段是否明确；

7、考虑资料的描述是否合理正确、用户理解是否会存在歧义、对原有功能的变更修改是否全面等。

### 2.关键数据、测试场景的构造方法，用例自动化方法，可能涉及的测试框架说明。

#### （1）测试方法说明

1、对于接口层面的测试，主要采用等价类、错误推测类方法进行覆盖。

2、对于导入导出基本功能，主要采用场景法、错误推测法进行设计覆盖。

3、  对于并发场景，从开发需求实现机制的角度出发，重点采用场景法进行场景梳理，涉及到难点构造场景，及时和第一开发责任人同步对齐。

#### （2）用例自动化方法

1、该需求设计到YCR工具层面的接口增加，guider上需要添加新的入口，可与框架开发同事对齐。

2、关于并发、故障等场景，可以考虑用HA框架实现。

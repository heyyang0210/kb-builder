#   [子查询展开设计](#子查询展开设计)  

##   [1. Overview（概述）](#1-overview概述)  

1.本文档主要用于说明WHERE条件中包含子查询展开为JOIN场景的设计与实现（不包含投影列，join filter等场景下的子查询）。其中子查询包含in/not in, exists/not exists,  标量子查询,  any/all 这几种。将以前rewrite实现子查询改为join的场景，在CBO中重实现。

2.改进已有功能实现（可参见改进用例）

- 优化器更优路径丢失的问题，如 YDBRD-13997
- 减少跨层引用改写时引起的功能异常


##   [2. Features（功能特性）](#2-features功能特性)  

###   [2.1子查询展开为Join的类型](#21子查询展开为join的类型)  

- A. 展开Semi Join的子查询： in, exists,  any。
- B. 展开Anti  Join的子查询：not in,  not exists,  all。
- C. 展开为Left join的子查询： 标量子查询(<,<=,>,>=,=, != 比较运算符对应），并带有中返回单行约束（onerow标记)。


###   [2.2 展开/改写（前提）限制条件](#22-展开改写前提限制条件)  

####   [父查询限制](#父查询限制)  

- 子查询在父查询不能OR条件被包含。


####   [子查询限制](#子查询限制)  

- 子查询相关条件不能出现在OR条件中。


###   [生成join应满足](#生成join应满足)  

- **子查询为静态或者通过上拉解关联，不再包含引用**


其中：包含父查询等相关的引用不允许出现在Join filter的子查询当中（即自底改写不成功，上层亦不再改写）。

###   [2.3 改写后实现的功能](#23-改写后实现的功能)  

**简单子查询改写为semi/anit Join，其中简单查询是指不包含aggr, group by, connect by, windows function，limit的关联查询或非关联（静态）查询**  。

- 其中关联谓词为 in/not in、exists/not exists、any/all 三种场景。
- in 在行存场景可以为多列，列存不支持多列；
- 分布式场景delete/update不支持join，子查询也不进行上述改写。

##   [5. Detail Design（详细设计）](#5-detail-design详细设计)  

###   [1 子查询解关联算子](#1-子查询解关联算子)  

|逻辑算子|解关联位置|说明|
|---|---|---|
|OP_LOGICAL_SCAN|filter||
|OP_LOGICAL_TABLE_FUNC_SCAN|表函数输入expr||
|OP_LOGICAL_DBLINK_TABLE_SCAN|等同OP_LOGICAL_RESULT||
|OP_LOGICAL_VIEWSCAN|子算子无引用时可改写，否则不能改写|主要为from未上提场景或CTE|
|OP_LOGICAL_JOINGRAPH|join edge，参见解关联处理||
|OP_LOGICAL_RESULT|filter，暂不改写||
|OP_LOGICAL_AGGR|静态可改写；否则不可改写||
|OP_LOGICAL_GROUP|只有group by 静态可改写；否则不可改写(即含grouping_set不改写|存在filter上拉情况时，需要groupExprs增加上拉相关列|
|OP_LOGICAL_PROJECT|columns，子查询可合并时，可解引用||
|OP_LOGICAL_DISTINCT|columns,静态可改写；否则不可改写||
|OP_LOGICAL_SELECT|-||
|OP_LOGICAL_COUNT/OP_LOGICAL_LIMIT|静态可改写；否则不可改写。||
|OP_LOGICAL_CONNECT_BY/OP_LOGICAL_WINFUNC|静态可改写；否则不可改写。||
|OP_LOGICAL_UNION...|去重集合操作静态可改写；否则不可改写。||
|OP_LOGICAL_FIRSTROW|不改写||
|OP_LOGICAL_SORTAGGRDIST|不改写||
|OP_LOGICAL_ACSCAN|不改写||
|OP_LOGICAL_EXPAND|不改写||


###   [2 解关联处理](#2-解关联处理)  

|**子查询**  引用参数位置||处理|说明|
|---|---|---|---|
|join 条件||当join条件为inner join时，可上拉解关联；其他join类型时，不可解关联||
|where条件|一般filter(非子查询)|上拉解关联||
||子查询|暂不改写|~~可提取到join filter上~~|
||in-list|解关联||


改写成功的  **充要**  条件：子查询生成的算子树中成功能解关联（不包含引用）。

###   [3 相对旧版本的改进之处](#3-相对旧版本的改进之处)  

1. 子查询为静态时，进行改写（提升CTE，connect by, windows func等）
1. 子查询中当关联条件  **仅为where条件**  时，只含group by时会进行改写，含有aggr时，会要求关联条件必须全部为等于时才会改写。
1. 子查询投影列包含引用并且可合并到父查询的单表查询时，可进行改写。

typedef struct StDecorCtx {
    MemoryContext* mctx;
    ObjectArray*   outerRefs;
    ObjectArray*   srcExprs;
    ObjectArray*   filters;        // 上拉的filter

    CodBool        isDecorrelated; // 是可以解关联
    CodBool        isEqual;

typedef struct StSubqDesc {
    SelectDesc*  subQuery;   // 子查询
    ExprNode*    exprNode;   // 父查询对应子查询vQuery(EXPR_QUERY类型)
    FilterNode*  parentNode; // 父查询对应子查询的filter
    DecorCtx*    decorCtx;   
    SubQueryMode mode;       // 子查询类型，如exists,in 等
    CodUint16    subQId;     // 子查询ID
    CodUint8     isMergable; // 子查询是否合并到父查询中  
    CodBool      isShared;
    CodBool      isTransfed;
    CodUint8     unused[7];
} SubqDesc;

typedef struct StLogiApply {
    ApplyType    type;  // 子查询改写为Join对应类型分类
    CodUint16    dsId;  
    CboOperator* outer; // 父查询对应的算子
    SubqDesc*    subq;  
    ObjectArray* refs;
    Filter*      filter;
} LogiApply;

**transSubQs**   在对每个算子生成的Group在trans阶段时，如果当前算子有子查询，刚通过transSubQs进入。

1. extraSubq 针对当前算子进行子查询提取处理，调用每个逻辑算子的extraSubq 处理流程。
1. extraFilterSubQuery：逻辑算子内部对其filter 进行遍历，从而设置提取出来的子查询是否rewritable（可改写）。
1. tryTransApplies/transOpApply/transFilterApply: 对每一个算子包含的子查询逐一调用，生成Apply 逻辑算子尝试进行解关联生成Join。
1. genLogicApply：尝试对当前算子树进行逐个解关联，生成Apply算子。
1. transApply2Join：检查生成Join条件，生成当前子查询改写Join 逻辑算子。

##   [6. Testcases（自测用例）](#6-testcases自测用例)  

自测用例场景包含

1. 父查询中包含多个关联子查询（AND/OR条件组合）。
1. 父查询为集合操作
1. 父查询中where条件单个filter 左侧包含多个表的列。
1. 父查询为join tree，同时关联子查询（单个/多个）引用父查询中的多个表。
1. 父查询为join tree，同时子查询为join tree, 子查询引用父查询中的多个表。
1. 子查询为view 合并生成（CTE？）
1. in/not in,  exists/not exists 等单层组合的情况
1. in/not in,  exists/not exists 等深度嵌套多层的情况，包含跨层引用的情况。
1. 子查询中包含跨层引用的场景，即子查询中再次包含嵌套查询引用父查询的场景。
1. insert/update/delete/merge 语句场景。
1. 子查询中带参数（类型推导）场景（改写对类型推导是否有影响）

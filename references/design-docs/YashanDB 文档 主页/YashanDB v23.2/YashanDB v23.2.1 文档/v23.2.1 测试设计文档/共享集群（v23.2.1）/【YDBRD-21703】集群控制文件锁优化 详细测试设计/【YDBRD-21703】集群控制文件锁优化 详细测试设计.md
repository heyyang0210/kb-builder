# 1. 概述

前提：

在集群整个reform流程中，我们恢复出  宕机实例的recover block SET需要获取控制文件锁，而获取控制文件锁需要先获取grc->latch

背景：

1、2节点场景下，reform流程中可以成功获取控制文件锁，且不会有死锁现象（两节点场景下，控制文件锁只可能被未宕机的实例持有，即使宕机实例持有也没有影响，宕机实例死掉后直接释放了）

2、3节点场景下，reform流程中会锁住所有GRC资源，导致无法获取控制文件锁（因为当前控制文件锁可能被集群中其它存活实例持有）

实现：

1、基于上述现状，该需求做了如下优化："reform流程中，在任何情况下都可以获取控制文件锁，且不会有死锁产生"，具体实现细节如下：

（1）如果控制文件锁被其它节点持持有：  等待控制文件锁结束，并清理master上的锁标记；控制文件锁是最后持有的一定会结束，而且不会产生死锁。（等待时间是1min，超时后reform报错，master角色的reform操作退出）

（2）如果控制文件锁没有持有：直接使用

# 2. 需求分析

## 2.1 功能点分析

功能：

reform流程中，在任何情况下都可以获取控制文件锁，且不会有死锁产生

实现原理：

（1）如果控制文件锁被其它节点持持有：  等待控制文件锁结束，并清理master上的锁标记；控制文件锁是最后持有的一定会结束，而且不会产生死锁。（等待时间是1min，超时后reform报错，master角色的reform操作退出）

（2）如果控制文件锁没有持有：直接使用

## 2.2 应用场景

需求本身应用场景：所有触发reform流程的操作，主要涉及以下两类：

（1）DB实例加入退出

（2）DB实例故障-多个实例故障/单个实例故障

## 2.3 规格约束

- 部署形态：共享集群
- 节点数：3节点及以上

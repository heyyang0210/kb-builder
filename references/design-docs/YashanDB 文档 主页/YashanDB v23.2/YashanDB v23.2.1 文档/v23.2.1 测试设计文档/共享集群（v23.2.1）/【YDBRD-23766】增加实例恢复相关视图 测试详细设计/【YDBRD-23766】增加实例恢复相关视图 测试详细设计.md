# 1. 概述

增加视图  V$INSTANCE_RECOVERY  ，展示实例恢复相关信息

# 2. 需求分析

## 2.1 功能点分析

- 提供实例恢复期间，恢复的详细信息，包括：是否处于故障恢复中，恢复实例列表，实例恢复开始/结束时间，实例恢复涉及的redo量，单位字节


|字段|类型|描述|默认值|
|---|---|---|---|
|IN_RECOVERY|BOOLEAN|是否处于故障恢复中|false|
|INSTANCES|BIGINT|恢复实例列表，64位整型值，每一位代表节点的ID|0|
|BEGIN_TIME|TIMESTAMP|实例恢复开始的时间|NULL|
|END_TIME|TIMESTAMP|实例恢复结束的时间|NULL|
|RECOVERY_REDO_SIZE|BIGINT|实例恢复涉及的redo量，单位字节|0|


  


详细逻辑：

- 该视图中"in_recovery"字段和v$instance视图中的"IN_REFORM"字段的区别："实例加入/退出"操作也会被认为是reform任务，v$instance视图中的"IN_REFORM"字段会记录为"TRUE"
- recovery_redo_size-这个字段值的正确性如何校验？怎么知道的确需要恢复这么多redo量？-----在故障恢复前，查一下当前redo量，flush_point和rcy_point之间的redo差距量（第2个字段按照redo文件大小来换算），故障恢复后，拿"recovery_redo_size"字段的值和该值做对比
- master发生切换之后，原master上已有的恢复任务记录是否会保留？------不会保留，是内存的
- 通过yasql方式进行shutdown之后，该视图是否会记录这种情况？------不会记录，这种情况在db层面会被认为是正常退出
- 故障恢复的过程中，所有实例被干掉了，再次重新拉起所有实例，该视图中的值如何记录？----------值会被清空，因为实例经过了重启，并不会保留内存的东西


## 2.2 应用场景

- RTO测试时可以通过该视图字段直接读取到RTO时间，减少了筛日志的时间，提高了效率  （从"begin reform之后[多了一个广播的时间] 到end reform"的时间）
- 用例自动化时可以通过该视图字段获取集群当前的恢复状态，对于下一步的操作在时间是上可以有较为精准的判断，提高自动化用例的稳定性
- 在出现问题时可以通过该视图的字段做初步分析，提高定位效率


## 2.3 规格约束

- 该视图无gv$视图，只有master实例查看存在记录

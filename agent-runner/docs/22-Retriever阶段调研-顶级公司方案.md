# Retriever 阶段调研：5 大顶级公司解决方案

> 调研日期：2026-07-22
> 调研目标：梳理业界顶级公司在 RAG 系统 Retriever 阶段的解决方案，分析对本项目的实际参考价值。

---

## 1. 项目背景与素材特点

本项目有大量原始素材需要被检索和利用：

| 素材类型 | 存放位置 | 特点 |
|---------|---------|------|
| YashanDB 知识库 MCP | MCP Server（实时查询） | 结构化知识点，按 ku_name 索引 |
| 特性设计文档 | `references/design-docs/` | 详细的功能规格、设计方案 |
| Oracle 知识库 | `references/oracle-kb/` | 高质量参考内容，需改写为 YashanDB 版本 |
| 测试用例 | `references/test-cases/` | 可执行验证 SQL，包含边界测试 |
| 源码分析 | `references/source/` | 实现细节，兜底资料 |

**核心挑战**：这些素材格式各异、规模不一，如何让查询词精准匹配到高相关的文档和知识，是 Retriever 阶段需要解决的问题。

## 2. 五大公司方案

### 2.1 OpenAI — File Search（托管式 RAG）

- **核心思路**：全托管的端到端检索方案，开发者只需上传文件，OpenAI 自动完成分块、向量化、索引和检索
- **技术要点**：
  - 内置混合检索（向量相似度 + 全文搜索）
  - 自动 query 改写与扩展
  - 2025-2026 年升级为 Agentic RAG，Agent 可迭代搜索、阅读、再搜索
- **优势**：零运维，开箱即用

### 2.2 Google — Gemini File Search + Vertex AI RAG Engine

- **核心思路**：双层方案——轻量级用 Gemini API File Search，企业级用 Vertex AI RAG Engine
- **技术要点**：
  - **ScaNN 算法**：Google Research 自研的高性能向量搜索算法
  - 支持多模态检索（文本 + 图片 + PDF）
  - RAG Engine 提供评估、调优、数据源管理等企业级功能
- **优势**：多模态能力强，ScaNN 在大规模数据上性能优异

### 2.3 Microsoft — Azure AI Search（Agentic Retrieval）

- **核心思路**：企业级混合检索引擎，2025-2026 年推出"Agentic Retrieval"专用管道
- **技术要点**：
  - **混合检索**：向量搜索 + BM25 关键词搜索 + 语义排序（Semantic Ranker）
  - **Agentic Retrieval**：Agent 可动态决定检索策略
  - 支持 100+ 数据源连接器
- **优势**：数据源连接器最丰富，企业安全合规能力最强

### 2.4 Anthropic — Contextual Retrieval（上下文增强检索）

- **核心思路**：通过为每个文档块添加上下文前缀，大幅提升检索精度
- **技术要点**：
  - **上下文嵌入（Contextual Embedding）**：在每个 chunk 前注入由 LLM 生成的上下文描述
  - **上下文 BM25**：同样为关键词检索添加上下文前缀
  - 混合检索：上下文嵌入 + 上下文 BM25 + 交叉编码器重排序
  - 实测检索失败率降低 67%（相比朴素 RAG）
- **优势**：以最小工程代价获得最大的检索质量提升

### 2.5 Meta / LlamaIndex — Agentic Retrieval（智能体驱动检索）

- **核心思路**：将检索从"一次性查询"升级为"Agent 多轮自主检索"
- **技术要点**：
  - **多种高级检索器**：递归检索、自动合并检索、知识图谱检索、层级检索
  - **Query 路由**：自动将查询分发到最合适的索引/数据源
  - **Reranking**：支持交叉编码器、LLM-based 重排序
- **优势**：开源灵活，检索策略最丰富

## 3. 对本项目的实际参考价值

### 3.1 参考价值分析

本项目与上述公司方案的场景有本质区别：

| 维度 | 顶级公司方案 | 本项目 |
|------|------------|--------|
| 数据规模 | 海量非结构化文档 | 中等规模结构化知识点 + 原始素材 |
| 检索目标 | 找到"相关"文档片段 | 找到"精准匹配"的知识条目 |
| 索引方式 | 自建向量数据库 | MCP 知识库（已有索引） |
| 核心痛点 | 文档分块后语义丢失 | 查询词缺少上下文意图 |

### 3.2 各方案的具体参考价值

#### Anthropic Contextual Retrieval — 参考价值：⭐⭐⭐⭐⭐（最高）

**核心启示**：上下文信息是检索精准度的关键。

Anthropic 发现 chunk 脱离原文后语义丢失，通过注入上下文前缀解决。本项目的问题类似：**查询词脱离知识点上下文后，MCP 无法理解检索意图**。

**可直接借鉴的做法**：
- 为查询词注入知识点上下文（核心术语 + 类型 + 目标库）
- 将单词查询升级为意图化查询句

**本项目的对应实现**：
```
改进前：
  查询词："NCHAR"
  → MCP 无法判断要查什么

改进后（借鉴 Anthropic 上下文增强思路）：
  查询词："NCHAR 定长字符串 语法定义 长度范围 使用规则"
  → MCP 理解要查 NCHAR 的语法和规则
```

#### LlamaIndex Query Routing — 参考价值：⭐⭐⭐⭐（高）

**核心启示**：不同类型的知识点应该路由到不同的检索策略。

本项目有多种素材类型（设计文档、测试用例、源码、MCP 知识库），不同知识点类型需要检索的素材维度不同：

| 知识点类型 | 主要检索目标 | 次要检索目标 |
|-----------|------------|------------|
| SQL/开发参考 | MCP 知识库（语法/边界/兼容性） | 设计文档、测试用例 |
| 理论机制 | MCP 知识库（概念/机制） | 设计文档、源码 |
| 实战调优 | MCP 知识库（参数/最佳实践） | 测试用例、源码 |
| 架构对比 | MCP 知识库（架构/兼容性） | 设计文档、Oracle KB |
| 运维SOP | MCP 知识库（步骤/参数） | 测试用例、设计文档 |

**可直接借鉴的做法**：
- 根据知识点类型确定检索维度
- 每个维度生成一条意图化查询词
- 按维度组织检索结果

#### Microsoft Agentic Retrieval — 参考价值：⭐⭐⭐（中等）

**核心启示**：多数据源整合需要统一的检索管道。

本项目有 MCP 知识库 + 本地文件（设计文档/测试用例/源码）多个数据源，需要一个统一的检索服务来协调。

**可借鉴但非核心的做法**：
- 统一检索服务入口（RetrievalService）
- 多源结果合并和去重

**不适用的部分**：
- Azure 的数据源连接器（本项目数据源固定）
- 企业级安全功能（本项目无需）

#### OpenAI Agentic RAG — 参考价值：⭐⭐（较低）

**核心启示**：Agent 可以迭代检索，判断结果是否充分。

**对本项目的参考价值有限**：
- 本项目的 MCP 知识库是结构化索引，一次查询通常能返回足够结果
- 迭代检索会增加 LLM 调用成本，收益不明显

**可借鉴的点**：
- 如果首次检索结果不足，可以放宽 Score 阈值重试

#### Google ScaNN + RAG Engine — 参考价值：⭐（最低）

**核心启示**：向量搜索算法的性能优化。

**对本项目几乎无参考价值**：
- 本项目使用已有的 MCP 知识库，不涉及自建向量索引
- ScaNN 算法是底层优化，与查询词生成无关
- 多模态检索不适用于纯文本技术文档

### 3.3 总结：本项目应重点借鉴什么

| 借鉴点 | 来源 | 本项目实现方式 |
|--------|------|--------------|
| **上下文增强查询** | Anthropic | 为查询词注入知识点上下文，生成意图化查询 |
| **多维度检索路由** | LlamaIndex | 根据知识点类型确定检索维度，每个维度一条查询 |
| **统一检索管道** | Microsoft | RetrievalService 统一协调 MCP 和本地文件检索 |
| **迭代检索降级** | OpenAI | 结果不足时放宽阈值重试 |

**不需要借鉴的**：
- 自建向量数据库（已有 MCP 知识库）
- 多模态检索（纯文本场景）
- 企业级安全功能（非本项目重点）
- Token 预算裁剪（质量优先，不做人为限制）

## 5. 下一步行动

基于以上分析，本项目的 Retriever 优化应重点实现：

1. **意图化查询词生成**（借鉴 Anthropic）：为每个知识点生成携带上下文意图的查询词
2. **多维度检索覆盖**（借鉴 LlamaIndex）：根据知识点类型覆盖语法/边界/兼容性/错误码/参数等维度
3. **统一检索服务**（借鉴 Microsoft）：协调 MCP 知识库和本地文件检索

详细设计见 `23-Retriever精准检索优化设计.md`。

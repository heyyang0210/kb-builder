# 通用素材上传映射下载与加工平台概要设计

## 1. 文档信息

- **定位**：PingCode 下载之外的通用素材接入设计。
- **适用范围**：本地上传、PingCode 映射下载、后续其他来源接入，以及统一的素材加工清洗流程。
- **基准流程**：本设计在 `27-资料预处理框架概要设计.md` 的五阶段加工流程之上，增加统一素材接入层。
- **当前阶段**：概要设计，不直接实现代码。

## 2. 已确认决策

| 项目 | 决策 |
|---|---|
| 上传素材归属 | 先进入独立临时区，不立即归属正式素材空间 |
| 大文件上传 | 分片、断点续传、失败重试、完整性校验、可配置大小限制 |
| 上传权限 | 先采用管理员配置的上传令牌，不接入用户登录体系 |
| 临时区保留 | 上传完成或失败后保留 30 天；正式批次保留原始快照，临时分片完成后删除 |
| 压缩包 | 安全递归解压，原压缩包和解压清单均保留 |
| 图片 | 原始图片保留并建立关联；默认不作为独立文本进入清洗，视觉/OCR启用后生成派生描述 |
| 加工入口 | 上传批次和 PingCode 下载批次进入同一个加工任务体系 |

## 3. 建设目标

### 3.1 目标

1. 前端提供统一的“素材接入”入口，支持本地多文件、目录和压缩包上传。
2. 上传素材先进入临时区，支持暂停、恢复、重试、取消和过期清理。
3. 上传完成后自动识别格式、生成资源清单，并可直接进入扫描、转换、清洗、分块和索引流程。
4. PingCode 映射下载继续保留，和上传使用统一的批次、资源、任务、日志和数据集模型。
5. 处理原始文件时保留来源、哈希、路径、转换产物和每一步执行记录，支持回溯和重复执行。

### 3.2 非目标

- 第一阶段不实现完整的组织级用户、角色和 SSO 权限体系。
- 第一阶段不允许上传内容直接覆盖正式素材空间中的原始文件。
- 第一阶段不把图片强制 OCR 为正文，不以 OCR 结果替换原始图片。
- 第一阶段不承诺所有未知格式都能转换；未知格式进入待处理或隔离状态。

## 4. 当前问题与总体架构

当前批次创建接口直接依赖 PingCode `SourceSelection`，批次创建时必须存在 PingCode 空间映射，无法表达“本地上传、临时区、尚未映射”的来源。

目标架构如下：

```text
┌─────────────────────── 素材接入层 ───────────────────────┐
│                                                         │
│  本地上传                 PingCode 映射下载                 │
│  分片/断点/校验           空间映射/树选择/下载               │
│       │                         │                       │
│       └────────── 统一来源适配器 MaterialSource ──────────┘
│                              │                          │
└──────────────────────────────┼──────────────────────────┘
                               ▼
                    原始素材临时区 / 批次原件
                               │
                               ▼
       格式识别 → 安全解压 → 多格式转换 → 质量过滤
                               │
                               ▼
            Markdown 统一化 → 图片/资源关联保留
                               │
                               ▼
            清洗 → 语义分块 → 特性分类汇总
                               │
                               ▼
                 向量索引 + 知识图谱 + 发布
```

## 5. 核心领域模型

### 5.1 MaterialSource

统一描述素材来源，后续可扩展工单、代码仓库、对象存储等来源。

```text
MaterialSource
├── type: upload | pingcode | ticket | repository | object_storage
├── source_id
├── display_name
├── captured_at
├── uploader_token_id / operator_label
├── configuration
└── snapshot
```

### 5.2 UploadSession

表示一次上传会话，不等同于加工批次。

```text
UploadSession
├── id
├── state: created | uploading | verifying | ready | failed | cancelled | expired
├── token_id
├── operator_label
├── total_files
├── total_bytes
├── uploaded_bytes
├── chunk_size
├── expires_at
├── created_at
├── updated_at
└── files[]
```

### 5.3 UploadFile

```text
UploadFile
├── id
├── session_id
├── relative_path
├── original_name
├── detected_media_type
├── size
├── whole_sha256
├── chunk_count
├── received_chunks[]
├── state: pending | uploading | assembled | verified | rejected
├── archive_parent_id
└── rejection_reason
```

### 5.4 MaterialBatch

现有 `MaterialBatch` 扩展为来源无关的批次模型：

```text
MaterialBatch
├── id
├── name
├── source: MaterialSource
├── state
├── staging_session_id?
├── local_space_id?
├── source_snapshot
├── original_manifest
├── active_task_ids[]
├── latest_dataset_version_id?
├── created_at
└── updated_at
```

兼容策略：

- 现有 PingCode 批次保留 `source_selection`，迁移时同时生成 `source.type=pingcode`。
- 现有 `local_space_name` 和 `local_space_logical_path` 继续返回，前端旧页面不立即失效。
- 上传批次允许 `local_space_id` 为空；正式数据集发布前必须选择或创建本地素材空间。
- 加工预览和候选数据集可以在临时区完成，不要求上传后立即映射正式空间。

## 6. 端到端业务流程

### 6.1 本地上传流程

```text
创建上传会话
  → 选择文件/目录/压缩包
  → 文件分片上传
  → 断点恢复与缺块补传
  → 文件哈希校验
  → 会话完整性校验
  → 写入临时区 manifest
  → 创建 upload 类型素材批次
  → 格式扫描与安全检查
  → 进入统一加工页面
  → 选择正式素材空间并发布
```

### 6.2 PingCode 流程

```text
发现 PingCode 空间
  → 创建或更新空间映射
  → 选择文档树和附件类型
  → 生成 pingcode 类型素材批次
  → 下载原始文件和页面资源
  → 进入统一加工页面
```

### 6.3 临时区到正式空间

- 临时区是上传的默认归属，不与正式素材空间共享目录。
- 加工期间允许用户查看原始文件、扫描报告、转换结果、清洗结果和失败原因。
- 发布数据集时要求绑定正式素材空间；绑定只改变逻辑归属，不修改来源快照。
- 原始文件采用不可变快照，重复加工只生成新的执行快照和数据集版本。
- 30 天到期的临时会话自动清理分片和未转正式批次的原始文件；清理前生成审计事件。

## 7. 大文件上传设计

### 7.1 上传参数

| 参数 | 默认值 | 说明 |
|---|---:|---|
| 单文件大小 | 2GB | 可通过后端配置覆盖 |
| 单上传会话大小 | 10GB | 可通过后端配置覆盖 |
| 分片大小 | 8MB | 允许 4MB、8MB、16MB 等配置 |
| 单会话并发文件数 | 3 | 防止局域网客户端占满带宽 |
| 单 IP 并发会话 | 2 | 上传令牌限流维度之一 |
| 分片重试次数 | 5 | 指数退避 |
| 临时区保留 | 30 天 | 已确认策略 |

### 7.2 完整性与幂等性

- 每个分片携带 `SHA-256`，服务端校验后才标记为已接收。
- 文件完成时校验完整文件 `SHA-256`、大小和分片数量。
- 会话完成时校验所有文件状态和会话总大小。
- 客户端重试相同会话、文件和分片编号时，服务端按哈希幂等处理。
- 相同文件哈希只允许复用已验证内容，不复用未经安全扫描的内容。
- 上传会话通过 `Idempotency-Key` 防止重复创建。

### 7.3 断点恢复

客户端重新打开上传页面后，以会话 ID 查询：

```text
GET /api/upload-sessions/{session_id}
  → session state
  → file states
  → received chunk indexes
  → missing chunks
  → server limits
```

客户端只补传缺失分片，不重新发送已校验分片。

## 8. 多格式识别与转换

### 8.1 格式分层

| 类型 | 示例 | 默认处理 |
|---|---|---|
| 原生文本 | md、txt、json、xml、csv、sql | 直接读取并统一编码 |
| Web 文档 | html、htm | HTML 解析后转 Markdown |
| PDF | pdf | 文本层提取；扫描 PDF 进入 OCR 候选 |
| Office | doc、docx、ppt、pptx、xls、xlsx | 解析文本、表格、备注和资源 |
| 压缩包 | zip、tar、tar.gz、tgz | 安全解压后递归识别 |
| 图片 | png、jpg、jpeg、gif、svg、webp | 保留资源，不默认单独文本加工 |
| 未知格式 | 其他 | 保留原件，进入待转换或隔离列表 |

### 8.2 工具策略

- Markdown、文本、JSON、XML：原生 Python/Node 解析器。
- DOCX：`mammoth` 或 Python OOXML 解析；保留图片资源引用。
- PPTX：解析幻灯片文本、备注、表格和嵌入媒体；复杂 SmartArt 使用 LibreOffice 渲染兜底。
- XLSX/XLS：`xlsx`/`openpyxl` 提取 Sheet、表格、公式和图表信息。
- PDF：`pdfplumber`/`pypdf` 提取文本；扫描页由 OCR 适配器处理。
- DOC/PPT 等旧格式：LibreOffice headless 转换为 DOCX/PPTX 或 PDF 后再处理。
- 压缩包：Python `zipfile`、`tarfile`；7z/rar 仅在服务器安装对应工具后启用。
- 视觉描述：使用已配置的视觉模型接口；未配置时保留图片并生成“待视觉描述”状态，不伪造内容。

所有格式适配器统一输出 `NormalizedDocument`，不得由加工任务直接判断文件后缀。

## 9. 压缩包安全处理

### 9.1 安全规则

1. 解压前检查归档格式、大小和内容清单。
2. 拒绝路径穿越，如 `../a.md`、绝对路径和 Windows 盘符路径。
3. 拒绝或隔离符号链接、硬链接和设备文件。
4. 单个归档最大解压文件数默认 10,000。
5. 递归解压最大层级默认 3。
6. 解压后总大小默认不超过 20GB。
7. 解压膨胀率默认不超过 100 倍。
8. 密码保护归档进入人工处理队列，不在服务端猜测密码。
9. 可执行文件、脚本和高风险类型默认标记为隔离，不执行文件内容。
10. 解压失败不影响原归档保留，生成可追踪的安全事件。

### 9.2 归档与子文件关系

```text
archive.zip
├── extracted/guide.docx
├── extracted/assets/diagram.png
└── extracted/data.xlsx
```

manifest 中记录：

```text
parent_resource_id
archive_member_path
extraction_depth
archive_sha256
child_sha256
```

归档原件可下载和审计；解压子文件才进入格式适配器链。

## 10. 图片与媒体资源规则

### 10.1 默认规则

- 图片作为原始资源保留在批次资源目录中。
- 图片不进入普通文本文件清单，不单独执行文本清洗和语义分块。
- Markdown、DOCX、PPTX、PDF 中的图片通过 `asset_id` 和相对路径关联。
- 文件预览页面默认展示关联图片，而不是把图片作为独立文档行展示。
- 资源清单记录图片尺寸、媒体类型、来源文件和页码/幻灯片编号。

### 10.2 视觉/OCR启用后的派生物

启用视觉模型或 OCR 后，系统生成派生资源，不覆盖原图：

```text
assets/diagram.png
derived/image-descriptions/asset_xxx.md
derived/ocr/asset_xxx.txt
```

派生描述必须记录：

- 模型提供方、URL、模型名和配置版本。
- 输入图片哈希、生成时间和提示词版本。
- 描述置信度或人工复核状态。
- 是否允许进入索引。

视觉服务不可用时使用“待描述”状态，不用上下文猜测替代真实视觉结论。

```text
        │       └── file.json
```

### 11.2 正式批次目录

```text
scripts/pingcode/runtime/web/batches/
└── {batch_id}/
    ├── source.json
    ├── original/
    │   ├── files/

    ├── derived/
    ├── indexes/
    ├── reports/
```

### 11.3 保留与清理

- 上传分片在文件完成校验并转移到 `assembled` 后可清理。
- 上传失败或未完成会话保留 30 天，超期先记录清理事件再删除。
- 形成正式批次后，正式批次中的 `original/` 是不可变快照。
- 正式批次不依赖临时目录，临时目录清理不会影响加工回溯。
- 清理任务必须使用 manifest，不允许按目录名直接递归删除。

## 12. 接口设计

### 12.1 上传会话

```http
POST /api/upload-sessions
Authorization: Bearer <upload-token>
Content-Type: application/json
```

```json
{
  "name": "YashanDB 本地资料上传-20260724-170000",
  "operatorLabel": "knowledge-team",
  "totalFiles": 20,
  "totalBytes": 524288000
}
```

返回：

```json
{
  "id": "upload_xxx",
  "state": "created",
  "chunkSize": 8388608,
  "maxFileSize": 2147483648,
  "maxSessionSize": 10737418240,
  "expiresAt": "2026-08-23T00:00:00Z"
}
```

### 12.2 文件和分片

```http
POST /api/upload-sessions/{session_id}/files
PUT /api/upload-sessions/{session_id}/files/{file_id}/chunks/{chunk_index}
GET /api/upload-sessions/{session_id}
POST /api/upload-sessions/{session_id}/complete
POST /api/upload-sessions/{session_id}/cancel
```

分片请求要求：

- `Content-Range`。
- `X-Chunk-SHA256`。
- `Content-Length`。
- 不接受通过 URL 查询参数传递上传令牌。

### 12.3 统一批次

```http
GET /api/material-batches
GET /api/material-batches/{batch_id}
GET /api/material-batches/{batch_id}/files
POST /api/material-batches/{batch_id}/scan
POST /api/material-batches/{batch_id}/preprocess
POST /api/material-batches/{batch_id}/promote
```

上传会话完成后可以：

```text
POST /api/upload-sessions/{session_id}/create-batch
```

也可以在前端临时区列表中稍后创建批次。两种方式都只生成一个批次，使用会话级幂等键避免重复。

### 12.4 安全准备处理

```http
POST /api/preprocess/prepare
Content-Type: application/json

{"batchId":"batch_xxx"}
```

该接口执行 P4 安全扫描、格式识别、ZIP/TAR 递归安全解压和图片资源登记，返回 `runId`、输入 manifest 哈希、资源统计、安全问题和产出路径。每次执行写入：

```text
<batch-root>/preparation/
├── latest.json
└── runs/<run_id>/
    ├── manifest.json
    ├── events.jsonl
    └── extracted/
```

原始 `resources.json` 和 `original/` 不被覆盖；图片仅在准备处理 manifest 中作为 `asset` 登记，不进入普通文本清单。未知格式进入 `conversion_pending`，可执行文件、危险归档和密码归档进入 `quarantined`。

### 12.5 临时批次发布

```http
POST /api/material-batches/{batch_id}/promote
Content-Type: application/json
```

```json
{
  "localSpaceSlug": "local-upload",
  "localSpaceName": "本地上传素材",
  "publishDataset": true
}
```

发布前检查：

- 所有高严重级别安全问题已处理或明确豁免。
- 转换失败文件有处理策略。
- 质量门禁通过，或用户显式确认发布。
- 本地素材空间标识不与现有空间冲突。

## 13. 上传令牌与安全边界

当前采用方案 C：管理员配置上传令牌。

### 13.1 令牌配置

- 支持环境变量或本地受保护配置文件配置令牌。
- 推荐使用 `MATERIAL_UPLOAD_TOKEN`，不写入前端构建产物。
- 浏览器通过 `Authorization: Bearer` 发送令牌。
- 服务端只记录令牌 ID 或哈希前缀，不记录原始令牌。
- 令牌轮换后旧令牌立即失效；已创建会话是否继续由配置决定，默认允许完成当前会话。

### 13.2 限流与风险控制

- 按令牌、IP 和会话维度限制并发数。
- 对创建会话、分片上传、解压和转换分别限流。
- 单个 IP 连续失败超过阈值后短时封禁。
- 不信任客户端提交的 MIME 类型和文件名，以内容探测和扩展名双重判断。
- 任何路径都经过安全规范化，禁止目录穿越。
- 运行日志、错误响应和测试报告中不出现令牌、Cookie 和密码。

### 13.3 后续升级

未来接入 SSO 时，保留 `operator_label`、`token_id` 和审计字段，增加：

```text
operator_id
organization_id
roles[]
```

不改变上传会话、批次和加工任务接口的主体结构。

## 14. 前端页面设计

### 14.1 入口调整

将当前“素材空间”升级为“素材接入”：

```text
素材接入
├── 本地上传
├── PingCode 映射下载
└── 临时素材批次
```

PingCode 现有空间列表和映射面板保留，上传不要求先选择 PingCode 空间。

### 14.2 本地上传页面

页面区域：

1. 上传令牌输入和校验状态，不在页面回显完整令牌。
2. 文件/目录拖拽区，显示支持的格式和大小限制。
3. 上传队列，按文件分页，显示进度、速度、剩余时间和失败原因。
4. 暂停、继续、重试、取消和重新连接后恢复按钮。
5. 图片和归档显示资源标识，不在“可加工文本”列表中重复展示。
6. 上传完成后的“创建素材批次”和“进入加工”操作。

### 14.3 临时素材批次页面

每个临时批次显示：

- 上传会话状态。
- 文件总数、原始大小、归档数、图片资源数、待转换数。
- 安全扫描状态和质量扫描状态。
- 原始文件、转换结果、清洗结果和执行日志入口。
- “选择正式素材空间并发布”按钮。
- 30 天过期时间和清理状态。

### 14.4 大列表原则

- 所有文件列表服务端分页，默认每页 20 条，最大 100 条。
- 图片作为资源统计和关联预览，不作为普通文件行展示。
- 解压子文件默认折叠，展开后分页加载。
- 转换失败、隔离文件和待视觉描述资源分别使用筛选器展示。

## 15. 加工流程衔接

上传和 PingCode 批次统一进入以下任务链：

```text
ingest
  → security_scan
  → format_detect
  → archive_extract
  → normalize
  → quality_scan
  → clean
  → chunk
  → classify
  → vector_index
  → graph_index
  → quality_gate
  → publish
```

### 15.1 执行原则

- 安全扫描失败不能进入格式转换。
- 格式转换失败不丢弃原件，进入 `conversion_pending` 或 `conversion_failed`。
- 质量过滤只标记或排除低质量正文，不删除原始文件。
- “适用版本”仅作为可选元数据信号：明确出现时写入 `applicableVersions`，未出现时保持空数组，不生成 `METADATA_VERSION_UNCLEAR`，也不进入质量问题、人工复核或发布门禁。
- 图片资源始终通过资源关系进入预览和索引上下文，不强行写入 Markdown 正文。
- 每次加工使用 `input_manifest_hash + config_hash + pipeline_version` 计算执行指纹。
- 相同指纹重复执行可复用已验证产物，不同配置生成新的快照。

### 15.2 原始、规范化和清洗产物

```text
original/       原始上传文件或 PingCode 下载文件，不修改
normalized/     格式转换后的 Markdown/结构化中间结果
cleaned/        应用清洗预设后的 Markdown
derived/        OCR、视觉描述、表格结构化等派生结果
chunks/         语义分块结果
indexes/        向量索引、图谱和结构化索引
```

任意层失败都能从上一层重试，不重新上传或覆盖原件。

## 16. 日志、审计与回溯

### 16.1 结构化事件

每个上传会话、文件、批次和任务都有 JSONL 事件：

```json
{
  "eventId": "evt_xxx",
  "occurredAt": "2026-07-24T09:00:00Z",
  "scope": "upload_file",
  "scopeId": "file_xxx",
  "stage": "verify",
  "event": "chunk_hash_mismatch",
  "severity": "warning",
  "message": "分片校验失败",
  "inputSha256": "...",
  "pipelineVersion": "..."
}
```

### 16.2 不可记录内容

- 上传令牌原文。
- PingCode Cookie、密码和视觉模型 API Key。
- 未脱敏的第三方响应头。
- 未经授权写入日志的原始文档正文。

### 16.3 回溯链

```text
dataset_version
  → preprocess_task
  → normalized_document / cleaned_document
  → source_resource
  → upload_file / PingCode resource
  → upload_session / PingCode batch
```

前端提供“查看来源”“查看转换差异”“查看执行日志”“重新执行本阶段”入口。

## 17. 异常与恢复

| 异常 | 处理 |
|---|---|
| 分片网络失败 | 自动重试，超过阈值后保留会话并允许手工继续 |
| 浏览器关闭 | 会话状态持久化，重新打开后补传缺块 |
| 哈希不一致 | 丢弃当前分片或组装文件，保留错误事件 |
| 文件超限 | 创建文件级拒绝记录，不影响其他文件上传 |
| 压缩包炸弹 | 终止解压，原件隔离，生成安全告警 |
| 密码压缩包 | 原件保留，状态为待人工处理 |
| 格式未知 | 原件保留，进入待转换列表 |
| LibreOffice/转换器崩溃 | 进程级超时和隔离，允许单文件重试 |
| 视觉服务不可用 | 保留图片，派生描述状态为待处理，不阻塞其他正文加工 |
| 临时区过期 | 先写审计事件，再清理分片和未晋级原件 |

## 19. 分阶段实施计划

| 阶段 | 内容 | 产出 | 难度 | 维护成本 |
|---|---|---|---:|---:|
| P0 | 统一来源与批次模型设计、旧 PingCode 兼容 | 接口和迁移方案 | 中 | 低 |
| P1 | 上传令牌、会话、分片、断点和临时目录 | 可恢复上传 API | 高 | 中 |
| P2 | 上传页面、队列、进度和临时批次列表 | 可用上传入口 | 高 | 中 |
| P3 | 安全扫描、归档解压和资源 manifest | 安全原始素材集 | 高 | 中高 |
| P4 | 多格式适配器统一接入上传批次 | 上传素材可转换 | 中高 | 中 |
| P5 | 上传批次接入扫描、清洗、分块和索引 | 端到端加工 | 中 | 中 |
| P6 | 临时批次发布、保留清理和完整审计 | 可运营闭环 | 中 | 中 |
| P7 | 全量单元、集成、浏览器和局域网验证 | 测试报告 | 中 | 低 |

### 19.1 推荐实施顺序

1. 先扩展模型接口和存储 manifest，不修改现有 PingCode 页面行为。
2. 实现单文件普通上传作为后端骨架，再加入分片和断点。
3. 实现安全扫描和归档处理，确保原始文件不可变。
4. 接入现有多格式适配器和加工任务。
5. 最后实现前端上传队列、临时批次和发布流程。

## 20. 待后续确认项

以下内容不阻塞本概要设计，但实施前需要形成配置或产品决策：

1. 上传令牌是单个全局令牌，还是多个令牌分别对应团队和限额。
2. 临时批次发布时是否自动创建本地素材空间，还是必须选择已有空间。
3. 归档中包含大量图片时，是否提供“图片资源单独导出”操作。
4. OCR 和视觉描述是否允许阻塞质量门禁，还是只作为可选增强产物。
5. 单文件、单会话、单 IP 的最终容量和并发值是否按部署环境调整。

## 21. 验收标准

1. 本地多格式文件可通过分片上传，断开网络后能够继续，不重复上传已校验分片。
2. 上传完成后生成独立临时批次，不要求先创建 PingCode 映射。
3. 临时批次能够进入与 PingCode 批次相同的扫描、转换、清洗、分块和索引流程。
4. ZIP/TAR 安全解压，原始归档、子文件关系和安全事件可追溯。
5. 图片保留原件和关联关系，默认不作为独立文本加工；视觉/OCR启用时只新增派生结果。
6. 上传令牌不进入前端构建产物、URL 和日志，未授权请求返回明确错误。
7. 临时区按 30 天策略清理，正式批次原始快照不受临时区清理影响。
8. 既有 PingCode 映射下载和加工功能回归通过。

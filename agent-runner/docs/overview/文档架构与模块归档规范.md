# 文档架构与模块归档规范

> 文档类型：系统概要设计
>
> 版本：1.0.0
>
> 更新日期：2026-08-17
>
> 适用范围：`agent-runner/docs/`、`.codex/requirements/`、`.codex/workflow/`

## 1. 目标

解决设计、需求、任务、进度和测试报告在同一目录混放的问题，让产品经理、Architect、Project Manager 和 Worker 都能从固定入口找到各自负责的信息，并保持需求、设计、任务和验收之间可追踪。

## 2. 架构依据

模块边界同时参考：

- `diagrams/knowledge-processing-pipeline.drawio` 的前端工作台、API/控制面、加工流水线、规则处理、Agent/Skill、产物仓储与质量审计。
- `agent-runner/routes/` 的 API 业务边界。
- `agent-runner/lib/` 的工作流、Agent、文档、预处理和检索代码边界。
- 当前用户路径：素材进入、结构处理、知识检索/生成、大纲管理、文档管理和工作台操作。

旧版 `01-系统架构设计.md` 是历史基线。若其描述与当前代码或架构图不一致，文档必须标注现状差异，不得把目标设计写成已实现能力。

## 3. 模块边界

| moduleId | 用户价值 | 上下游 | 不包含 |
|---|---|---|---|
| `platform-foundation` | 提供可配置、可持久化、可观测的服务基础 | 承载所有业务模块 | 具体业务解析和生成规则 |
| `generation-workflow` | 将知识点与资料编排为可追踪的文档生成流程 | 使用检索、模型和文档管理 | 大纲格式准入、素材下载 |
| `outline-management` | 让用户安全地上传、修订和治理知识点大纲 | 向生成工作流提供标准知识点树 | 原始资料预处理、正文生成 |
| `document-management` | 让用户查看、编辑和管理生成结果 | 接收生成工作流结果 | 工作流编排、资料清洗 |
| `material-processing` | 将外部或本地素材转换为可追溯的标准资产 | 为检索和生成提供资料 | 大纲业务语义、最终文档编辑 |
| `knowledge-retrieval` | 为生成流程提供有证据的相关上下文 | 消费标准资产，服务生成工作流 | 素材下载、文档发布 |
| `workbench-shell` | 提供一致的中文入口、导航、反馈和跨模块操作 | 聚合各模块 API | 复制后端业务判定规则 |

## 4. 四类核心文档

| 文档类型 | 必须回答 | 唯一存放位置 | 主要读者 |
|---|---|---|---|
| 概要设计 | 模块为何存在、边界、组件、上下游、主流程和关键决策 | `agent-runner/docs/modules/<moduleId>/overview/` | Architect、全体 Worker |
| 开发设计 | API、Schema、伪代码、状态、异常、配置、兼容和测试 | `agent-runner/docs/modules/<moduleId>/development/` | Architect、Worker、Test Engineer |
| 模块需求 | 用户、场景、痛点、范围、优先级、业务规则和验收 | `.codex/requirements/modules/<moduleId>/` | Product Owner、产品经理、Project Manager |
| 任务开发进度 | 计划、责任人、状态、依赖、风险、证据和下一步 | `.codex/workflow/modules/<moduleId>/` 与 `tasks/<moduleId>/` | Project Manager、Planner、Worker、Reporter |

测试设计可与开发设计同目录；测试执行报告、问题记录和动态统计属于验收证据，由模块 `PROGRESS.md` 链接，不得放入设计目录。

## 5. 文档元数据

新增或实质修改的文档应在标题后提供以下字段；历史文档迁移时至少补齐前三项：

```yaml
documentType: overview-design | development-design | requirement | plan | progress | task
moduleId: outline-management
owner: Architect | Project Manager | Planner | Worker role
status: draft | review | approved | implementing | verified | deprecated
version: 1.0.0
updatedAt: YYYY-MM-DD
relatedRequirements: []
relatedDesigns: []
relatedTasks: []
```

状态只表达文档自身生命周期。实现进度不得写入概要设计或开发设计正文，应链接模块 `PROGRESS.md`。

## 6. 单一事实来源

1. 需求只描述 `why/what` 和业务验收，不复制接口与伪代码。
2. 概要设计只描述稳定边界和主要决策，不维护逐任务完成情况。
3. 开发设计负责技术契约，不承担排期、负责人和日报。
4. `PLAN.md` 管理路线图、RACI、门禁和依赖；`PROGRESS.md` 管理动态状态和验收证据。
5. 任务卡必须反向链接需求和开发设计，不在任务卡重新定义公共契约。
6. 一个主题只有一个可编辑正文；历史路径通过 `MIGRATION-MAP.md` 查找，不保留双写副本。

## 7. 归档流程

1. 依据内容而非文件名判定文档类型和主模块。
2. 混合文档先拆分单一事实源，再移动；禁止把整份混合文档复制到两个目录。
3. 使用稳定语义文件名，不再依赖全局连续编号。
4. 创建或更新模块 `README.md`，列出概要设计、开发设计、需求、任务和进度入口。
5. 全仓修复 Markdown 链接和反引号路径，登记旧路径到新路径。
6. 检查本地链接、文件唯一性、标题/元数据和 `git diff --check`。

## 8. 迁移顺序

1. `outline-management`：作为首个完整试点，迁移规格、P1-P5 设计、Epic 需求、计划、进度和任务卡。
2. `material-processing` 与 `knowledge-retrieval`：对齐现行知识加工架构图和根目录 `docs/` 的新设计。
3. `generation-workflow` 与 `document-management`：区分生成编排和结果管理。
4. `workbench-shell` 与 `platform-foundation`：收敛跨模块前端与基础设施文档。
5. 清理剩余测试报告、问题记录、备份文件和失效引用。

每个模块必须独立验收，不以一次性大范围移动替代内容分类。

## 9. 完成定义

- 启用模块有 `README.md`、至少一份概要设计和一份开发设计；暂缺时明确标记计划，不创建空文档。
- 模块需求、计划、进度和任务卡均位于 `.codex`，且互相可追踪。
- `agent-runner/docs` 新增内容不再出现 Epic 计划、动态进度、待办和测试执行报告。
- 旧路径全部登记，仓库内不存在指向已迁移文件的失效引用。
- 当前修改文件通过空白检查；全仓既有无关问题单独报告。

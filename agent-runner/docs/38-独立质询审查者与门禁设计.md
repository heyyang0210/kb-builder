# 独立质询审查者与门禁设计

> 版本：V1.0
> 日期：2026-08-20
> 状态：G0 决策已确认，G1 独立审查整改中；角色文档已接入，自动策略、编排和校准尚未实现

## 1. 目标与已确认决策

本设计在现有 Planner、Architect、Worker、Test Engineer、Project Manager 和 Product Owner 之外，引入 `Independent Reviewer`（独立质询审查者）。该角色贯穿需求、设计、代码、运行、决策和失败复盘，通过反向证伪提高决策与验收证据的可信度。

2026-08-20 人类 Product Owner 已确认：

1. 正式名称为“独立质询审查者”。
2. 审查规范仅在治理任务中装载，独立 Agent 按明确风险或人工要求触发。
3. 只对预定义红线和证据缺口拥有条件或硬阻断权，业务取舍由 Product Owner 决定。
4. 审查者与产出者使用独立上下文，原则上只读待审产物和证据。
5. 低风险任务不默认抽样；未来是否启用自动抽样必须先用真实任务校准并单独批准。

本阶段只定义治理契约和角色编排，不修改业务公共 API，不引入外部依赖，不实现生产自动发布。

## 2. 底层原则

### 2.1 三方分离

```text
产出者（Maker）提出主张和证据
  -> 独立质询审查者（Checker）尝试证伪
  -> 与产出者分离的阶段责任人或 Product Owner（Approver）裁决
```

审查者不得是同一运行中待审产物的作者，不以产出者的结论性解释代替原始证据，也不替代 Product Owner 做业务价值和残余风险决策。

### 2.2 正向构建与反向证伪

- Architect 回答“为谁解决什么问题，如何解决”；Reviewer 质疑问题、假设、必要性、最小性和替代方案。
- Test Engineer 验证实现是否符合已冻结规格；Reviewer 质疑规格是否正确、评价器是否可信、证据是否足以支持结论。
- Project Manager 运营门禁；Reviewer 审查门禁证据是否真实、完整、可重建。

### 2.3 可证据化质疑

没有可解析的已批准 `policyRef`、该政策规定的必需证据/红线、可观察影响、可执行验证方法和解除条件的意见，只能记为非阻断 `advice`。审查者不按“发现问题数量”考核。

## 3. 阶段审查 Profile

| Profile | 核心质询 | 主要产出 | 可阻断边界 |
|---|---|---|---|
| `requirement-review` | 问题是否真实、谁受益、不做代价、是否有更小替代、指标是否会被游戏化 | 事实/假设/反例/替代方案/待验证项 | 缺用户与场景、问题不可复现、无成功定义可阻断 G0 |
| `design-review` | 是否最小闭环、是否过度设计、异常/兼容/回退/观测是否成立 | 失败预演、反例、替代设计、未关闭风险 | 受限变更未审批或不可逆变更无回退时阻断 G1 |
| `plan-review` | 拆解是否扭曲目标、是否漏掉反证任务、验收是否能证明目标 | 拆解缺口、依赖/文件归属冲突、验收修订建议 | 任务无可执行验收或并发归属冲突时条件阻断 G2 |
| `code-review` | 是否偏离设计、夹带范围、硬编码、隐式副作用、只测正常路径 | Blocker/Major/Minor 发现、位置、复现与修复建议 | 只有安全/数据破坏、未批准公共契约或已配置必需契约/测试缺失可阻断 G2/G3；未映射政策的设计偏离仅为 `advice` |
| `runtime-assurance` | 是否真实 API，聚合指标是否遮蔽坏样本，引用/忠实性/ACL/时效/成本是否越界 | 证据充分性、反例样本、护栏偏差和放行建议 | 硬阈值失败、证据不可重建或未跑真实 API 时阻断 G3/G4 |
| `decision-review` | 是否伪二选一、选择性呈现证据、决策是否可逆、什么证据会推翻它 | 质询单、反对意见、失效条件、复审日期 | 受限决策缺审批或关键证据/选项缺失可阻断；明示接受的残余业务风险由 Product Owner 裁决 |
| `failure-review` | 根因还是表象、组件归因是否可证、是否单样本过拟合、评价器是否出错 | 竞争性根因、验证实验、回归样本、组件升级建议 | 无可证根因、无回放/回归或护栏退化时阻断失败关闭和组件晋级 |

## 4. 结构化契约

### 4.1 Challenge Record

```yaml
reviewId: review_<stable-id>
runId: run_<id>
taskId: TASK-...
profile: requirement-review
reviewer:
  componentId: independent-reviewer
  version: 1.0.0
  actorId: reviewer-actor-id
  contextId: isolated-context-id
  permissions:
    mode: read_only
    allowedArtifactIds: [artifact-id]
subject:
  artifactIds: [artifact-id]
  creator:
    actorId: creator-actor-id
    componentId: architect
    contextId: creator-context-id
  artifactOwnership:
    artifact-id: creator-actor-id
  claim: "待质疑的可验证声明"
challenge:
  policyRef: "G0.DoR.user-evidence"
  policyRuleType: requiredEvidence | redline
  requiredEvidence: [user-scenario-evidence]
  evidenceGap: "缺失的证据或存在的冲突"
  counterexample: "反例或失败条件"
  impact: "对用户、数据、安全、质量或成本的影响"
  verification: "可执行的补证或证伪步骤"
  releaseCondition: "解除阻断所需的可验证条件"
  severity: advice | conditional_hold | hard_stop
disposition:
  status: open | accepted | rejected | resolved | escalated
  owner: role-or-human
  reason: "接受、拒绝或裁决理由"
  evidenceIds: []
  decidedBy: {actorId: null, componentId: null, contextId: null}
  decidedAt: null
```

### 4.2 Review Result

```yaml
decision: pass | pass_with_advice | hold | stop | escalate
blockingRecords: []
advisoryRecords: []
policyVersion: reviewer-policy@1.0.0
checklistVersion: requirement-review@1.0.0
startedAt: timestamp
completedAt: timestamp
nextReviewAt: null
```

`hold` 只能由明确证据清单解除；`stop` 必须命中已批准红线；`escalate` 交由 Product Owner 或对应阶段责任人裁决。裁决不覆盖原质询记录。

`stop` 并非不可恢复终态：修复后按 `releaseCondition` 提交证据并重审；无法修复或仍存争议时转 `escalate`。`escalate` 的裁决者必须与待审产物的产出者分离。

### 4.3 Versioned Reviewer Policy Schema

`reviewer-policy` 是审查编排唯一的数值和阻断来源，必须通过人工审批后才能加载：

```yaml
policyVersion: reviewer-policy@1.0.0
approval: {status: approved, approvedBy: product-owner-id, approvedAt: timestamp}
profiles: {requirement-review: {gates: [G0], rules: [G0.DoR.user-evidence]}}
rules:
  G0.DoR.user-evidence: {type: requiredEvidence, requiredEvidence: [user-scenario-evidence], releaseCondition: user-scenario-recorded}
riskTriggers:
  - {id: restricted-scope, profiles: [design-review, code-review], gates: [G1, G2, G3], conditionRef: task.touchesRestrictedScope, mandatoryDeepReview: true, enabled: true}
  - {id: unclear-requirement, profiles: [requirement-review], gates: [G0], conditionRef: task.requirementEvidenceIncomplete, mandatoryDeepReview: true, enabled: true}
  - {id: evidence-conflict, profiles: [design-review, runtime-assurance], gates: [G1, G3], conditionRef: task.hasEvidenceConflict, mandatoryDeepReview: true, enabled: true}
  - {id: execution-anomaly, profiles: [runtime-assurance, failure-review], gates: [G3, G4], conditionRef: history.hasExecutionAnomaly, mandatoryDeepReview: true, enabled: true}
  - {id: component-promotion, profiles: [decision-review], gates: [G4], conditionRef: task.promotesComponent, mandatoryDeepReview: true, enabled: true}
  - {id: failure-closure-gap, profiles: [failure-review], gates: [G4], conditionRef: task.failureClosureEvidenceIncomplete, mandatoryDeepReview: true, enabled: true}
samplingSeed: stable-seed
initialSampleRate: configured
currentSampleRate: configured
targetSampleRate: configured
requiredConsecutiveWindows: configured
escapeRateLimit: configured
falseBlockRateLimit: configured
restoreEscapeRateLimit: configured
restoreFalseBlockRateLimit: configured
maxReviewRounds: configured
onInvalidOrMissingPolicy: fail_closed_for_high_risk_advice_only_for_low_risk
```

`rules` 中每条阻断规则必须声明 `type`、`requiredEvidence` 或 `redline` 及 `releaseCondition`；`riskTriggers` 必须声明稳定 ID、Profile/Gate、可解析输入条件、是否强制深审和启停状态。非法或未批准策略不得驱动阻断。高风险任务在策略不可用时闭门，低风险任务只能记录 `advice` 并等待人工处理。

## 5. 触发、抽样与阻断状态机

### 5.1 触发策略

以下情况必须启动独立 Agent 深审：

- 新增模块、改变技术栈、修改公共 API 或引入外部依赖；
- 涉及安全、性能、ACL、敏感数据或生产写入；
- 需求价值、用户场景或成功指标不清；
- 设计重大变更，规格、测试或评价器结论冲突；
- 重试耗尽、人工接管或同类失败重复发生；
- 角色、工具、Skill、Prompt、模型或评价器准备晋级为默认版本；
- 失败准备关闭，但根因、回放或防复发证据存在缺口。

普通直接处理和标准开发不进入 G0-G4，也不默认执行 Reviewer 清单或抽样。治理任务按明确风险加载相应审查 Profile；自动抽样当前不实现。

### 5.2 状态流

```text
not_required / sampled / triggered
  -> reviewing
  -> pass | pass_with_advice | hold | stop | escalate
hold -> evidence_supplied -> reviewing
stop -> remediation_supplied -> reviewing
stop -> non_remediable_or_disputed -> escalate
escalate -> human_decided -> pass | hold | stop
```

同一质疑最多两轮。第二轮后仍无法依据契约和证据解决时必须转 `escalate`，不得通过改写表述重复阻断。

## 6. 编排伪代码

```text
function evaluateReviewTrigger(task, gate, policy, history):
    checklistResult = runDeterministicChecklist(task, gate, policy)
    if checklistResult.hitsHardStop:
        return trigger("policy-redline")
    matchedTrigger = policy.riskTriggers.find(rule ->
        rule.enabled and rule.appliesTo(gate) and evaluate(rule.conditionRef, task, history)
    )
    if matchedTrigger and matchedTrigger.mandatoryDeepReview:
        return trigger(matchedTrigger.id)
    if stableSample(task.id, policy.samplingSeed) < policy.currentSampleRate:
        return sampled("low-risk-sample")
    return checklistOnly(checklistResult)

function conductIndependentReview(subject, profile, policy):
    assert reviewer.contextId != subject.creator.contextId
    assert reviewer.actorId != subject.creator.actorId
    assert reviewer.permissions.mode == "read_only"
    assert reviewer.permissions.allowedArtifactIds == subject.artifactIds
    assert noneOwnedBy(subject.artifactOwnership, reviewer.actorId)
    records = reviewer.challenge(subject.rawArtifacts, subject.rawEvidence, profile)
    validated = records.map(record -> validateChallengeContract(record, policy))
    blockers = validated.filter(record ->
        policyAllowsBlock(
            record.policyRef,
            record.policyRuleType,
            record.requiredEvidence,
            record.releaseCondition
        )
    )
    return decideReviewResult(blockers, validated)

function adjudicate(record, approver, subject, reviewer):
    if record.severity in ["conditional_hold", "hard_stop"]:
        assert approver.actorId != subject.creator.actorId
        assert approver.actorId != reviewer.actorId
    return appendDecision(record, approver)

function resolveChallenge(record, response):
    appendImmutableResponse(record.reviewId, response)
    if record.completedReviewRounds >= policy.maxReviewRounds:
        return escalateToHuman(record)
    if response.supplies(record.requiredEvidence)
       or response.satisfies(record.releaseCondition):
        return reReview(record, response.evidenceIds)
    return keepHoldOrEscalate(record)

function adjustSamplingRate(iterationMetrics, policy):
    windows = iterationMetrics.last(policy.requiredConsecutiveWindows)
    if windows.count < policy.requiredConsecutiveWindows:
        return policy.currentSampleRate
    if every(windows, window ->
        window.escapedIssueRate <= policy.escapeRateLimit
        and window.falseBlockRate <= policy.falseBlockRateLimit
    ):
        return policy.targetSampleRate  // 已批准策略内自动转换；改变策略参数仍需人工审批
    if any(windows, window ->
        window.escapedIssueRate > policy.restoreEscapeRateLimit
        or window.falseBlockRate > policy.restoreFalseBlockRateLimit
    ):
        return policy.initialSampleRate
    return policy.currentSampleRate
```

## 7. RACI 与门禁接入

| 活动 | 原主责 | Independent Reviewer | 最终裁决 |
|---|---|---|---|
| 需求与价值 | Architect / Product Owner | 独立反证与补证要求 | Product Owner |
| 设计与契约 | Architect | 失败预演、备选和风险质询 | 与设计产出者分离的阶段负责人；受限或争议决策为 Product Owner |
| SMART 拆解 | Planner / Project Manager | 验收充分性和缺口审查 | Project Manager |
| 实施与自测 | Worker | 风险触发或抽样审查 | Architect 或 Project Manager（不得是待审产物作者） |
| 真实 API 与 RAG 验收 | Test Engineer | 证据充分性与评价器有效性审查 | Project Manager / Product Owner（不得是待审证据产出者） |
| 发布与残余风险 | Project Manager / Product Owner | 红线、证据和回退审查 | Product Owner |
| 失败关闭与组件晋级 | 组件 owner | 根因反证、回放与回归审查 | Project Manager / Product Owner |

G0–G4 的正向责任人不变。Maker 可以补证和修改，但不能裁决针对自己产物的争议性阻断；Reviewer 只增加独立质疑证据，不取代原门禁最终责任人。

## 8. 可观测、校准与演进

每个迭代至少统计：

- 有效发现率与人类接受率；
- 错误阻断率和被人类推翻率；
- 关键风险漏检率和上线后逃逸率；
- 审查 P50/P95 时延与平均补证轮数；
- 同类失败复发率；
- 深审抽样覆盖率和抽样逃逸率。

审查结论、人类裁决和上线后逃逸样本进入 Reviewer 专用评估集。新版审查清单或 Prompt 必须先对历史记录回放，比较漏报、误报、延迟和成本，再由人类晋级为默认版本。

## 9. 首期边界与验收

首期只在治理任务的 G0 需求、G1 架构、G3 验收和失败关闭节点人工试行，不覆盖低风险代码任务。

验收标准：

1. 待审产物的作者与 Reviewer 上下文不同，所有深审可追溯到 `reviewId/runId/taskId`。
2. 100% 质疑记录包含声明、契约或证据缺口、影响、验证方法和严重级别。
3. `conditional_hold` 和 `hard_stop` 100% 可定位到已批准政策、DoR/DoD 或阈值；无依据意见不阻断。
4. 同一质疑完成第二轮仍无法解决时直接升级人类，不进入第三轮。
5. 实际进入治理路径且明确要求深审的场景均有审查结论；普通任务不纳入覆盖率分母。
6. Reviewer 不改写待审产物，所有裁决都保留原质疑、回应和决策证据。

## 10. 风险与非目标

- 不以 Reviewer 取代确定性测试、Schema、静态检查、真实 API 或 RAG 固定评估集。
- 不对纯格式化、已批准模板化且确定性检查完全覆盖的修改强制深审。
- 不将 Reviewer 的自由文本结论直接作为生产阻断信号。
- 不让 Reviewer 直接修改它正在审查的需求、设计、代码、测试或失败结论。
- 审查自动化的抽样种子、阈值、红线和清单必须版本化配置，后续实现时不得散落硬编码。

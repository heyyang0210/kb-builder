# 12-文档生成与管理功能设计

## 1. 功能概述

实现基于大模型的文档生成系统，支持：
- 根据提示词通过 LLM 直接生成文档
- 文件列表展示与管理（搜索、排序、元数据）
- 前端在线编辑与实时同步（预览/编辑双模式，沉浸式展示）
- 文件版本管理与追踪
- 文档统计信息
- 目录结构浏览与文件树导航
- 双层搜索（前端即时过滤 + 后端全文搜索）

## 3. 核心功能点 — 方案对比与选型

### 3.1 功能点一：编辑模式与内容区域展示

#### 问题描述
- 当前编辑模式（Textarea）和源码模式（Pre）功能重叠，都是查看原始 Markdown 文本
- 内容区域有边框包裹，视觉上像"框中框"，不够沉浸
- 用户需要更简洁的展示方式

#### 方案 A：保留三模式 + 去掉边框

```
┌──────────────────────────────────────────────┐
│  [📄 预览]  [✏️ 编辑]  [📝 源码]             │
├──────────────────────────────────────────────┤
│  预览: Markdown 渲染 (无边框)                │
│  编辑: Textarea (无边框)                     │
│  源码: Pre 深色背景 (无边框)                 │
└──────────────────────────────────────────────┘
```

| 维度 | 评价 |
|------|------|
| 实现复杂度 | 低 — 仅修改 CSS |
| 用户体验 | 中 — 三模式仍有冗余 |
| 维护成本 | 中 — 需维护三种模式的状态 |
| 信息密度 | 中 — 源码模式与编辑模式重复 |

#### 方案 B：合并为双模式 + 沉浸式展示 ✅ 推荐

```
┌──────────────────────────────────────────────┐
│  [📄 预览]  [✏️ 编辑]                        │
├──────────────────────────────────────────────┤
│  元数据栏 (路径 | 大小 | 版本 | 时间)        │
├──────────────────────────────────────────────┤
│                                              │
│  预览模式: 直接渲染 Markdown                  │
│  ──────────────────────────────────────────  │
│  # 数据类型映射                               │
│  ## 概述                                     │
│  CHAR / VARCHAR2 → YashanDB 等价类型...      │
│  | 源类型 | 目标类型 | 说明 |                 │
│  ──────────────────────────────────────────  │
│                                              │
│  编辑模式: 带行号的编辑器 (浅灰背景)          │
│  ──────────────────────────────────────────  │
│  1 │ # 数据类型映射                           │
│  2 │                                         │
│  3 │ ## 概述                                 │
│  4 │ CHAR / VARCHAR2 → YashanDB 等价类型...  │
│  5 │                                         │
│  6 │ | 源类型 | 目标类型 | 说明 |             │
│  ──────────────────────────────────────────  │
│                                              │
│  核心: 同一区域切换, 无边框, 沉浸式           │
└──────────────────────────────────────────────┘
```

| 维度 | 评价 |
|------|------|
| 实现复杂度 | 中 — 需实现行号编辑器 |
| 用户体验 | 高 — 简洁清晰，无冗余 |
| 维护成本 | 低 — 仅两种模式 |
| 信息密度 | 高 — 编辑时看源码，预览时看渲染 |

#### 方案 C：WYSIWYG 所见即所得编辑器

```
┌──────────────────────────────────────────────┐
│  [📄 预览]  [✏️ 富文本编辑]                   │
├──────────────────────────────────────────────┤
│  编辑模式: 富文本编辑器                       │
│  ──────────────────────────────────────────  │
│  [B] [I] [H1▼] [链接] [表格] [代码]         │
│  ──────────────────────────────────────────  │
│  # 数据类型映射        ← 直接渲染的标题       │
│  概述                  ← 可直接编辑           │
│  CHAR / VARCHAR2...   ← 所见即所得           │
│  ┌────────┬────────┬──────┐                  │
│  │源类型  │目标类型│说明  │  ← 可视化表格     │
│  └────────┴────────┴──────┘                  │
│  ──────────────────────────────────────────  │
│  底层自动转换为 Markdown 存储                 │
└──────────────────────────────────────────────┘
```

| 维度 | 评价 |
|------|------|
| 实现复杂度 | 高 — 需引入 TipTap/Quill 等库 |
| 用户体验 | 高 — 最直观的编辑体验 |
| 维护成本 | 高 — 依赖第三方库，HTML→MD 转换有损 |
| 信息密度 | 中 — 工具栏占用空间 |

#### ✅ 选型结论：方案 B

**理由：**
1. 编辑和源码本质是同一件事（查看/修改 Markdown 源码），合并后逻辑更清晰
2. 沉浸式无边框展示提升阅读体验
3. 编辑模式带行号方便定位，浅灰背景比深色框更协调
4. 实现复杂度适中，不需要引入重量级 WYSIWYG 库

### 3.2 功能点二：搜索方式

#### 问题描述
- 搜索框应支持什么程度的搜索？标题匹配？全文搜索？
- 业界最佳实践是什么？

#### 业界主流方案对比

| 方案 | 代表产品 | 实现复杂度 | 效果 | 适用规模 |
|------|---------|-----------|------|---------|
| 纯前端模糊过滤 | GitHub 文件搜索 | 低 | 一般 | <100 文件 |
| 后端全文搜索 | Notion | 中 | 好 | 100-1000 |
| 双层搜索 | VS Code | 中 | 最佳 | 通用 |
| Elasticsearch | Confluence | 高 | 最强 | >1000 |

#### 方案 A：纯前端标题模糊过滤

```
┌──────────────────────────────────────────────┐
│  🔍 [数据类型...                    ]        │
├──────────────────────────────────────────────┤
│  搜索范围: 仅标题                             │
│                                              │
│  已加载文档列表 (内存中)                      │
│       │                                      │
│       ▼                                      │
│  前端 filter: title.includes(keyword)        │
│       │                                      │
│       ▼                                      │
│  📄 数据类型映射     ← 标题匹配              │
│  📄 数据类型转换     ← 标题匹配              │
└──────────────────────────────────────────────┘
```

| 维度 | 评价 |
|------|------|
| 实现复杂度 | 低 — 纯前端 JS filter |
| 搜索质量 | 低 — 只能匹配标题 |
| 响应速度 | 极快 — 无网络请求 |
| 可扩展性 | 差 — 无法搜索文档内容 |

#### 方案 B：后端全文搜索 (服务端 grep)

```
┌──────────────────────────────────────────────┐
│  🔍 [VARCHAR2...                    ]        │
├──────────────────────────────────────────────┤
│  搜索范围: 标题 + 内容                        │
│                                              │
│  POST /api/document/search                   │
│  { keyword: "VARCHAR2" }                     │
│       │                                      │
│       ▼                                      │
│  后端: 遍历 output/*.md, grep 内容           │
│       │                                      │
│       ▼                                      │
│  📄 数据类型映射                              │
│     └─ "...CHAR / **VARCHAR2** → ..."        │
│  📄 字符集转换                                │
│     └─ "...Oracle **VARCHAR2** 编码..."       │
└──────────────────────────────────────────────┘
```

| 维度 | 评价 |
|------|------|
| 实现复杂度 | 中 — 需后端搜索 API + 文件遍历 |
| 搜索质量 | 高 — 可搜索全文 |
| 响应速度 | 中 — 依赖文件大小和数量 |
| 可扩展性 | 中 — 文件数量大时性能下降 |

#### 方案 C：双层搜索策略 ✅ 推荐

```
┌──────────────────────────────────────────────────────────┐
│  🔍 [VARCHAR2...                    ]                    │
├──────────────────────────────────────────────────────────┤
│  搜索范围:  (●) 标题和内容   ( ) 仅标题                  │
│                                                          │
│  ┌─ 搜索流程 ──────────────────────────────────────┐    │
│  │                                                  │    │
│  │  用户输入关键词                                   │    │
│  │       │                                          │    │
│  │       ▼                                          │    │
│  │  ┌─ 防抖 300ms ─┐                               │    │
│  │  │              │                                │    │
│  │  ▼              ▼                                │    │
│  │  前端即时过滤    后端全文搜索                      │    │
│  │  (已加载列表)   POST /api/document/search        │    │
│  │  │              │                                │    │
│  │  │  匹配:        匹配:                           │    │
│  │  │  • 标题       • 标题 + 文件内容               │    │
│  │  │  • 知识点     • 元数据标签                    │    │
│  │  │              │                                │    │
│  │  ▼              ▼                                │    │
│  │  合并去重 → 高亮匹配关键词 → 展示结果             │    │
│  │                                                  │    │
│  └──────────────────────────────────────────────────┘    │
│                                                          │
│  搜索结果:                                                │
│  📄 数据类型映射          📦 2KB  │  v1                  │
│     └─ 匹配: "CHAR / **VARCHAR2** → YashanDB..."        │
│                                                          │
│  📄 字符集转换            📦 3KB  │  v2                  │
│     └─ 匹配: "Oracle **VARCHAR2** 编码..."               │
└──────────────────────────────────────────────────────────┘
```

| 维度 | 评价 |
|------|------|
| 实现复杂度 | 中 — 前端 filter + 后端 search API |
| 搜索质量 | 高 — 标题即时 + 内容深度 |
| 响应速度 | 高 — 前端即时反馈 + 后端补充 |
| 可扩展性 | 高 — 后续可平滑升级到 Elasticsearch |

#### ✅ 选型结论：方案 C（双层搜索）

**理由：**
1. 前端即时过滤保证输入时的即时反馈（<100ms）
2. 后端全文搜索补充内容级别的深度搜索（防抖 300ms 触发）
3. 两者合并去重，结果最完整
4. 渐进式实现：先做前端过滤，再加后端搜索，不需要一步到位
5. 后续可平滑迁移到 Elasticsearch，API 接口不变

## 4. 最终设计方案

### 4.1 内容区域设计

## 8. HTML 原生预览设计（2026-08-17）

### 8.1 问题与设计结论

GET /api/document/:id/content 已返回文件扩展名，但旧前端将所有内容统一交给 marked.parse() 并注入宿主页面。完整 HTML 因此丢失独立的 body、CSS、脚本生命周期和相对链接基准。直接触发问题是前端渲染分流缺失，根因是预览器没有定义“文件类型 -> 渲染器”契约，不是文件读取编码错误。

预览规则固定为：

~~~
.md/.markdown/文本 -> 现有 Markdown 渲染器
.html/.htm         -> 独立 iframe 加载原文件
其他格式          -> 保持现有下载或文本兜底行为
~~~

### 8.2 原文件接口

GET /api/document/raw/:rootId/*relativePath

rootId 只能来自 document-paths.json 的注册根目录，relativePath 保留源文件的完整目录层级。例如 ai-cognitive/智能知识平台/L0_02_PyTorch核心架构.html。服务端以原始字节响应，HTML 返回 text/html; charset=utf-8，并设置 Content-Disposition: inline、X-Content-Type-Options: nosniff。

路径安全必须同时执行：

1. 对规范化路径做注册根目录边界检查；
2. 目标存在时对根目录和目标执行 realpath，再次检查真实路径边界；
3. 拒绝目录、未知根、路径穿越、编码穿越和根外符号链接；
4. 错误响应不能泄露服务器绝对路径。

原文件路由必须定义在 /:id、/:id/content 等参数路由之前，避免 raw 被解释为文档 ID。

### 8.3 内容接口兼容扩展

现有 /api/document/:id/content 的字段保持不变，新增服务端生成的只读 raw_url：

~~~
{
  "ext": ".html",
  "raw_url": "/api/document/raw/ai-cognitive/%E6%99%BA%E8%83%BD%E7%9F%A5%E8%AF%86%E5%B9%B3%E5%8F%B0/L0_02_PyTorch%E6%A0%B8%E5%BF%83%E6%9E%B6%E6%A7%8B.html"
}
~~~

raw_url 必须逐段 URL 编码生成，前端不得从标题或展示路径自行拼接。

### 8.4 前端 iframe 生命周期

HTML 预览区使用独立 iframe，初始 sandbox 只授予 allow-scripts allow-forms allow-popups allow-downloads，不授予 allow-same-origin。切换文档、进入编辑模式或关闭预览时，必须清空旧 src，防止旧页面脚本继续运行。Markdown 仍执行原有 YAML 清理、marked.parse() 和代码块增强。

~~~javascript
function renderDocument(doc, mode) {
  hideAllPreviewPanes();
  if (mode === 'preview' && ['.html', '.htm'].includes(doc.ext.toLowerCase())) {
    htmlFrame.src = new URL(doc.raw_url, BACKEND).href;
    htmlFrame.hidden = false;
    return;
  }
  htmlFrame.src = 'about:blank';
  renderMarkdownOrEditor(doc, mode);
}
~~~

### 8.5 验收要点

- 原生 HTML 在 iframe 中保留自己的 CSS、脚本、图表、动画和同目录导航；
- L0_02_PyTorch核心架构.html 的 raw 响应为 UTF-8 HTML，且相对链接仍位于“智能知识平台”目录；
- 未注册根目录、路径穿越、根外符号链接和目录目标均返回 404；
- Markdown 预览、编辑、保存、下载和特殊代码块行为不回归；
- 真实 API 验证必须连接 localhost:4100，不能用 mock 替代。

### 8.6 预览区域高度契约

文档管理页面的高度必须沿着 `main` -> `#main-doc-mgmt` -> `.doc-mgmt-viewer` -> `.doc-viewer-content` -> iframe 连续传递。`#main-doc-mgmt` 显示时使用纵向 flex 布局并设置 `min-height: 0`，切换逻辑不得将其降级为普通 block；查看器和内容区分别使用 `flex: 1`，iframe 使用 `width: 100%; height: 100%`。这样工具栏、元数据栏固定占用自身高度，剩余视口全部交给 HTML 原生预览。

伪代码：

~~~javascript
function showTab(tabName) {
  mainDocMgmt.style.display = tabName === 'doc-mgmt' ? 'flex' : 'none';
}

// CSS 约束：每一层都必须有可计算的剩余高度
#main-doc-mgmt, .doc-mgmt-viewer, .doc-viewer-content { min-height: 0; }
#main-doc-mgmt { flex-direction: column; height: 100%; overflow: hidden; }
.doc-mgmt-viewer, .doc-viewer-content { flex: 1; }
.doc-html-preview-frame { width: 100%; height: 100%; }
.doc-html-preview-frame[hidden] { display: none; }
~~~

验收时需在真实浏览器中断言 iframe 的可见高度接近 `#main-doc-mgmt` 内容高度，且切换到 Markdown/编辑模式后不产生旧 iframe 残留。

### 8.7 文档阅读工作台布局

文档查看器顶部采用“面包屑/标题 + 操作”两列布局，标题区只承担当前位置和当前文档识别，低频文件信息放入紧凑元数据行。操作区提供目录切换、沉浸阅读、刷新、预览/编辑、打开新窗口、下载等动作；只读文档隐藏编辑和删除动作，HTML 文档才显示原始页面入口。

外层文档树和 HTML 原文内部导航属于两套不同层级的导航。默认保留外层文档树用于切换文件，提供“目录”按钮快速折叠；“沉浸阅读”会临时隐藏外层侧栏、顶部品牌栏和 Tab 栏，仅保留查看器工具栏和 HTML 原文导航，退出时恢复用户此前的侧栏状态。宿主页面不注入或覆盖 iframe 内部 CSS，以保证与直接打开 HTML 的展示一致。

交互伪代码：

~~~javascript
function toggleDocumentReadingMode() {
  app.classList.toggle('document-reading-mode');
  // document-reading-mode 使用 0 0 1fr 网格行，只保留阅读区
  syncDocumentLayoutControls();
}

function renderDocumentHeader(doc) {
  breadcrumb.textContent = formatBreadcrumb(doc.root_name, doc.file_path);
  title.textContent = doc.title;
  meta.textContent = formatMeta(doc.ext, doc.file_size, doc.version, doc.updated_at);
  openWindowButton.hidden = !isHtmlDocument(doc.ext) || !doc.raw_url;
}
~~~

验收标准：工具栏高度压缩且标题/操作不互相挤压；HTML 预览可折叠外层目录并进入沉浸阅读；切换 Markdown 后恢复普通布局；窄屏下操作区换行而不产生横向溢出。

## 10. 技术要点

- **路由顺序**：Express 路由中，固定路径必须在参数路径之前定义
- **元数据管理**：`metadata.json` 与文件系统并行维护
- **Base64 编码**：文档 ID 使用文件路径的 Base64 编码
- **按格式分流**：Markdown 使用现有渲染器，HTML 使用隔离 iframe
- **双模式切换**：预览/编辑共享同一内容数据，切换时保持状态
- **沉浸式展示**：内容区域无边框，与元数据栏无缝衔接
- **行号编辑器**：编辑模式使用 CSS counter 实现行号，无需引入第三方库
- **双层搜索**：前端即时过滤 + 后端全文搜索，防抖 300ms
- **目录树**：后端基于 output/ 目录扫描生成树结构，前端递归渲染

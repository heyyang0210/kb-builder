## 1. 背景与用户故事

仅在正式上传接口返回错误，用户无法直观看到自动转换改变了哪些层级，也无法确认叶子标题的处理。作为上传者，我希望先预检文件、查看源结构与标准结构差异、处理阻断项和未决映射，确认看到的版本后再正式上传；未确认前系统不得写入正式大纲库。

## 2. 范围与非范围

范围：无正式落库副作用的预检 API；转换差异；未决映射决策；中文预览；带内容摘要和短期令牌的确认上传；状态恢复和幂等。

非范围：P4 不计算质量分、不生成 AI 修改建议；不直接编辑原文件；不支持多人实时协作；不引入新前端框架或外部服务。

## 3. 用户流程

```text
选择文件
 → 预检上传
 → 显示方言/统计/阻断问题
 → 显示源树与规范树差异
 → 用户处理未决映射
 → 重新预检并得到 previewToken
 → 用户确认
 → 正式上传校验 token + hash + ruleVersion
 → 安全提交并返回大纲 ID
```

前端状态建议为：`idle → checking → needs_action|ready → confirming → uploaded|failed`。`needs_action` 时确认按钮禁用；重新选择文件、修改映射或规则版本变化都会使旧令牌失效。

## 4. API 契约

### 4.1 POST /api/outline/preflight

请求为 `multipart/form-data`，字段 `file`、可选 `mappingDecisions` JSON、`name`、`type`。接口不写正式 outlines metadata。

```json
{
  "success": true,
  "data": {
    "preflightId": "preflight_<id>",
    "previewToken": "<opaque-short-lived-token-or-null>",
    "expiresAt": "2026-08-17T12:30:00Z",
    "contentHash": "sha256:<hex>",
    "dialect": "heading-tree-v1",
    "specVersion": "1.0.0",
    "ruleVersion": "outline-parser-v1",
    "statistics": { "parts": 10, "chapters": 31, "knowledgePoints": 11 },
    "outline": {},
    "diff": [],
    "diagnostics": [],
    "unresolvedMappings": [],
    "canConfirm": true
  }
}
```

只有 `canConfirm=true` 才签发 `previewToken`。

### 4.2 POST /api/outline/confirm

```json
{
  "previewToken": "<opaque-token>",
  "contentHash": "sha256:<hex>",
  "name": "管理员手册知识点大纲",
  "type": "db",
  "idempotencyKey": "<client-generated-key>"
}
```

成功复用 P3 上传成功契约。令牌过期、摘要不一致、规则版本变化或重复消费返回稳定错误码，绝不使用客户端回传的 `outline` 直接落库。

## 5. 差异契约

```json
{
  "operation": "promote|renumber|add_description|drop|unchanged",
  "sourceRef": { "line": 7, "path": "2/2.1", "text": "## 2.1 数据库初始化配置" },
  "targetRef": { "path": "三、基本数据库管理/3.1 数据库初始化配置/3.1.1" },
  "reasonCode": "LEAF_PROMOTED_BY_USER",
  "explanation": "已按用户确认提升为知识点",
  "requiresConfirmation": false
}
```

禁止用完整文本 diff 代替结构化差异；每个删除、合并、提升、重编号和描述补充都必须可定位。

## 6. 配置策略

预检会话 TTL、最大会话数、令牌签名/存储方式、差异条数上限、允许的映射动作、响应体大小、幂等窗口和中文文案键进入版本化配置。密钥只从安全配置读取。映射决策需符合 JSON Schema，不能传任意代码或正则。

## 7. 伪代码

```text
function preflight(file, decisions):
  parsed = parseAndValidate(file, decisions)
  diff = compareSourceToNormalized(parsed.sourceAst, parsed.outline)
  canConfirm = noBlockingDiagnostics(parsed) and noUnresolvedMappings(parsed)
  session = storeEphemeral(
    sourceBytes=file.bytes,
    normalizedOutline=parsed.outline,
    hash=parsed.hash,
    ruleVersion=parsed.ruleVersion,
    canConfirm=canConfirm,
    ttl=config.preflightTtl
  )
  token = canConfirm ? signReference(session) : null
  return renderPreflight(session, diff, token)

function confirm(token, hash, idempotencyKey):
  session = verifyAndLoad(token)
  assert session.notExpired and session.notConsumed
  assert constantTimeEqual(session.hash, hash)
  assert session.ruleVersion == activeRuleVersion
  result = safeCommit(session.normalizedOutline, session.sourceBytes, idempotencyKey)
  markConsumedAfterCommit(session)
  return result
```

## 8. 中文界面要求

- 顶部展示文件名、识别格式、部分/章节/知识点数量和状态。
- 阻断项按严重度排列，包含行号、原文、原因和操作建议。
- 源结构与目标结构支持切换或并排比较；变化节点有文本标签，不能只靠颜色。
- 未决项使用明确选项控件；确认上传仅在无阻断、无未决且令牌有效时可用。
- 上传失败保留预检结果，允许修复后重试；过期时明确提示重新预检。
- 桌面和移动视口不得出现文字遮挡、溢出或不可操作控件。

## 9. 异常与安全

- 预检数据短期保存并按 TTL 清理，不进入正式列表；存储需限制总量和单用户数量。
- 令牌绑定摘要、规则版本和会话 ID，防重放、防篡改；消费成功后失效。
- 映射决策必须引用当前 `sourceRef`，源摘要变化即拒绝。
- 诊断证据限制长度并转义，防止存储型 XSS。
- 预检与确认均校验权限、速率和请求大小；日志不记录令牌或全文。

## 10. 迁移兼容

保留 P3 直接上传用于已符合标准格式的旧客户端，但应逐步引导新界面走预检确认；是否最终强制预检属于公共 API 决策，需另行确认。P4 不修改旧 metadata。令牌和会话不作为长期业务数据，规则升级后旧令牌自然失效并提示重新预检。

## 11. 验收标准

- 预检相同文件与决策两次，标准树、差异和诊断一致。
- 未确认前，正式 metadata 和文件集合无变化。
- 管理员手册每个叶子歧义均展示行号和选择；处理完后 `canConfirm=true`。
- 确认后的详情树、计数、摘要和预览完全一致。
- 过期、篡改、摘要变化、规则升级、重复消费和重复提交均按契约处理。
- 中文界面在桌面与移动端无重叠/溢出，错误状态可恢复。
- 真实 API 和浏览器端到端流程完整走通。

## 12. 测试策略

- 后端契约测试：预检、决策重算、令牌、确认、幂等和清理。
- 安全测试：令牌篡改/重放、XSS 文本、超量会话、摘要替换、越权访问。
- 前端测试：状态机、禁用条件、中文诊断、结构差异和恢复。
- 真实 API 测试：预检时断言无正式落库，确认后查询详情并比对。
- 视觉验证：桌面/移动截图检查长中文标题、错误列表和差异树。

## 13. 依赖、风险与完成定义

依赖 P2/P3、临时存储策略和鉴权上下文。风险是预检会话占用磁盘、规则升级导致令牌失效、双入口行为差异和差异树的大响应体。新增 API/模块、令牌安全方案和资源限额需人类确认；新增依赖需单独审批。

完成定义：API/状态机/安全评审获批；后端和中文界面实现；管理员手册完成预检到正式上传闭环；测试与视觉证据齐全；设计和 README 同步；`git diff --check` 通过。

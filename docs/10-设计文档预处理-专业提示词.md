# YashanDB 设计文档预处理系统 — 专业提示词

> 版本：v1.0
> 日期：2026-07-23
> 用途：指导设计文档预处理系统的需求分析、方案设计与实现

---

## 一、背景与现状

### 1.1 项目背景

YashanDB 知识库文档生成系统通过「知识点驱动 + AI 智能生成 + 自动化工作流」，将 200+ 数据库知识点自动转化为标准化技术文档。系统依赖多源参考资料：

- **MCP 实时检索**：YashanDB 知识库（最高优先级）
- **设计文档**：`references/design-docs/YashanDB 文档 主页/`（权威来源）
- **Oracle 知识库**：`references/oracle-kb/`（140 篇，~7 万行）
- **测试用例**：`references/test-cases/`
- **源码参考**：`references/source/`

### 1.2 核心问题

`references/design-docs/YashanDB 文档 主页/` 目录包含从 Confluence 导出的 YashanDB 各版本设计文档，是文档生成系统最权威的参考资料来源，但存在以下问题：

**数据规模**：
- 2,596 个 `.md` 文件，~59.5 万行
- 覆盖 4 个主版本（v23.1 ~ v23.4），其中 v23.2 含 12 个小版本
- 文档类型：特性设计(1,118) / 测试设计(1,072) / 需求分析(149) / 概要设计(109) / 开发概要(124) / 架构设计(10)

**质量问题**：
- 87% 文件含内部链接（`conf.yasdb.com`/`jira.yasdb.com`/`pingcode.yasdb.com`），引用不可达
- 42% 文件含图片引用（`![...](...)`），图片大概率不可用
- 每个文件头部含 Confluence 元数据（`Created by ... on ...`）
- 锚点链接（`[text](#anchor)`）干扰 LLM 理解
- v23.2 有 12 个小版本，同一特性跨版本存在大量重复/演进内容

**检索问题**：
- 当前 `retrieval-strategy/index.js` 中的 `executeDesignDocsRetrieval()` 采用简单关键词扫描
- 无法高效定位相关文档，检索噪声大
- 直接加载全部文件会浪费大量 token（~59.5 万行）

### 1.3 当前架构

```
前端 → API → Retriever Agent → MCP/文件检索 → Generator Agent → 文档输出
                    ↓
            retrieval-strategy/index.js
            - executeMcpQueries()
            - executeDesignDocsRetrieval()  ← 需要改造
            - executeOracleKbRetrieval()
            - executeTestCasesRetrieval()
            - executeSourceCodeRetrieval()
```

## 二、核心诉求

### 诉求 1：清洗后的文件易于被 LLM 读取和理解

**关键要求**：
- 去除格式噪音（Confluence 元数据、内部链接、图片引用、锚点链接）
- 统一文档结构（标题层级、章节组织）
- 保留核心知识内容（表格、代码块、正文）
- **关键挑战**：长文档（>1000 行）可能超出 LLM context window，需要语义分块

**业界最佳实践参考**：
- **语义分块（Semantic Chunking）**：按语义边界切分，而非固定长度
  - 使用 embedding 相似度检测语义断点
  - 每个 chunk 保持完整语义单元
  - 支持重叠（overlap）避免上下文丢失
  - 研究表明：语义分块比固定长度分块 Top-1 命中率提升 28%
- **上下文前缀**：为每个 chunk 添加文档元信息（标题、版本、类型）
- **Q&A 对生成**：对关键章节生成问答对，支持问题式检索

**评估标准**：
- LLM 能够在 3 次尝试内从 chunk 中提取出关键信息
- chunk 平均 token 数控制在 500-1500 之间
- 上下文前缀包含足够的元信息（标题、版本、类型、章节）

### 诉求 2：清洗后的文件质量不会下降

**关键要求**：
- 信息完整性：保留全部原始知识内容（表格、代码块、正文）
- 语义完整性：不破坏表格/代码块的完整性（不在内部切分）
- 可追溯性：保留原始文件路径，支持溯源
- **关键挑战**：清洗过程中可能丢失关键上下文（如表格标题与表格分离）

**业界最佳实践参考**：
- **元素级清洗**：使用专门模型识别文档元素类型（标题/表格/代码/段落）
- **结构化保护**：表格和代码块作为整体处理，不在内部切分
- **质量验证**：每个 chunk 经过质量检查（内容长度、结构化元素、上下文完整性）

**评估标准**：
- 表格/代码块保留率 100%
- 关键术语覆盖率 ≥ 95%
- chunk 级质量验证通过率 ≥ 98%

### 诉求 3：支持后续增量文档的训练和知识库体系的扩展

**关键要求**：
- 增量更新：新增文档时仅处理变更文件，不重新处理全部
- 版本管理：追踪文档变更（新增/修改/删除），支持回溯
- 多源扩展：支持其他格式（PDF/Word/HTML）和数据源（Jira/代码仓库）
- **关键挑战**：当前方案仅针对 Confluence 导出的 Markdown，扩展性有限

**业界最佳实践参考**：
- **基于 hash 的增量更新**：计算文件 hash，仅处理变更文件
- **数据源适配器模式**：统一接口，支持多种数据源
- **版本链管理**：保留历史版本关系，支持演进追踪

**评估标准**：
- 增量更新速度 ≥ 50 文件/秒
- 支持至少 3 种数据源（Confluence/PDF/Word）
- 版本回溯支持 ≥ 5 个历史版本

## 三、方案演进路径

### 阶段 1：基础清洗 + 分层索引（当前方案）

**核心思路**：
1. **基础清洗**：6 条规则清理 Confluence 格式噪音
   - 去除元数据、清理内部链接、处理图片引用、清理锚点、统一标题、标注元信息
2. **分层索引**：构建 L1 全局索引 → L2 文档摘要 → L3 清洗原文
   - L1：轻量索引（~130K tokens），支持关键词匹配
   - L2：结构化摘要（~300 tokens/篇），支持相关性判断
   - L3：清洗原文（按需加载），保留完整内容

**优点**：
- 实现简单，可控性强
- 信息完整性好
- 与现有架构兼容
- Token 效率可接受

**缺点**：
- 未做语义分块，LLM 可读性受限
- 缺乏增量更新能力
- 未做深度结构化提取
- 跨版本冗余未处理
- 扩展性有限

### 阶段 2：语义分块 + 增量更新（改进方案）

**核心改进**：
1. **语义分块**：按章节/语义边界切分文档
   - 每个 chunk ~500-1500 tokens
   - 添加上下文前缀（文档标题、版本、类型、章节）
   - 保护表格/代码块完整性
2. **增量更新**：基于文件 hash 的增量处理
   - 仅处理新增/修改的文件
   - 维护文件清单（manifest）
   - 支持删除检测
3. **多源适配**：数据源适配器模式
   - 统一接口，支持 Confluence/PDF/Word
   - 可扩展到 Jira/代码仓库

**预期效果**：
- LLM 可读性显著提升（语义分块 + 上下文前缀）
- 支持增量更新（基于 hash）
- 支持多源数据（适配器模式）
- 接近业界顶级方案水平

### 阶段 3：LLM 驱动的深度结构化（未来方案）

**核心改进**：
1. **实体/关系提取**：使用 LLM 提取技术实体和关系
2. **Q&A 对生成**：为关键章节生成问答对
3. **知识图谱**：构建技术知识图谱，支持图查询
4. **向量检索**：引入向量数据库，支持语义检索

**预期效果**：
- 检索精度最高（语义理解）
- 支持复杂查询（知识图谱）
- 成本较高（需要大量 LLM 调用）

## 四、技术约束

### 4.1 架构约束

- 与现有 `retrieval-strategy/index.js` 对接
- 不引入重型外部依赖（如向量数据库，除非必要）
- 支持渐进式改造，不阻塞现有功能

### 4.2 性能约束

- 清洗速度：≥ 50 文件/秒
- 索引构建：≥ 20 文件/秒（含摘要生成）
- 检索耗时：≤ 5s（含 LLM 摘要读取）
- Token 预算：L1 索引 ≤ 200K tokens

### 4.3 质量约束

- 表格/代码块保留率：100%
- 关键术语覆盖率：≥ 95%
- chunk 级质量验证通过率：≥ 98%
- 检索命中率：已知知识点能匹配到相关设计文档

## 六、关键决策点

### 决策 1：是否引入语义分块？

**选项**：
- A. 不引入：保持完整文档，依赖三层索引控制 token
- B. 引入：按语义边界切分，每个 chunk 带上下文前缀

**建议**：选择 B。理由：
- 长文档（>1000 行）超出 context window 的风险高
- 语义分块可显著提升 LLM 可读性
- 业界研究表明命中率提升 28%

### 决策 2：是否引入增量更新？

**选项**：
- A. 不引入：每次重新处理全部文件
- B. 引入：基于 hash 增量处理

**建议**：选择 B。理由：
- 设计文档会持续更新（新版本发布）
- 增量更新可节省 80%+ 处理时间
- 实现成本低（基于 hash）

### 决策 3：是否引入向量检索？

**选项**：
- A. 不引入：保持关键词匹配 + 三层索引
- B. 引入：向量数据库 + 混合检索

**建议**：暂不引入（阶段 1-2），未来考虑（阶段 3）。理由：
- 当前关键词匹配 + 三层索引已能满足基本需求
- 向量检索需要引入外部依赖（ChromaDB/FAISS）
- 维护成本高（需要定期重建索引）
- 可在阶段 3 作为增强方案引入

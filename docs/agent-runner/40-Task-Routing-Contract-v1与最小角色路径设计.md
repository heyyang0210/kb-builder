# Task Routing Contract v1 与最小执行路径

> 版本：V1.2
> 日期：2026-08-21
> 状态：人工试行；自动路由尚未实现

## 1. 核心原则

先判断当前执行者能否在用户授权内安全闭环；能则直接做，不能再补设计、验证或人工决策。路由的目标是减少无效流程，不是为任务贴更多标签。

- 用户明确提出的功能需求，默认视为产品范围已授权；实现中扩大范围、改变业务规则或出现重大取舍时才重新确认。
- Bugfix 不单独设路径：明确根因、局部可逆且验收清楚时直接处理；需要补设计或独立验证时走标准开发；触及人工边界时走治理任务。
- 规则和角色按需加载。未命中条件的文档不读取、不说明跳过原因。
- 验收方式与风险匹配，不要求所有任务都能完全机器验收。

## 2. 三条路径

| 路径 | 何时使用 | 最小流程 | 默认上下文 |
|---|---|---|---|
| 直接处理 | 查询、文档维护、明确局部 Bugfix、低风险可逆修改 | 执行 -> 相关检查 | 任务、相关文件、工作区底线 |
| 标准开发 | 功能开发、需要补设计、跨文件/模块协作或独立验证 | 设计检查 -> 实施 -> 验证 | 再加载相关模块设计和必要 Role |
| 治理任务 | 命中人工决策边界，或用户明确要求正式项目治理/验收 | 方案与影响 -> 人工决定 -> 实施 -> 独立验证 | 再加载审批、PM、Reviewer 和门禁规范 |

文件数量、跨模块、安全、性能和配置只是判断线索，不自动决定路径。契约稳定、可回退且不扩大权限或公共承诺的修改可以留在直接处理或标准开发。

## 3. 路由判断

按顺序只问三个问题：

1. 是否命中 [Approval Boundary v1](./41-Approval-Boundary-v1人工审批边界.md) 的人工决策边界？是则走治理任务。
2. 是否需要补设计、多人/跨模块协调或独立验证才能可靠完成？是则走标准开发。
3. 其余走直接处理。

执行中发现范围扩大、关键事实冲突、不可回退影响或审批边界时，停止对应受限操作并升级路径；已经完成的安全工作和证据保留，不重走无关流程。

## 4. 最小结果

直接处理只需报告实际结果：

```yaml
outcome: succeeded | failed | needs_decision
changedFiles: []
checks: []
```

标准开发增加设计和验证证据，但不创建完整治理状态：

```yaml
outcome: succeeded | failed | needs_decision
designCheck: passed | updated | not_needed
changedFiles: []
verification: []
knownLimits: []
```

只有治理任务需要任务卡、审批引用、独立审查结论和正式状态迁移。未命中人工边界时，不生成完整 `approvalAssessment`；一句“未触及人工边界”即可，且无需写入固定模板。

## 5. 角色装载

- Architect：产品/架构契约缺失或存在重要取舍时加载。
- Planner：任务复杂到需要拆分、依赖或文件归属协调时加载。
- Worker：需要专业前端或后端实施上下文时加载。
- Test Engineer：需要独立验证或正式验证结论时加载。
- Project Manager、Independent Reviewer：只在治理任务、项目级推进或用户明确要求时加载。
- Doc Writer、Reporter：只在需要专项文档交付或项目事实投影时加载。

角色是责任参考，不是固定 Agent 列表。一个执行者能够完成责任时，不为角色名称额外启动 Agent。

## 6. 校准

V1.2 不实现自动路由、Policy 加载、抽样或事件存储。先用真实任务观察：

- 是否因多余设计、角色和状态造成等待；
- 是否因缺少设计、验证或审批导致返工和风险逃逸；
- 相同质量下耗时和上下文是否下降。

只有重复出现且有证据的问题才增加规则；优先删除无效规则，不以文档完整度衡量治理效果。

# Agent Runner 开发方式分析与阶段规划

## 一、两种开发方式对比

### 方式 A：一次性全流程开发

一次性完成 Phase 1~6 全部代码，最终统一交付。

**优点：**
- 整体架构一致性好，代码风格统一
- 无需阶段间衔接适配
- 最终交付物完整

**缺点：**
- 风险集中：任何模块的返工都会影响全局
- 无法中途验证：前端无法在开发过程中预览效果
- 上下文过长：AI 单次处理 39 天工期的代码量，容易出现遗漏和不一致
- 调试困难：问题定位范围大，排查成本高
- 不可中断：如果中途出错，需要大量回退

### 方式 B：分阶段逐步开发（推荐 ✅）

按 Phase 1→6 逐步实施，每个阶段独立交付可验证的成果。

**优点：**
- 风险分散：每阶段独立验证，问题早发现早修复
- 渐进可见：每个阶段都有可运行的成果，前端可逐步预览
- 上下文可控：每次聚焦一个模块，代码质量更高
- 可调整：后续阶段可根据前序阶段的实际情况调整设计
- 可中断恢复：每阶段有明确交付物，中断后可继续

**缺点：**
- 需要阶段间衔接设计
- 总体耗时略长（约多 10% 的衔接开销）
- 需要维护阶段间的接口约定

## 二、推荐方案：分阶段逐步开发

### 理由

1. **前端预览需求**：用户明确要求"生成的文件需要能够在前端支持进行预览"，这要求后端每完成一个阶段都能与前端联动验证
2. **精美 UI 需求**：CSS 交互和用户体验需要反复打磨，分阶段可以逐步优化
3. **中间过程保留**：分阶段天然支持中间产物管理
4. **项目复杂度**：6 个模块、4 个 Agent、WebSocket 实时通信，一次性开发超出单次上下文能力

### 阶段交付物与验证点

| 阶段 | 交付物 | 可验证成果 |
|------|--------|-----------|
| Phase 1 | 项目骨架 + 配置管理 + API Server + 日志 | `npm start` 启动成功，API 可访问，配置可读写 |
| Phase 2 | BaseAgent + 4 个 Agent + LLM Client | 各 Agent 可独立调用大模型并返回结构化结果 |
| Phase 3 | Workflow 引擎 + 步骤执行器 + 错误重试 + WebSocket | 4 步流程可串联执行，进度实时推送 |
| Phase 4 | MCP Client + FileReader/Writer + ToolManager | 工具可被 Agent 调用，文件可读写 |
| Phase 5 | 前端配置面板 + 进度面板 + 错误处理 + 结果预览 | 完整 UI 交互，可配置→执行→查看结果 |
| Phase 6 | 集成测试 + 端到端验证 | 全流程跑通，生成文档输出到正确目录 |

### 前端预览集成策略

前端预览功能不在最后集中实现，而是分散到合适的阶段：

- **Phase 1 完成后**：前端新增"连接状态指示"，显示后端是否在线
- **Phase 3 完成后**：前端新增"执行进度面板"骨架，接收 WebSocket 数据
- **Phase 5 完成后**：前端完整集成配置面板 + 进度面板 + 结果预览 + 错误处理

## 三、各阶段开发提示词

### Phase 1 提示词

```
根据 01-系统架构设计.md 和 08-开发任务分解.md 中 Phase 1 的内容，实现 Agent Runner 基础框架：

1. 创建项目骨架：package.json、目录结构、.env.example
2. 实现 ConfigManager：配置加载/保存/AES-256 加密/验证
3. 实现 API Server：Express 入口 + CORS + 限流 + 错误处理中间件
4. 实现 Winston 日志系统

验收标准：
- npm start 可启动服务
- GET /api/config/model 返回配置
- POST /api/config/model 可保存配置（API Key 加密存储）
- 日志输出到 logs/ 目录

前端预览：在 prompt-generator.html 中添加连接状态指示器（小圆点），显示后端在线/离线状态。

临时文件放在 agent-runner/tmp/ 目录下。
```

### Phase 2 提示词

```
根据 03-Agent模块设计.md 和 08-开发任务分解.md 中 Phase 2 的内容，实现 Agent 模块：

1. 实现 BaseAgent 基类：execute/buildPrompt/parseResponse 模板方法
2. 实现 LLMClient：OpenAI SDK 封装，支持多厂商（OpenAI/阿里云/智谱）
3. 实现 PlannerAgent：输入知识点 → 输出执行计划 JSON
4. 实现 RetrieverAgent：输入执行计划 → 输出参考资料 Markdown
5. 实现 GeneratorAgent：输入计划+资料 → 输出文档草稿 Markdown
6. 实现 ValidatorAgent：输入文档草稿 → 输出验证报告 JSON + 最终文档

验收标准：
- 每个 Agent 可独立执行并返回正确格式的输出
- LLMClient 支持切换不同厂商 API
- Prompt 模板从文件加载

临时文件放在 agent-runner/tmp/ 目录下。
```

### Phase 3 提示词

```
根据 02-Workflow引擎设计.md 和 08-开发任务分解.md 中 Phase 3 的内容，实现 Workflow 引擎：

1. 实现 WorkflowEngine：工作流创建/启动/状态管理
2. 实现 StepExecutor：步骤执行 + 数据格式转换
3. 实现错误处理：自动重试 3 次 + 失败暂停 + 用户干预（强制继续/终止）
4. 实现 WebSocket 推送：Socket.IO 实时进度更新
5. 实现任务队列：并发控制（最多 3 个任务并行）

验收标准：
- POST /api/agent/execute 启动工作流
- WebSocket 实时推送进度（progress/step_failed/completed）
- 失败步骤重试 3 次后暂停
- POST /api/agent/force-continue/:taskId 可跳过失败步骤

前端预览：在 prompt-generator.html 中添加执行进度面板骨架，接收并显示 WebSocket 进度数据。

临时文件放在 agent-runner/tmp/ 目录下。
```

### Phase 4 提示词

```
根据 04-工具模块设计.md 和 08-开发任务分解.md 中 Phase 4 的内容，实现工具模块：

1. 实现 MCPClient：HTTP 调用 MCP Server + 缓存 + 批量查询
2. 实现 FileReader：读取本地文件 + 批量读取
3. 实现 FileWriter：写入文件 + 自动创建目录 + 唯一路径
4. 实现 ToolManager：工具注册/获取/统一调用接口

验收标准：
- MCPClient 可查询知识库并缓存结果
- FileReader 可读取 templates/ 和 references/ 下的文件
- FileWriter 可将生成文档写入 output/ 对应目录
- Agent 可通过 ToolManager 调用工具

临时文件放在 agent-runner/tmp/ 目录下。
```

### Phase 5 提示词

```
根据 06-前端交互设计.md 和 08-开发任务分解.md 中 Phase 5 的内容，在 prompt-generator.html 中实现完整前端集成：

核心要求：前端界面精美，CSS 交互流畅，用户体验良好。

1. 配置子窗口（Modal）：
   - 三个 Tab：模型配置 / MCP 配置 / Agent 配置
   - Provider 选择联动 Base URL 和 Model 下拉
   - API Key 输入带显示/隐藏切换
   - 连接测试按钮（带 loading 动画）
   - 保存配置调用后端 API

2. 执行进度面板：
   - 进度条动画（带百分比）
   - 4 步流程状态指示（pending/running/completed/failed）
   - 每步可展开查看中间结果（Markdown 渲染 + JSON 格式化）
   - 取消执行按钮

3. 错误处理界面：
   - 错误详情对话框
   - 强制继续 / 终止 两个操作按钮
   - 重试倒计时显示

4. 结果预览：
   - 生成完成后显示最终文档（Markdown 渲染）
   - 验证报告显示（评分 + 检查项列表）
   - 一键复制 / 下载 .md 按钮

CSS 要求：
- 与现有主题系统一致（亮色/暗色联动）
- Modal 打开/关闭有过渡动画
- 进度条有平滑过渡
- 步骤状态切换有颜色过渡
- 按钮有 hover/active 反馈
- 所有交互有视觉反馈（loading、success、error 状态）

临时文件放在 agent-runner/tmp/ 目录下。
```

### Phase 6 提示词

```
根据 08-开发任务分解.md 中 Phase 6 的内容，进行集成测试和优化：

1. 端到端测试：选择知识点 → 配置 → 执行 → 生成文档 → 验证输出
2. API 接口测试：所有 REST API 和 WebSocket 接口
3. 性能优化：MCP 缓存、并发控制、内存检查
4. 前端体验优化：响应式适配、加载状态、错误提示

验收标准：
- 完整流程可跑通
- 生成的文档保存到正确的 output/ 目录
- 前端所有交互正常
- 无内存泄漏

临时文件放在 agent-runner/tmp/ 目录下。
```

## 四、临时文件管理策略

| 类型 | 路径 | 说明 |
|------|------|------|
| 调试日志 | `agent-runner/tmp/debug-*.log` | 开发调试用 |
| 测试输出 | `agent-runner/tmp/test-output/` | 测试生成的文件 |
| 临时配置 | `agent-runner/tmp/test-config/` | 测试用配置 |
| 接口草稿 | `agent-runner/tmp/api-drafts/` | API 设计草稿 |

正式输出始终写入 `output/` 目录，`tmp/` 仅存放开发过程中的临时文件。

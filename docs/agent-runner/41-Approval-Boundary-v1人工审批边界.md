# Approval Boundary v1 人工审批边界

> 版本：V1.0
> 日期：2026-08-21
> 状态：人工执行规范；运行时强制尚未实现

## 1. 目的与原则

本文件是项目人工审批边界的单一事实源，但不是每次任务的必读 Prompt。只有路由显示可能触及受限影响，或执行中出现升级信号时，才展开本文件；目标不是让人审批所有变更，而是让 AI 在明确授权内快速执行。

用户明确提出的功能需求默认视为产品范围已授权。实施该需求本身不重复审批；只有扩大原需求范围、改变关键业务规则/成功标准、引入原需求未包含的重大取舍时，才进入产品决策审批。

判断遵循以下顺序：

1. 命中“必须审批”任一项，停止对应受限操作并返回 `needs_decision`。
2. 未命中必须审批，且能证明满足“默认无需审批”的前提，可以继续执行。
3. 事实未知、证据冲突或无法确定影响时，AI 先做只读分析并给出推荐；不能以猜测选择“无需审批”。
4. 已有批准只覆盖记录中的决策、范围和前提，范围或前提变化后必须重新判断；未触及受限边界的任务不要求创建完整审批记录。

文件数量、代码行数、角色数量和“只是配置修改”都不能单独决定是否审批。判断对象是变更带来的权限、契约、数据、可逆性和责任影响。

## 2. 默认无需人工审批

以下事项在用户已授权的任务范围内，且不命中第 3 节任一项时，可以直接执行并保留相应证据：

### 2.1 只读与分析

- 阅读代码、配置、文档、日志和已有运行结果。
- 搜索、静态分析、差异检查、状态查询和原因诊断。
- 提出方案、设计草案、伪代码、测试计划和审批材料，但不执行受限变更。

### 2.2 局部可逆维护

- 修正文档错字、格式、失效链接和与事实一致的 README 导航。
- 在既有设计和公共契约内修复明确根因的局部缺陷。
- 重构内部实现，但不改变外部可观察行为、公共接口、数据格式和权限边界。
- 调整用户可见文案、样式和布局，但不改变产品规则、关键流程或无障碍承诺。
- 在已批准配置范围内调整非敏感配置；不得扩大权限、数据范围或资源承诺。

### 2.3 测试与验证

- 新增或修复单元、集成、端到端、回归和静态检查。
- 使用隔离 fixture、临时目录、沙箱或明确授权的测试环境进行读写验证。
- 启动本地开发服务、执行构建、测试和真实后端 API 验收，但不得写入生产数据或调用未授权外部服务。
- 修复测试代码和确定性检查本身，但不得降低已批准验收标准来使结果通过。

### 2.4 已批准范围内实施

- 按有效审批记录实施已经批准的方案、接口、依赖或数据操作。
- 完成不扩大批准范围的配套代码、测试、文档和回退准备。
- 普通性能优化可以直接执行，前提是不改变性能承诺、部署拓扑、容量预算、安全边界或外部依赖。

## 3. 必须人工审批

以下任一事项必须在人类明确批准后才能执行对应变更：

### 3.1 产品与业务决策

- 超出用户已明确要求的范围，新增、删除或实质改变产品功能、业务规则、关键用户流程、成功标准或优先级。
- 将有歧义的领域语义、分类、评分、质量门禁或默认策略确认为生产基线。
- 接受无法由测试证明的业务取舍或残余风险。

### 3.2 架构与公共契约

- 新增或删除模块、服务、存储类型，改变技术栈、部署拓扑或核心架构边界。
- 新增、删除或不兼容修改公共 API、事件、Schema、持久化格式、错误语义或对外默认行为。
- 改变兼容周期、迁移策略、回退策略或旧数据处置方式。

兼容性扩展只有在能够证明旧调用、旧数据和既有语义不变时才可免审批；无法证明时按公共契约变更审批。

### 3.3 外部依赖与外部系统

- 引入、替换或删除 npm/Python 包、数据库、模型、MCP、云服务或其他外部服务。
- 新增凭据、网络出口、供应商绑定、付费资源或外部数据传输。
- 对外部仓库、工单、消息、发布平台或其他系统执行会改变状态的操作，除非用户已对该具体操作明确授权。

### 3.4 安全、权限与敏感信息

- 改变认证、授权、ACL、角色权限、租户隔离、密钥、审计或安全策略。
- 扩大任何主体可访问的数据、文件、接口、工具或执行权限。
- 处理、暴露、迁移或改变敏感信息、个人数据和生产凭据的保存方式。
- 接受已知安全缺陷、降低安全控制或绕过安全检查。

### 3.5 数据与不可逆操作

- 对生产或用户真实数据执行新增写入、批量更新、删除、迁移、回填或清理。
- 删除功能、文件、历史记录、索引、快照或其他难以恢复的材料。
- 执行不可逆操作，或回退方案未经验证、恢复成本超出已授权范围。
- 改变数据保留周期、备份、恢复、归档或销毁策略。

### 3.6 性能、资源与运行承诺

- 新增或改变对外性能、可用性、容量、成本或时延承诺。
- 改变生产资源规格、并发上限、限流、超时、重试或降级策略，可能影响稳定性或成本边界。
- 为提升性能而降低正确性、一致性、安全性、可观测性或回退能力。

### 3.7 治理与发布

- 启用自动阻断、自动发布、自动删除、自动迁移或无人值守生产写入。
- 修改审批清单、红线、Policy 阈值、豁免条件或将候选 Role/Skill/Prompt/模型晋级为默认版本。
- 正式发布高风险变更，或接受 Independent Reviewer 尚未解除的有效阻断。

## 4. 不确定项判断

不确定项由 AI 进行事实分析，但不能由 AI 自行扩大授权。AI 至少回答：

```yaml
approvalAssessment:
  proposedAction: 准备执行的具体动作
  knownFacts: 已确认事实和证据路径
  unknowns: 仍不确定的事实
  affectedBoundaries: 产品 | API | 依赖 | 安全 | 数据 | 不可逆 | 性能承诺 | 发布
  reversibility: 可回退 | 有条件可回退 | 不可回退 | 未知
  recommendation: proceed | needs_decision
  rationale: 对照本清单的具体依据
  safeWorkWhileWaiting: 可继续的只读分析、设计或测试准备
```

只有 `unknowns` 不影响第 3 节边界，并且存在证据证明变更属于第 2 节时，才能推荐 `proceed`。否则返回 `needs_decision`，同时继续不依赖该决策的只读分析、方案比较和测试准备。

不得通过拆小任务规避审批；若多个局部改动组合后产生受限影响，以组合后的实际效果判断。

## 5. 审批记录的最小要求

一次有效审批至少记录：

```yaml
approval:
  decision: approved | rejected | revise
  subject: 被审批的具体决策
  scope: 允许实施的范围
  constraints: 必须遵守的条件
  evidenceRefs: []
  rollbackCondition: 回退或停止条件
  approvedBy: human-reference
  approvedAt: timestamp
```

以下情况视为未获批准：只有模糊的“继续”“看着办”；无法定位审批对象；缺少范围；使用其他任务的批准；或者实现扩大了批准范围。

具体审批人、授权有效期、跨任务复用、撤销和等待超时规则尚未确定。本阶段由当前任务中的人类用户作显式决策，运行时不得声称已经自动校验审批。

## 6. 角色边界

- Architect：识别受限决策，提供方案、影响、证据和回退条件，不代替人批准。
- Planner：在任务卡标记 `approvalRequired`、依据和依赖，不自行判断业务取舍。
- Project Manager：核对审批是否覆盖当前范围，未覆盖时保持 `needs_decision/blocked`。
- Worker：执行前核对审批引用；发现范围扩大时停止受限操作。
- Test Engineer：验证实现和审批约束，不批准产品、架构或残余风险。
- Independent Reviewer：质疑审批证据和范围；没有已批准红线时只能提出建议。
- Reporter：只投影审批事实，不创建、解释或扩展授权。

## 7. 清单划分逻辑

清单不按文件数量、技术关键词或角色数量划分，而按“谁有权决定后果”划分：

- AI 可以承担已授权范围内、可验证、可回退的实施判断，因此只读分析、局部维护、测试和已批准实施默认放行。
- 人类必须保留产品价值、组织责任、公共承诺、权限扩大、真实数据处置、不可逆后果和残余风险的决定权，因此这些事项强制审批。
- 安全、性能、配置和跨模块只是影响线索，不是审批结论；例如修复安全缺陷、优化局部算法可免审，但扩大权限、降低安全控制或改变容量承诺必须审批。
- 模型适合整理事实和给出建议，不适合在证据不足时自行授予权限，所以不确定项必须显式转为 `needs_decision`。

这一划分的工程目标是同时控制两类错误：清单过宽导致低风险任务频繁等待，清单过窄导致模型替人作不可授权的决定。V1 优先建立可执行边界，后续依据真实任务中的误阻断和漏阻断样本校准。

## 8. 最小装载摘要

在无法或无需读取全文时，只需保留以下判断：

1. 只读、局部可逆、既有契约内修复、隔离测试和已批准范围内实施，通常可继续。
2. 超出已授权范围的产品规则，以及公共契约、外部依赖、权限/敏感数据、生产真实数据、不可逆操作、资源承诺和残余风险接受，必须停下请求人工决定。
3. 事实不明、证据冲突或范围扩大时，不猜测放行；先做只读分析并返回 `needs_decision`。

摘要不能替代专项判断；一旦涉及上述第二、三类情况，应加载本文件全文。

## 9. 后续优化顺序

1. 确认审批主体、代理关系和各类决策的责任人映射。
2. 确认审批粒度、有效期、跨任务复用、撤销、超时和等待期间允许动作。
3. 用代表性任务与反例校准清单，记录误阻断、漏阻断、人工改判和范围扩大事件。
4. 规则稳定后再设计版本化 Policy、结构化审批存储和运行时门禁；未完成前三步前不启用自动批准或自动阻断。

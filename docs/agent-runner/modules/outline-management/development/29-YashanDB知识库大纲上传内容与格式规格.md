# YashanDB 知识库大纲上传内容与格式规格

> documentType: development-design
> moduleId: outline-management
> owner: Architect
> 规格版本：1.0.0
> 更新日期：2026-08-17
> 适用系统：`agent-runner` 中的 YashanDB 知识库文档生成器
> 用途：作为知识点大纲上传、解析、评分和修改建议的统一基线。

---

## 1. 适用边界

本文规范的是“知识点大纲上传”，对应接口为 `POST /api/outline/upload`。

它不是 PingCode 素材平台的“本地素材上传”。后者支持 Office、PDF、图片、压缩包和大文件分片，对应 `tools/pingcode-cli` 链路，不适用于本文的 10 MB 大纲限额和三种大纲格式。

本规格将要求分为三类：

| 类别 | 含义 | 不满足时的结果 |
|---|---|---|
| 实现硬约束 | 当前前后端已执行的校验或解析规则 | 拒绝上传、解析失败，或上传后得到 0 个知识点 |
| 质量推荐规则 | 为保证生成质量而建议遵守，当前未在上传 API 强制 | 评分扣分或建议修改 |
| 待增强项 | 当前实现缺少但应补充的防护 | 不得对外宣称已强制校验 |

## 2. 当前上传接口硬约束

### 2.1 文件约束

| 检查项 | 实现硬约束 | 检查位置 |
|---|---|---|
| 扩展名 | 仅 `.json`、`.md`、`.csv`，不区分大小写 | 前端和后端 |
| 单文件大小 | 不得超过 `10 * 1024 * 1024` 字节，即 10 MiB | 前端和 Multer 后端 |
| 上传数量 | 每次一个文件 | `upload.single('file')` |
| 请求类型 | `multipart/form-data` | 上传路由 |
| 文件表单字段 | `file` | 前端和后端 |
| 大纲名称 | 表单字段 `name`；不传时使用原始文件名 | 后端 |
| 大纲类型 | 表单字段 `type`；不传时为 `db` | 后端 |
| 已解析内容 | 可选表单字段 `content`，值必须是 JSON 字符串 | 前端上传器/后端 |

推荐使用 UTF-8 无 BOM 编码。当前前端使用 `FileReader.readAsText`，后端使用 `fs.readFileSync(..., 'utf-8')`；实现没有独立编码检测，非 UTF-8 文件可能乱码且不会给出准确的编码错误。

### 2.2 请求和响应示例

```bash
curl -X POST "http://localhost:4100/api/outline/upload" \
  -F "file=@./outlines/共享集群领域知识点大纲.md" \
  -F "name=共享集群领域知识点大纲" \
  -F "type=db"
```

成功响应：

```json
{
  "success": true,
  "data": {
    "id": "outline_1780000000000",
    "name": "共享集群领域知识点大纲",
    "kp_count": 89,
    "message": "大纲上传成功"
  }
}
```

错误响应统一为 HTTP 400：

```json
{
  "success": false,
  "message": "只支持 JSON、Markdown、CSV 格式"
}
```

注意：前端可能在请求发出前抛出“文件格式不支持或文件过大”；超过 10 MiB 时后端的 Multer 错误文本可能不同。

## 3. 归一化后的标准大纲树

无论上传 JSON、Markdown 还是 CSV，后续生成流程期望使用以下结构：

```json
{
  "title": "YashanDB 知识点大纲",
  "parts": [
    {
      "part": "一、数据库基础",
      "level": "⭐",
      "chapters": [
        {
          "name": "1.1 数据库基本概念",
          "kps": [
            {
              "id": "1.1.1",
              "name": "数据库的定义",
              "desc": "说明数据库的组成、边界与核心价值"
            }
          ]
        }
      ]
    }
  ]
}
```

当前实现没有 JSON Schema 校验。为保证后续知识点选择和提示词生成可用，应将下表视为质量必填契约：

| 路径 | 类型 | 质量要求 |
|---|---|---|
| `title` | string | 非空，准确表达大纲范围 |
| `parts` | array | 至少 1 项 |
| `parts[].part` | string | 非空，部分名唯一 |
| `parts[].level` | string | 建议为 `⭐`、`⭐⭐`、`⭐⭐⭐` |
| `parts[].chapters` | array | 至少 1 项 |
| `chapters[].name` | string | 建议为“二级编号 + 章节名” |
| `chapters[].kps` | array | 至少 1 项 |
| `kps[].id` | string | 全大纲唯一，建议三级数字编号 |
| `kps[].name` | string | 非空，单一、明确、可作为文档标题 |
| `kps[].desc` | string | 非空，描述边界、要点或验证目标，不建议只重复 `name` |

## 4. Markdown 格式

### 4.1 能被当前解析器识别的语法

```markdown
# YashanDB 数据库知识点大纲

## 一、数据库基础 ⭐
- **1.1 数据库基本概念**
  - 1.1.1 ⭐ 数据库的定义：说明数据库的组成、边界与核心价值
  - 1.1.2 ⭐⭐ DBMS 核心能力：说明定义、操纵、事务和安全能力
```

硬解析规则：

1. 大纲标题使用 `# `；后端取最后一个匹配标题，没有时为“上传的大纲”。
2. 部分必须匹配 `## 中文数字、部分名 [可选星级]`；当前仅接受一至十的中文数字字符组合。
3. 章节必须是 `- **x.y 章节名**`，且必须位于已识别的部分之后。
4. 知识点必须是 `- x.y.z [可选星级] 名称：描述`，且必须位于已识别的章节之后。
5. 名称和描述仅使用第一个中文全角冒号 `：` 分隔。英文冒号 `:` 不会拆分描述；无全角冒号时 `desc` 自动等于 `name`。
6. 空行、`---`、表格行、代码围栏标记、部分树形图行和特定说明项会被忽略。普通说明段落不会进入标准大纲树。
7. 前端解析后会丢弃知识点星级，因此不应依赖 `kps[].difficulty` 被持久化。

实际大纲可包含“文档说明、大纲定位、目标人群、前置知识、难度分级、学习路径、章节依赖”等人读说明，但当前大纲树不保留这些内容。

### 4.2 常见的不可解析写法

| 写法 | 问题 | 修改为 |
|---|---|---|
| `## 第一部分 基础` | 不匹配中文序号加顿号 | `## 一、基础` |
| `### 1.1 基本概念` | 章节不使用列表加粗 | `- **1.1 基本概念**` |
| `- 1.1 基本概念` | 章节缺少 `**` | `- **1.1 基本概念**` |
| `- 1.1.1 名称: 描述` | 英文冒号不分割名称和描述 | `- 1.1.1 名称：描述` |
| 知识点出现在章节前 | `currentChapter` 为空 | 先定义部分和章节 |

## 5. JSON 格式

JSON 文件必须是语法有效的 JSON，并直接使用第 3 章的标准树结构。顶层不得再包一层 `data` 或 `outline`。

当前前端只执行 `JSON.parse`，不校验字段、类型、空数组、重复 ID 或层级。因此：

- 损坏 JSON 会在前端报“JSON 格式错误”。
- 语法有效但结构错误的 JSON 可能上传成功，但 `kp_count` 为 0 或后续界面不可用。
- 若绕过前端且不提供 `content`，后端会把 JSON 文件当 Markdown 文本解析，并可能以 0 个知识点“成功”入库。

## 6. CSV 格式

当前 CSV 解析器要求至少包含表头和一行数据，预期表头为：

```csv
chapter,kp_id,name,desc
1.1 数据库基本概念,1.1.1,数据库的定义,说明数据库的组成、边界与核心价值
1.1 数据库基本概念,1.1.2,DBMS 核心能力,说明定义、操纵、事务和安全能力
```

归一化行为：

- 所有内容进入一个 `默认部分`，难度为 `⭐`。
- 按 `chapter` 原始字符串分组为章节。
- `kp_id` 缺失时生成随机 ID，`name` 缺失时为“未命名”，`desc` 缺失时为空字符串。这是当前容错行为，不是合格输入标准。

重要限制：当前使用简单的 `split(',')`，不是标准 CSV 解析器。即使用双引号包围，单元格内的英文逗号仍会错位。在修复解析器前，不得在任何字段中使用英文逗号 `,`；可改用中文逗号 `，`。

## 7. 质量推荐规则

下列规则不是当前上传 API 的硬校验，但是将大纲用于高质量文档生成的建议准入条件：

1. 每个大纲至少有 1 个部分、1 个章节和 1 个知识点。
2. `part`、章节名、知识点 ID 在各自作用域内唯一；知识点 ID 全大纲唯一。
3. 章节编号与所属部分顺序一致，知识点 `x.y.z` 与所属章节 `x.y` 一致。
4. 每个知识点只覆盖一个可独立成文的主题；同义项应合并，复合项应拆分。
5. `name` 使用稳定的数据库/YashanDB 术语，不使用“其他”“杂项”“高级内容”等模糊名称。
6. `desc` 至少说明内容边界和预期覆盖点；不应只重复名称。
7. 顺序应符合前置概念→机理→操作→验证→故障/调优的学习或业务依赖。
8. 大纲应说明目标人群、前置知识、难度口径、版本范围和资料来源线索。
9. 每个知识点都应能映射到七类模板之一：通用基础、理论机制、实战调优、架构对比、运维 SOP、SQL/开发参考、兼容性差异。
10. 每个知识点都应能设计至少一个可验证结果；兼容性类应明确对比数据库。

## 8. 大纲评分规则

### 8.1 阻断项

先执行可解析性检查，再计算质量得分。命中任一阻断项时，结论一律为“不可上传/不可进入批量生成”：

- 扩展名不是 `.json`、`.md`、`.csv`，或单文件超过 10 MiB。
- JSON/CSV 语法无法解析，或 Markdown 不包含可识别的标准层级。
- 归一化后 `parts` 为空，或知识点总数为 0。
- 任一知识点缺少 `id`、`name` 或所属章节。
- 存在重复知识点 ID，导致后续选择无法稳定定位。
- 文件包含未脱敏的凭据、客户数据、个人信息或内网敏感信息。

其中“重复 ID”和“敏感信息”是评分器应执行的推荐阻断规则，当前上传 API 尚未强制。

### 8.2 百分制

| 维度 | 分值 | 满分标准 |
|---|---:|---|
| 格式与可解析性 | 20 | 文件限制、格式语法和标准树全部正确，且无阻断项 |
| 层级与字段完整性 | 15 | 部分、章节、知识点层级完整，必要字段非空 |
| 标识和编号稳定性 | 10 | ID 唯一，三级编号与章节一致，不使用随机 ID |
| 描述可生成性 | 15 | 名称边界清晰，描述足以指导文档生成且可验证 |
| 领域覆盖与去重 | 15 | 核心领域覆盖合理，无明显缺失、同义重复或极端粒度 |
| 学习路径与难度 | 10 | 前置关系清晰，顺序递进，目标人群和难度口径明确 |
| 模板映射与验证准备 | 10 | 各知识点可映射模板，可设计操作、查询、观测或对比验证 |
| 版本与来源准备度 | 5 | 大纲有版本范围与 MCP/设计文档/测试用例线索 |
| **合计** | **100** |  |

分级与准入：

| 得分 | 等级 | 结论 |
|---:|---|---|
| 90–100 | A | 可直接作为批量生成输入，仅需人工复核专业覆盖 |
| 80–89 | B | 修复明确扣分项后可进入批量生成 |
| 60–79 | C | 需修改层级、描述、粒度或覆盖，不建议直接生成 |
| 0–59 | D | 需重构大纲 |

建议放行条件：无阻断项、总分不低于 80，且“格式与可解析性”为 20 分。

### 8.3 评分伪代码

```text
function review(file, normalizedOutline):
  blockingIssues = validateUploadContract(file)
  blockingIssues += validateRequiredTree(normalizedOutline)
  blockingIssues += findDuplicateKnowledgePointIds(normalizedOutline)
  blockingIssues += detectSensitiveContent(file)

  dimensionScores = scoreAllDimensions(normalizedOutline)
  totalScore = sum(dimensionScores)

  if blockingIssues is not empty:
    decision = "blocked"
  else if totalScore >= 90:
    decision = "ready"
  else if totalScore >= 80:
    decision = "revise_then_ready"
  else:
    decision = "revise"

  return buildReviewReport(totalScore, dimensionScores,
                           blockingIssues, decision)
```

## 9. 评分与修改建议输出契约

机器可读输出建议使用：

```json
{
  "specVersion": "1.0.0",
  "file": "待评审大纲.md",
  "score": 82,
  "grade": "B",
  "decision": "revise_then_ready",
  "dimensionScores": [
    {
      "id": "description_quality",
      "name": "描述可生成性",
      "score": 10,
      "maxScore": 15,
      "evidence": ["2.3.4 只包含名称，无描述"]
    }
  ],
  "blockingIssues": [],
  "recommendations": [
    {
      "severity": "high",
      "location": "2.3.4",
      "issue": "desc 与 name 相同，不足以限定文档内容",
      "action": "补充机制边界、关键步骤和可验证结果",
      "acceptance": "desc 至少包含覆盖点和验证方式"
    }
  ]
}
```

人读报告必须同时包含：总分与等级、阻断项、分项得分与证据、按严重度排序的问题、可执行修改动作、可测量验收条件，以及至少一段修改后示例。

修改建议必须引用具体 ID、章节或原文，不得只写“优化结构”“提高完整性”等无法验收的笼统意见。

## 10. 实现差距与待办

以下项目尚未在当前上传链路强制，后续实现时应将规则、权重和阈值放入版本化配置，不在业务代码中硬编码：

- [ ] 上传后服务端按扩展名选择 JSON、Markdown 或 CSV 解析器，不依赖前端 `content`。
- [ ] 引入标准 JSON Schema 和 CSV 解析器。
- [ ] 拒绝空文件、空树、0 知识点、必填字段缺失和类型错误。
- [ ] 检查重复 ID、编号与父级不一致、重复名称和随机 ID。
- [ ] 统一前后端 Markdown 标题解析逻辑并保留知识点难度。
- [ ] 返回结构化错误码、文件行号、字段路径和修改提示。
- [ ] 增加上传前预检和大纲评分接口，将本文评分表转为可配置规则。

## 11. 规格核对记录

| 样本 | 核对结果 |
|---|---|
| `agent-runner/outlines/outline_1783581157782_guxcaa.md` | 能匹配“中文序号部分→加粗章节→三级知识点”；大量无冒号条目的 `desc` 会等于 `name` |
| `outlines/共享集群领域知识点大纲.md` | 结构模式与当前 Markdown 解析器目标一致；人读说明区不会进入标准树 |
| `## 第一部分` + `### 1.1` + `- 知识点` | 三层都不匹配当前正则，归一化后为 0 知识点；当前后端仍可能返回上传成功 |

# 管理员手册大纲兼容阶段五：评分、修改建议与持续治理设计

> documentType: development-design
> moduleId: outline-management
> owner: Architect / Backend Worker / Test Engineer
> 阶段：P5
> 状态：设计待评审，评分门禁和运营数据策略需人类确认
> 前置：P4 预检确认闭环完成
> 目标时限：批准后 3 个工作日内完成配置化评分、建议和运营基线

## 1. 背景与用户故事

格式可上传不代表大纲适合批量生成。规格 1.0.0 已定义 100 分维度、阻断项和修改建议契约，但尚未成为可版本化、可回归、可运营的能力。作为知识库维护者，我希望在预检中看到有证据的分项得分和可执行修改建议，修改后能稳定复评；作为管理员，我希望知道哪些规则有效、哪些误报高，并能审计规则版本变化。

## 2. 范围与非范围

范围：确定性规则评分；配置化权重/阈值/文案模板；证据与建议；准入决策；规则版本治理；脱敏运营指标和人工反馈闭环。

非范围：不对生成文档的事实正确性评分；不自动执行修改；不让大模型直接决定准入；不采集完整敏感正文；不在本阶段引入外部模型或服务。

## 3. 架构与流程

```text
P4 标准大纲 + 诊断
 → 阻断规则
 → 维度规则执行器
 → 分数聚合器
 → 建议模板渲染器
 → 准入策略
 → 评分报告
 → 用户修改/人工反馈
 → 脱敏指标与规则版本评审
```

解析与评分解耦：解析器只说明结构是否成立，评分器只消费版本化标准 AST 和上下文。相同 AST、规格版本和规则版本必须得到相同结果。

## 4. 评分配置与配置策略

配置建议：

```json
{
  "specVersion": "1.0.0",
  "ruleVersion": "outline-quality-v1",
  "dimensions": [
    { "id": "format", "weight": 20, "rules": ["non_empty_tree"] },
    { "id": "completeness", "weight": 15, "rules": ["required_fields"] }
  ],
  "thresholds": { "ready": 90, "reviseThenReady": 80 },
  "admission": { "minimumScore": 80, "requiredDimensionScores": { "format": 20 } },
  "messageCatalogVersion": "zh-CN-v1"
}
```

完整八维权重必须与规格第 8 章合计 100。启动时校验维度唯一、权重合计、阈值顺序、规则实现存在和消息模板完整；失败时禁用评分门禁并告警，不能静默套用旧配置。规则提示词若未来引入，同样必须版本化配置，不写入业务代码。

## 5. 评分报告契约

```json
{
  "reportId": "review_<id>",
  "specVersion": "1.0.0",
  "ruleVersion": "outline-quality-v1",
  "contentHash": "sha256:<hex>",
  "score": 82,
  "grade": "B",
  "decision": "revise_then_ready",
  "dimensionScores": [{
    "id": "description_quality",
    "name": "描述可生成性",
    "score": 10,
    "maxScore": 15,
    "evidence": [{ "path": "2.4.1", "sourceLine": 15, "code": "DESC_EMPTY" }]
  }],
  "blockingIssues": [],
  "recommendations": [{
    "id": "rec_<stable-id>",
    "severity": "high",
    "location": "2.4.1",
    "issue": "知识点缺少描述",
    "action": "补充内容边界、关键步骤和验证结果",
    "acceptance": "描述包含至少一个覆盖点和一个验证方式",
    "ruleId": "description_has_boundary_and_validation"
  }],
  "evaluatedAt": "2026-08-17T12:00:00Z"
}
```

报告时间不参与确定性比较。建议稳定 ID 由内容摘要、规则 ID 和位置派生，便于追踪修复率。

## 6. 接口集成

P4 `POST /api/outline/preflight` 响应增加 `review`。也可提供 `POST /api/outline/review` 供已标准化 AST 复评，但是否新增独立接口由架构评审决定。正式确认时重新校验报告绑定的 `contentHash/ruleVersion`，并按门禁策略判断：

- 有阻断项：`blocked`，禁止确认。
- 无阻断且分数不低于 90：`ready`。
- 无阻断且 80-89：`revise_then_ready`；默认要求修复后复评，是否允许有权限的人工豁免需确认。
- 低于 80：`revise`，禁止进入批量生成。

## 7. 伪代码

```text
function reviewOutline(outlineAst, context, config):
  validateScoringConfig(config)
  blocking = runBlockingRules(outlineAst, context, config)
  dimensions = []
  for dimension in config.dimensions:
    results = runDeterministicRules(dimension.rules, outlineAst, context)
    dimensions.add(aggregateWithEvidence(dimension, results))

  score = sum(dimensions.score)
  decision = decide(blocking, score, dimensions, config.admission)
  recommendations = renderRecommendations(
    failedRules(dimensions, blocking),
    catalog=config.messageCatalogVersion
  )
  return immutableReport(outlineAst.hash, config.versions, decision,
                         dimensions, blocking, recommendations)
```

## 8. 修改建议策略

- 每条建议必须定位到知识点 ID、字段路径或源行，并引用触发规则。
- 建议必须包含问题、动作和可测量验收条件，不使用“优化结构”等空泛文字。
- 对同一问题去重并按阻断、高、中、低排序；不因建议数量重复扣分。
- 系统只提供修改候选，不直接改写原稿或已确认标准树。
- 未来可增加 AI 建议器，但只能消费脱敏上下文并作为非决定性补充；模型、提示词、安全和成本需另立设计并审批。

## 9. 持续治理

### 9.1 版本生命周期

规则配置经历 `draft → review → active → deprecated`。激活需要双人评审、固定回归集通过、分数差异报告和回滚版本。历史报告永远保留其 `ruleVersion`，不后台重算。

### 9.2 脱敏指标

可记录：规则命中次数、阻断率、人工接受/驳回建议数、修改后通过率、误报反馈、各方言失败率、P95 评分耗时。默认不记录完整正文、凭据或客户标识；低样本量聚合需抑制展示。

### 9.3 反馈契约

```json
{
  "reportId": "review_<id>",
  "recommendationId": "rec_<id>",
  "outcome": "accepted|rejected|partially_accepted",
  "reasonCode": "NOT_APPLICABLE|FALSE_POSITIVE|DOMAIN_REVIEW|OTHER",
  "comment": "<可选、受长度与脱敏限制>",
  "actorRole": "reviewer"
}
```

反馈只用于规则评审，不自动在线调整权重，避免不可审计漂移。

## 10. 异常与安全

- 配置签名/摘要、权限和审计日志防止未授权改权重或阈值。
- 报告和反馈按最小权限访问；证据片段转义并限制长度。
- 敏感信息检测本身为阻断项，原文不进入运营指标。
- 评分超时或内部错误采用“失败关闭”：不能标为通过，并返回可重试错误。
- 人工豁免若批准，必须记录操作者、理由、原决策、目标版本和有效期。

## 11. 迁移兼容

P5 初期可只展示评分，不立即阻断正式上传；经过影子运行和误报评审后再启用门禁。门禁启用、阈值变化和人工豁免属于产品/公共行为决策，需人类确认。旧记录可按需显式复评，但报告标注“非上传时评分”，不得伪装为历史准入结果。

## 12. 验收标准

- 八维权重合计 100，配置校验能拒绝缺规则、重复维度和非法阈值。
- 同一 AST、上下文和规则版本重复评分结果一致。
- 管理员手册及固定正反样本的分项分、证据、建议和决策符合规格。
- 每个扣分都有证据；每条建议都有位置、动作和验收条件。
- 有阻断项或不满足准入阈值时不能进入批量生成。
- 规则版本升级产生可审阅差异报告且可回滚。
- 运营指标不含原始正文或敏感标识，反馈不会自动修改线上规则。

## 13. 测试策略

- 配置契约测试：权重、阈值、规则注册、消息目录、版本升级。
- 黄金样本测试：固定输入的分数、证据、建议和决策快照。
- 变形测试：仅修复一个问题时对应维度不下降，其他无关维度不漂移。
- 安全测试：越权改配置、证据 XSS、敏感信息、超长反馈、评分超时。
- 真实 API 测试：预检得到评分、修改后复评、确认门禁和详情追溯。
- 影子运行：启用门禁前统计至少一个约定观察周期的误报和人工反馈。

## 14. 依赖、风险与完成定义

依赖 P4 的摘要绑定和预检流程、规格 1.0.0、固定回归集及领域审核者。风险包括规则鼓励机械凑分、描述质量难以纯规则判断、阈值误伤和运营数据隐私。评分门禁、指标留存、豁免机制和任何 AI/外部依赖都需人类确认。

完成定义：配置和治理方案评审通过；确定性评分、建议、版本审计和反馈实现；影子运行证据达到约定门槛后才启用门禁；真实 API、黄金样本和安全测试通过；相关设计/README/运营手册同步；`git diff --check` 通过。

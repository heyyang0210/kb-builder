# 管理员手册大纲兼容阶段二：统一解析与结构化诊断设计

> documentType: development-design
> moduleId: outline-management
> owner: Architect / Backend Worker
> 阶段：P2
> 状态：设计待评审，实施需人类确认
> 前置：P1 基线与规范副本完成
> 目标时限：批准后 2 个工作日内完成接口、实现和契约测试

## 1. 背景与目标

当前浏览器和后端各维护一套 Markdown 正则，行为存在漂移；后端还信任客户端提交的 `content`，并允许 0 知识点写入。通用预处理设计中的 `sections` 树也不等于大纲业务所需的 `parts → chapters → kps`。

P2 建立服务端单一解析入口：先产生保留来源位置的统一 AST，再按方言适配为标准大纲，并输出稳定、中文、可定位的结构化诊断。前端仅消费服务端结果，不再作为解析事实来源。

## 2. 用户故事

作为上传者，我希望系统识别标准 Markdown 或普通标题树，并在无法确定映射时指出具体行、原因和修改动作，而不是显示“上传成功但没有知识点”。

## 3. 范围与非范围

范围：标准 Markdown、标题树 Markdown 的识别与归一化；统一 AST；字段和树校验；结构化诊断；0 知识点阻断；前后端计数一致。

非范围：不新增预检确认页面；不实现评分；不自动生成领域描述；不支持 PDF/DOCX；默认不引入第三方解析依赖。

## 4. 架构

```text
上传文件字节
  → 文件契约校验/UTF-8 检测
  → 方言探测器
  → Dialect Parser
  → Source AST（含行列和原文）
  → Normalizer
  → Outline AST（标准树）
  → Validator
  → Diagnostic Report
```

建议模块边界：`dialect-detector` 只判断候选及置信度；解析器只构建源 AST；归一化器只做可解释映射；校验器不改数据；诊断器负责错误码到中文消息模板的渲染。路由只编排，不包含正则和规则。

## 5. 统一 AST 契约

```json
{
  "astVersion": "outline-ast-v1",
  "dialect": "heading-tree-v1",
  "source": { "filename": "示例.md", "sha256": "<hex>", "encoding": "utf-8" },
  "outline": {
    "title": "YashanDB 数据库管理员手册",
    "parts": [{
      "id": "part-2",
      "name": "基本数据库管理",
      "sourceRef": { "line": 5, "column": 1, "raw": "# 2. 基本数据库管理" },
      "chapters": [{
        "id": "2.4",
        "name": "进程/线程管理",
        "sourceRef": { "line": 13, "column": 1 },
        "kps": [{
          "id": "2.4.1",
          "name": "进程/线程体系介绍",
          "desc": "",
          "sourceRef": { "line": 15, "column": 1 }
        }]
      }]
    }]
  },
  "unresolvedMappings": []
}
```

运行时标准树可继续兼容现有 `part/level/chapters/kps` 字段；`sourceRef` 和内部稳定 ID 是否持久化由实施评审决定，不要求旧消费者立即识别新字段。

## 6. 解析接口与诊断契约

服务层接口：

```text
parseOutline(buffer, filename, options) -> ParseResult
validateOutline(outline, context) -> Diagnostic[]
```

`ParseResult`：

```json
{
  "success": false,
  "dialect": "heading-tree-v1",
  "dialectConfidence": 0.98,
  "specVersion": "1.0.0",
  "ruleVersion": "outline-parser-v1",
  "astVersion": "outline-ast-v1",
  "contentHash": "sha256:<hex>",
  "knowledgePointCount": 11,
  "outline": {},
  "diagnostics": [{
    "code": "OUTLINE_UNRESOLVED_LEAF",
    "severity": "error",
    "message": "二级叶子标题无法确定为章节或知识点",
    "location": { "line": 7, "column": 1, "path": "2/2.1" },
    "evidence": "## 2.1 数据库初始化配置",
    "action": "补充三级知识点，或确认将该标题提升为知识点"
  }],
  "unresolvedMappings": []
}
```

最低错误码集：`UNSUPPORTED_FORMAT`、`INVALID_ENCODING`、`DIALECT_AMBIGUOUS`、`PARSE_SYNTAX_ERROR`、`UNRESOLVED_LEAF`、`EMPTY_OUTLINE`、`ZERO_KNOWLEDGE_POINTS`、`REQUIRED_FIELD_MISSING`、`DUPLICATE_KP_ID`、`NUMBERING_MISMATCH`。对外建议加统一 `OUTLINE_` 前缀。

## 7. 方言与配置策略

版本化配置至少包含：支持扩展名、文件上限、方言特征、标题层级映射、叶子策略、编号策略、字段必填规则、诊断消息键和规则版本。配置加载失败必须快速失败，不退回隐式正则。

标题树默认策略为“保守”：H1→部分、含 H3 的 H2→章节、H3→知识点；叶子 H1/H2 进入未决映射并阻断正式写入。自动提升只能由显式请求选项和用户确认驱动。

## 8. 伪代码

```text
function parseOutline(bytes, filename, options):
  fileInfo = validateFileContract(bytes, filename)
  text = decodeUtf8Strict(bytes)
  dialect = detectDialect(text, configuredDetectors)
  if dialect.isAmbiguous: return failure(DIALECT_AMBIGUOUS)

  sourceAst = parsers[dialect.id].parse(text, preserveSource=true)
  normalized = normalizers[dialect.id].normalize(sourceAst, options)
  diagnostics = validate(normalized.outline)
  diagnostics += normalized.unresolvedDiagnostics

  return buildResult(
    outline=normalized.outline,
    diagnostics=sortBySourceAndSeverity(diagnostics),
    success=noBlockingDiagnostic(diagnostics)
  )
```

路由不得优先采用客户端 `content`。如果为兼容保留该字段，服务端必须用文件重新解析并比对摘要/结构，不一致则拒绝。

## 9. 异常与安全

- 严格按字节上限、扩展名、编码和解析深度限制输入，防止资源耗尽。
- 诊断只返回必要原文片段，日志不记录完整敏感内容。
- 文件名规范化，持久化路径由服务端生成，防止路径穿越。
- 解析失败、0 知识点、重复 ID 和未决映射均不得进入写文件/metadata 阶段。
- 同一输入、规则版本和选项必须产生确定性结果，不生成随机 ID。

## 10. 迁移与兼容

- 标准 Markdown 的既有有效输入必须得到等价标准树和相同知识点计数。
- 旧 `content` 字段先标记弃用并记录使用量；过渡期可接受但不信任，后续版本删除需另行确认。
- 旧 metadata 继续可读；列表接口不得在读取时静默用新规则改写旧记录。
- 0 知识点由成功改为结构化失败属于公共行为变更，实施前必须获得人类确认并发布迁移说明。

## 11. 验收标准

- 当前管理员手册样本被识别为 `heading-tree-v1`，基线标题统计不变，11 个显式 H3 可追溯到源行。
- 所有叶子 H1/H2 都进入未决映射，不静默丢弃或自动虚构描述。
- 标准格式回归样本的树与计数保持一致。
- 空树、0 知识点、重复 ID、缺字段在任何持久化前失败。
- 前端展示的方言、计数、树和诊断完全来自服务端结果。
- 每条阻断诊断包含稳定错误码、中文消息、位置、证据和修改动作。

## 12. 测试策略

- 解析器单元测试：两种方言、CRLF/BOM、混合标题、代码块内伪标题。
- 契约测试：AST Schema、错误码、确定性、行号和排序。
- 属性测试思路：任意失败输入不得产生可持久化结果；重复解析结果一致。
- 回归测试：标准 Markdown、JSON、CSV 既有行为；JSON/CSV 的服务端统一解析另行按规格任务实现。
- 真实 API 测试在 P3 执行，P2 至少提供可由路由调用的服务层契约测试。

## 13. 依赖、风险与完成定义

依赖 P1 样本、规格 1.0.0 和现有技术栈。主要风险是标题层级不等于领域语义、前端对旧 `content` 的依赖以及规则扩展导致误识别。新增模块与公共行为变化需人类确认；如需第三方 Markdown 解析库须单独审批。

完成定义：设计评审和公共行为变更获批；统一 AST、配置、两类解析器、校验器和诊断契约完成；相关设计同步；测试通过；无随机 ID、无规则散落硬编码；`git diff --check` 通过。

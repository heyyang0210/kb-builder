## 1. 背景

用户希望上传 `outlines/yashan数据库管理员手册知识点大纲.md` 生成知识点大纲。样本是普通 Markdown 标题树，包含 10 个一级标题、31 个二级标题和 11 个三级标题；现有上传器要求“中文序号部分 → 加粗列表章节 → 三级列表知识点”。当前样本会归一化为 0 个知识点，但后端仍可能返回成功。

P1 不修改系统行为，先保留原文件并交付可由现有上传接口消费的规范副本，为后续兼容解析建立可重复基线。

## 2. 用户故事

作为知识库维护者，我希望得到一份不覆盖原稿、每个转换动作可追溯、歧义项可人工确认的规范大纲，以便先完成当前管理员手册的上传，并把验收结果作为后续系统改造的基准。

## 3. 范围与非范围

范围：

- 冻结原样本的文件摘要、标题统计、行号和现行解析结果。
- 生成规范 Markdown 副本，不修改原始文件。
- 生成机器可读映射报告和中文复核报告。
- 通过真实 `POST /api/outline/upload` 验证规范副本，并隔离、清理测试数据。

非范围：

- 不修改前后端解析器、公共 API 或持久化结构。
- 不自动虚构领域描述，不决定存在歧义的叶子标题语义。
- 不引入 Markdown/CSV 外部依赖，不实现评分引擎。

## 4. 处理流程与产物

```text
只读原稿
  → 计算 SHA-256 与标题统计
  → 建立源标题树
  → 应用经确认的映射决策
  → 生成规范 Markdown 候选
  → 按规格 1.0.0 校验
  → 人工复核未决项
  → 生成最终副本与映射报告
  → 真实上传 API 验收
```

建议产物名称由实施任务决定，但必须包含：规范副本、JSON 映射报告、中文复核报告和 API 验收记录。目录新增或结构调整时同步所在目录 `README.md`。

## 5. 数据契约

映射报告建议契约：

```json
{
  "specVersion": "1.0.0",
  "mappingRuleVersion": "outline-copy-v1",
  "source": {
    "file": "outlines/yashan数据库管理员手册知识点大纲.md",
    "sha256": "<hex>",
    "headingCounts": { "h1": 10, "h2": 31, "h3": 11 }
  },
  "targetFile": "<规范副本路径>",
  "mappings": [
    {
      "sourcePath": ["2. 基本数据库管理", "2.4 进程/线程管理"],
      "sourceLine": 13,
      "targetPath": ["三、基本数据库管理", "3.4 进程/线程管理"],
      "action": "map_chapter",
      "status": "confirmed",
      "reason": "存在三级子标题"
    }
  ],
  "unresolvedMappings": [],
  "validation": { "knowledgePointCount": 0, "blockingIssues": [] }
}
```

`sourceLine`、`sourcePath`、`action`、`status` 必须存在。编号重排时同时保留原编号，不以目标编号覆盖来源证据。

### 5.1 验收接口

P1 不新增 API，复用现有 `POST /api/outline/upload`，请求为 `multipart/form-data`，字段为 `file`、可选 `name` 和 `type`。成功后使用列表或详情接口比对 `id`、`kp_count` 和标准树；测试请求必须使用可唯一识别的名称，以便精确清理本次记录。

## 6. 映射策略

- 一级标题作为部分候选；无子节点的 `# 0`、`# 1` 标为未决，不静默删除。
- 有三级子项的二级标题映射为章节，三级标题映射为知识点。
- 叶子二级标题只有在人工确认后才能提升为知识点；未确认时留在 `unresolvedMappings`。
- 目标知识点必须有唯一三级 ID、非空名称、非空描述和所属章节。
- 缺失描述只生成“待补充”诊断，不将标题复制为合格描述，也不生成未经审阅的领域事实。
- 原稿中的编号与目标规范冲突时，目标编号按确定顺序生成，映射报告保留双向关系。

具体标题识别、默认难度、编号起始值和描述质量门槛应写入版本化映射配置；P1 若通过脚本实现，脚本只读取配置。

### 6.1 配置策略

配置至少声明 `mappingRuleVersion`、源方言、层级映射、叶子策略、编号策略、默认难度、必填字段和输出命名规则。配置缺失或版本不匹配时停止转换；人工决策单独记录并绑定源文件摘要，不反写配置。确需临时硬编码的规则必须登记到待办文档，并在 P2 前清理。

## 7. 伪代码

```text
function buildStandardCopy(sourceFile, mappingConfig, humanDecisions):
  assert sourceFile is readOnly
  baseline = collectBaseline(sourceFile)
  sourceTree = parseHeadingTreeWithLineNumbers(sourceFile)
  plan = mapNodes(sourceTree, mappingConfig, humanDecisions)

  if plan.hasUnresolvedBlockingNodes:
    return reviewReport(plan, writable=false)

  outline = renderStandardOutline(plan)
  validation = validateAgainstSpec(outline, specVersion="1.0.0")
  assert validation.blockingIssues is empty
  writeNewCopy(outline)
  writeMappingReports(baseline, plan, validation)
  return artifacts
```

## 8. 异常与安全

- 输入摘要变化时停止生成，防止基于旧审阅结果覆盖新原稿。
- 输出路径不得与原文件相同；目标已存在时拒绝覆盖，除非实施任务定义可恢复的版本化命名。
- 报告不得包含凭据、客户数据或内网敏感内容；命中敏感信息时阻断。
- 上传验收使用专用名称和记录 ID，仅删除本次创建的数据，不使用通配删除。
- 文件读取、解析或上传失败须保留阶段、源行和中文修复建议。

## 9. 迁移与兼容

P1 仅新增产物，不改变现有上传链路。规范副本使用当前解析器可识别的格式，因此可直接回退为手工上传。P2 上线后，原稿和规范副本都保留为回归样本；不得把规范副本反向覆盖原稿。

## 10. 验收标准

- 原稿路径和内容摘要未变化，基线记录为 H1=10、H2=31、H3=11。
- 映射报告覆盖所有源标题，每项都有行号、动作和状态；未决项为 0 后才能形成最终副本。
- 规范副本按规格解析后 `parts >= 1`、`chapters >= 1`、`kp_count > 0`，知识点 ID 全局唯一。
- 所有知识点名称和描述非空；描述缺失不能仅靠复制名称被判为合格。
- 真实后端 API 返回成功且详情树、计数与本地校验一致。
- 失败测试不污染 `metadata.json` 或残留上传文件。
- 格式与可解析性得分 20/20，总分至少 80，且无阻断项。

## 11. 测试策略

- 基线测试：摘要、标题统计、行号稳定性。
- 契约测试：规范 Markdown 的部分、章节、知识点和全角冒号规则。
- 映射完整性测试：源节点集合等于已映射与未决节点集合之和。
- 负向测试：未决叶子、重复 ID、空描述、目标文件冲突、源摘要变化。
- 集成测试：启动真实后端，上传、查询详情、比对计数，再按测试 ID 清理。

## 12. 依赖、风险与确认点

- 依赖规格 1.0.0 和领域人员对叶子标题语义的确认。
- 风险：31 个二级标题中多数没有三级子项，自动提升可能改变知识粒度。
- 风险：为缺失描述补充领域事实需要人工审核，不能由转换规则替代。
- P1 不包含架构变更；若实施中新增依赖、覆盖原稿或改变 API，必须重新请求人类确认。

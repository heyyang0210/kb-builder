## 架构头脑风暴思考维度

执行前必须逐项审视以下维度，并把结论、证据、未决项和影响范围写入本轮交付物。维度用于发现问题，不等于未经验证就扩大范围：

1. **业务目标与边界**：平台要为谁解决什么问题，成功指标是什么，哪些能力明确不在本轮范围。
2. **现状事实与能力保全**：三个原型已有的功能、入口、接口、事件、数据和运维方式分别是什么，哪些能力不能退化。
3. **用户角色与关键旅程**：资料接入、加工、生产、审核、发布、检索和回退的角色、前置条件、异常分支和人工接管点。
4. **领域对象与生命周期**：Document、MaterialBatch、DatasetVersion 等对象的稳定 ID、状态机、版本关系、血缘和删除/归档语义。
5. **事实源与数据归属**：数据库、文件/对象存储、配置资源、缓存和中间产物各自的主写边界，如何避免双事实源。
6. **服务边界与契约**：网关、文档生产、资料加工、认证和存储服务的职责，API、SSE、Socket.IO、下载和预览的兼容方式。
7. **一致性与异步任务**：幂等、revision、请求关联、队列、重试、取消、补偿、断点恢复和最终一致性的可观测状态。
8. **前端信息架构与体验**：统一外壳和工作区如何降低认知负担，权限/空态/降级/失败/长任务/深链如何真实表达，桌面和移动端如何适配。
9. **安全、合规与审计**：认证授权、租户/密级、文件安全、敏感配置、操作留痕、保留期和外部发布边界。
10. **迁移、兼容与回滚**：历史数据和文件如何盘点、导入、对账、试运行、切换和恢复，旧入口/API 如何受控共存和退役。
11. **可观测性与运行治理**：健康检查、指标、日志、告警、容量、性能预算、依赖故障隔离和运维排障路径。
12. **验证与质量门禁**：能力矩阵、契约测试、真实 API、黄金流程 E2E、权限/安全/性能/四视口检查，以及证据的有效性。
13. **演进性与成本**：哪些能力应抽象为平台能力，哪些保持业务服务自治，新增基础设施、外部依赖和长期维护成本是否有明确收益。
14. **人工决策边界**：哪些动作不可逆或涉及产品/合规取舍，何时必须停止写入并请求审批，审批如何记录和过期。

以下内容可完整交给负责本仓库的开发智能体。它要求先基线化、再重构和验证，避免将三个原型界面机械合并后造成能力、数据或运维路径退化。

## 3. 目标模式

### 3.1 产品与浏览器入口

`/knowledge-center/` 是唯一主入口，采用一个统一外壳和下列专业工作区：

1. 工作台：跨工作区待办、失败任务、发布状态、服务健康和可追溯入口；
2. 知识资产：手册、来源、版本、责任人与资产状态；
3. 资料加工：接入、批次、扫描、转换、清洗、分块、索引、数据集和异常恢复；
4. 大纲与模板：大纲、模板、Skill、Prompt 及其版本和适用范围；
5. 文档生产：生成任务、输入快照、过程、产物、质量结果与重试；
6. 审核与发布：候选版本、意见、证据、门禁、发布和回退；
7. 平台管理：用户权限、连接器、配置版本、运行状态和审计。

统一外壳只负责导航、会话、授权投影和跨域聚合；不得复制或重算下游业务状态。资料加工要将既有真实能力接入上述工作区，使用契约适配器和渐进迁移；禁止长期用 iframe 作为最终集成方案，iframe 只能作为明确标识、受控期限的过渡兼容措施。

### 3.2 服务与接口边界

保留“入口网关/聚合层、文档生产服务、资料加工服务、认证服务、YashanDB 存储服务”的职责边界：

- 网关：同源入口、身份转发、粗粒度授权、聚合只读投影、旧路径兼容；不成为新的业务数据库或工作流编排中心；
- 文档生产服务：大纲、生成、检索、文档、评审相关能力的权威实现；
- 资料加工服务：来源接入、加工流水线、数据集、索引和图谱的权威实现；
- 认证服务：会话、身份与角色事实源；
- 存储服务：结构化业务记录的唯一持久化边界，提供乐观并发、迁移、导出与回读对账。

为跨服务操作定义明确的命令、查询和事件契约。每个 API 都需包含稳定资源 ID、请求 ID、操作者、幂等键（写操作）、状态版本或 revision、错误码、可重试性和脱敏错误信息。长任务使用统一任务状态机与事件语义，至少区分 `queued/running/succeeded/failed/cancelled`，并保留步骤、输入快照、输出引用、错误和重试记录。

### 3.3 数据、文件和配置的责任划分

建立并落地“对象归属矩阵”，不能笼统地说“全部迁入数据库”：

| 数据类别 | 目标事实源 | 要求 |
| --- | --- | --- |
| 用户、角色、会话、资产、大纲、模板元数据、任务、审核、发布、审计、映射和配置元数据 | YashanDB | 使用版本/revision 防并发覆盖，数据库模式下不回写 JSON |
| 原始文件、附件、标准化内容、清洗产物、生成文档和大体积索引/图谱产物 | 受控文件或对象存储 | 数据库保存不可变对象标识、哈希、大小、介质类型、逻辑归属、保留期和血缘，不把大文件复制进 JSON/CLOB |
| 配置、规则、模板、Prompt、Skill 和 Schema | 版本控制资源 + 数据库登记的版本/引用 | 密钥只由环境变量或密钥系统注入；运行时使用冻结快照，不从前端写入或散落硬编码 |
| 临时分片、缓存、日志和中间文件 | 生命周期受控的工作目录 | 具有任务归属、过期策略、清理审计和失败保留策略，不能成为业务真相 |

一个业务对象在一个阶段只能有一个主写事实源。迁移期间允许只读兼容和一次性幂等导入，不允许长期双写。切换到数据库模式后，数据库不可用应明确失败并返回可恢复错误，不得悄悄回退写 JSON。

为 Document、MaterialBatch、DatasetVersion、Outline、Template、PromptProfile、WorkflowRun、GeneratedDocument、Review、Publication、Artifact、AuditEvent 和外部 SourceSnapshot 定义稳定 ID、状态机、版本关系与血缘关系。保留旧 ID，必要时建立显式映射表；不得靠文件名或路径推断身份。

### 3.4 安全、可靠性与可观测性

- 所有写接口在服务端进行认证和授权；前端隐藏菜单不能替代鉴权。
- 上传、解压、预览、文件读取和下载必须执行路径约束、大小限制、类型校验、哈希验证和权限校验。
- 连接器、模型、CAS、数据库和 GitLab 的密钥不进入页面、日志、错误响应、能力包或 Git 历史新增内容。
- 每次导入、加工、生成、审核、发布、回退和清理都可追溯到操作者、输入快照、规则/Prompt/模型版本、产物哈希和时间。
- 健康检查区分进程存活、依赖可用、配置一致和可执行业务；单个工作区故障时，其他工作区可用并显示真实降级状态。
- 为网关调用、后台任务和跨服务请求串联 `requestId/correlationId`；指标至少覆盖成功率、延迟、队列长度、失败原因、重试、积压、存储异常和迁移对账差异。
- 长任务取消必须声明可中断边界。当前下载任务仅支持页面边界取消：`queued/running -> cancelling -> cancelled`，页面处理完成后才停下；取消后保留未完成页面并允许 `resume`，不得将批次误标记为完成。除非有真实后端和浏览器证据，不得声称支持页面内部强制中断、所有任务通用取消或断线自动恢复。

## 4. 实施方法：按阶段交付，不跨阶段偷跑

### P0：架构与兼容基线

先更新必要的总体设计、接口契约、伪代码、目录归属和 README。生成下列基线并纳入测试资产：

- 三个入口的用户旅程与权限矩阵；
- API、WebSocket、SSE、下载与预览深链契约快照；
- 核心实体、状态机、数据归属、文件血缘和配置清单；
- 历史 JSON/目录/数据库数据的数量、哈希摘要和可回读清单；
- 启动拓扑、端口、依赖和健康检查清单；
- 关键流程黄金样例：上传到数据集、生成到文档、评审到发布、失败重试和回退。

没有 P0 基线，不得删除入口、改写数据或宣称“无退化”。

### P1：冻结目标契约与适配层

先定义统一的错误外壳、分页、任务、事件、权限、幂等、审计、文件引用和版本契约。为旧 API 建立薄适配层，新增字段只能追加。网关的聚合接口只读，不可借聚合接口重写下游数据。为资料加工和文档生产定义能被知识中心模块使用的领域 API，而不是让前端直接耦合两个服务的内部数据结构。

### P2：存储与数据迁移

将结构化业务记录按对象迁入 YashanDB；将文件与产物登记为可校验的 Artifact。迁移必须按“导出/冻结范围 -> 导入 -> 数量与哈希对账 -> 业务回读 -> 试运行 -> 单主写切换”进行。迁移脚本应幂等、可恢复、可报告，不删除源文件。回退只切回上一版本的应用和主写配置，不进行无审计的数据逆迁移。

### P3：统一工作区迁移

按资料加工、文档生产、审核发布的依赖顺序逐个接入知识中心。每个工作区交付后：

- 统一入口可真实完成该工作区的关键用户旅程；
- 旧入口仍可完成相同关键旅程，或有明确、可逆的兼容适配；
- 两个入口读取到同一事实源和同一任务状态；
- 页面没有演示数据、死按钮、永久加载或无解释的空白状态；
- 移动端和桌面端均无横向溢出，权限不足、服务降级和任务失败均有可理解的中文状态。

### P4：切换、观测和收口

仅在所有能力矩阵、数据对账、真实 API、浏览器 E2E、性能和安全检查通过后，才为旧入口增加迁移引导。旧入口先进入受监控兼容期，不能直接删除。根据真实使用量、失败率和人工确认决定是否退役；退役前导出审计与数据，并保留可恢复的回滚版本。

## 5. 每轮必须交付的内容

每个可合并阶段都输出：

1. 架构决策、影响范围、接口和伪代码的设计文档更新；
2. 变更文件、数据迁移版本、配置样例与 README 更新；
3. 能力矩阵，明确“保留、已迁移、兼容中、未实现、风险”状态；
4. 真实 API 证据、迁移对账报告、单元/集成/E2E 结果和关键界面截图；
5. 回滚步骤、已知限制和需要人工决策的事项；
6. `prompt.md` 中的决策、证据和复盘记录。

## 6. 验收门禁

只有同时满足下列条件才能宣布目标模式重构完成：

- 三类核心流程在统一入口真实可用：资料接入并加工、生成并沉淀为文档、审核并发布；
- 每个核心对象都有权威事实源、稳定 ID、版本/状态、审计和血缘；
- 数据库、文件和配置的归属矩阵已落实，且不存在未登记的业务 JSON 主写；
- 历史数据迁移经数量、哈希和业务回读对账；新增写入不发生长期双写；
- 旧入口与旧 API 的兼容基线回归通过，或有用户批准的替代与退役计划；
- 前后端真实 API、长任务事件、权限、失败恢复、服务降级、浏览器深链和四种视口通过验证；
- 提示词、规则、阈值和敏感信息符合配置化与安全要求；
- 设计、实现、测试、README、运行脚本和 `prompt.md` 的口径一致。

## 7. 需要停下并请求人工决策的情况

遇到以下任一情况，只做只读分析、测试准备和方案比较，不擅自放行：

- 要删除旧入口、破坏兼容 API、修改已发布数据或不可逆清理文件；
- 身份权限模型、数据保留期、外部发布范围、密级或多租户边界需要改变；
- 数据对账失败、同一对象存在冲突主写事实源，或历史数据无法可靠识别；
- 需要新增外部付费服务、生产凭证或改变网络暴露面；
- 性能、安全或合规结论缺少真实环境证据。

开始执行：先给出 P0 的仓库事实、能力基线、差距、目标对象归属矩阵、风险分级和最小实施批次；设计通过自检后再修改代码。不要只输出方案，也不要在没有验证的情况下宣称完成。

## 使用说明

审核发布实现约定：活动任务的审核依据使用默认折叠的 `.review-evidence-drawer`；阅读区和差异区可同时存在意见表单，浏览器验收只操作当前可见表单，并通过真实后端状态回读确认意见、审核决定和发布结果。

该提示词将重构控制在标准开发路径：先补齐架构与契约，再逐步实施和独立验证。需要退役旧入口、改变保留策略或处理无法对账的数据时，应升级为人工决策，而非由执行者自行裁定。

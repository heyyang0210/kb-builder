# 文档治理与周期对账概要设计

> documentType: overview-design
> moduleId: platform-foundation
> owner: Architect
> status: approved
> version: 1.0.0
> updatedAt: 2026-08-17

## 1. 用户问题

项目经过一段时间开发后，需求、设计、代码、配置和验证证据可能不同步。仅根据当前代码更新文档会把临时实现、缺陷或模型经验误写成正式业务事实；每次从零理解全仓又会显著增加执行耗时。

目标是建立周期性、可重复、可增量的文档对账能力，让 Architect、Project Manager、Worker 和 Reporter 能够基于上次成功快照、变更原因、当前实现和验证证据更新文档，并将证据不足的事项交由用户确认。

## 2. 核心方法

```text
已批准基线 Baseline
      + 业务意图 Intent
      + 当前实现与验证 Evidence
      ↓
证据驱动三方对账
      ↓
高置信度修改草案 / 不确定项确认
      ↓
文档更新、验证、成功检查点
```

确定性脚本回答“事实是什么”，Skill 回答“事实对文档意味着什么”，人类回答“证据无法确定的业务决策”。

## 3. 组件边界

| 组件 | 职责 |
|---|---|
| 项目治理配置 | 定义模块代码路径、文档路径、意图来源、结构失效条件和忽略项 |
| 上下文采集器 | 冻结运行开始的 Git HEAD，采集结构、依赖、工作区和增量变化 |
| 就绪检查器 | 检查上次成功检查点、祖先关系、配置版本、快照完整性和冲突 |
| 三方对账 Skill | 关联需求、任务、决策、代码、配置和测试，输出置信度与文档影响 |
| 交互确认门禁 | 对缺少原因、契约冲突、模块变化和未验证实现请求用户决策 |
| 验证与检查点 | 检查链接、追踪关系和格式；成功后原子推进增量基线 |

## 4. 执行频率

- 每次合并后：轻量刷新结构哈希和变更账本。
- 每周：从上次成功检查点执行增量文档审计。
- 发布前：执行全量需求、设计、实现和验证对账。
- 公共 API、模块边界或业务状态语义变化后：立即执行专项审计。

## 5. 不变量

1. 增量范围固定为 `lastSuccessfulRef..runStartHead`，运行中新提交不进入本轮。
2. 未提交文件只登记，不自动归因于当前审计。
3. Git 提交信息只是意图线索，不等于批准的业务需求。
4. 缺少业务原因、需求冲突或验证证据时，不自动修改正式业务文档。
5. 失败、中止或仍有阻断项时，不推进成功检查点。
6. Skill 不自动提交代码，不修改业务代码，不批准架构决策。
7. 同一基线、目标和规则版本重复执行，机器报告语义保持一致。

## 6. 数据位置

```text
skills/reconcile-docs/                         # 稳定能力
.codex/config/doc-governance.json              # 项目特定治理配置
.codex/context/reconcile-docs/                 # 最新机器快照与成功检查点
.codex/workflow/audits/documentation/<runId>/ # 每次审计报告与证据
```

运行产物不复制源文件正文，只保存路径、哈希、结构索引、变更区间、证据引用和人工确认记录。

## 7. 成功标准

- 周期执行无需重新探索全部项目结构，只扫描失效或变化范围。
- 所有建议能够追溯到需求、任务、代码或验证证据。
- `NEEDS_CONFIRMATION` 项在确认前不会触发正式文档改写。
- 失败运行不丢失下一次应审计的提交区间。
- 文档漂移、无原因行为变化和未验证能力能够被单独统计。

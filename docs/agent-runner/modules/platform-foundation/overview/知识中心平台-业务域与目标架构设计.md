## 1. 结论

知识中心不是单一的“文档生成器”，而是覆盖知识资产建设全生命周期的平台：

```text
身份与组织
  -> 手册资产
  -> 大纲与文档内容
  -> 生产、审核与发布
  -> 资料加工、知识索引与图谱
  -> 检索、生成、模型与外部集成
```

当前系统已具备 Node 文档生成服务、Python 资料加工服务、统一入口和独立认证服务四个运行边界。目标架构应保留这些服务边界，不建议合并语言或重写全部服务。

需要实施的是渐进式领域模型重构：

1. 用关系型主数据替代手册、大纲、文档、人员责任、审核发布等高频业务对象的 JSON 聚合。
2. 用“关系型元数据 + 文件/对象产物 + 检索/图谱投影”替代把所有东西塞进关系表或 `KC_RECORD` 的做法。
3. 以统一网关完成会话校验和权限传递；内部服务只接受经过网关签发的调用上下文。
4. 让每个业务对象只有一个主写源，其他服务只能读取投影、消费事件或保存自己的执行产物。

`KC_RECORD` 不应立即删除。它继续作为兼容记录仓储、迁移导出源和低频配置/历史聚合的过渡层；但不能继续成为手册、目录、文档、任务和人员协作的长期主模型。

## 2. 现状边界

### 2.1 运行单元

| 单元 | 当前职责 | 架构定位 |
|---|---|---|
| 统一入口（13510/3500） | 知识中心前端、同源代理、平台总览、资产/GitLab/增量构建入口 | BFF 与浏览器唯一入口 |
| Node 文档服务（4100） | 大纲、文档、评论、工作流、Agent、模型网关 | 内容生产域与模型能力适配器 |
| Python 资料加工服务（8001） | 素材接入、批次、下载、预处理、数据集、知识提取、索引、图谱 | 资料加工与知识计算域 |
| 认证服务（4200） | CAS 校验、本地管理员、会话、角色 | 身份与访问控制域 |
| YashanDB 存储服务 | `KC_RECORD` 的 HTTP/JDBC 访问、迁移与导出 | 过渡存储适配器，后续承载关系型领域表 |

### 2.2 当前前台模块与真实能力

| 一级页面 | 对应业务域 | 当前真实状态 |
|---|---|---|
| 工作台 | 跨域只读投影、待办和风险 | 已有聚合入口，统计口径尚未统一 |
| 知识资产 | 手册资产、负责人、状态、仓库映射 | 已有 CRUD，但主数据仍是 `assets/catalog` 聚合 |
| 资料清洗 | 素材接入、批次、预处理、数据集、知识图谱 | Python 服务能力较完整；知识中心页面仍以跳转/待建设状态为主 |
| 大纲管理 | 大纲候选、预检、版本、目录树 | 已有服务端能力；当前模型仍以 JSON 大纲对象保存 |
| 模板管理 | 模板、版本、适用范围 | 前端为占位页；实际模板主要是文件资源和能力包引用 |
| 文档生产 | 生成任务、增量构建、文档版本 | 已有 Agent/Workflow 和增量构建能力，但对象关联尚未规范化 |
| 审核与发布 | 审核意见、发布决策、版本、外部同步 | 前端为占位页；评论、数据集发布、大纲发布和 GitLab 阅读分散存在 |
| 平台管理 | 连接器、权限、审计、运行配置 | 已有 GitLab、用户角色和部分配置；审计与配置没有统一模型 |

因此，八个页面是合理的信息架构，但并不等于八个已经完成的后端业务模块。模板管理、审核与发布应作为后续优先补齐的领域，而不是继续用页面占位或散落文件替代。

## 3. 已识别的架构问题

### 3.1 主数据分裂

同一“手册”目前可同时出现在：

- `assets/catalog` 的 `handbookId`；
- 大纲对象的 `handbookId`；
- 文档输出索引和文件路径；
- GitLab 映射；
- 增量构建任务；
- Python 资料批次或数据集。

这些标识没有受到数据库外键、唯一约束或统一 ID 映射约束。它会导致“资产页显示一套状态、目录页显示另一套结构、生产任务找不到对应文档”的问题。

### 3.2 业务状态粒度不适合长期协作

`KC_RECORD` 以整个 JSON 聚合做读写和乐观并发，适合低频配置和无损迁移，但不适合：

- 多人同时维护手册、目录、文档和审核意见；
- 按负责人、技术领域、状态、时间筛选工作；
- 维护完整版本链、评论链、审批链和审计链；
- 对单个任务或单条评论做精确授权与保留策略。

### 3.3 生命周期未统一

大纲发布、文档生成、资料数据集发布、图谱版本发布、GitLab 分支内容和增量构建发布各有自己的状态，尚未由一个“知识发布版本”协调。当前不能严格回答“某一正式手册版本使用了哪份大纲、哪些文档版本、哪些资料集和质量证据”。

### 3.4 权限边界不完整

认证服务已有 CAS、本地管理员、会话和角色投影；知识中心入口会校验会话。但 Node 4100 的业务路由本身未统一消费身份上下文，且内部端口、旧入口和代理路径仍需逐项冻结访问策略。权限不能只依赖前端隐藏菜单或某个网关路径。

### 3.5 运行与数据存储分散

Node 使用文件、`KC_RECORD` 和本地输出目录；Python 使用 `state.json`、运行目录和不可变产物目录；GitLab 保存外部内容；模型、Prompt、Skill 和模板又分散在能力包及文件中。问题不在于“文件存在”，而在于没有定义每一类数据的权威来源与保留方式。

## 4. 目标业务域

### 4.1 领域划分

| 领域 | 核心对象 | 主责服务 | 关系型主写数据 |
|---|---|---|---|
| 身份与访问控制 | 用户、外部身份、角色、权限、会话、审计 | 认证服务 | 用户、身份绑定、角色授权、会话、认证审计 |
| 组织与责任 | 部门、技术领域、人员领域、责任分配 | 平台基础服务 | 部门、技术领域、人员领域映射 |
| 知识资产 | 手册、产品、资产状态、负责人 | 知识中心 BFF/资产域 | `manuals` 及资产审计 |
| 大纲与内容 | 大纲版本、目录节点、文档、小节 | Node 文档服务 | 大纲、目录、文档、小节、内容版本 |
| 内容生产 | 生成请求、工作流运行、任务、文档草稿 | Node 文档服务 | 生产任务、任务步骤、文档版本、产物引用 |
| 审核与发布 | 审核包、意见、决策、发布版本、回滚标记 | 发布域，初期由 Node 承担 | 审核、发布、证据和版本基线 |
| 资料加工与知识计算 | 来源、批次、资源、处理任务、数据集、知识点、图谱版本、索引 | Python 资料加工服务 | 批次/资源/任务/数据集元数据和发布血缘 |
| AI 资源治理 | 模板、Prompt、Skill、Workflow、质量规则、模型配置引用 | 平台基础服务 + Node/Python 消费 | 版本化资源目录、适用范围、发布状态、引用关系 |
| 外部集成 | GitLab 连接、手册映射、PingCode 空间映射、同步记录 | BFF/连接器适配器 | 连接定义、映射、同步游标和脱敏审计 |
| 平台运行治理 | 异步任务、审计事件、通知、幂等键、Outbox | 各领域服务 | 领域事件、操作审计、任务运行元数据 |

### 4.2 领域关系

```text
users --< user_roles >-- roles
users --< personnel_domains >-- tech_domains
departments --< manuals
manuals --< manual_outline_versions --< manual_outline_nodes
manual_outline_nodes(document) 1 -- 1 manual_documents --< manual_document_sections

manuals --< content_production_runs --< document_versions
manuals --< review_packages --< review_decisions
manuals --< knowledge_release_versions

material_sources --< material_batches --< material_resources
material_batches --< processing_runs --< dataset_versions --< graph_versions
dataset_versions --< knowledge_release_inputs >-- knowledge_release_versions

manuals --< external_repository_mappings >-- external_connections
manuals --< resource_bindings >-- template_versions / prompt_versions / workflow_versions
```

关键约束：

1. 文档是大纲树的 `document` 叶子节点，不能脱离大纲单独存在。
2. `section` 是正文和责任颗粒度，不是目录层级。
3. 有效大纲版本至少包含一篇文档。
4. 每一个正式发布版本必须固定引用：大纲版本、文档版本、审核决定、质量证据和资料/图谱版本。
5. 外部 GitLab/PingCode ID 只是外部标识，不得替代平台内部主键。

## 5. 数据主写与存储策略

| 数据类别 | 权威来源 | 持久化方式 | 不应作为主写源 |
|---|---|---|---|
| 用户、角色、部门、责任 | 认证/组织域 | YashanDB 关系表 | `auth/state`、前端会话 |
| 手册、大纲、文档、小节、评论、审核 | 资产与内容域 | YashanDB 关系表，正文可用 CLOB | `KC_RECORD`、GitLab 路径 |
| 生成任务、幂等键、任务步骤、发布基线 | 内容生产/发布域 | YashanDB 关系表 | `incremental/state` |
| 原始文件、转换文件、Markdown、图谱 JSON、向量 | 文件或对象存储 | 不可变目录/对象，数据库保存引用、哈希、大小和生命周期 | CLOB 全量复制、浏览器缓存 |
| 素材批次、资源索引、数据集、图谱版本元数据 | 资料加工域 | YashanDB 关系表 | Python `state.json` |
| 检索索引、图谱查询投影 | Python 资料加工域 | 可重建索引/图存储或版本化文件 | 手工编辑的业务主表 |
| 模板、Prompt、Skill、质量规则 | 版本化资源域 | 文件资源保留正文；数据库保存版本、状态、适用范围和引用 | 代码硬编码、前端内存 |
| 密码、OAuth 密钥、模型密钥、CAS 票据 | 密钥系统或受控环境变量 | 不进入业务表、导出或前端响应 | 能力包、`KC_RECORD` |
| 低频兼容配置和迁移快照 | 兼容仓储 | `KC_RECORD` | 长期高频协作主表 |

## 6. 接口与权限边界

### 6.1 网关与身份传播

浏览器只能访问 13510/3500 的同源入口。网关完成 Cookie 会话校验、CSRF/请求追踪、权限判断和内部身份传播；4100、4200、8001、YashanDB 存储服务不应作为浏览器的直接依赖。

内部服务不重新解析 CAS ticket。网关在每个内部调用中附带短时、可验证的身份上下文，例如：

```json
{
  "requestId": "req_...",
  "actor": {
    "userId": "usr_...",
    "roles": ["OUTLINE_MANAGER"],
    "permissions": ["outline:write"]
  },
  "issuedAt": "2026-09-08T11:59:34+08:00"
}
```

该上下文必须由可信网关签名或通过受限内网凭证传递；服务端仍按动作校验权限，不能相信浏览器提交的 `userId` 或角色。

### 6.2 关键应用服务契约

```text
createManual(command, actor):
  require actor.permission("manual:create")
  validate department and owners
  insert manuals
  append audit event
  publish ManualCreated outbox event

createOutlineVersion(manualId, command, actor):
  require actor.permission("outline:write")
  require manual exists and is active
  parse -> normalize -> validate tree
  require at least one document leaf
  insert outline version, nodes and document bindings in one transaction
  append audit event
  publish OutlineVersionCreated event

startProduction(manualId, command, actor):
  require actor.permission("production:run")
  resolve one published outline version and released resource versions
  create production run with immutable input snapshot
  enqueue execution command

publishKnowledgeRelease(manualId, command, actor):
  require actor.permission("publish:manage")
  require accepted review package
  require fixed outline/document/resource/dataset/graph references
  require all quality gates passed
  insert immutable knowledge release version
  publish KnowledgeReleasePublished event
```

所有跨域异步动作使用“本地事务 + outbox 事件”或等价可靠任务表：先提交本域事实，再异步通知其他服务。禁止一个 HTTP 请求内跨 Node、Python、GitLab 和数据库做不可回滚的分布式写入。

## 7. 重构策略

### 7.1 不做的事情

- 不合并 Node 和 Python 服务。
- 不一次性把全部文件、图谱和向量转成关系表。
- 不删除 `KC_RECORD`、旧 JSON 或旧入口后再验证。
- 不长期双写同一业务对象。
- 不让 GitLab、PingCode 或前端成为手册、大纲、文档的主写源。

### 7.2 分阶段演进

| 阶段 | 交付 | 切换范围 | 完成标准 |
|---|---|---|---|
| P0：事实冻结 | ID 对照表、当前导出、对象清单、字段映射 | 只读分析 | 任一现存对象可定位到来源和目标域 |
| P1：身份、组织、资产 | 用户/角色/部门/技术领域/手册关系表与资产 API | 知识资产主写切换 | 手册、负责人、部门和审计可按字段查询；旧目录仍可读 |
| P2：大纲与内容 | 大纲版本、节点、文档、section、评论和内容版本 | 大纲与文档主写切换 | 大纲文档约束在数据库事务内生效；可无损导入现有 8/38/133 结构 |
| P3：生产、审核、发布 | 任务运行、审核包、发布版本、证据和外部同步记录 | 生产与发布主写切换 | 一个发布版本可完整追溯其输入和审核结论 |
| P4：资料加工元数据 | 批次、资源、任务、数据集、图谱版本的关系元数据 | Python 状态主写切换 | 文件产物仍可读，批次和版本可按条件查询及恢复 |
| P5：AI 资源与连接器治理 | 模板/Prompt/Skill/Workflow 版本目录、GitLab/PingCode 映射 | 配置主写切换 | 任务输入固定引用已发布资源版本；密钥不入库 |

每一阶段采用“导入校验 -> 单域切换 -> 旧源只读保留 -> 回读对账”的方式。若验收失败，回退到上一域的唯一主写实现，不做跨域反向同步。

### 7.3 `KC_RECORD` 的退出原则

当某领域切换到关系表后：

1. 旧记录保留为只读迁移快照，带来源哈希和迁移批次。
2. 新写入只进入领域表和审计/事件表。
3. 兼容接口从领域表投影，不再回写 JSON 聚合。
4. 在至少一个完整发布周期、完整导出恢复和回归验收后，才能讨论是否归档该逻辑记录。

## 8. 数据迁移与无损要求

当前已知大纲数据包含 8 个部分、38 个章节、133 个旧知识点。按“文档是大纲叶子”的规则迁移时，133 个旧知识点不能继续作为文档之下的目录层级，必须逐条给出归宿：

- 映射为一个新的 `document` 叶子；或
- 合并到某个文档的 `manual_document_sections` 正文；或
- 标记为弃用/重复并记录人工确认原因。

每批迁移至少输出：

```text
source object id
  -> target primary key
  -> target type
  -> source hash
  -> target hash or content summary
  -> migration disposition
  -> operator and timestamp
```

验收不得只比较记录总数，还必须比较：

- 手册、版本、目录、文档、section、评论和任务的数量；
- 每本手册的树结构、顺序、路径、负责人、状态和版本关系；
- 文档正文/文件产物哈希及附件引用；
- 发布版本到大纲、文档、资料集、图谱和审核证据的可追溯性；
- 未映射、合并、弃用对象的人工确认清单。

## 9. 优先级建议

第一优先级是 P1 和 P2：知识资产、手册大纲、文档与 section 是用户当前负责范围，也是所有后续生产、审核和发布能力的业务锚点。

第二优先级是 P3：没有统一审核与发布模型，平台无法形成可信的“正式知识版本”。

第三优先级是 P4：Python 资料加工已具备丰富能力，应先把批次/数据集/图谱的元数据和血缘规范化，保留大文件、向量和图谱明细为外部或版本化产物。

模板管理、平台管理和资料清洗页面的补全必须建立在上述真实契约之上。不能先为占位页面补一套独立 JSON，再在后续迁移时二次拆除。

## 10. 架构验收

目标架构完成一个阶段时，必须同时满足：

1. 每个迁移对象有唯一主写域和稳定内部 ID。
2. 关系约束、状态机和权限在服务端生效，不依赖前端。
3. 对外接口保持现有兼容字段或提供明确版本化替代。
4. 领域事务不跨服务直接写入；跨域通过可追溯事件/任务衔接。
5. 数据库可导出、可恢复、可核对；文件产物有稳定引用与哈希。
6. 真实 API 验证覆盖创建、查询、并发冲突、权限拒绝、失败恢复和发布追溯。

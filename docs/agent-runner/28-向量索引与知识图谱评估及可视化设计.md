# 28-向量索引与知识图谱评估及可视化设计

> 版本：v1.0  
> 日期：2026-07-24  
> 状态：设计基线  
> 当前方案：方案 2，本地评估服务  
> 前置文档：`27-资料预处理框架概要设计.md`、`26-设计文档预处理与分层索引设计.md`

## 1. 文档目的

本文档定义向量索引和知识图谱构建后的存储、评价、可视化和版本对比方案。

当前采用方案 2：

```text
本地预处理流水线
    |
    +-- 结构化索引：JSON 文件
    +-- 向量索引：本地 ChromaDB
    +-- 知识图谱：JSON 持久化 + 运行时内存图
    +-- 评估服务：agent-runner 本地 API
    +-- 可视化页面：本地 Web 页面
```

方案 3（ChromaDB/Milvus + Neo4j）保留数据模型、接口契约和迁移边界，后续可以替换存储后端，不改变上层检索接口。

## 2. 范围与目标

### 2.1 处理对象

- 清洗后的 Markdown 文档
- 语义分块后的 chunk
- chunk 的 embedding 向量
- 文档、chunk、特性、术语等图谱节点
- 引用、依赖、属于、相关等图谱边
- 每次索引构建的统计和质量报告

### 2.2 建设目标

1. 能明确统计向量索引和知识图谱构建了多少内容。
2. 能识别向量记录、chunk、图谱节点和边之间的不一致。
3. 能直观看到特性分布、图谱全景和单点关联关系。
4. 能比较本次构建和上次构建的增量变化。
5. 能通过检索样例评价向量召回质量。
6. 后续可以迁移到 Milvus 和 Neo4j，而不重写上层业务接口。

### 2.3 非目标

- 本文档不定义 embedding 模型的最终选型。
- 本文档不实现完整知识图谱自动推理。
- 本文档不要求第一阶段部署独立的 Neo4j 或 Milvus 集群。

## 3. 关键概念

### 3.1 ChromaDB 不是知识图谱

ChromaDB 是向量索引，主要存储：

```text
id + embedding + document + metadata
```

它支持相似度搜索，但不直接表达“文档 A 引用文档 B”或“特性 A 依赖特性 B”等图关系。

知识图谱是独立的数据结构：

```text
节点（node） + 边（edge） + 关系类型 + 权重 + 证据
```

两者通过稳定 ID 关联：

```text
chunk_id -> ChromaDB 向量记录
chunk_id -> 知识图谱 Chunk 节点
chunk_id -> chunks/{doc_id}/chunk_xxx.md
```

### 3.2 内容源与索引的关系

```text
cleaned Markdown / chunk Markdown
              |
              +--> 结构化索引
              +--> embedding 向量
              +--> 图谱节点和边
```

Markdown 和 chunk 文件是可读的事实源。向量库和图谱是面向检索的派生索引，删除后可以根据源文件重新构建。

### 4.1 当前运行方式

方案 2 采用本地服务方式：

- `agent-runner` 负责预处理、索引构建和评估接口。
- ChromaDB 使用本地持久化目录，服务重启后数据仍保留。
- 知识图谱使用 JSON 文件持久化，查询时加载为内存邻接表。
- 前端通过本地 HTTP API 读取统计和子图数据。
- 图谱页面默认按特性、文档或节点展开，不一次性渲染全部节点。

### 5.1 向量记录形态

```json
{
  "id": "chunk-001",
  "document": "事务提交依赖日志刷盘机制。",
  "embedding": [0.012, -0.083, 0.147],
  "metadata": {
    "doc_id": "doc-001",
    "feature": "事务管理",
    "source_format": "pdf",
    "source_path": "cleaned/事务设计.md",
    "chunk_path": "chunks/doc-001/chunk-000.md",
    "content_hash": "sha256:...",
    "index_version": "20260724-001"
  }
}
```

实际 embedding 数组由 ChromaDB 管理，`manifest.json` 只保存可审计的映射和统计信息，避免重复保存大数组。

### 5.2 图谱节点形态

```json
{
  "id": "chunk-001",
  "type": "Chunk",
  "label": "事务提交机制",
  "properties": {
    "doc_id": "doc-001",
    "feature": "事务管理",
    "source_path": "cleaned/事务设计.md",
    "chunk_path": "chunks/doc-001/chunk-000.md"
  }
}
```

建议节点类型：

| 类型 | 说明 |
|------|------|
| `Document` | 原始文档或标准化文档 |
| `Chunk` | 语义分块，是向量和图谱的主要关联对象 |
| `Feature` | 特性或模块 |
| `Term` | 技术术语、参数、组件名称 |
| `Version` | 产品或文档版本 |

### 5.3 图谱边形态

```json
{
  "from": "chunk-001",
  "to": "feature-transaction",
  "type": "BELONGS_TO",
  "weight": 0.92,
  "evidence": {
    "source": "rule",
    "source_chunk_id": "chunk-001",
    "reason": "路径和关键词均命中特性事务管理"
  },
  "created_at": "2026-07-24T10:00:00+08:00"
}
```

第一阶段关系类型：

- `HAS_CHUNK`
- `BELONGS_TO`
- `MENTIONS`
- `REFERENCES`
- `DEPENDS_ON`
- `SEMANTICALLY_RELATED`
- `SAME_TOPIC`

每条边必须保存来源、置信度或证据，禁止只保存无来源的关系。

## 6. 评价体系

### 6.1 向量索引结构评价

| 指标 | 计算方式 | 目标 |
|------|----------|------|
| 向量覆盖率 | 成功向量化 chunk / 有效 chunk | ≥ 99% |
| 向量孤儿率 | 找不到源 chunk 的向量 / 向量总数 | 0% |
| chunk 孤儿率 | 没有对应向量的有效 chunk / 有效 chunk | ≤ 1% |
| 元数据完整率 | 必填 metadata 完整记录 / 向量总数 | 100% |
| embedding 失败率 | embedding 失败 chunk / 待向量化 chunk | ≤ 1% |
| 重复向量率 | hash 重复记录 / 向量总数 | 需监控，不设绝对阈值 |
| 模型一致率 | 使用当前模型版本的记录 / 向量总数 | 100% |

必填 metadata：`chunk_id`、`doc_id`、`feature`、`source_path`、`chunk_path`、`content_hash`、`index_version`。

### 6.2 向量检索效果评价

建立一组人工标注的查询样例：

```json
{
  "query": "事务提交依赖什么机制？",
  "expected_chunk_ids": ["chunk-001", "chunk-018"],
  "feature": "事务管理"
}
```

评价指标：

- `Recall@K`：正确 chunk 是否出现在前 K 条。
- `Precision@K`：前 K 条中相关 chunk 的比例。
- `MRR`：第一个正确结果的排名质量。
- `nDCG@K`：多相关结果的排序质量。
- 查询延迟：P50、P95、P99。
- 版本一致性：同一模型和同一输入重复构建的结果是否稳定。

建议基线：

```text
Recall@5 >= 0.85
MRR@10   >= 0.75
P95 查询延迟 <= 500ms
```

### 6.3 知识图谱结构评价

| 指标 | 说明 |
|------|------|
| 节点总数 | 所有节点数量 |
| 边总数 | 所有关系数量 |
| 节点类型数量 | Document、Chunk、Feature、Term 等分类统计 |
| 关系类型数量 | 各类边的数量和占比 |
| 平均度数 | 每个节点平均关联边数 |
| 孤立节点率 | 没有任何边的节点比例 |
| 连通分量数 | 图被分割成多少个独立子图 |
| 特性覆盖率 | 已归属 Feature 的 chunk / 全部 chunk |
| 证据完整率 | 带证据的边 / 全部边 |
| 重复节点率 | 相同业务实体被重复创建的比例 |
| 异常边率 | 抽样确认错误的边 / 抽样边数 |

建议基线：

```text
Chunk 节点覆盖率 >= 99%
特性归属覆盖率 >= 90%
证据完整率     = 100%
孤立 Chunk 率  <= 5%
异常边率       <= 5%
```

孤立节点不一定都是错误。例如某些独立的配置说明可能没有引用关系。因此孤立节点应作为待检查项，而不是直接删除。

### 6.4 图谱关联质量评价

关系质量采用“规则校验 + 抽样人工评估 + 检索效果”组合评价：

1. 规则校验：检查边两端节点是否存在、类型是否允许、权重是否在 `0-1` 范围。
2. 证据校验：检查关系是否能回溯到源文档或 chunk。
3. 人工抽样：按关系类型和置信度分层抽样，确认关系是否成立。
4. 检索验证：从一个 chunk 扩展出的关联内容是否提升召回率，是否引入明显噪声。

关系置信度来源建议：

```text
路径规则命中       0.90
关键词规则命中     0.80
文档显式引用       0.95
LLM 关系抽取       LLM score
向量相似度关系     cosine similarity
```

## 7. 本地评估服务设计（方案 2）

### 7.1 服务职责

- 读取索引统计信息。
- 查询向量索引健康状态。
- 查询图谱全景统计和局部子图。
- 对比两个构建版本。
- 返回前端可直接渲染的数据。
- 输出 JSON 和 HTML 质量报告。

### 7.2 API 接口

```text
GET /api/preprocessing/index/statistics
GET /api/preprocessing/index/vector-quality
GET /api/preprocessing/graph/statistics
GET /api/preprocessing/graph/nodes
GET /api/preprocessing/graph/edges
GET /api/preprocessing/graph/subgraph?node_id=...&depth=2
GET /api/preprocessing/index/diff?from=...&to=...
GET /api/preprocessing/index/report?run_id=...
POST /api/preprocessing/index/evaluate
```

### 7.4 页面设计

#### 总览页

展示：

- 当前构建版本和上次构建版本。
- 文档、chunk、向量、节点、边数量。
- 向量覆盖率和图谱证据完整率。
- 失败数、孤立节点数、异常边数。
- 质量评分及相对上次的变化。

#### 向量索引页

展示：

- embedding 数量和维度。
- 模型名称及模型版本。
- 向量覆盖率、孤儿记录和失败记录。
- 查询样例的 Recall@K、MRR、P95。
- 按特性、版本和文档格式分布。

#### 图谱全景页

展示：

- 节点和边的数量。
- 不同颜色表示不同节点类型。
- 不同线型或颜色表示不同关系类型。
- 按特性、版本、文档类型和关系类型筛选。
- 点击节点查看属性和关联 chunk。
- 支持只显示某个节点的 1-3 跳子图。

#### 版本对比页

展示：

- 新增、删除和变化的文档、chunk、向量、节点、边。
- 新增特性和关系类型。
- 质量指标变化。
- 失败记录和待重新处理记录。

### 7.5 图谱展示原则

不默认渲染全量图谱。全量图只展示统计和聚合关系，详细图采用逐层展开：

```text
全局统计
  -> 特性聚合图
    -> 文档关系图
      -> chunk 局部子图
```

这样可以避免节点过多导致页面不可读，也能降低 API 返回和浏览器渲染压力。

## 8. 版本和增量对比

每次索引构建生成唯一 `run_id`，并保存当前版本和上一个版本的差异：

```json
{
  "run_id": "exec-20260724-001",
  "previous_run_id": "exec-20260723-003",
  "diff": {
    "new_documents": 12,
    "deleted_documents": 2,
    "changed_documents": 18,
    "new_chunks": 328,
    "deleted_chunks": 21,
    "new_vectors": 310,
    "failed_embeddings": 3,
    "new_nodes": 328,
    "deleted_nodes": 21,
    "new_edges": 1240,
    "deleted_edges": 85,
    "quality_score_delta": 0.042
  }
}
```

差异计算必须以稳定的 `doc_id`、`chunk_id`、内容 hash 和关系唯一键为依据，不能用数组下标判断变化。

## 9. 方案 3 扩展设计

方案 3 作为后续规模化方案保留，不在当前阶段部署。

### 9.1 后端替换

| 当前方案 2 | 后续方案 3 | 上层不变接口 |
|------------|------------|--------------|
| 本地 ChromaDB | Milvus | `upsert()`、`query()`、`delete()` |
| JSON + 内存图 | Neo4j | `addNode()`、`addEdge()`、`subgraph()` |
| 本地评估 API | 独立索引服务 | 统计和评价 API |
| 本地 HTML 页面 | Neo4j Bloom + 监控看板 | 节点、边、统计数据模型 |

### 9.2 迁移约束

1. 所有向量记录必须拥有稳定的 `chunk_id`。
2. 所有图谱节点和边必须使用明确的类型和唯一键。
3. 关系数据不能依赖 JSON 数组顺序。
4. 评估指标定义不能依赖具体数据库实现。
5. API 返回字段保持兼容，存储后端通过 Repository 接口替换。

### 9.3 Repository 抽象

```javascript
class VectorStore {
  async upsert(records) {}
  async query(vector, options) {}
  async delete(ids) {}
  async statistics() {}
}

class GraphStore {
  async addNodes(nodes) {}
  async addEdges(edges) {}
  async getSubgraph(nodeId, depth) {}
  async statistics() {}
}
```

当前实现：

```text
VectorStore -> ChromaLocalStore
GraphStore  -> JsonGraphStore
```

后续实现：

```text
VectorStore -> MilvusStore
GraphStore  -> Neo4jStore
```

## 10. 测试与验证设计

### 10.1 单元测试

- 向量记录 metadata 完整性校验。
- 向量和 chunk 一一对应校验。
- 节点、边、关系类型合法性校验。
- 图谱统计指标计算。
- 孤立节点和孤儿向量检测。
- 版本差异计算。
- RRF 或多路结果融合的排序稳定性。

### 10.2 集成测试

准备固定的小型资料集，至少包含：

- 多格式文档。
- 多个特性。
- 显式引用和隐式语义关联。
- 空文档、重复文档和解析失败文档。
- 删除和修改场景。

验证：

1. 预处理完成后每个有效 chunk 都有向量记录。
2. 图谱节点和边可以回溯到源 chunk。
3. API 能返回完整统计和子图。
4. 前后两次构建的增量信息准确。
5. 页面能够展示全景统计和局部关系。

### 10.3 端到端验证

```text
PingCode 素材
  -> 解析、过滤、清洗、分块
  -> 向量化和图谱构建
  -> 质量评估
  -> API 查询
  -> 页面展示
  -> 语义检索和图谱扩展
```

质量门禁建议：

- 向量覆盖率低于 99% 时标记 warning。
- 孤儿向量大于 0 时构建失败。
- 关系证据完整率低于 100% 时禁止发布图谱。
- Recall@5 低于 0.85 时标记检索质量风险。

## 11. 实施计划

### Phase 1：数据模型和统计

- 定义 `VectorStore`、`GraphStore`、`IndexQualityEvaluator` 接口。
- 实现 manifest、nodes、edges、statistics 文件格式。
- 实现向量和图谱结构完整性评价。
- 增加单元测试和固定数据集。

### Phase 2：本地评估服务

- 接入本地 ChromaDB。
- 实现 JSON 图谱存储和内存查询。
- 实现统计、质量、子图、版本差异 API。
- 实现本地可视化页面。
- 增加后端 API 集成测试。

### Phase 3：质量和性能优化

- 增加人工标注查询集。
- 增加 Recall@K、MRR、nDCG 评价。
- 增加按特性和版本的过滤。
- 对全景图和子图查询进行性能测试。

### Phase 4：规模化扩展

- 根据数据规模评估是否迁移 Milvus。
- 根据关系查询复杂度评估是否迁移 Neo4j。
- 实现 `MilvusStore` 和 `Neo4jStore`。
- 对新旧存储执行双写或离线数据校验。

## 12. 关键决策

| 决策项 | 当前选择 | 理由 |
|--------|----------|------|
| 当前部署方式 | 本地评估服务 | 便于开发、测试和离线回溯 |
| 向量存储 | 本地 ChromaDB | 起步成本低，支持持久化 |
| 图谱存储 | JSON + 内存图 | 无额外服务依赖，便于审计 |
| 图谱展示 | 本地 Web 页面 + 局部子图 | 避免全量图不可读 |
| 质量报告 | JSON + HTML | 机器可读和人工可读兼顾 |
| 版本对比 | run_id + 稳定 ID + hash | 支持增量构建和回溯 |
| 后续扩展 | Milvus + Neo4j | 保留企业级规模化能力 |

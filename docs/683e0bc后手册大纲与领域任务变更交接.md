## 1. 交接结论

本轮将“手册大纲”从文件兼容能力推进为可在 YashanDB 中协作治理的关系模型，并完成从大纲导入、目录维护、技术领域分工、发布到领域建设任务生成和任务项改派的业务闭环。前端同步迁移为三阶段工作区，工作台按领域聚合建设任务。

当前建议状态为：**可继续集成和验收，不建议未经预发布复核直接投入生产**。

主要原因如下：

1. 核心代码、设计、测试和 Windows 启动修复已经提交，Node 语法检查通过，当前 YashanDB 领域 API 可只读访问。
2. `prompt.md` 记录了文件模式和数据库模式的真实 API 验收，包括导入、预检、保存、发布阻断、任务生成及责任人改派。
3. 本机当前缺少 `apps/knowledge-center-api/node_modules`，本次无法重跑依赖 `xlsx` 的核心单测；前端相关 3 个套件 32 个用例通过。
4. 领域建设任务仍是独立协作入口，尚未与现有文档生产、增量构建和审核发布状态机自动衔接。
5. 负责人和领域成员仍以种子配置为主，尚未完成与认证用户、组织主数据的稳定 ID 绑定。

## 2. 本轮交付的业务链路

```text
手册主数据
  -> 下载六列 XLSX 模板或样例
  -> 在手册上下文导入候选大纲
  -> 维护目录、页面说明和技术领域分工
  -> 预检未分工页面及结构完整性
  -> 发布大纲版本
  -> 按技术领域生成建设任务
  -> 按 document-domain 生成任务项
  -> 领域负责人在工作台改派本领域成员
  -> 大纲详情实时投影当前责任人
```

关键业务约束：

- 手册是知识资产主对象，大纲版本必须绑定已有手册。
- `document` 是大纲叶子节点；没有 document 的候选不能预检或发布。
- 一个 document 可分配多个技术领域；目录可提供继承分工。
- 候选版本可修改说明和分工；已发布版本只允许调整技术领域，不允许清空有效分工或修改内容说明。
- 发布必须在同一事务内完成版本状态切换和任务生成；失败时不得出现半发布状态。
- 发布产生的任务与现有文档生产任务相互独立，目前不自动触发内容生成。

## 5. 数据与兼容性影响

### 5.1 主写源

| 运行模式 | 手册/大纲主写源 | 兼容与回退 |
|---|---|---|
| `file` | 原 JSON/metadata | 保持既有本地行为，治理和任务以内嵌投影保存 |
| `database` | `MANUALS`、`MANUAL_OUTLINE_*`、`MANUAL_DOCUMENT*`、领域和任务关系表 | `LEGACY_PAYLOAD`、旧 JSON、`KC_RECORD` 保留，不做长期双写 |

切换原则：一个业务对象只能有一个主写源。数据库不可用时返回明确的 503，不静默回写文件，避免双源分叉。

### 5.2 关键唯一性与状态约束

- 手册 code 唯一；同一手册的大纲 `VERSION_CODE` 唯一。
- 每个大纲节点领域组合唯一；每个大纲版本和技术领域只生成一个建设任务。
- 每个任务、文档和技术领域组合只生成一个任务项。
- `NODE_TYPE` 仅允许 `directory` 或 `document`。
- 分工来源仅允许 `explicit` 或 `inherited`；领域成员角色仅允许 `leader` 或 `member`。
- 已发布或已废止大纲不能删除；候选删除不应影响正式版本。

### 5.3 对调用方的影响

- 仍调用旧上传接口的客户端必须迁移到 `/api/outline/import`。
- 大纲写操作必须通过知识中心 BFF，直连 API 且无内部令牌会被拒绝。
- 部署时必须同步配置 BFF 和 API 的内部令牌；空值会使写接口返回 503，不一致会返回 403。
- 数据库模式上线前必须确认 SQL `001` 至 `016` 已由当前服务成功检查或执行。

## 7. 风险矩阵

| 等级 | 风险 | 影响 | 当前控制 | 建议措施 |
|---|---|---|---|---|
| 高 | 关系模型切换后的数据一致性 | 手册、大纲、节点或任务缺失会阻断治理链路 | dry-run、摘要对账、事务、保留旧源 | 在预发布执行全量迁移和按手册对账，保存报告后再切换主写源 |
| 高 | 领域任务未接入文档生产状态机 | 发布后只能分工，不能自动形成内容生产闭环 | 设计中明确任务独立，未伪装为已接通 | 明确接口映射、幂等键和状态转换，再实现任务转生产任务能力 |
| 高 | 用户与组织主数据未绑定 | 展示名可能重名，责任人改派和权限审计不稳定 | 当前保存负责人 ID/名称，种子区分 leader/member | 接入认证用户和部门目录，迁移为稳定 userId/departmentId 并对账 |
| 中 | BFF 与 API 内部令牌配置漂移 | 所有大纲写操作返回 403/503 | 双层权限检查，配置模板已说明 | 由密钥系统统一注入，增加启动自检和部署探针 |
| 中 | 文件模式与数据库模式实现漂移 | 两种环境行为、错误码或投影不一致 | 共享业务函数，已有双模式验收记录 | 将同一契约测试参数化运行于两种模式，并纳入 CI |
| 中 | 本地依赖安装口径不统一 | 根目录测试命令无法加载 `xlsx`，降低可复现性 | 子包已声明依赖并有 lock 文件 | 统一 workspace 安装与测试入口，CI 从干净目录验证 |
| 中 | 发布后允许领域调整会重建任务投影 | 错误实现可能丢失人工改派或产生孤儿任务 | 服务端先完整校验，再同步任务；数据库事务保护 | 增加保留已改派责任人的回归测试和并发更新测试 |
| 中 | 领域接口返回较大兼容载荷 | 大纲节点和 `LEGACY_PAYLOAD` 增长后可能增加延迟与内存 | 内部端口访问，当前数据规模有限 | 增加分页/轻量列表 DTO，详情按需加载并设置体积监控 |
| 中 | SQL 迁移主要依赖启动期执行 | 生产账号权限不足或部分 DDL 失败会阻止启动 | 文件有序、重复执行、健康检查 | 生产改为 DBA 预执行和版本化迁移报告，应用账号最小权限 |
| 低 | 根目录二进制模板被误替换 | 下载内容和解析契约可能不一致 | 模板生成脚本、表头单测 | CI 校验模板摘要、表头和样例 document 数量 |
| 低 | 既有文档格式告警 | 影响 `git diff --check` 作为严格门禁 | 已识别具体文件，不影响运行 | 单独提交清理，避免与业务改动混合 |

3. 清理历史文档路径和格式告警，更新全局《开发者交接手册》中已经过时的目录引用。
4. 为模板和样例建立版本号、摘要和兼容策略，避免线下文件与解析器契约失配。

## 9. 建议下一步执行顺序

| 顺序 | 任务 | 完成标准 | 建议责任 |
|---:|---|---|---|
| 1 | 修复依赖安装和测试入口 | 干净检出后单命令可运行 4 个相关 Jest 套件 | 开发/构建负责人 |
| 2 | 预发布数据库迁移演练 | 有 dry-run、apply、回读、行数和摘要报告 | DBA + 后端 |
| 3 | 真实 API 回归 | 从 BFF 完成全链路且错误码、状态、任务数符合契约 | 测试 + 后端 |
| 4 | 权限与组织数据确认 | 令牌、角色、领域负责人和成员均使用受控真实数据 | 平台管理员 + 业务负责人 |
| 5 | E2E 与故障注入 | 桌面/移动端通过，发布失败无部分数据 | 测试负责人 |
| 6 | 任务链路集成设计 | 领域任务到内容生产的状态图、幂等和回滚契约评审通过 | 架构/产品/开发 |
| 7 | 灰度切换数据库主写 | 指标、日志和回退开关齐备，小范围运行无数据漂移 | 运维 + DBA |

## 10. 部署、运行与回退要点

### 10.1 上线前配置

```text
KNOWLEDGE_STORAGE_MODE=database
YASDB_STORAGE_URL=http://127.0.0.1:14210
KNOWLEDGE_CENTER_OUTLINE_INTERNAL_TOKEN=<由密钥系统注入>
KNOWLEDGE_CENTER_OUTLINE_TEMPLATE_PATH=<可选，默认仓库根目录/大纲模板.xlsx>
KNOWLEDGE_CENTER_OUTLINE_SAMPLE_PATH=<可选，默认仓库根目录/基本数据库管理手册大纲示例.xlsx>
```

同时配置 YashanDB JDBC URL、应用账号、密码、驱动路径和连接池参数。生产账号只授予应用所需的 `KC_*` 与本轮关系表权限，DDL 建议由 DBA 在发布窗口预执行。

### 10.2 最小健康检查

```bash
curl http://127.0.0.1:14210/health
curl http://127.0.0.1:14110/api/outline/tech-domains
curl http://127.0.0.1:13510/knowledge-center/
```

浏览器写操作必须从知识中心入口执行，不能用存储服务内部 API 代替权限验收。

### 10.3 回退策略

1. 停止写入并导出当前 YashanDB 数据及迁移/发布审计记录。
2. 将 `KNOWLEDGE_STORAGE_MODE` 切回 `file`，重启知识中心相关服务。
3. 使用切换前保留且经过摘要确认的 JSON 源恢复读取。
4. 不删除关系表、`KC_RECORD` 或 `LEGACY_PAYLOAD`，保留现场用于差异分析。
5. 对比切换窗口内的新增候选、分工、发布和改派操作，制定人工补偿清单。

注意：当前回退是“切换主写源并保留数据库现场”，不是自动反向同步。切换后发生过数据库写入时，必须先完成差异确认，不能直接长期在两侧继续写入。

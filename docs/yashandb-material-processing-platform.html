技术交流文档 · 2026 年 8 月

一、背景与挑战

数据库产品积累了海量技术文档，如何将这些散落在 Wiki、Office、PDF 中的知识转化为结构化、可检索、可推理的知识资产，是我们构建本平台的出发点。

📚

文档规模大、格式杂

YashanDB 知识库涵盖 200+ 空间、8000+ 页面，涉及 Markdown、DOCX、PPTX、PDF、SQL 等多种格式，人工整理成本极高。

🔗

知识关联缺失

文档之间缺少显式语义关联，同一概念在不同文档中表述不一致，导致检索碎片化、回答不完整。

🤖

LLM 直接处理不可控

大模型存在幻觉风险，直接将原始文档喂给 LLM 无法保证输出的准确性、可追溯性和质量一致性。

🔄

增量更新困难

文档持续迭代，需要一套能感知变更、增量加工、版本可追溯的流水线，而非每次全量重建。

二、平台定位与设计原则

平台定位为面向数据库知识域的"资料→知识"转化引擎，不是通用 RAG 工具，而是深度适配技术文档特性的垂直知识工程系统。

🎯

知识域垂直深耕

针对数据库产品文档（SQL 语义、存储引擎、运维手册等）定制提取规则和知识本体，而非通用 NLP。

🔍

证据优先

每一条知识产物都必须追溯到原始文档段落，支持"为什么得出这个结论"的审计链路。

⚙️

LLM 可控执行

提示词版本化、Skill 可插拔、模型调用可审计，杜绝"黑箱调用"。

🛡️

质量门禁前置

在知识进入图谱之前设置多层校验：Schema 校验、证据校验、语义复核、人工确认。

核心理念：原始资料永久保留，步骤之间只传递结构化元数据和候选结果；模型输出不能直接进入图谱，必须经过代码校验；任何失败和降级都生成中文说明和可追溯事件。

四、六步骤知识加工流水线

将"原始资料→知识图谱"的复杂过程分解为六个前端可见、产物可追溯的固定步骤，每步只读取上一步已落盘并通过 Schema 校验的产物。

资料预处理

格式识别、安全解压、文本清洗、字符分块。将杂乱的原始文件转化为标准化的处理单元。

输入: MaterialBatch 输出: chunks.jsonl, source-documents.jsonl

元数据构建

为每个处理单元附加上下文元数据：文档层级、面包屑路径、关联资源、格式特征。

输入: chunks.jsonl 输出: documents.jsonl, chunk-contexts.jsonl

知识提取

调用知识提取 Skill（Agent 执行），从处理单元中提取知识点候选、实体关系候选，标记不确定项。

输入: chunk-contexts.jsonl Agent: 知识提取 Skill 输出: knowledge-candidates.jsonl

按需语义补充

对第 3 步标记的不确定项，调用语义复核 Skill 进行消歧、补全和交叉验证。

输入: pending.jsonl (不确定项) Agent: 语义复核 Skill 输出: semantic-resolution.jsonl

知识校验与合并

代码级 Schema 校验、证据链校验、实体对齐和去重。不通过校验的产物进入 rejected 集合。

输入: candidates + resolutions 输出: knowledge.jsonl (最终), rejected.jsonl

图谱与数据集生成

基于 final-results 构建知识图谱（节点+边），生成可发布的数据集清单和运行报告。

输入: knowledge.jsonl 输出: nodes.json, edges.json, manifest.json
设计约束：原始资料永久保留；步骤之间传递结构化元数据而非原文副本；处理单元是原文的"处理视图"，不代表删除或覆盖原文；任何失败、跳过和降级都生成中文说明和可追溯事件。

六、技术亮点

在通用 RAG 方案基础上，针对数据库知识域的特殊性做了多项针对性设计。

  • LLM 可控执行体系：提示词版本化（草稿→发布→不可变版本）、Skill 可插拔注册、模型调用全链路审计（Provider、模型、Token、耗时、重试），杜绝"黑箱调用"。
  • 证据化知识提取：每个知识点候选都必须携带原文证据片段（段落级定位），支持"为什么得出这个结论"的审计链路，消灭 LLM 幻觉。
  • 不确定项路由机制：知识提取阶段自动标记低置信度候选，由专门的语义复核 Skill 进行消歧和补全，而非将所有判断都交给单一模型。
  • 源文件加工预览 Cockpit：1366px 宽度下一屏完成"是否可解析、解析到什么程度、转换是否保真"的判断，区分"已统计/明确为0/不适用/未统计/解析失败"五种状态。
  • Office 轻量字符统计：直接解析 OOXML 结构统计可见文本字符数，不依赖 LibreOffice 转换，避免格式降级造成的统计偏差。
  • 密钥零暴露：模型密钥仅由独立的 ConfigManager 解密调用，不进入加工服务、前端、Prompt、事件和运行快照。
  • 产物不可变性：步骤间传递的产物一旦写入不可修改，新版本生成新文件，保证审计链路完整。
  • 安全边界明确：压缩包解压设置膨胀率上限（100x）、文件数上限、递归深度上限，防止恶意文件攻击。

八、当前痛点与业界最佳实践

知识工程领域面临的核心挑战，以及我们当前应对策略和业界参考方案。

痛点 1：LLM 幻觉与事实准确性

大模型在知识提取时可能生成看似合理但实际错误的知识点，尤其在专业领域（如数据库 SQL 语义、存储引擎原理）。

我们的方案：证据化提取 + 多层校验。每个知识点必须携带原文证据片段，通过 Schema 校验和证据链校验后才能进入图谱。

业界实践：Anthropic 的 Constitutional AI、Microsoft GraphRAG 的社区摘要交叉验证、RAG 领域的"检索增强 + 事实核查"双链路。

痛点 2：长文档上下文丢失 (Lost in the Middle)

数据库技术文档通常较长（运维手册可达数万字），LLM 在处理长上下文时容易忽略中间部分的关键信息。

我们的方案：结构化分块策略（结构优先 + 元数据边界上下文），控制单块在 6000 字符以内，保留文档层级和面包屑路径作为上下文锚点。

业界实践：LangChain 的 RecursiveCharacterTextSplitter、LlamaIndex 的 SentenceWindowNodeParser、Google 的 LongT5 长文档编码器。

痛点 3：实体消歧与知识融合

同一概念在不同文档中可能有多种表述（如"事务隔离级别"与"Transaction Isolation"），需要统一为标准实体。

我们的方案：知识校验与合并步骤中的实体对齐机制，结合语义复核 Skill 进行消歧。当前为规则+模型混合，后续引入图数据库的实体合并能力。

业界实践：Microsoft GraphRAG 的实体合并（LLM 驱动的实体解析）、Neo4j 的 APOC 图算法（相似度合并）、Google Knowledge Graph 的 Freebase 融合。

痛点 4：Token 成本控制

几万篇文档的知识提取需要大量 LLM 调用，Token 成本可能成为规模化落地的瓶颈。

我们的方案：模型分级使用 — 确定性步骤（清洗、分块、校验）用规则，只有提取和语义复核调用模型；不确定项才触发额外的语义补充调用。

业界实践：用小模型（如 qwen-turbo）做初筛和 Embedding，大模型（如 qwen-max）只处理复杂提取；Microsoft 的 cost-aware RAG 调度。

痛点 5：多格式文档解析保真度

Office、PDF、Wiki 页面中的表格、代码块、图片、公式在转换为统一格式时容易丢失结构信息。

我们的方案：源文件加工预览 Cockpit 提供"转换保真"诊断，区分五种状态；Office 字符数使用轻量 OOXML 解析而非 LibreOffice 转换，避免格式降级。

业界实践：Unstructured.io 的多格式解析引擎、Azure Document Intelligence 的布局分析、Marker 的 PDF→Markdown 高保真转换。

痛点 6：加工过程可观察性与可恢复性

大规模知识加工任务耗时长，中途失败后需要能从断点恢复，而非全量重跑。

我们的方案：设计 SQLite 控制面 + 租约式 Worker（规划中），支持租约过期恢复、幂等键复用、SSE 运行事件和断线重连。

业界实践：Celery + Redis 的任务队列、Temporal 的持久化工作流、Apache Airflow 的 DAG 断点续跑。

九、演进规划

平台按"验证→工程化→规模化"三阶段演进，每阶段有明确的交付边界和验收标准。

Phase 1

端到端框架验证 已完成

PingCode 素材下载、本地上传、源文件扫描与预览、Prompt/Skill Registry、Prompt 草稿/发布/Diff、质量门禁基础规则。首期用 JsonStore + 后台线程验证最小闭环。

Phase 2

LLM 可控执行 进行中

统一 Model Provider 接入、四类 Skill 真实执行器、加工预检与成本估算、SSE 运行事件协议、前端 Prompt/Skill 管理界面。实现"每次加工都能回答用了什么模型、什么提示词、处理了什么输入"。

Phase 3

证据化图谱框架 规划中

SQLite 控制面 + 独立 Worker、证据化实体关系图谱、Embedding Provider + 向量库、人工质量门禁、数据集版本发布。产物可追溯到原文段落，支持审计和人工确认。

Phase 4

规模化与下游对接 规划中

增量加工能力、检索评测（固定查询集）、FastGPT/RAG Pipeline 集成、真实模型故障验收（限流、断网、重启、SSE 重连）。支撑万级文档规模的日常加工和持续更新。

总结

YashanDB 资料加工平台不是又一个通用 RAG 工具，而是面向数据库知识域的垂直知识工程系统。通过六步骤流水线、LLM 可控执行和证据化知识图谱，我们将"原始技术文档→可追溯知识资产"的过程变得透明、可控、可审计。

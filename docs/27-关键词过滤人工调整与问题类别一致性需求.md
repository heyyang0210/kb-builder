# 关键词过滤人工调整与问题类别一致性需求

> 版本：V1.1（已实现）
>
> 更新日期：2026-08-14
>
> 前置依赖：`docs/26-关键词过滤决策审计与历史记录需求.md`

## 1. 需求目标

把当前“点击整行切换保留/排除”的隐式交互改为明确、可校验、可审计的人工复核。系统必须保证动作与问题类别始终满足业务不变量，并在应用前清楚呈现模型建议、人工修改和最终结果。

## 2. 现状与问题

当前 `QualityPage.vue` 的结果行整体是按钮，点击即在 `keep` 和 `exclude` 间切换。类别字段仍沿用模型原值：

- 保留改排除时可能没有合法类别；
- 排除改保留时可能残留排除类别；
- 点击原因或关键词文字也可能误触切换；
- 页面只显示“已人工调整”，不能恢复修改前值，也没有人工备注；
- `filter-apply` 只校验关键词 ID 完整性，不校验动作与类别的一致性。

底层逻辑是 `action` 与 `issueCategory` 不是两个独立字段，而是一个受约束的复合状态。只在前端改变动作无法保证传输、刷新、并发和后端落盘后的数据一致性。

## 3. 业务不变量

| 最终动作 | `finalIssueCategory` | 备注 |
| --- | --- | --- |
| `keep` | 必须为 `null` | 不参与排除类别统计 |
| `exclude` | 必须是当前规则版本的合法类别 ID | 无法判断时允许 `other`，但标记待复核 |
| 模型排除改人工保留 | 清空最终类别 | 模型类别仍保存在模型快照中 |
| 模型保留改人工排除 | 必须显式选择类别 | 未选择时禁止保存和应用 |

任何客户端均不能绕过上述规则；后端是最终校验边界。

## 4. 用户故事

1. 作为审核人员，我希望用明确的保留/排除控件修改结果，避免点击文字时误操作。
2. 当我改为排除时，我希望系统要求选择问题类别，从而保证统计有效。
3. 我希望填写人工备注并在刷新后继续复核，从而保留判断依据。
4. 应用前，我希望看到模型建议和人工调整的差异汇总，从而确认最终排除数量。
5. 当其他页面或请求已更新同一运行时，我希望收到冲突提示，而不是静默覆盖。

## 5. 状态与数据契约

### 5.1 复核决策

```json
{
  "keywordId": "keyword:abc",
  "modelAction": "keep",
  "modelIssueCategory": null,
  "modelReason": "明确的数据库概念",
  "reviewAction": "exclude",
  "reviewIssueCategory": "generic_term",
  "reviewNote": "在本批文档中缺少可独立检索含义",
  "reviewedAt": "2026-08-14T10:10:00+08:00",
  "reviewedBy": "anonymous",
  "userOverride": true
}
```

`userOverride` 由服务端根据模型值与复核值计算，客户端不能自行声明。`reviewNote` 首版限制 500 个字符，去除首尾空白；禁止在提示词或 Vue 中硬编码类别字典。

### 5.2 应用前汇总

```json
{
  "modelKeep": 565,
  "modelExclude": 78,
  "changedToKeep": 5,
  "changedToExclude": 3,
  "categoryChanged": 4,
  "finalKeep": 567,
  "finalExclude": 76,
  "invalidDecisionCount": 0,
  "unreviewedOtherCount": 2
}
```

恒等式：`finalKeep + finalExclude = candidateTotal`。类别总数只统计最终排除项，并必须等于 `finalExclude`。

## 6. API 设计

依赖需求 26 的运行资源：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `PATCH` | `/api/datasets/{datasetId}/keyword-filter-runs/{filterRunId}/review-decisions` | 批量保存复核增量 |
| `GET` | `/api/datasets/{datasetId}/keyword-filter-runs/{filterRunId}/review-summary` | 获取模型/人工/最终差异汇总 |
| `POST` | `/api/datasets/{datasetId}/keyword-filter-runs/{filterRunId}/apply` | 校验完整性和一致性后原子应用 |

PATCH 请求：

```json
{
  "expectedRevision": 3,
  "changes": [
    {
      "keywordId": "keyword:abc",
      "action": "exclude",
      "issueCategory": "generic_term",
      "note": "人工复核说明"
    }
  ]
}
```

服务端返回新的 `revision`、规范化后的变更项和汇总。非法类别或不一致状态返回 422 `KEYWORD_FILTER_REVIEW_INVALID`；版本冲突返回 409 `KEYWORD_FILTER_RUN_REVISION_CONFLICT`；已应用运行返回 409 `KEYWORD_FILTER_RUN_IMMUTABLE`。

## 7. 核心伪代码

```python
def normalize_review_change(change, valid_categories):
    action = require_one_of(change.action, {"keep", "exclude"})
    if action == "keep":
        category = None
    else:
        category = require_one_of(change.issue_category, valid_categories)
    return normalized(action, category, sanitize_note(change.note))

def save_review_changes(run_id, expected_revision, changes):
    with run_lock(run_id):
        run = require_reviewable_run(run_id)
        assert_revision(run, expected_revision)
        current = read_review_snapshot(run_id)
        for change in changes:
            current[change.keyword_id] = merge_with_model_snapshot(change)
            append_audit_event(before, current[change.keyword_id])
        validate_all_decisions(current)
        atomic_write(review_snapshot(run_id), current)
        return increment_revision_and_summary(run)

def apply_reviewed_run(run_id, expected_revision):
    decisions = effective_decisions(model_snapshot, review_snapshot)
    assert_complete(decisions)
    assert all(action == "keep" and category is None
               or action == "exclude" and category in valid_categories
               for action, category in decisions)
    apply_filter_run_atomically(decisions)
```

## 8. 前端交互设计

每一行改为非点击式容器，包含：

```text
关键词：对象
模型建议：排除 / 通用词     最终决策：[保留 | 排除]
问题类别：[通用词/过于宽泛 v]
模型理由：范围过宽
人工备注：[________________________________]
```

交互规则：

- 只有分段控件改变动作，查看关键词、选中文字和滚动不触发修改；
- 改为保留时自动清空最终类别，但保留模型类别只读展示；
- 改为排除时类别为空，立即展开类别选择并提示必填；
- 修改先进入本地脏状态，使用 300ms 批量保存；离开页面前仍有未保存变更时显示浏览器确认；
- 保存冲突时停止自动覆盖，提示“结果已在其他窗口更新”，提供重新加载；
- 应用按钮旁显示差异摘要，存在非法项时禁用并可一键筛选问题项；
- `other` 显示“需人工复核”标识，但是否强制填写备注由人类确认。

## 9. 验收标准

| 编号 | 验收项 | 通过条件 |
| --- | --- | --- |
| REV-01 | 明确操作 | 点击行内文本不会改变动作，只有保留/排除控件可修改 |
| REV-02 | 保留不变量 | 任意保留项保存后类别均为 `null` |
| REV-03 | 排除不变量 | 排除项缺少或使用非法类别时前端禁用应用、后端返回 422 |
| REV-04 | 模型字段隔离 | 人工修改不覆盖模型动作、类别和理由 |
| REV-05 | 刷新恢复 | 保存成功后刷新页面，复核动作、类别和备注均可恢复 |
| REV-06 | 汇总一致 | 差异汇总恒等式和最终类别统计在前后端一致 |
| REV-07 | 并发冲突 | 两个客户端用同一 revision 写入，只有一个成功，另一个收到 409 |
| REV-08 | 完整应用 | 分页、筛选或搜索状态不会改变提交的完整决策集合 |
| REV-09 | 可访问性 | 控件有中文标签、键盘可操作、焦点状态清晰，移动端无重叠 |
| REV-10 | 真实 API | 隔离数据集完成复核保存、刷新恢复、冲突和应用测试 |

## 10. 依赖与风险

- 必须先完成需求 26，否则复核草稿无法跨刷新保存，也无法区分模型与人工值。
- 类别配置可能在运行后变化；复核必须使用运行冻结的类别版本，不得使用最新配置静默改写历史。
- 自动保存会增加请求量，需批量合并变更并处理页面关闭时的未保存状态。
- 当前没有登录用户身份时只能记录 `anonymous`，审计责任范围有限。
- 应用关键词状态和冻结最终快照必须具有一致的失败恢复策略，避免图谱已更新但运行仍为未应用。

## 11. 待人类确认

1. **复核保存策略**：确认采用后端批量自动保存，而不是只在最终应用时一次提交。
2. **`other` 规则**：建议 `other` 允许应用但必须填写人工备注；该规则影响后端校验和用户工作量。
3. **并发策略**：确认使用运行级 `revision` 乐观锁，冲突时整体重新加载，不做字段级自动合并。
4. **原子应用边界**：确认以可恢复事务日志实现“图谱状态 + 最终快照”一致性，不引入数据库依赖。

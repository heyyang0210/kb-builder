# 模板管理多角色执行计划（中间文档）

> 状态：待评审。本文档用于比较切分方案；T1-T10 的持久化任务总览和三任务包映射见 `.codex/workflow/tasks/TASK-TEMPLATE-EPIC.md`。实际开始时间、命令和证据在每批完成后补录。

## 角色约束

| 角色 | 职责 | 必须产出 |
|---|---|---|
| 架构师（ARCH） | 接口、数据模型、依赖边界 | 设计决策和兼容性说明 |
| 后端工程师（BE） | API、权限、存储、生成链路 | 代码、单测、真实 API 证据 |
| 前端工程师（FE） | 预览、编辑、上传、历史交互 | 页面实现、浏览器证据 |
| QA Lead（QA） | 契约、回归、验收矩阵 | 可复现测试报告 |
| 安全/数据工程师（SEC/DB） | 凭证、导入、迁移和审计 | schema、迁移与安全检查 |
| 发布负责人（REL） | 分支、提交、回滚和发布检查 | 发布清单和回滚点 |

## 三种切分与执行方案

### 方案 A：按技术层串行（推荐默认）

阶段顺序：契约/测试基线 → 后端权限与保存 → 上传草稿 → 前端交互 → 数据迁移 → 生成链路 → 全量验收。

优点：依赖清晰、风险最小、适合当前已有实现不完整且需要保持 API 兼容的仓库。缺点：整体周期最长，前端需等待接口稳定。

任务包：

1. A1（ARCH+QA）：冻结接口、权限、错误码和测试夹具。
2. A2（BE）：修复列表权限、JSON 请求解析、保存并发和校验。
3. A3（BE+SEC/DB）：实现 multipart 导入、DOCX 转换、草稿和临时文件清理。
4. A4（FE）：预览/编辑、历史抽屉、错误反馈、筛选和草稿状态。
5. A5（SEC/DB）：schema、初始化导入、聚合迁移和幂等验证。
6. A6（BE）：生成任务固定模板 ID、版本和 hash。
7. A7（QA+REL）：真实 HTTP、浏览器回归、静态检查和发布验收。

决策门：A2 通过权限和保存闭环后才进入 A3；A5 迁移演练通过后才允许 A6 改生成链路。

### 方案 B：按业务闭环垂直切片（适合并行团队）

并行切片：

- B1 只读浏览：列表、详情、权限、预览；
- B2 编辑保存：Markdown 编辑、校验、版本冲突；
- B3 导入恢复：上传、转换、草稿、历史恢复；
- B4 生成可复现：任务固定版本、停用规则；
- B5 迁移与安全：schema、seed、凭证与审计。

每个切片由 ARCH 定义契约，BE/FE/QA 组成小队，完成独立端到端测试后再合并。优点是价值交付快、并行度高；缺点是容易重复修改共享路由和状态，必须先建立契约测试与合并顺序。

合并顺序：B5 → B1 → B2 → B3 → B4；任何切片不得改变公共 API 形状。

### 方案 C：按风险优先级分波次（适合生产风险高）

- C0 阻断风险：列表权限、保存 Content-Type、版本乐观锁、敏感信息检测；
- C1 核心可用：预览/编辑、历史查看恢复、上传草稿；
- C2 数据正确性：初始化导入、迁移幂等、生成版本固定；
- C3 体验完善：筛选、响应式抽屉、无障碍、审计查询。

每波次设置“继续/暂停/回滚”评审点。优点是先降低安全和数据损坏风险；缺点是早期页面能力不完整，需明确对外标记未完成功能。

## 推荐选择

采用方案 A 作为主线；若有足够独立人员，可将 A3 与 A4 在 A2 契约冻结后按方案 B 并行。生产发布严格遵循方案 C 的风险门，不因并行而跳过迁移和真实 API 验证。

## 统一完成定义

- 设计、代码、测试和 `prompt.md` 同步；
- 权限、上传草稿、保存、历史恢复和生成版本闭环均有真实证据；
- 未执行测试标记为“待确认”，不得标记通过；
- 每批保留 `git status`、差异检查和可回滚提交点；
- 不写入真实凭证，不修改 `prompt-log.md`。

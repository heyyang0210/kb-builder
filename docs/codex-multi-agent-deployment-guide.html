ENGINEERING PLAYBOOK

把 Codex 多角色协作
部署到任何开发环境

适用于 Web 应用、微服务、数据平台、AI 工程、CLI 工具和文档仓库：用角色契约、任务卡片和质量门禁复用同一套工程协作方法。YashanDB 仅作为角色定义来源之一，不是使用边界。

平台无关仓库级配置六类角色模板更新于 2026-08-14

先判断：什么时候值得用多角色？

多角色解决的是“职责边界和并行协作”问题，不是把一个简单任务拆得更复杂。满足下列条件中的两项以上，再启用它。

🧩

跨模块、跨技术栈

同一需求同时影响客户端、服务端、数据存储、接口契约和文档，例如订单平台、数据管道或 AI 工作流改造。

⚡

可以安全并行

任务能按文件或目录隔离，各角色有清晰输入和输出，不会修改同一文件或共享生成物。

🔍

需要独立验收

功能之外还需要真实 API、构建、迁移、回归或风险报告，独立验证能降低遗漏和自证偏差。

典型场景建议角色组合
修改一个函数、配置项或一处文案单 Agent实现者直接完成并做定向验证。
前后端功能、移动端 + API 联调适合多角色Planner + Frontend + Backend + Test。
ETL、数据迁移、模型服务或性能治理适合多角色Planner + Backend/Data Worker + Test + Reporter。
大型重构、版本升级、跨仓库发布适合多角色先设计与风险审查，再并行实现和独立验收。
删除公共 API、引入依赖、安全策略先人工确认属于破坏性或架构决策，角色不能替代审批。

设计依据与取舍

以下是可审计的需求分析结论，用来解释文档为什么这样组织；它呈现决策依据和结果，不依赖某个具体业务域。

目标识别
用户真正需要的不是复制一个 YashanDB 专用目录，而是把角色治理方法迁移到其他平台。因此区分“通用协作协议”和“项目路径/指标参数”。
抽象边界
Planner、Frontend、Backend、Test、Doc、Reporter 是稳定角色；框架名称、目录、命令、性能阈值和语言要求是项目参数，部署时必须替换。
示例策略
角色内容以当前 .codex/roles/ 为来源，示例业务改用通用订单管理平台，同时说明如何映射到数据平台、AI 工程和 CLI 项目。
风险控制
多角色只在文件边界清晰时并行；公共接口、数据结构、依赖、安全和删除操作继续保留人工审批。
验收原则
输出不能只写“已完成”，必须给出真实系统验证、构建/测试结果、变更文件和残余风险，形成可追溯交付证据。

协作模型：角色是契约，不是聊天群

Planner 先把目标变成可验收任务；Worker 只在声明的文件边界内工作；Test Engineer 用真实链路验证；Reporter 汇总证据。

Planner拆解 SMART 任务
→
Workers前端 / 后端 / 文档
→
Test Engineer真实 API + 构建
→
Reporter进度 / 风险 / 下一步

仓库内的最小组成

.codex/roles/*.md 定义职责；.codex/workflow/tasks/ 保存任务卡片；AGENTS.md 规定审批、并发和验证边界；.codex/commands/ 提供自然语言快捷命令。

并发边界

并行 Worker 不得编辑同一文件、同一段落或同一生成产物。接口契约、数据库迁移和公共 API 等共享边界必须串行并经人工确认。

Planner：规划与任务拆解 输入高层需求 → 输出任务卡片

职责：接收高层需求，按 SMART 原则拆解子任务，分析依赖和并行度，生成 .codex/workflow/tasks/TASK-*.md，并标注架构、破坏性、安全、性能等人工确认点。

通用配置示例：

角色：planner 输入：需求描述、当前进度、设计文档、仓库结构 输出：任务卡片、依赖关系、并行文件边界、确认摘要 完成条件：每个任务有负责人、输入、输出、验收标准和预计时限 禁止：未冻结共享契约就启动会修改同一文件的 Worker

迁移参数：把“docs/”和任务模板换成目标平台的设计文档目录；单任务工作量上限按团队节奏调整。

Backend Worker：服务端、接口与数据层 实现接口 → 真实 API 验证

职责：实现 Node.js、Python、Java、Go 或其他服务端功能，遵循现有分层架构，编写单元/集成测试，同步设计文档和 REST/事件接口说明。

继承的工程规则：外部调用要有超时和重试；关键操作输出结构化日志；统一错误码；密钥不能硬编码；性能指标必须可测量。当前仓库示例为 P95 小于 500ms，迁移到其他平台时应替换为实际 SLO。

角色：backend-worker 允许目录：server/、api/、services/、tests/ 交付：实现代码、接口契约、错误码、测试命令、设计文档更新 验收：真实启动后端并调用 API，不用 mock 代替集成验收
Frontend Worker：界面、交互与构建 实现页面 → 构建与可用性验证

职责：实现 Vue、React、Angular、SwiftUI 或 HTML 界面，复用已有组件，保持响应式、无障碍和中文/本地化约束，并同步前端设计文档。

继承的工程规则：用户可见文本遵循项目语言策略；修改后执行构建；交互状态覆盖加载、成功、失败、取消和空状态。当前仓库的首屏 3 秒、交互 100ms 是示例指标，不是通用硬编码。

角色：frontend-worker 允许目录：web/、app/、src/、frontend-tests/ 交付：组件/页面、状态处理、构建结果、必要的截图或浏览器证据 联调：先确认 API 字段和错误契约，再接入真实后端
Test Engineer：测试策略与独立验收 设计测试 → 记录证据和风险

职责：设计正常、边界、异常、性能和端到端测试，维护测试设计卡片，执行自动化测试并输出报告；发现问题记录到 RISKS.md。

继承的工程规则：后端优先真实 API；核心逻辑覆盖率目标大于 80%，边界条件覆盖完整；测试可重复、相互独立。具体阈值由项目配置覆盖。

角色：test-engineer 输入：任务卡片、接口契约、构建产物、测试环境 输出：测试设计、自动化代码、命令与结果、缺陷/风险记录 门禁：集成测试、端到端测试和性能测试均不能只凭静态检查通过
Doc Writer：设计、API 与用户文档 实现变化 → 文档同步

职责：维护设计文档、API 文档、README、CHANGELOG 和用户指南；从实现者获取变更意图，从测试者获取验证结果，并用图表解释复杂流程。

继承的工程规则：中文优先（可改为项目语言）；代码示例可运行；文档标注版本和更新日期；使用相对路径交叉引用；复杂流程优先图示。

角色：doc-writer 输入：设计决策、变更文件、接口/测试结果 输出：设计文档、API 示例、README、图表、版本记录 检查：路径、版本、示例命令和状态文案与实现一致
Reporter：进度、风险与交付汇总 读取任务状态 → 输出项目视图

职责：汇总 Worker 结果，更新 PROGRESS.md、NEXT.md、RISKS.md 和日报，确保统计数据与任务卡片一致。

继承的工程规则：状态使用 pending/in_progress/completed/blocked；完成必须同时满足验收标准；报告包含时间戳、变更文件、验证结果、风险和下一步。

角色：reporter 输入：任务卡片、执行日志、测试结果、风险信息 输出：进度看板、日报、风险清单、下一步计划 禁止：把“代码已修改”直接统计为“验收完成”

在新开发环境部署

1. 复制可迁移目录

# 在目标仓库根目录执行 cp -R /path/to/source/.codex ./ cp /path/to/source/AGENTS.md ./AGENTS.md # 确认目录 find .codex -maxdepth 2 -type f | sort

如果目标仓库已经有 .codex/ 或 AGENTS.md，先合并内容再覆盖。角色文件是规范资产，应纳入版本控制；密钥、个人偏好和运行日志不要提交。

2. 检查宿主环境

✓Codex CLI/IDE 扩展已登录，并能在目标仓库根目录读取 AGENTS.md。
✓项目已有 Node.js/Python、包管理器和真实后端启动方式；角色不会替你安装未经批准的依赖。
✓执行用户对代码、.codex/workflow/ 和测试产物目录有读写权限。
✓敏感配置通过环境变量或密码管理器注入，例如 OPENAI_API_KEY，不写入角色提示词。

3. 迁移后做一次只读校验

test -f AGENTS.md && test -d .codex/roles rg -n "职责|验收标准|需人类确认|真实 API" .codex/roles AGENTS.md git diff --check

仓库级 AGENTS.md 片段

# Codex 协作规则 ## 角色路由 - 架构和任务拆解：Planner - 服务端 API、任务和数据层：Backend Worker - Web、桌面端或移动端界面：Frontend Worker - 自动化与真实 API：Test Engineer - 设计文档和 README：Doc Writer - 进度、风险和日报：Reporter ## 执行约束 - Planner 必须先写任务卡片，再开始实现。 - 并行任务必须声明不重叠的文件集合。 - 修改公共 API、删除功能、引入依赖或安全策略变更，先请求人工确认。 - 后端验收必须真实调用 API；前端修改必须执行构建。 - 业务规则、提示词和环境差异优先从配置/文件读取，禁止新增未记录的硬编码。

任务卡片示例

# TASK-2026-001: 实现订单退款申请 状态: pending 分配: planner → backend-worker, frontend-worker, test-engineer 依赖: 无 可并行: 后端与前端（接口字段冻结后） 需人类确认: 否 ## 输入 - docs/refund-design.md - server/api/orders.py - web/src/views/OrderDetail.vue ## 验收标准 - [ ] 先冻结 POST /api/orders/{id}/refund 请求和错误码 - [ ] 后端校验订单状态并幂等创建退款申请 - [ ] 前端展示提交中、成功、失败和不可退款状态 - [ ] 真实 API 验证成功、重复提交、越权和非法状态 - [ ] 前端 npm run build 通过 - [ ] 更新设计文档、PROGRESS.md 和 RISKS.md

日常使用：从需求到交付

01

创建任务

输入“新任务：……”；Planner 读取进度和设计文档，生成 SMART 任务卡并标注依赖、文件归属和人工确认点。

02

执行与联调

确认关键节点后启动 Worker。共享接口先写契约，随后并行开发；每个 Worker 在任务卡片记录变更和验证命令。

03

验收与汇总

Test Engineer 执行真实后端 API、前端构建和必要的浏览器检查；Reporter 更新看板、风险清单和日报。

常用指令：“新任务: [描述]”启动拆解；“查看进度”读取 PROGRESS/NEXT/RISKS；“生成今日报告”生成日报。也可以直接指定“只用单 Agent”，跳过并发流程。

推荐的交接格式

完成：TASK-2026-001 变更：orders.py、OrderDetail.vue、docs/refund-design.md 验证：后端测试；前端构建；真实 API POST/GET；必要的浏览器验证 风险：无 / RISK-xxxx（说明影响与缓解措施） 下一步：Reporter 汇总，或等待人工确认

验收清单与故障排查

部署验收

□新环境能发现 AGENTS.md 与全部角色文件。
□Planner 能生成任务卡片并写入 workflow。
□角色输出包含变更文件和验证证据。
□README 已链接本指南，项目语言和路径已完成适配。

常见问题

角色没有生效：确认从仓库根目录启动 Codex，检查 AGENTS.md 是否被更深层同名文件覆盖。

并行冲突：暂停 Worker，重新划分文件归属；同一文件改动必须串行。

测试无法执行：先启动真实服务并确认端口、环境变量和测试数据，不要用 mock 冒充集成验收。

任务失控：回到任务卡片收窄范围，必要时改为单 Agent。

安全边界：角色文件不是权限系统。生产凭据、客户数据、破坏性命令和外部服务变更仍需按团队审批流程执行；不要把密钥写入 HTML、AGENTS.md 或任务卡片。

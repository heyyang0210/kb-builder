# 知识中心平台 E2E 测试概要设计

## 1. 文档目的

### 用户权限赋权回归（2026-10-12）

用户权限保存必须看护浏览器是否使用当前用户行版本以及独立幂等键，防止后端契约升级后页面持续保存失败。`knowledge-center-permissions.spec.js` 在隔离实例使用真实管理员登录、用户投影 fixture 和截获的写请求，验证连续赋权/撤销使用刷新后的版本、本地账号禁止赋权、并发冲突显示具体原因而非成功。接口层另由 `knowledge-center-permissions-view.test.js` 使用真实 HTTP handler 验证缺版本返回 428、缺幂等键返回 400、历史 CAS 文件记录不阻断数据库角色更新且本地账号仍拒绝；数据库写入适配器在该测试中使用隔离替身，不对真实账号赋权。

本次定向 Jest 17/17、Chromium E2E 2/2 通过；浏览器证据位于 `runtime/test-results/e2e/20261012-120154-572339-e2e/`。共享平台已验证登录、用户读取及旧请求返回 409，尚未重启部署修复版本，也未进行真实用户角色写入。

本设计定义知识中心平台浏览器端到端测试的范围、价值、使用场景、看护内容、分层策略和验收口径。目标不是让每个按钮都通过浏览器重复验证，而是用少量真实用户旅程证明：浏览器、同源网关、认证会话、业务 API、数据库迁移和关键外部连接能够协同工作。

工作台当前只有页面框架和概览投影，尚未完成“真实任务续办”业务设计与实现。因此本阶段不新增“工作台真实任务 → 手册/生产/审核 → 返回续办”的 E2E；该场景列入后续阶段，待业务契约落地后再补用例。 :codex-annotation{index="1"}

## 2. 为什么需要 E2E

单元测试可以证明渲染函数、状态机或 API 处理器的局部规则；契约测试可以证明请求和响应结构；但以下问题只有真实浏览器旅程才能发现：

- Cookie 会话是否能从登录页传递到同源网关和后端服务。
- 深链、刷新、后退是否保持当前手册、任务或标签页上下文。
- 页面操作是否真的触发正确的 API，而不是只改变前端内存状态。
- 上传、分块、审核、发布等跨页面状态机是否能完成闭环。
- 浏览器权限、服务端权限和模块可见性是否一致。
- GitLab OAuth、仓库正文、数据库服务不可用时，页面是否给出诚实且可恢复的状态。

因此 E2E 的最小价值是验证“用户主路径 + 真实边界”，不是替代所有低层测试。

## 3. 当前模块范围

平台当前有 8 个一级模块，路由事实来自 `apps/knowledge-center-web/frontend/knowledge-center/common/state/navigation.js`：

| 模块 | 路由 | 本阶段 E2E 目标 |
|---|---|---|
| 工作台 | `/knowledge-center/` | 仅做入口和诚实状态门禁；真实任务续办待后续实现 |
| 知识资产 | `/knowledge-center/assets` | 资产列表、详情、映射、生命周期和权限 |
| 资料清洗 | `/knowledge-center/cleaning` | 真实上传、分块、取消和权限 |
| 大纲管理 | `/knowledge-center/outlines` | 目录治理、分工、深链和响应式关键交互 |
| 模板管理 | `/knowledge-center/templates` | 新建/上传、编辑保存、版本回读和权限 |
| 文档生产 | `/knowledge-center/production` | 手册工作区、草稿、模板选择、增量任务 |
| 审核与发布 | `/knowledge-center/review` | 阅读、差异、意见、审核和发布 |
| 平台管理 | `/knowledge-center/platform` | 人员、团队、权限、GitLab 连接和管理员边界 |

仓库阅读工作区 `/knowledge-center/assets/{handbookId}/repository`、手册级生产 `/knowledge-center/production/handbook/{handbookId}` 和认证会话属于跨模块能力，不能只按一级导航统计。

## 4. 测试分层原则

### L0：模块可达性门禁

每个一级模块至少有一条浏览器门禁，验证正确角色可进入、错误角色不能越权、深链或刷新不丢失上下文、无数据时不伪造业务事实。

### L1：关键用户旅程

只有会跨页面、跨服务、写入数据库或包含不可逆状态转换的路径才进入真实 E2E：

- 上传资料并完成批次。
- 创建增量任务并进入审核/发布。
- 维护人员、团队或权限。
- 创建/编辑模板并刷新回读版本。
- 发起评审、提交意见、审核和发布。

### L2：专项门禁

性能、浏览器兼容、响应式和外部系统降级按风险选择，不要求每个模块复制四个视口、两个浏览器的完整流程。

以下内容优先使用单元或契约测试：纯字段投影、固定错误码、每一种 503 组合、HTML 文案、公共组件所有尺寸排列和只验证请求体的场景。

## 5. 用例使用场景与看护内容

| 用例/模块 | 使用场景 | 看护内容 | 预期效果 |
|---|---|---|---|
| 认证 | 管理员登录、错误密码、匿名访问 | Cookie、登录恢复、会话不落 Web Storage | 登录失败可恢复，越权不进入业务页 |
| 知识资产 | 管理员维护手册、普通用户只读 | 列表、详情、映射、停用、权限投影 | 资产状态与后端事实一致 |
| 资料清洗 | 上传资料并继续加工 | 分块、完成、取消、预览错误、权限 | 真实文件写入链路可闭环 |
| 大纲管理 | 编辑目录和分工 | 深链、目录操作、团队关系、关键响应式 | 目录治理不因重绘或空值中断 |
| 模板管理 | 模板管理员新建/编辑/刷新 | 表单保存、版本号、正文回读、权限 | 模板版本持久化且无假成功 |
| 文档生产 | 编辑手册正文或创建增量任务 | 模板选择、页面草稿、任务阶段和恢复 | 生产状态可继续处理 |
| 审核与发布 | 审核员处理候选内容 | 阅读、差异、行级意见、权限和发布门禁 | 发布前置条件被真实执行 |
| 平台管理 | 管理人员、团队、GitLab | 角色、名册、OAuth、连接验证 | 平台治理操作可审计、可恢复 |
| 工作台（阶段二） | 从风险/任务卡续办业务 | 真实任务投影、上下文传递、返回恢复 | 仅在该业务实现后加入 E2E |

## 6. 当前用例布局

现有 E2E 文件按资源分为只读/Mock、真实写入和性能门禁。真实写入用例必须使用统一入口提供的 `test_hy` 隔离实例；只读用例可以对不可控外部系统做局部 Mock，但不得用 Mock 伪造成功写入。

新增模板主路径用例：

- `tests/e2e/agent-runner/knowledge-center-template-management.spec.js`
- 管理员进入模板管理。
- 新建唯一名称的 Markdown 模板。
- 保存后验证成功消息、模板列表和版本 `v1`。
- 刷新页面并验证正文仍可回读。
- 结束时将模板停用，避免后续运行把测试模板当作业务模板。

## 7. 环境与数据隔离

统一入口负责复制 `pf_knowledge` 到 `test_hy`、执行当前迁移、启动带 `testRunId` 的隔离实例并在 finally 回收。写入用例必须：

1. 使用唯一名称或幂等键。
2. 不修改 `pf_knowledge`。
3. 共享角色或名册变更前保存原值，结束后恢复。
4. 失败时保留报告和日志，不通过全局 stop 清理其他服务。

## 8. 预期效果

- 8 个一级模块均有可追踪的最小浏览器门禁。
- 关键跨服务业务有真实闭环，不把页面 Mock 当成后端验收。
- 重复布局、字段和错误组合下沉到更快的测试层，降低 E2E 运行时间和抖动。
- 模板管理从“只有性能门禁”提升到真实创建、保存和刷新回读。
- 工作台不提前引入未实现的业务假设；待续办能力落地后再增加阶段二 E2E。

## 9. 验收指标

- 新增模板 E2E 在 Chromium 下通过，失败时返回非零退出码。
- `full --dry-run` 能发现新文件并将其归入 `database-write` 通道。
- 入口单元测试覆盖资源归类和命令参数。
- 真实 full 测试中，模板创建后最终状态为停用或由测试夹具清理，不污染生产 Schema。

## 1. 目标与主要场景

本设计为 M08 建立统一授权基线，回答“谁在什么资源范围内、基于什么责任、可以执行什么动作，以及哪些运行时条件仍需满足”。它服务于以下场景：

- 同一用户兼任文档撰写人、手册责任人、手册大纲责任人、模板责任人或文档审核责任人。
- 业务责任只在指定空间、手册、大纲、模板、文档或审核实例内生效，不能因角色名称扩大为全局权限。
- 前端按授权结果展示入口，后端对每个读写请求重新鉴权。
- 审核人可以参与本人提交内容的审核，但本人不能成为该内容唯一的有效通过者。
- 权限、责任、资源状态或审核策略变化后，能够立即拒绝新请求并保留审计证据。

## 2. 非目标与实施边界

- 本文不设计 CAS 票据、会话和单点退出，认证边界见《知识中心-认证-CAS登录与会话-概要设计文档》。
- 本文不冻结数据库表、接口传输协议、缓存中间件和策略引擎选型。
- 本文不把五类业务角色设计为互斥岗位，也不要求每类角色对应独立账号。
- 本文不授予平台管理员默认读取全部敏感正文的能力；技术管理与业务数据访问分开授权。
- 当前仅形成概要设计和后续详细设计输入，不表示完整资源授权、多人审核和权限失效机制已经实现。

## 3. 第一性原理

权限系统的目的不是维护角色标签，而是控制业务动作产生的影响。一次授权判断必须同时回答五个问题：

```text
主体是谁
× 在哪一个资源范围
× 承担什么有效责任
× 请求什么动作
× 当前状态和业务条件是否允许
= 允许 / 拒绝 / 需要补充条件
```

因此采用五层模型：

```text
Principal（主体）
  → Role（业务角色能力包）
  → Scope（资源范围）
  → ResponsibilityAssignment（责任绑定）
  → Action + Condition（动作与运行时条件）
```

授权公式为：

```text
decision = ExplicitDeny
        ∨ ResourceStateDeny
        ∨ !(IdentityValid ∧ RoleAllows ∧ ScopeMatches ∧ AssignmentValid ∧ ConditionSatisfied)
```

解释如下：允许权限可由一个用户的多个有效角色取并集；显式拒绝、资源冻结/归档、职责分离和审核门禁优先于允许。角色只说明“可能具备什么能力”，责任绑定说明“对哪个具体对象承担责任”，运行时条件决定“这一次能否执行”。

## 4. 核心概念与资源层级

| 概念 | 含义 | 不应混同 |
|---|---|---|
| 主体 | 平台用户、用户组或服务主体 | CAS 身份本身不等于业务权限 |
| 业务角色 | 一组稳定动作能力 | 不等于全局职务或资源所有权 |
| 资源范围 | 授权可生效的企业、部门、空间、手册或具体对象 | 不等于前端菜单范围 |
| 责任绑定 | 主体对具体手册、大纲、模板、文档或审核实例的责任关系 | 不等于永久角色 |
| 策略条件 | 状态、审核级次、内容归属、有效期等运行时约束 | 不应散落在页面代码中 |

资源继承主链为：

```text
企业 → 部门 → 知识空间 → 手册 → 文档 → 章节/版本
                           ├→ 大纲 → 大纲版本
                           ├→ 模板引用
                           └→ 审核实例 → 审核级次/决定
```

模板可跨手册共享，因此模板正文权限按模板自身范围判断；手册责任人对模板的“选择/绑定”权限不自动产生“修改模板正文”权限。审核实例绑定固定候选版本和流程版本，不从后来变更的空间策略动态替换规则。

## 5. 五类业务角色

| 业务角色 | 默认职责 | 典型允许动作 | 必须匹配的范围 | 明确禁止或不自动获得 |
|---|---|---|---|---|
| 文档撰写人 | 编写、生成和修订被分配内容 | 读取来源快照、编辑草稿、处理评论、提交候选 | 被分配的文档/章节及其必要只读上下文 | 不自动修改大纲、共享模板、审核策略或发布正式版本 |
| 手册责任人 | 对整本手册交付、责任分工和生产批次负责 | 维护责任绑定、创建生产批次、确认来源与候选范围、查看全局进展 | 负责的手册 | 不自动修改共享模板正文，不绕过审核发布 |
| 手册大纲责任人 | 对手册结构及其演进负责 | 创建大纲候选、调整章节、分析影响、提交/发布大纲版本 | 负责的手册及大纲 | 不静默删除已发布内容对应节点，不直接改正式文档正文 |
| 模板责任人 | 对模板结构、规则和版本负责 | 创建模板版本、维护槽位与规则、提交/发布或停用模板 | 被绑定的模板或模板集合 | 不因模板被某手册引用而获得该手册正文权限；不覆盖历史版本 |
| 文档审核责任人 | 对固定候选版本作出审核决定 | 阅读候选和证据、评论、通过、退回或拒绝 | 被分配的审核实例、级次和资源范围 | 不无痕改写候选，不单独使本人提交的内容通过，不自动发布 |

角色允许一人多任。平台管理员、空间管理员、发布者、阅读者和审计人员仍作为平台治理或通用角色存在，但不替代上述业务责任角色。

## 6. 多角色合并与冲突规则

1. 同一用户可拥有多个角色和多条责任绑定，正向动作权限在有效范围内取并集。
2. 资源状态门禁、显式拒绝、审核流程条件和不可变版本规则优先，不因叠加更多角色而绕过。
3. 权限沿资源层级继承时采用“默认继承、显式缩小、拒绝优先”；跨空间共享必须显式授权。
4. 责任绑定必须包含作用对象、责任类型、有效期、来源和状态；撤销后仅影响新请求，历史行为保留原策略版本。
5. 一个动作同时需要多种责任时必须全部满足。例如发布既需要发布权限，也需要候选完成审核和质量门禁。
6. 角色变化不能修改已经形成的审核决定；但失效用户不能继续对未完成级次作出新决定。

## 7. 自审与多人审核约束

自审不是一律禁止，但审核通过必须保留独立判断。最低不变量为：

```text
若候选提交人参与了有效通过决定，
则该候选最终通过前，至少还需要一个 userId != submitterId 的有效审核通过决定。
```

该约束按候选版本判断，不只比较角色名；同一自然人拥有多个角色仍视为同一审核人。空间可以配置更严格的审核级数、人数、指定审核组或全票规则，但不能配置为“提交人一票即可通过”。候选正文摘要变化、审核人权限失效或决定被撤销时，系统重新计算有效通过条件。

建议的确定性判断伪代码：

```text
evaluateReviewGate(reviewInstance):
  assert reviewInstance.candidateDigest 未变化
  assert reviewInstance.workflowVersion 已冻结
  validApprovals = 过滤(决定有效 && 审核人当时有权 && 级次匹配)
  if validApprovals 包含 submitterId:
      require 存在 approval.reviewerId != submitterId
  require 每个审核级次满足其版本化通过策略
  return pass 或 unmetConditions
```

## 8. 授权判断契约

逻辑输入：

| 字段 | 说明 |
|---|---|
| `principalId` | 平台稳定用户或服务主体 ID |
| `action` | 规范化动作，如 `document.edit`、`review.decide` |
| `resourceType/resourceId` | 目标资源稳定身份 |
| `context` | 空间、手册、版本、状态、提交人、审核实例等最小上下文 |
| `requestId` | 链路和审计关联 ID |

逻辑输出：

| 字段 | 说明 |
|---|---|
| `decision` | `allow`、`deny` 或 `conditional` |
| `reasonCode` | 稳定原因码，不返回敏感策略内容 |
| `policyVersion` | 本次判断使用的策略版本 |
| `matchedAssignments` | 命中的责任绑定引用 |
| `unmetConditions` | 尚未满足的审核、状态或职责分离条件 |

后端处理伪代码：

```text
authorize(request):
  principal = 验证平台会话并取得稳定主体
  resource = 读取目标资源及其当前状态
  policies = 读取适用的版本化策略和责任绑定
  decision = 计算主体、动作、范围、责任、状态和条件
  记录允许或拒绝的必要审计摘要
  拒绝时不执行任何业务写入；允许时与业务并发版本一并校验
```

## 9. 前后端和模块边界

- 前端读取 `visibleModules`、`allowedActions` 和条件提示，用于隐藏、禁用和解释；前端结果不是授权事实。
- M01-M07、M09-M12 在读取受限投影或执行写操作前，均使用资源和动作调用 M08；禁止按中文角色名自行判断。
- M07 拥有审核流程与决定事实，M08 判断审核人是否有权；最终审核门禁由 M07 使用冻结流程版本和 M08 授权证据共同计算。
- M10 的列表、数量、搜索摘要和关系投影必须先过滤权限，不能只保护正文接口。
- M09 审计记录主体、资源、动作、结果、原因码、策略版本和关联业务事件，不记录令牌、密码或不必要正文。
- 权限缓存只能按主体、资源、动作和策略版本建立；策略或责任变更应使相关缓存失效，失效不确定时默认重新判断。

## 10. 配置、审计与失败处理

角色动作映射、继承规则、审核策略和例外规则必须版本化保存，不在前端或业务服务中硬编码。系统至少记录授权变更、责任绑定变更、审核分配、审核决定、发布尝试和拒绝原因。

| 异常 | 处理原则 |
|---|---|
| 身份、资源或策略事实缺失 | 默认拒绝，不猜测补齐 |
| 多条允许与拒绝冲突 | 拒绝优先，返回稳定原因码 |
| 资源已冻结/归档 | 禁止修改；按策略保留只读 |
| 权限在编辑期间被撤销 | 后续保存重新鉴权并拒绝，不覆盖现有事实 |
| 审核提交人与审核人相同 | 允许记录决定，但标记仍缺少非提交人有效通过 |
| 候选内容发生变化 | 原审核失效，新候选重新审核 |

## 11. 验收标准

1. 一个用户可以同时绑定多个业务角色，并只在各自资源范围内获得权限。
2. 手册责任人可绑定模板但不能因此修改无责任绑定的共享模板正文。
3. 未授权资产的标题、摘要、数量、搜索结果和关系均不可见。
4. 前端篡改角色或按钮状态不能绕过后端鉴权。
5. 提交人参与本人候选审核时，缺少其他人有效通过则候选不能进入待发布。
6. 两名不同用户满足冻结的审核策略后可以通过；候选摘要变化后原决定失效。
7. 权限和责任撤销影响后续请求，历史版本和审核证据仍可追溯到当时策略版本。
8. 所有规则均来自版本化配置或业务事实，不依赖散落的角色名判断和固定人数常量。

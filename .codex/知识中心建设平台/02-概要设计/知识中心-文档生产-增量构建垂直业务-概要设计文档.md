## 1. 目标与主要场景

本设计定义官方手册已有发布基线后，如何围绕需求或代码变更修订指定章节、增加或调整章节，并经过审核、验证和发布形成新版本。它解决：

- 目标由人从已验收的 PingCode 只读入口选择具体文档内容，或上传 Markdown 文件，并固化不可变来源快照；两类来源均属于 MVP 正式入口。
- 作者对官方手册指定章节执行新增、删除、修改、移动或章节内内容增删改。
- 变更始终形成新草稿和候选版本，不覆盖已发布基线。
- GitLab/CI 不属于本次 MVP 完成条件；平台发布后即完成 MVP，外部交付不进入本阶段状态机。
- 未来由 PingCode 与 GitLab 证据自动形成变更候选，辅助或替代人工检索，但不替代人工范围确认、审核和发布。

## 2. 核心判断与非目标

增量构建不是“让模型直接改官方文档”，而是建立从变化证据到可审阅补丁的受控转换：

```text
变化证据 → 人工确认影响范围 → 可比较变更集 → 候选版本
→ 按文档审核 → 确定性验证 → 新发布版本集合
```

本阶段不实现或不假定：

- 不自动发现 PingCode/GitLab 变化并直接确定影响章节。
- 不自动修改正式发布版本、自动通过审核或自动发布。
- 不把 GitLab 受控模拟结果描述为真实分支、提交、MR 或 CI 成功。
- 不要求当前平台与 GitLab 发布形成一个分布式事务。
- 不在本设计中冻结具体 CI 工具、API URL 或 DTO；MR 按目标分支拆分和手册内容映射边界由关联概要设计统一冻结。

## 3. 能力分层

### 3.1 MVP 目标闭环

```text
人工选择 PingCode 文档内容或上传 Markdown 文件
→ 完整预览并固化来源快照
→ 选择一个任务内的多个官方手册文档、目标章节和变更类型
→ 创建变更草稿并人工编辑或调用已批准生成方案
→ 查看差异、引用和影响检查
→ 固化各文档候选版本并按文档审核
→ 所有文档通过后平台内整体原子发布新版本集合
```

这是 MVP 的目标业务闭环，不等于仓库当前已全部实现。闭环的完成不依赖 GitLab/CI；平台发布成功即达到 MVP 完成终点。外部交付如后续需要，作为独立状态和能力扩展，不得改变平台版本已发布事实。

### 3.2 目标闭环

```text
PingCode 需求/变更 + GitLab 提交/MR 证据
→ 自动形成带证据和置信度的变更候选
→ 人工确认影响章节和变更范围
→ 平台编写/生成或上传本地变更，并完成差异与审核
→ 按目标业务分支创建工作分支、提交和 MR
→ GitLab CI 执行构建、格式、链接和内容检查
→ 人工在 GitLab 合入
→ 发布官方文档
→ 回写平台的外部任务状态和证据
```

目标闭环需要真实连接器、凭证隔离、目标映射、幂等、失败恢复和端到端专项验收后才能启用。

| 目标范围 | 手册、大纲版本、文档和章节集合 | 必须人工确认 | M05 |
| 变更集 | 对基线执行的结构和正文操作 | 可比较、可重放、可撤销 | M05 |
| 工作草稿 | 可编辑的增量产物 | 不等于正式版本 | M05 |
| 候选版本 | 提交审核的冻结内容 | 绑定摘要、基线、快照和变更集 | M06 |

## 5. MVP 目标主流程

| 步骤 | 操作者与动作 | 系统结果 | 失败边界 |
|---|---|---|---|
| 1. 建立任务 | 手册责任人选择手册和增量模式 | 任务绑定多个目标文档及其当前发布基线 | 无已发布基线的目标文档不能加入任务 |
| 2. 选择材料 | 作者选择 PingCode 页面或上传 Markdown，可为多个目标文档提供共同或分别的来源 | 保存来源选择，不自动扩大范围 | 无权限或来源不可用时明确失败；不能生成空快照 |
| 3. 固化证据 | 作者完整预览后确认 | 生成不可变来源快照 | 抓取失败不得生成假快照 |
| 4. 确认范围 | 作者选择文档/章节及变更类型 | 形成目标范围版本 | 系统推荐只能提示，不能代替确认 |
| 5. 生成草稿 | 人工编辑或调用冻结生成方案 | 形成相对基线的变更集 | 模型不得引入无来源事实 |
| 6. 差异检查 | 作者查看结构、正文、引用和范围差异 | 形成检查报告及警告/阻断项 | 阻断项未处理不能提交 |
| 7. 提交候选 | 文档撰写人提交，手册责任人按策略确认范围 | 固化候选版本和摘要 | 基线冲突返回重放/合并选择 |
| 8. 审核 | 被分配审核人按文档评论、退回、拒绝或通过 | 每个文档形成独立审核决定 | 是否允许同一人承担多个角色由权限和审核策略控制 |
| 9. 平台发布 | 有权发布者确认全部文档审核通过后执行批量发布 | 形成整体原子的新版本集合 | 任一文档发布失败，所有文档保持原当前版本 |

## 6. MVP 目标状态机

```mermaid
stateDiagram-v2
    [*] --> 待选来源
    待选来源 --> 待确认范围: 来源快照已固化
    待确认范围 --> 编辑中: 基线与目标范围已确认
    编辑中 --> 待提交: 差异检查完成
    待提交 --> 审核中: 候选版本已冻结
    审核中 --> 编辑中: 退回后创建新草稿
    审核中 --> 已拒绝: 拒绝
    审核中 --> 待发布: 所有文档审核门禁满足
    编辑中 --> 无有效变化: 检查结果没有可发布变更
    待发布 --> 平台已发布: 批量发布全部成功
    待发布 --> 批量发布失败: 任一文档发布失败
    批量发布失败 --> 待发布: 修复后整体重试
    ```

平台发布后即达到 MVP 完成终点；GitLab、MR 和外部文档仓库交付不属于本阶段状态机，不得为了流程完整创建虚假外部任务。

## 7. 变更生成和冲突处理

变更必须面向稳定章节 ID，而不是只依赖标题或行号。执行前同时冻结 `baselineVersionId`、`baselineDigest`、`outlineVersionId`、`sourceSnapshotIds`、`targetScopeVersion` 和生成方案版本。

伪代码：

```text
createIncrementalCandidate(command):
  鉴权(document.edit, command.targetScope)
  校验每个目标文档的发布基线摘要、来源快照和目标范围仍有效
  依据变更类型为每个目标文档生成可比较 patch，不直接覆盖发布版
  执行结构、引用、事实来源和格式检查
  若任一目标文档当前基线 != command.baselineVersionId:
      返回 baseline_conflict 及对应文档三方差异，不自动覆盖
  若全部文档没有有效变更:
      返回 no_change，不创建审核候选
  固化各文档候选正文、patch、摘要和完整追溯引用

publishBatch(batch):
  校验所有目标文档候选、审核、权限和基线仍有效
  在同一事务中切换全部文档的当前版本
  任一文档失败则整体回滚，不留下部分生效版本
```

重复提交使用由任务、基线、目标范围和客户端请求组成的幂等键。相同幂等键返回原结果；相同目标出现不同基线时进入冲突，不按最后写入覆盖。

## 8. 审核、CI 与发布边界

- 候选提交后正文冻结；修改必须形成新草稿和新候选。
- 审核规则使用提交时冻结的流程版本；允许一人多角色，是否允许提交者审核以及是否需要其他人通过，由审核策略和权限配置决定。
- 当前阶段的确定性检查可在平台内运行，但只有实际执行并保存日志、版本和结果的检查才可标记成功。
- GitLab/CI 和外部文档仓库交付不属于 MVP 完成条件；如后续启用外部交付，必须独立记录执行人、执行时间、目标引用、结果和证据链接/摘要，不能改写平台发布事实。
- 目标阶段 GitLab 分支/MR 与 CI 是异步外部交付链。外部失败不回滚已合法发布的平台版本，但阻止端到端交付状态变为完成。
- 一个 PingCode SR/任务可以产生多个 MR；不同目标分支必须拆分，同一分支默认一个并允许用户在提交前继续拆分。
- 目标阶段采用用户 OAuth 权限，不把 CAS 登录当作外部 API 授权；知识中心不自动合并 MR。
- 目标阶段启用前必须批准目标映射、OAuth 最小权限、凭证托管、正式 HTTPS、日志脱敏、重试上限、人工接管和回退方案。

## 9. 权限检查点

| 检查点 | 所需责任/动作 |
|---|---|
| 创建手册增量任务 | 手册范围内的责任绑定与 `incremental.create` |
| 选择并固化 PingCode 来源 | 来源读取权限、文档编辑责任与 `source.snapshot` |
| 修改目标章节 | 目标文档/章节的撰写责任与 `document.edit` |
| 调整大纲结构 | 手册大纲责任与 `outline.edit`，不能由正文编辑权限替代 |
| 提交候选 | `document.submit` 且差异门禁满足 |
| 作出审核决定 | 审核实例分配、资源范围与 `review.decide` |
| 发布平台版本 | `release.publish` 且全部审核/质量条件满足 |
| 登记外部证据 | `delivery.record`，不能修改平台发布事实 |
| 目标阶段执行 GitLab/CI | 已验收连接能力、目标映射和服务主体权限 |

## 10. 自动变更候选待办

**状态：待论证、待设计、未实现。** 该能力的目标是辅助或替换人工检索材料，不是替代人工决定。

建议待办定义：

| 项目 | 内容 |
|---|---|
| 输入 | PingCode 需求/变更快照、GitLab 提交/MR 快照、官方文档发布基线和稳定章节索引 |
| 输出 | 候选影响章节、建议变更类型、证据引用、差异摘要、置信度和未知项 |
| 人工门禁 | 人工确认采用/拒绝候选、影响章节、来源范围和修改意图后，才能创建草稿 |
| 禁止动作 | 不直接改正式文档，不自主扩大来源，不作审核决定，不触发发布 |
| 完成标准 | 在真实历史样本上评估召回、误报、证据可追溯和人工节省时间；失败时可完整回退人工选择 |

在准确率、漏检代价和责任归属没有真实样本证据前，不设自动通过阈值，也不把置信度当作业务正确性。

## 11. 审计与可观测性

每次增量构建应可反查：操作者和责任绑定、发布基线、人工选择的具体来源、来源捕获方式与快照、目标范围、变更集、生成方案、检查结果、候选摘要、审核流程/决定、平台发布记录和实际存在的外部证据。

运行指标至少区分：来源抓取失败、基线冲突、审核退回、平台发布失败、外部交付失败和人工接管；不能合并成一个“任务失败”。日志和 DTO 不保存或返回外部令牌、密码及不必要的完整敏感正文。

## 12. 验收标准

### 12.1 MVP 目标验收

1. PingCode 只读连接器和 Markdown 上传入口均可用，用户可选择具体来源，完整预览并固化不可变快照；来源不可用时不得生成空快照或伪造成功。
2. 一个增量任务可以绑定多个已发布文档基线，能对各文档指定章节执行新增、删除、修改和移动并展示差异影响。
3. 生成或编辑只形成草稿/候选，不覆盖已发布版本；基线变化时阻止静默覆盖。
4. 候选绑定来源、目标范围、变更集和内容摘要，退回修改后形成新候选。
5. 各文档按权限和审核策略形成审核决定；任务内全部文档满足门禁后才能进入批量发布。
6. 批量发布整体成功或整体失败，不能留下部分文档已切换、部分文档未切换的状态。
7. 平台发布即达到 MVP 完成；GitLab/CI 外部交付不改变平台发布状态。
8. 失败可重试或人工接管，重复请求不生成重复快照、候选或发布记录。

### 12.2 目标阶段启用门禁

1. PingCode/GitLab 自动候选经过历史样本评测，输出证据、置信度和未知项，并保留人工确认。
2. 真实 GitLab 连接器在隔离环境完成权限、幂等、冲突、限流、凭证和日志脱敏验收。
3. CI 结果绑定提交和配置版本，失败不能被平台重试逻辑伪造为成功。
4. 从候选发现到官方发布和状态回写完成端到端验收，且可回退到当前人工选择和人工衔接路径。

## 12A. 手册级文档生成页面边界

每本手册由一个独立的文档生成页面承载人工编辑入口。页面只负责当前手册的目录、当前文档正文草稿、文档参考来源和评审批次选择，不拥有审核决定或发布事实。

```mermaid
flowchart LR
    A[手册与大纲] --> B[手册级文档生成页面]
    B --> C[当前文档草稿]
    B --> D[当前文档参考来源]
    B --> E[多文档评审批次]
    E --> F[审核与发布模块]
    F --> G[不可变发布版本集合]
```

页面边界规则：

- 左侧目录支持全量文档和只看当前用户负责文档；
- 右侧一次编辑一个文档；
- 参考来源绑定当前文档草稿；
- 多个文档可进入同一提交批次，但审核对象仍按文档拆分；
- 页面通过业务契约读取责任人、版本、草稿和能力声明，不自行推断；
- 具体页面布局和交互以 `../03-详细设计/知识中心-文档生产-手册级文档生成页面-前端详细设计文档.md` 为准。

## 13. 后续优化顺序

1. 先详细设计当前人工选择 PingCode 内容、来源快照、目标范围和变更集接口。
2. 再冻结候选版本、多人审核、平台发布与人工外部证据登记契约。
3. 使用真实增量修订样例完成垂直薄切和失败恢复验证。
4. 收集人工选材数据后论证自动变更候选，避免先建模型后寻找问题。
5. 最后在 OAuth、HTTPS、专项审批和隔离仓库验收后接入真实 GitLab/MR/CI，不与当前闭环绑定上线。

当前实现盘点、完成度评分和实施任务统一维护在 [知识中心-文档生产-增量构建MVP完成度评估-进展报告文档](../08-进度与报告/知识中心-文档生产-增量构建MVP完成度评估-进展报告文档.md)，概要设计不重复保存动态进度。

## 14. MVP 退出门禁

以下条件全部满足时，才能将增量文档构建标记为“MVP 已完成”：

1. 基线、大纲、文档、section 和发布版本来自正式事实源，不再依赖增量状态内部的合成注册表。
2. 用户不需要手工输入文档 ID、节点 ID 或 `beforeDigest` 才能完成正常修订。
3. 角色兼任和审核决定严格按权限与审核策略执行，候选变化会使旧审核决定失效。
4. 发布前服务端能同时校验基线、候选、审核、阻断意见、确定性检查和发布权限。
5. 发布形成正式不可变文档版本，多文档批次不会留下部分生效状态。
6. 一个真实样例在 YashanDB 主写模式下通过创建、取源、编辑、检查、审核、退回、重提、发布和追溯验收。
7. 相关 API、前端、E2E、并发、故障恢复和权限回归全部通过，并产生可引用的测试报告。

## 15. 下一步实施顺序

当前产品决策已经足以冻结本概要设计的业务边界，但还不应直接并行开发完整 MVP。后续按以下顺序推进：

1. **概要设计收口**：确认多文档任务、按文档审核、批量原子发布、角色兼任和 MVP 外部交付边界；将本章仍标记为“待冻结”的规则形成评审结论。
2. **详细设计**：把已确认的业务规则落成状态机、对象模型、接口契约、权限矩阵、幂等键、并发控制、批量发布事务和失败接管规则。
3. **M0 核心契约准备**：冻结资料清洗、文档生成器和知识中心之间的来源快照、生成运行、草稿、变更集、审核和发布契约，并先完成契约测试。
4. **M1 垂直闭环开发**：在同一条真实链路中同时接入 Markdown 与 PingCode，支持多个目标文档，完成生成、按文档审核和批量原子发布的最小可验收闭环。
5. **再扩展治理与体验**：在 M1 真实样例稳定后，补齐持久会话、反馈修订、血缘查询、恢复和效果指标，不以模拟状态替代真实验收。

底层逻辑是：需求回答“用户要达成什么结果”，概要设计回答“模块如何分工、业务事实如何组织”，详细设计回答“状态、接口、权限和事务如何实现”，M0 则把跨模块语言冻结为可测试契约。只有完成这四层递进，AI 协作编程任务才具备单一目标、有限上下文、明确验收和可回退边界。

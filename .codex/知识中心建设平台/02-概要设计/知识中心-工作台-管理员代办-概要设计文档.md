# 工作台管理员代办概要设计

日期：2026-11-05
状态：核心代办链路已在工作树实施；共享平台与完整业务联合验收待完成

## 1. 目标与决定

管理员在工作台选择责任人后，能查看并处理其任务，不再停留在“本地预览 · 只读”。用户已确认管理员可以代为作出**全部平台业务决定**，包括范围确认、文档处理、审核通过、发布/交付决定。实际操作人始终是登录管理员，任务归属人始终是原责任人；绝不通过改写浏览器会话或伪造目标人员身份实现代办。企业 GitLab 合并仍需管理员自己的有效企业授权，平台不能替代 GitLab 授权或自动合并。

原先“管理员仅看本人分派事项”和本地只读预览口径，由本次明确要求取代。现有普通用户的“我的工作”仍仅展示本人事项。

## 2. 当前事实与问题

| 环节 | 当前实现 | 缺口 |
| --- | --- | --- |
| 责任人切换 | 仅在 `KNOWLEDGE_CENTER_LOCAL_OWNER_PREVIEW=1` 且有 `platform:manage` 时提供，调用 `/workbench/preview` | 正式部署不可用，返回 `readOnly: true` |
| 他人事项 | 预览接口临时构造目标会话做只读投影 | 浏览器行只有“只读预览”，审核与大纲可能是部分数据 |
| 工单改派 | 管理员已可改派工单、手册和文档责任人及计划时间 | 范围确认接口 `owns()` 只允许原责任人，管理员代办不可用 |
| 写作/审核/交付 | 各来源按当前会话和业务角色再次授权 | 深链直接打开不会变成“代办”，单改工作台按钮会被拒绝或造成错误归属 |
| 审计 | 工单已有 `operatorId` 和变更历史 | 跨来源缺统一的“管理员代谁处理何事”标记及回读展示 |

截图中的 528 项是部分数据，且是单一人员一次预览结果，不能作为完整工作量或所有来源的已验证容量。

## 3. 推荐方案：具名管理员代办

保留当前工作台五类任务、任务管理与来源模块。新增正式的“查看并处理某责任人工作”上下文，由服务端按管理员权限生成操作清单和每项能力；所有写请求继续使用登录管理员会话，显式携带 `onBehalfOfPrincipalId`、目标任务和动作，服务端检查管理员身份、目标责任关系、资产可见范围、任务当前版本及动作门禁。响应和审计同时记录 `operatorId`、`responsibleId`、`delegatedByAdmin=true`、动作、时间、前后值及关联任务 ID。源模块仍是状态事实源。

### 3.1 端到端处理流程

1. **进入工作台**：普通用户只见本人工作；管理员默认也先见本人工作，并在标题区看到“查看责任人”选择控件。切换时不改变 Cookie 或登录身份。
2. **选择人员**：人员来自有效目录，按姓名/账号搜索。请求服务端正式代办投影；服务端验证管理员、目标人员有效及可见范围。显示“何阳的工作 · 管理员代办”与登录操作者姓名；“切回我的工作”始终可见。
3. **读取清单**：分派、文档编写、审核发布、大纲、模板只纳入权威动作实例。每项返回稳定 ID、来源、责任人、状态、下一步、`allowedActions`、`blockedReason`、版本和最近更新时间。来源失败显示“部分数据”和不可用来源；不可把未读任务算 0。分页/筛选在服务端进行，避免将 528 项全部绘制在页面。
4. **打开任务**：行主按钮进入任务详情抽屉，显示来源链、业务状态、原责任人、管理员身份、允许的具体动作和影响。点击“进入处理”带任务 ID 与代办上下文到来源页面；来源页再次读取服务端能力，显示同一“管理员代办”横幅。
5. **执行决定**：按原流程逐步执行。例如工单范围→手册范围→文档编写/送审→逐篇审核→创建 MR→人工合并后回读。管理员能代做业务决定，但每一步仍校验对象版本、必填字段、审核/交付门禁和资源范围；不得把所有动作合成无校验的一键完成。关键决定前确认“以管理员身份代何人处理哪项任务”，确认页显示后果。
6. **结果与回读**：写请求携带幂等键和版本；服务端提交后回读来源对象与工作台投影。成功显示“由管理员张某代何阳完成”，任务从目标人员待办中消失或进入下一阶段；失败保留输入并指出权限、冲突或外部依赖原因。点击反馈与业务完成分别计时。
7. **返回与追溯**：返回工作台保留目标人员、分类、搜索和滚动位置。责任人及管理员在任务历史中可看见代办记录；审核、MR 和正文回读沿用原证据链。切回本人工作不改变已写入的审计和责任分派。

### 3.2 权限与业务门禁

| 动作 | 普通责任人 | 管理员代办 | 必须保留的校验 |
| --- | --- | --- | --- |
| 查看目标人员事项 | 仅本人 | 授权范围内有效人员 | 资产范围交集、有效身份、来源可用性 |
| 改派与计划时间 | 现有角色规则 | 可执行 | 人员有效、版本冲突、审计 |
| 两级范围确认/不涉及完成 | 对应责任人 | 可代确认 | 两级理由、目标版本、范围完整、版本检查 |
| 编写/保存/送审 | 指派文档负责人 | 可代执行 | 文档可见、草稿版本、来源快照、审核人有效 |
| 审核决定 | 指派审核人 | 可代审核 | 逐篇审核证据、禁止自审等现行业务门禁需单独核对；不得无证据放宽 |
| 创建 MR/刷新交付 | 具备现有能力者 | 可代发起平台动作 | 冻结内容、人员映射、GitLab 自身授权及回读 |
| 合并企业 MR | 企业授权人员 | 管理员本人有 GitLab 权限时可手动合并 | 企业侧授权、人工确认、目标正文与图片回读；平台不自动合并 |

管理员可代作决定不等于可以绕过业务事实。若现有审核服务禁止同一人既编写又审核，管理员也应受此门禁约束；需要独立审核人时明确提示并转交，不暗中放宽。个人 GitLab OAuth 不可冒用原责任人的令牌。

## 4. 页面方案与状态

采用[交互效果稿](./知识中心-工作台-管理员代办-效果稿.html)的紧凑布局：工作台标题右侧选择人员；顶部显示目标人员、登录操作者和返回本人入口；列表行仅一个与任务状态匹配的主操作，详情抽屉展示业务链和可执行动作。正常状态不使用大面积提示条；只有切换身份、来源不全、权限不足或操作失败时才显示清晰提示。移动端抽屉改为全屏层，操作按钮保持可见；不使用悬停作为唯一信息来源。

状态覆盖：本人、切换加载、管理员代办、部分数据、无任务、无权/人员停用、版本冲突、操作提交中、操作成功待回读、回读失败。部分数据的总数标为“已读取 N 项”，不显示确定性总数。无权动作在来源页说明原因，不给出看似可用的按钮。

## 5. 接口、兼容与实施顺序

- 正式人员检索与代办列表：从现有 `/workbench/responsibles`、`/workbench/preview` 迁移为明确的管理接口，返回分页、来源完整性、`allowedActions` 及目标人员标识；旧本地预览保留过渡期，不能继续作为写入上下文。接口、Schema、权限变更先详细设计并按仓库审批边界复核。
- 来源写接口：仅对明确支持代办的动作增加显式代办上下文；服务端从可信会话确定 `operatorId`，不采信请求体中的操作者。兼容原本人调用；管理员上下文与任务 ID/版本绑定，拒绝跨任务重放。统一 403、409 和外部授权失败的提示。
- 首先改工单两级范围、改派和状态回读；再接文档写作、审核、发布和大纲；模板只有真实个人动作事实时才接入，不凭可编辑资产伪造待办。最后移除“只读预览”入口。
- 后端权限测试覆盖管理员、普通用户、无资产权限、停用人员、并发冲突、越权伪造、审计和完成门禁；真实浏览器覆盖本人↔他人、五类筛选、桌面/390px、失败恢复、深链回读。专用测试数据与 Draft MR 可用于隔离验收；企业人工合并和容量压测单列证据。

## 6. 90 分验收目标

这是**实施后的验收目标，而非当前功能得分**。100 分评分表：任务入口与身份语义 15、五类来源完整性与部分数据 15、端到端动作可用 25、权限及审计 20、反馈与错误恢复 10、桌面/移动/键盘 10、性能及容量证据 5。达到 90 分须前四项均不低于各自的 80%，且真实管理员跨至少两名责任人完成分派、范围确认、文档保存/送审、审核决定和 MR 状态回读；没有企业合并及内容回读证据时不得称完整交付通过。当前仅有只读预览，不能按此表评为 90 分。

本次**设计预评估 92/100**：身份语义 15/15、来源及部分数据 13/15、流程覆盖 23/25、权限与审计 19/20、反馈恢复 9/10、桌面/移动/键盘 9/10、性能容量设计 4/5。扣分对应尚无模板个人动作来源、大纲来源仍部分不可用、没有真实后端写入/合并回读与压力数据。此分只评价方案完整性与效果稿，不代表生产功能质量。

## 7. 2026-11-05 实施现状

工作树已增加正式 `/workbench/delegated`、管理员人员选择、工单两级范围代办、审核决定代办及审计字段。大纲个人分派事项在数据库来源可读时投影；模板仍缺独立个人动作契约。工单 HTTP 27 项、正式代办 HTTP 3 项、审核原生回归 1 项，以及工作台浏览器 5 项（含 390px）通过。13511 源码实例提供页面与未登录 401 检查；共享 13510 仍加载旧构建，尚无管理员真实登录后跨来源写入、企业 MR 回读或全量性能证据，因此本次不赋正式功能 90 分，也不将完整流程记为通过。

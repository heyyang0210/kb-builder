## 1. 目标与实施边界

本设计定义 YashanDB 知识资产与 GitLab 仓库 `cod-doc/yasdoc` 的内容范围映射、双语多版本阅读、协作审阅，以及由 PingCode 只读任务来源驱动 GitLab 分支、提交、MR 和 CI 的目标闭环。

本轮只冻结概要设计，不实现连接器、页面或数据表，也不调用 GitLab/PingCode 写接口。真实能力默认关闭，只有完成 OAuth、HTTPS、隔离仓库、安全和端到端专项验收后才能启用。

截至 2026-09-02 已验证的事实：

- `https://git-tools.yasdb.com/cod-doc/yasdoc` 可从当前开发环境访问，网页登录跳转企业 CAS。
- GitLab API 未授权访问返回 `401`；当前开发机依赖已有 Git 凭证读取仓库，知识中心服务尚无可用授权。
- 仓库当前有 25 个分支，既有业务版本分支，也有功能和实验分支。
- 中文内容根目录为 `doc/产品文档`，英文内容根目录为 `doc/Manuals`；两个根目录均由 `_index.md` 声明 14 组手册顺序。
- 当前资产台账有 40 本 YashanDB 手册。资产数量多于仓库顶层手册是合理事实，不要求全部映射。
- PingCode 未提供实例地址、项目、代表性 SR/任务或 API 文档，真实 OAuth 和读取字段尚未验证。

## 2. 核心业务关系

### 2.1 资产、内容范围与版本

```text
知识资产手册（稳定 handbookId）
  ├─ GitLab 内容范围（0..n 个目录/文件）
  │    ├─ 中文路径
  │    └─ 英文路径
  └─ 已启用版本（1..n 个分支）
       ├─ 默认分支
       ├─ 当前 branch HEAD
       └─ 变更任务基线 commit SHA
```

- 一本知识资产手册承载多个业务版本，不因分支不同重复创建资产。
- 映射支持目录、子目录和文件级路径；多本知识资产可以分别引用同一 GitLab 顶层手册的不同内容范围。
- 只有存在已确认映射的手册才展示仓库内容入口。未映射手册继续作为正常知识资产存在，不显示错误、缺口或虚构的 GitLab 状态。
- `_index.md`、名称和目录结构只用于生成候选。平台管理员必须确认中英文路径、启用分支和默认分支后，映射才能生效。
- 映射调整形成新配置版本；既有审阅、变更任务和 MR 继续引用创建时的映射版本。

### 2.2 分支和业务版本

分支发现规则只产生候选：

```text
master
或
^(?:br)?\d+\.\d+(?:\.\d+)*$
```

- `23.2.9`、`br23.2`、`br23.4.14` 等匹配版本规则；功能、实验和派生 `master-*` 分支不自动进入业务版本列表。
- 管理员确认后才开放候选分支，匹配规则本身不代表正式发布事实。
- 业务界面可去除版本分支的 `br` 前缀；必须同时保留真实分支名供审计和外部操作使用。
- `master` 显示为“主干（master）”，独立于业务版本，不转换成“最新版本”或某个版本号。
- 每本手册由管理员指定默认分支；用户上次选择仅作为个人界面偏好，不改变默认配置。
- 日常阅读解析分支最新 `HEAD`，通过短时缓存降低延迟和限流影响，并提供手动刷新。
- 创建变更任务时冻结 `baseCommitSha`；提交前若目标分支 `HEAD` 已变化，必须阻断提交并提供刷新差异或人工处理入口，不自动覆盖。

### 2.3 中英文关系

- 中文和英文是同一 `handbookId` 下的语言内容，不创建两本责任、状态相互独立的手册。
- 中英文分别保存路径集合，不依赖运行时翻译文件名猜测对应关系。
- 阅读页默认中文，允许切换 English；目标语言缺失时显示“该版本暂无对应语言内容”，不回退到另一语言冒充完整内容。
- `_index.md` 中的 `filename/enName` 可作为目录对应证据，但路径和文件缺失仍需在映射确认时单独检查。

## 4. 手册内容阅读工作区

知识资产列表继续承担资产发现、责任确认和阶段判断，不平铺 GitLab 分支、提交或文件路径。只有用户点击已映射手册的仓库内容入口后，进入完整阅读工作区：

```text
手册名称   业务版本/主干   中文/English   当前提交   刷新
──────────────────────────────────────────────────────
目录树与搜索          文档正文                   审阅区
章节和页面            Markdown完整渲染           批注
当前位置              图片、表格、代码和链接     修改建议
```

- 目录树按仓库层级和 `_index.md` 顺序构造；`_index.md` 是目录元数据，不作为普通正文重复展示。
- 首期完整支持仓库现存的 Markdown 和 PNG 内容。相对文档、锚点和图片引用按“仓库 + 分支当前提交 + 当前文件路径”解析。
- 无权限、分支不存在、路径缺失、内容过大、GitLab 限流和暂时不可用必须显示不同原因，不返回空白正文或旧内容冒充最新。
- 页面显示当前真实分支名、短提交 SHA 和内容获取时间；缓存命中也必须保留其对应提交。
- 手动刷新只更新阅读投影，不静默改变已创建任务、审阅锚点或候选变更的基线。

渲染视觉与现有 YashanDB 文档生成器保持一致，但不能复制其未经统一内容清理的 `innerHTML` 路径。后续详细设计必须抽取共享渲染层，至少包含 Markdown 解析、代码块、表格、提示块、链接、图片资源代理、HTML 清理和原文降级；外部仓库正文不得执行脚本或任意嵌入内容。

## 5. 协作审阅

### 5.1 能力和权限

- 获得该资产授权的 A/B 角、作者和审核者可以选择正文内容添加批注、回复和修改建议；只读成员只能查看。
- 正式分支正文始终只读。批注和建议不会直接修改 GitLab 文件，也不等于审核通过。
- A/B 角或该文档指定作者可以采纳修改建议并将其转入候选变更；其他审阅成员不能通过“解决讨论”间接修改正文。
- 审阅记录保存在知识中心。创建 MR 后只保存关联关系，不要求将既有批注同步成 GitLab Discussion。

### 5.2 锚点和版本漂移

审阅锚点至少绑定：手册、映射版本、真实分支、提交 SHA、文件路径、选中文本、前后文摘要和内容摘要。

页面重新读取分支最新内容时，系统可依据原文和上下文尝试定位，但不得静默改变锚点事实。无法唯一定位时显示“原位置已变化”，保留原提交内容查看入口，并要求人工重新定位或关闭讨论。

批注、修改建议、回复、采纳、拒绝和解决均记录操作者与时间。采纳只创建候选变更，不跳过文档生产的差异、审核和发布门禁。

## 6. PingCode 到 GitLab 的变更闭环

### 6.1 目标流程

```text
选择 PingCode SR/任务和网页文档（只读）
→ 固化来源引用/快照
→ 选择手册、语言、目标业务分支和文件范围
→ 在平台编辑/生成，或上传本地变更文件
→ 路径、基线和差异检查
→ 协作审阅与提交确认
→ 按目标分支拆分 GitLab 工作分支、提交和 MR
→ 读取 CI 和 MR 状态
→ 人工在 GitLab 合入
```

- PingCode 首期只读，不评论、不修改任务状态，也不扩大用户选定的 SR、任务或文档范围。
- 平台编辑/生成和本地文件上传是两个入口，但进入同一候选变更、路径校验、差异和审核流程。
- 一个 PingCode SR/任务可以关联多个 MR。不同目标分支必须拆分；同一分支默认合并为一个 MR，用户可在提交前继续拆分。
- 知识中心可以创建工作分支、提交和 MR，但不能自动合并。MR 合入由用户在 GitLab 完成。
- GitLab CI 与 MR 状态是外部事实；平台只读取并展示实际结果，不自行计算成功。
- 知识中心发布与 GitLab 交付相互独立。GitLab 失败不回滚已合法发布的知识版本，也不能被记录成端到端交付成功。

### 6.2 部分成功和幂等

多 MR 执行允许部分成功。每个目标分支/分组形成独立外部任务和幂等键；已经取得远端分支、提交或 MR 标识的步骤必须先查询确认，不能盲目重复创建。失败项可单独重试，成功项不得因其他项失败被删除或伪造回滚。

目标分支 `HEAD` 与任务的 `baseCommitSha` 不一致时进入需要人工处理。平台不得自动强推、自动合并或替用户选择冲突内容。

## 7. 认证、安全和事实归属

- 企业 CAS 只建立知识中心和 GitLab/PingCode 各自的用户登录，不会自动把外部 API 权限授予知识中心。
- GitLab 和 PingCode 分别采用用户 OAuth 授权。外部平台管理员需要注册 OAuth Application，外部平台继续决定用户实际可读写范围。
- 知识中心只在后端密钥存储中保存加密凭证或引用；前端、Skill、提示词、日志和业务 DTO 不得出现令牌、CAS 票据或 OAuth Secret。
- 真实 OAuth 回调使用正式 HTTPS 域名。`http://192.168.130.180:13510` 只作为局域网开发入口，不作为生产回调地址。
- 浏览器不直连外部 API；仓库读取、资源代理、分支、提交、MR 和状态查询均通过受控连接器。
- GitLab 写入必须使用当前操作者的有效授权并再次经过知识中心资源权限校验。知识中心不创建 GitLab 权限，也不把平台角色转换成外部仓库权限。
- Skill 可以分析已经授权和固化的内容，不能读取 OAuth 凭证、选择目标仓库、创建分支/MR 或合并代码。

## 8. 模块职责和逻辑契约

| 事实或动作 | 负责模块 | 关键边界 |
|---|---|---|
| 手册基础资料和责任人 | 知识资产 | 不复制 GitLab 文件正文 |
| 手册与仓库路径/分支映射配置 | 集成管理 | 管理员确认、版本化，不从名称自动生效 |
| 分支内容树、正文和资源读取 | 来源管理与连接器 | 返回提交 SHA、完整性和缓存事实 |
| 批注和修改建议 | 审核与发布/协作审阅 | 绑定固定提交，不修改正式正文 |
| 候选正文、上传文件和变更集 | 文档生产 | 不覆盖分支或平台发布版本 |
| GitLab 分支、提交、MR 和 CI 查询 | 连接器与长任务 | 异步、幂等、允许部分成功 |
| 平台发布 | 审核与发布 | 与 GitLab 交付状态分离 |

概要设计冻结以下逻辑对象，具体 API URL、DTO 和 YashanDB 表结构在详细设计评审后确定：

```text
手册仓库映射
已启用分支与默认分支
双语内容路径
分支内容树与正文投影
审阅批注与修改建议
PingCode 来源引用
变更任务与基线提交
GitLab 交付任务与 MR/CI 结果
```

## 9. 分期和启用门禁

### 9.1 设计与只读验证

1. 管理员完成 40 本资产的中英文路径和正式分支确认。
2. 冻结 GitLab/PingCode OAuth、内容读取、缓存、渲染和审阅详细契约。
3. 建立正式 HTTPS 回调地址并完成密钥存储方案评审。
4. 使用隔离连接和测试身份验证只读目录、Markdown、图片、权限不足、令牌失效和限流。

### 9.2 受控写入验证

1. 在隔离 GitLab 仓库验证基线冲突、路径穿越、分支重名、提交失败、MR 失败、重复请求和部分成功。
2. 验证 OAuth 最小权限、撤销、过期、跨用户隔离和日志脱敏。
3. 验证知识中心不具备自动合并能力，真实 CI 结果绑定远端提交。
4. 形成专项验收和启用决策后，才允许对正式 `cod-doc/yasdoc` 开放写能力。

## 10. 验收标准

- 40 本 YashanDB 资产均有可追溯的盘点结论，候选与正式启用映射严格区分。
- 分支发现只产生 `master` 和符合版本规则的候选；非版本分支不自动开放。
- 已映射手册按同一 `handbookId` 切换分支和中英文，未映射手册不显示伪缺口。
- 目录遵循 `_index.md`，Markdown、PNG、相对链接、代码和表格可以安全完整显示。
- 阅读缓存明确对应提交 SHA，手动刷新不改变任务和审阅基线。
- 批注和修改建议绑定固定提交；位置漂移时明确提示，采纳只形成候选变更。
- PingCode 保持只读；知识中心使用用户 OAuth 权限创建 GitLab 分支、提交和 MR，但不自动合并。
- 一个任务可跨版本产生多个 MR；部分失败可单独重试且不重复成功动作。
- 平台发布和 GitLab MR/CI 使用独立状态，没有远端证据不显示外部成功。
- PingCode 实例信息、OAuth 应用、HTTPS、隔离仓库和管理员映射确认均作为未完成前置条件如实跟踪。

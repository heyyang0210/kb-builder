# 任务详情弹窗三方案评审

状态：方案一已进入正式页面实现；效果稿仍使用示例数据，真实用户验证待完成。

### 正式页面实现补充（2026-11-13）

工单详情使用原生模态对话框后，详情内打开范围/改派子弹窗时，父对话框先关闭并标记为暂停；取消子弹窗会恢复父层，成功提交则重新读取任务并重建详情。子弹窗必须挂在 `document-task` 公共弹窗宿主中，不能留在已关闭父弹窗内部，否则实际可见点击区域会归零。点击返回后恢复页面列表及原触发焦点。手册文档范围在任务详情模态打开期间使用顶层子模态，不采用内联 `dialog.show()`。责任人和当前状态保留在详情头部可见区；来源与时间等低频事实可折叠，避免用户改派后还要展开才能确认接手人。

验收脚本以 `.document-task-dialog[open]` 区分子弹窗与仍保留的父层；仅子弹窗关闭不代表任务详情也关闭。真实隔离 HTTP 浏览器流程覆盖分派弹窗取消/恢复、手册范围弹窗桌面和 390px 点击目标、成功提交后的服务端回读。若完整任务管理套件在其他改派/任务完成场景失败，必须作为独立失败记录，不能由范围弹窗专项通过替代。

## 方案一实施契约（2026-11-13）

- 待分派工单从任务列表直接打开“任务分派”对话框，内容顺序为工单事实、工单范围、手册分派；不重复显示当前负责人、待确认范围等次要说明。
- 手册候选按名称或产品类型搜索。每行展示手册名称、产品类型、GitLab 目标分支映射结果和负责人，行高接近任务列表。确认按钮统一写“确认”。
- 产品类型来自知识资产的手册元数据；目标分支由服务端按手册、工单产品和业务版本解析。前端只预览，手册负责人确认文档范围时服务端重新解析并冻结映射；匹配失败显示错误，不推断分支。
- 工单责任人确认后，任务详情展示手册名称、产品类型、目标分支和文档名称。手册负责人尚未确认文档范围时，文档名称显示“待手册负责人确认”，不虚构文档事实。
- 已确认范围再次调整仍走原有影响预览与二次确认；手册负责人仍独立确定文档范围和负责人。来源、时间、审计、权限与失败恢复沿用既有契约。

## 第一性原理

把任务详情拆成不可再省略的事实：

1. 用户打开的是一张工单，必须能确认编号、摘要、责任人和当前状态。
2. 工单责任人先决定该工单是否涉及文档变更。
3. 只有“涉及”时才选择手册，并逐本指定手册负责人。
4. 手册负责人接手后，才独立确定本手册中的文档范围和文档负责人。
5. 每次确认都必须显示保存结果；取消不能静默改变范围；历史仍可追溯。

所以界面顺序应是“任务事实 → 工单范围 → 手册分派 → 确认”，而不是把“选文档”“选手册”“分派负责人”堆在同一级。工单范围回答“做不做文档工作”；手册分派回答“哪些手册交给谁”；文档范围属于下一位手册负责人的后续步骤。这个层级也与当前服务端 `ticket-scope` 和 `book-scope` 两级写入一致。

## 问题分析

**核心矛盾：** 一个局部任务处理动作被展开成全页工作区，同时工单层和手册层两个不同责任人的决定被放在一张长页面里。

| 类型 | 发现 | 影响 |
|---|---|---|
| 观察 | 截图中打开任务后占据主内容区，顶部、进度、范围、内嵌表单、待办和历史连续展开 | 用户离开任务列表上下文，主任务不易定位 |
| 观察 | 截图标题为“确定本手册涉及的文档”，但页面内又有工单范围与手册选择 | 标题指向手册层，操作同时涉及工单层，边界不清 |
| 观察 | 工单范围/分派与每本手册文档范围是两级独立确认 | 把两层压成一个动作会让责任人和确认后果变得含糊 |
| 推断 | 页面冗长和重复状态使用户难以分辨当前应完成的那一次交接 | 增加误分派或遗漏确认的可能；需通过用户任务测试验证 |

## 三种方案

### 方案一：单屏分层弹窗（推荐）

在同一弹窗内按固定顺序展示工单事实、工单范围、手册分派。选择“不涉及”时隐藏手册选择并要求填写原因；选择“涉及”时展开候选手册、勾选和负责人。底部固定一个“确认并分派 N 本手册”主操作。来源与历史折叠。

优点：两级关系同时可见；少量手册时一次完成；符合当前一次提交工单范围与手册负责人的接口。缺点：手册较多时弹窗需要滚动；搜索、筛选和大量候选需要加强。

适用：候选手册通常不多、责任人需要快速核对整体分派。代价：低至中；主要是把现有任务详情与工单范围组织进 dialog，并保留手册负责人后续独立处理。

### 方案二：两步确认弹窗

第 1 步只确认工单是否涉及文档；第 2 步选择手册并指定负责人。进度、上一步和取消始终可见。只有最终确认才提交，或在现有服务端契约明确后拆分保存。

优点：单屏信息最少，步骤边界鲜明；“确定范围在上、分派在下”表达直接。缺点：多一次操作；用户不容易同时对照范围结论和手册名单；若第一步即写入，需要提供撤销或恢复语义。

适用：不涉及判断复杂、手册数量多，且需要逐步审核的场景。代价：中至高；必须先确定是否复用一次提交，不能为了效果稿擅自改变事务边界。

### 方案三：主从分派弹窗

弹窗顶部固定工单范围判断；下方左侧列出手册和选择状态，右侧编辑当前手册负责人及交接说明。选择不同手册时右侧切换。

优点：多本手册时浏览、比较和改派更有效；选择与详情关系明确。缺点：占用更宽空间；只有一两本手册时显得空；窄屏必须转成上下结构，容易变成长表单。

适用：候选手册经常达到 5 本以上，或需要比较多位负责人的场景。代价：中；需要维护选中项、负责人编辑和移动端重排。

## 乔布斯视角的取舍

- **删除**：打开任务后重复呈现的整页工作区标题、重复进度和长篇详情铺陈；它们不是完成当前交接的必要控件。
- **简化**：把复杂的流程总览折叠为两级范围和分派区；状态只保留当前责任人最需要知道的内容。
- **强化**：弹窗标题“任务分派”、工单范围判断、已选手册数、每本手册负责人、确认后的交接结果。
- **保留**：权限、理由、来源、审计历史、错误恢复、取消和服务端确认。视觉简洁不能删除这些治理事实。

## 选择建议

方案一作为正式实施基线。它保留当前服务端一次保存范围和分派的边界。若真实数据证明手册数常常超过 5 本，再评估方案三；方案二只有在业务要求逐步审批或需要不同保存时点时才值得增加。

窄屏将居中 dialog 变成底部 sheet / 全屏弹窗；标题和底部动作保持固定，内容区独立滚动。工单范围选项纵向排列，手册卡片逐行呈现负责人选择，不做双栏缩小。所有交互目标至少 44px，焦点可见，Esc 与取消行为一致；提交失败保留输入，未保存关闭要明确提醒。

## 验收

- 点击任务编号打开弹窗，任务列表仍在背景且关闭后恢复滚动位置和焦点。
- 标题固定为“任务分派”；“工单范围”位于“手册分派”之前。
- 选择不涉及时手册分派不显示且必须填写原因；选择涉及时可勾选手册并逐本指派负责人。
- 手册负责人后续仍独立确认文档范围；不得把工单负责人决定误显示成文档范围已确认。
- 取消、Esc、提交中、提交失败和成功状态可观察；失败保留编辑内容。
- 桌面和 390px 浏览器截图无溢出；键盘可完成整个流程；真实 API 确认原权限、版本冲突和审计行为。
- 实测打开耗时符合仓库 100ms 要求；仅凭效果稿不作性能结论。

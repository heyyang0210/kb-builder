# 代码审查与提交遵守什么规则

**适用**：审查代码、修复审查问题和本地提交时。先按[任务路由](<./知识中心-平台-Task Routing Contract v1与最小执行路径-治理规范文档.md>)确定任务范围，再按实际风险选择验证。

1. 审查先找会影响正确性、安全、性能或维护的具体问题，指出位置、触发场景和修复方向。没有可行动的问题就明确说没有。
2. 验证与改动相称：纯文档检查空白和链接；前端交互检查相关测试；后端接口和端到端行为必须调用隔离环境中的真实 API；公共契约或构建变更再执行对应完整门禁。
3. 修改过程中跑相关测试；代码稳定后跑一次最终门禁。失败时针对失败原因复测，不用重复全量构建代替诊断。
4. 隔离验证只管理自己启动的进程、端口和临时状态，不复用或停止共享实例。
5. 提交前核对暂存范围、空白错误和构建产物；按 `git提交规范.md` 提交一个主题。`prompt.md` 默认留在本地，只有用户明确授权提交提示词资产时才单独提交。

**完成检查**：能列出实际执行的检查、结果和未验证风险；暂存区只包含本主题文件。具体命令以 `package.json` 和 `tools/repository/verify-change.sh` 当前实现为准；历史流程设计见[归档](<../07-决策与风险/知识中心-平台-Code Review与提交验证流程-设计归档.md>)。

# 开发角色如何分工

**适用**：任务需要多人分工或正式治理时。角色表示责任，不等于每个任务都要启动一个 Agent；普通任务能由一人完成时按[任务路由](<./知识中心-平台-Task Routing Contract v1与最小执行路径-治理规范文档.md>)直接推进。

1. **谁做，谁说明结果**：实施者交付代码和自检证据，但不能把自检写成独立验证。
2. **谁验证，谁说明证据**：需要正式独立验证时，由未实施该变更的验证者检查真实行为。后端及端到端验收必须调用真实启动的 API。
3. **谁批准，谁承担决定**：产品价值、受限架构、权限、真实数据和残余风险由有权的人决定；设计者、实施者和测试者不能代替批准。
4. **权限随任务给**：执行范围以当前任务允许的文件和有效批准为准，不能因角色名称自动扩大。
5. **状态随证据变**：完成、验证和接受分别报告；缺输入、越权或需人决定时明确说明阻断原因。

| 责任 | 主要交付 | 不能替代谁 |
|---|---|---|
| 设计 | 需求、方案、接口和风险 | 不能代人批准受限决定 |
| 计划 | 任务拆解、依赖和文件归属 | 不能代实施者宣布进度 |
| 实施 | 产物和自检 | 不能自称独立验证或最终接受 |
| 验证 | 测试和可复核证据 | 不能改产品规则让测试通过 |
| 项目治理 | 核对审批、门禁和状态 | 不能代做实现或验证 |
| 独立审查 | 质疑主张与证据 | 不能改待审产物或作业务取舍 |
| 报告 | 根据事实汇总进展 | 不能创造审批、验证或接受事实 |

**完成检查**：每项必要责任有承担者和证据来源；需要分离的验证、审查或批准没有由产出者自己完成。角色接口、字段、状态机和候选 Skill 属试行设计，见[归档](<../07-决策与风险/知识中心-平台-Role Contract v1与角色治理-设计归档.md>)。

## 通用角色契约与项目配置

`.codex/roles/` 中的角色定义跨项目稳定的责任、权限、证据和升级原则，不定义某个项目的目录、语言、框架、数据库产品、命令、审批字段或状态机。项目专属做法由任务上下文、仓库约定、已批准 Policy 或按需加载的项目配置提供；这些配置必须注明来源和适用范围。

角色执行时依次确认：目标与验收、相关输入和证据、当前任务授权的写入范围、项目采用的工具与流程。上下文没有提供某项项目事实时，先检查任务指定的权威来源；仍缺失则报告缺口，不自行补成默认事实。不能把本仓库路径、当前技术栈或角色目录当作其他项目的约定。

角色指引必须将不可变方向写成正向规则：基于目标和证据行动；在自身责任内产出；将事实、假设和建议区分；对未授权决策、关键事实冲突和超出范围的工作停止相应操作并升级。方法、工具和格式只在其确为适用项目规则时使用。技术性建议须附适用条件，例如重试仅用于可安全重试的操作，验证方式按任务风险和项目运行环境选择。

### 角色通用性验收

角色修改以以下各项全部通过作为 `5/5` 验收，而非以文字长度或检查项数量评分：

1. 在不改变责任目的的前提下，可用于不同项目、领域和技术栈；没有隐含当前仓库路径、产品、框架、语言、命令或组织流程。
2. 目标、责任范围、输入、产出、权限边界、证据要求和升级条件清楚，且职责之间没有自我批准、自我验收或事实来源冲突。
3. 不完整或冲突的上下文会触发查证、标注假设或升级，不会把示例或历史惯例提升为默认规则。
4. 条件性方法明确其触发条件及风险约束；项目策略和数值阈值来自适用的已批准来源。
5. 示例只解释契约，不把具体业务、路径、日期或阈值写成角色前提；项目细节由独立上下文提供。

目录和角色文件中的引用须可解析，角色数、标识、职责映射和样例须彼此一致。

# 知识中心管理平台术语规范

版本：V1.0
状态：实施中
更新时间：2026-11-12

## 1. 文档目的

本文档是知识中心管理平台的公共术语基线，约束页面按钮、字段、状态、通知、设计文档、接口说明和测试用例中的中文表达。术语应让用户直接知道对象和动作，不通过额外的小字解释来弥补按钮含义不清。


## 2. 使用原则

1. 同一对象只使用一个中文名称。页面、接口说明、设计稿和测试用例不得为同一对象创造近义名称。
2. 按钮优先使用“动作 + 对象”的最短表达；对象已经由当前页面明确时，只保留动作，例如“查看”“确认”“取消”。
3. 状态描述事实，按钮描述可执行动作。不能用“已处理”代替“不采纳”“已采纳，待创建”等具体状态。
4. 角色名称使用职责名称，不使用“决定人”“操作人”等泛化词。实际执行人统一称为“处理人”；发生时间统一称为“时间”。
5. 技术对象保留行业通用写法，例如 GitLab、MR、API、URL；首次出现时在说明文档中给出中文含义。
6. 新增术语必须先检索本文档和代码现有用法；确需新增时，补充定义、适用范围、替代词和变更记录。

## 3. 已确认的统一替换

| 禁止或不推荐 | 统一使用 | 使用位置/含义 |
|---|---|---|
| 查看影响预览、影响预览（作为按钮） | 查看 | 打开范围影响或详情；“影响预览”仅可作为能力名称或设计说明 |
| 前往处理 MR、处理 MR | MR链接 | 打开 GitLab MR |
| 取消本次纠偏 | 取消 | 取消当前范围纠偏记录 |
| 决定人 | 处理人 | 显示实际作出处理的人员 |
| 决定时间 | 时间 | 显示处理发生时间 |
| 采纳并调整范围 | 采纳 | 范围负责人接受范围意见，后续进入范围调整 |
| 调整任务范围 | 查看 | 从意见或通知进入范围调整详情；实际确认动作使用“确认” |
| 确认范围变更 | 确认 | 提交已完成校验的范围变更 |
| 查看处理记录 | 查看历史 | 打开历史处理记录 |
| 进入文档编写 | 进入编写 | 打开文档编辑页面 |
| 查看新审核结果 | 查看审核 | 打开审核任务和最新审核结果 |
| 查看并处理 | 处理 | 当前用户具有服务端返回的处理权限时使用 |
| 查看并回复 | 回复 | 当前用户只能回复意见时使用 |
| 生成纠偏、创建纠偏单 | 范围纠偏 | 业务对象名称；按钮根据上下文使用“创建”或“查看” |
| 重新拉取、刷新数据（指外部交付状态） | 状态刷新 | 重新读取 GitLab 或交付状态 |
| 合入负责人 | 合入负责人 | GitLab MR Assignee 对应的平台角色 |
| 审核责任人、审核成员（指被分派审核的人） | 审核人 | 逐篇审核的责任角色 |
| 文档生产、写作任务（作为个人动作） | 文档编写 | 文档负责人编辑和保存正文的工作 |
| 修订文档并重新送审 、修订文档| 文档编写 | 文档负责人编辑和保存正文的工作和工作台位置 |


## 4. 平台对象与状态

| 统一术语 | 定义 | 不要混用 |
|---|---|---|
| 工单 | 外部需求或任务进入平台后的顶层业务对象 | 需求单、任务单（除非引用外部系统原名） |
| 手册 | 工单拆分后的文档集合及其负责人范围 | 文档集、资料包 |
| 文档 | 手册中的单篇内容及其正文、图片和版本 | 页面、文章（外部来源原名除外） |
| 范围 | 工单、手册或文档的当前有效对象集合 | 清单、范围列表 |
| 范围意见 | 审核中提出、需要范围负责人处理的意见 | 纠偏意见、范围建议 |
| 范围纠偏 | 由范围意见触发的范围调整记录 | 纠偏单、回流单 |
| 审核意见 | 审核人针对正文或范围提出的意见 | 评论（接口对象可使用 comment） |
| 审核任务 | 面向一篇或多篇文档的审核工作对象 | 审核单、评审单 |
| 候选 | 提交审核的正文版本 | 草稿、结果（未明确版本阶段时） |
| 草稿 | 尚未提交审核的正文版本 | 候选 |
| MR | GitLab Merge Request，文档交付变更请求 | 合并单、代码合并请求 |
| 回读 | 从目标分支读取合并后的正文和图片并核对 | 校验、同步（除非描述其他动作） |
| 待处理 | 当前用户有明确可执行动作的事项状态 | 未完成、进行中 |
| 跟进中 | 当前用户没有立即可执行动作，但仍需关注的事项 | 等待中（页面状态统一用“跟进中”） |
| 已闭环 | 范围意见及其受影响文档已完成全部门禁 | 已处理、完成（除非描述普通任务完成） |
| 人员已失效 | 人员管理状态为停用，历史记录仍保留 | 已删除、无效用户 |

## 5. 角色名称

| 统一术语 | 职责 |
|---|---|
| 工单责任人 | 确认工单涉及的手册范围并分派手册负责人 |
| 手册负责人 | 确认手册内文档范围并分派文档负责人 |
| 文档负责人 | 编写、保存和修订文档 |
| 审核人 | 逐篇审核候选正文并作出审核结论 |
| 合入负责人 | 处理 GitLab MR；平台不自动合并 |
| 知识中心负责人 | 平台配置的一名责任人，可被审核意见提及 |
| 处理人 | 某次采纳、不采纳、取消或核对动作的实际执行人 |

## 6. 页面按钮与字段

| 场景 | 主按钮 | 辅助按钮/字段 |
|---|---|---|
| 工作台 | 处理、进入编写、查看审核、MR链接 | 查看、刷新、查询条件 |
| 范围意见 | 采纳、不采纳、查看、取消、确认 | 查看历史、提交意见、重试 |
| 审核 | 审核通过、退回修改、提交意见 | 阅读文档、查看修改、审核意见 |
| 交付 | 创建 MR、MR链接、状态刷新 | 查看、查看历史 |
| 结果信息 | 处理人、时间、理由 | 范围版本、回读结果、处理状态 |

按钮文字必须与服务端能力一致。无权限、状态不允许或外部依赖不可用时，按钮应禁用并显示具体原因；前端不得根据本地猜测显示“处理”。

## 7. 状态写法

状态使用“事实 + 必要阶段”的写法：

- 已采纳，待创建
- 已采纳，待确认
- 已采纳，未生效
- 待重新编写
- 待重新审核
- 已闭环
- 不采纳
- 人员已失效

禁止把上述状态简化为“已处理”“已完成”或“失败”。“待处理”只表示当前仍有动作，不替代具体阻断原因。

## 8. 维护与检查

术语变更按以下流程处理：

1. 在本文档新增或修改术语，并填写适用场景和替代词。
2. 使用 `rg` 检索 `apps/`、`packages/`、`tests/` 和 `.codex/知识中心建设平台/`，清理旧称；外部系统原文引用可以保留，但需标明来源。
3. 更新相关模块 README、设计文档和测试用例；页面改动同时检查桌面与窄屏。
4. 运行 `npm run check:ui`、相关功能测试和 `git diff --check`。
5. 在 `prompt.md` 记录提示词、决策、变更时间和验证结果。

本表是持续维护的公共能力。后续发现新术语冲突时，先更新本表，再修改页面和文档，避免局部修复后再次出现同义词分裂。

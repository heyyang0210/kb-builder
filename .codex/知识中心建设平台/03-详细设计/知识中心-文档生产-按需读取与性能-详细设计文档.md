# 手册目录与草稿按需读取设计

## 草稿审核状态的异步回读（2026-10-29）

真实 13510 诊断发现：Storage 单篇草稿投影在 1/5/10 并发下 P95 约 9/9/17ms，但平台草稿 API 的 `draft_read` 阶段在同一轮可升到约 262/975/1187ms。草稿读取已走异步投影，随后投影审核状态时却调用 `reviewService.get(session, taskId)`；该方法缺少快照时会同步读取整份增量聚合，阻塞 Node 主线程。此处只调整 GET 草稿的异步路径，保持审核权限和逐篇结论规则。

伪代码：`draft = await store.readDraftAsync(key) → 若有 taskId，则 reviewSnapshot = await reviewService.readState(session) → reviewService.get(session, taskId, reviewSnapshot) → 只取当前 documentId 的审核结论 → 返回草稿`。审核任务不可读时沿用现有规则，返回草稿中最后已知的任务引用，不将读取故障误判为“已通过”。同步调用路径保留原逻辑，其他写操作不改。验收需覆盖真实 HTTP 草稿读取、逐篇状态投影、审核快照读取失败回退，并在原 1/5/10 并发门禁下复测；不降低 100/200/500ms 预算。

首次部署复测显示单人降至约 66ms，但 5/10 并发反而升至约 3.2/4.3 秒：并发请求重复读取同一份约 289KB 的审核聚合。因此审核服务只在同一批读取尚未完成时合并快照请求，完成后立即清除；不做跨请求时间缓存。数据库聚合每次成功写入增加本进程写入序号；若读取途中发生写入，重新读取直到序号稳定，避免把写入前的结果返回给写入后的请求。伪代码：`pending ||= readAsync(); if writeEpoch changed then retry readAsync(); finally pending = null`。外部其他进程写入仍由 Storage 的版本读取决定；本优化不改变数据库事实源。

## 范围与验收

解决目录等待草稿/GitLab/模板，以及单篇草稿同步读取全局生产状态的问题。保留现有持久化、CAS、幂等、审核及 AI 采用写入契约。目标：同机目录 API P95≤100ms、目录可见 P95≤200ms、草稿 API P95≤100ms；真实外部 GitLab 延迟单独呈现。

## 契约与伪代码

- 目录首屏可请求 `GET /outline/catalog?handbookId=<id>&view=directory`：数据库模式服务端按原 catalog 顺序定位该手册的首个版本，再读取同一版本的目录，一次返回 `items`、`selectedId` 和 `directory`。只返回该手册的索引条目；无匹配时返回空条目和空目录，前端继续原有候选/空手册识别。目录读取失败返回原错误，不转换为空手册。该入口沿用 `outline:read` 权限，不引入跨请求缓存；文件适配器及旧版服务未返回 directory 字段时，前端兼容原详情读取。非 directory 视图、指定版本和全平台 catalog 不变。伪代码：`catalog -> first matching handbook -> directory(selected.id) -> response`；减少浏览器串行往返，不宣称消除数据库读取或已达到性能预算。
- `GET /outline/governance/:id?view=directory`：只读指定大纲的节点、版本和责任分工；不读取所有大纲，不返回重复 content、任务和影响分析。兼容原 compact 接口。
- Storage `GET /v1/records/handbook-production/state?draftKey=<encoded context>`：只返回指定草稿元数据和当前 revision，历史、幂等响应、其他文档、AI 任务均不输出。Node 使用原生异步 HTTP。文件/测试适配器保留兼容读取。
- Storage 启动在监听端口前读取一次旧聚合并建立当前草稿索引；预热、单篇读取、写入前校验统一使用分块 CLOB 读取。所有聚合 PUT 提交后更新索引。索引不是事实源，不写数据库、不修改结构。每次读先用数据库小行查询 revision/deleted；匹配则 O(1) 查文档，不读 CLOB。跨实例或外部写入导致 revision 不匹配时，单飞重建并返回可重试 503，绝不把过期数据或重建失败解释为“草稿不存在”。删除后立即返回空，不泄露旧缓存。重建按 revision 发布，旧请求不能降级新快照。若持久化聚合 JSON 格式损坏，Storage 记录损坏 revision、保留原记录并继续启动其他 API；对应草稿读写返回 `DRAFT_STATE_INVALID`/503，绝不降级为空草稿或覆盖原记录。数据恢复须经有效备份核验，本次不自动修复。
- 目录读取与辅助请求并发。取得目录立即渲染，正文区域继续显示独立读取状态；正文上下文先解析映射分支，再读草稿；GitLab 元数据可与草稿并发，草稿存在时跳过仓库正文。已保存草稿优先。模板正文在选择/使用模板时读取。
- 进入手册时先发起目录读取，再渲染独立的 loading shell；loading shell 不依赖目录响应。目录投影完成并首次渲染后才发起映射读取，避免辅助仓库查询与目录存储读取在并发入口争用资源；映射仍在目录可用后立即开始，不改变序号、权限或正文上下文校验。
- 页面加载序号、文档上下文和 dirty 状态防止迟到响应覆盖当前路由/本地编辑；正文未 ready 时不可编辑、保存或送审。
- 增量审核创建成功后，按选中文档 ID 并发刷新共享草稿；批量遍历通过单参数包装调用，避免数组索引被当作上下文有效性回调，确保成功流程能关闭弹窗并显示成功通知。

伪代码：启动 `warm(state, revision) -> index(current drafts) -> listen`；写 `CAS aggregate -> commit -> publish(index, revision)`；读 `SELECT revision, deleted -> verify snapshot -> lookup(contextKey) -> current draft`；目录 `await directory -> render -> await body -> render`。

## 限制与验证

启动预热仍读取旧聚合一次；跨实例失效需重建一次，属于缓存恢复成本，未来若聚合继续增长，应将写入与历史拆分为独立领域记录。当前实现消除普通读取与其他请求间的同步阻塞，不把写入链路优化混入本次修复。测试必须覆盖版本失效、删除、空草稿、权限、当前版本裁剪及慢辅助请求；使用真实 Storage/API 和浏览器复测，明确隔离端口与线上尚未部署的区别。

## 辅助读取与上下文完整性

生产页映射通过 `GET /gitlab/mappings/:id?view=production` 获取，先校验手册读取权限，仅返回分支、连接标识及语言路径白名单；管理读取仍要求管理员。权限查询、映射、仓库分支读取改为异步，避免同步辅助查询阻塞草稿。我的文档模式与目录共用筛选函数。已有草稿跳过 GitLab 正文读取；发起写作时才补读缺失基线，保存保留原草稿 baselineDigest，防止空内容伪装仓库来源。

性能门禁：`tools/repository/check-handbook-performance.cjs`，预算为 `config/knowledge-center/handbook-performance.json`，采样证据写入 runtime；超预算非零退出。发布顺序为 Storage → Node/前端，旧 Storage 仅兼容功能，不能保证性能。当前方案的长期边界仍为聚合写入/预热成本，后续独立领域记录迁移需另行设计与授权。

### 2026-10-29 Storage 目录投影缓存与并发容量

目录投影先读取版本头，再以 `OUTLINE_VERSION_ID + ROW_VERSION` 作为缓存键，短时复用同一版本的节点和责任映射；每次请求仍校验版本头，编辑号变化会自动落到新缓存项，缓存只用于读性能，不改变权限和业务结果。默认缓存时长为 2000ms，可由 `YASDB_DIRECTORY_CACHE_TTL_MS` 调整。缓存最多保留 256 个条目，写入新条目前清理过期条目并淘汰最早发现的条目，避免历史编辑版本让进程内存持续增长。响应原文达到 1KB 且请求声明支持 gzip 时，Storage 和 Node 网关均协商 gzip 并返回 `Vary: Accept-Encoding`，客户端解压后仍使用同一 JSON 契约；Node 网关因原生 `fetch` 已自动解压 Storage 响应，必须单独压缩 Node 到浏览器的 JSON 响应。为覆盖 10 路读取门禁，Storage 默认工作线程和 JDBC 连接上限调整为 16，均可由 `YASDB_STORAGE_THREADS`、`YASDB_STORAGE_POOL_MAX` 覆盖。缓存命中、版本头、节点、责任映射耗时继续通过 `Server-Timing` 暴露；性能门禁仍以原 100/200/500ms 预算判定，不得通过放宽预算验收。

## 加载体验及运行版本验收

正文等待时保留标题、目录按钮及与阅读态一致的占位布局，标注 aria-busy，不显示未保存/无草稿的业务结论，不提供编辑保存动作。读取失败保留目录入口，允许转到其他文档。仅已知有草稿或本地修改时显示评审区。目录可用不等于正文就绪，两者必须分别计时；交付需核对实际运行API响应体积与草稿控件，禁止仅凭构建或隔离验证宣称运行实例生效。

手册入口未指定文档时自动展开目录；指定文档的深链保持正文视图，避免目录虽已加载却隐藏，用户只能等待首篇正文。

本地更新前置问题：统一构建未验证产品 Profile 的工作区引用；旧独立资料处理页移除后仍残留模块引用，导致文档服务启动失败。本次清除已失效引用，不跳过严格校验；运行验收包含实际服务启动。

目录存储响应增加连接获取、版本头、节点、责任人和总处理的 Server-Timing，用于区分数据库阶段与网关/浏览器延迟。运行更新还发现存储短暂不可用时异步会话检查异常未捕获会退出网关；修复为返回原503错误，恢复后继续处理请求，不放宽认证。真实HTTP回归覆盖失败后恢复。

目录数据库读取经 Node 代理返回时，代理必须透传 Storage 的 `Server-Timing`，并追加自身 `directory_read` 阶段；业务 JSON、状态码和错误语义保持不变。公共 `DomainStore.requestAsync()` 继续只返回业务正文，只有明确需要观测响应头的调用使用 `requestAsyncWithMeta()`，避免把传输元数据扩散到普通业务契约。阶段值只接受同一内部服务产生的响应头，并清除换行符后写入响应，性能工具据此区分 Storage 与网关耗时。
目录 GET 是只读事务，不执行显式 `commit`；JDBC 连接代理在关闭时回滚并归还连接，避免为无写入请求增加一次数据库提交往返。该规则仅适用于只读目录投影，写入接口仍按原事务提交。

资产目录数据库投影：当前页的 GitLab 映射读取采用受控并发，最多同时读取 20 条，并保持 `Promise.all` 返回顺序与资产列表顺序一致；不得恢复为逐条串行或无边界全量读取。映射读取失败仍按原错误语义处理，结果只用于 `repositoryMapped` 和仓库摘要投影，不改变资产权限、筛选和分页契约。性能门禁需覆盖冷启动首试与重试样本，首试超预算必须保留为不稳定证据，不能以重试通过替代稳定通过。

门禁目录计时要求：必须存在展开的目录，且在下一绘制帧检查其位于视口内、允许指针操作；不再把加载提示消失当成目录已可用。真实 click 起算，草稿保存状态控件出现单独记录正文就绪；慢正文/失败场景由独立只读浏览器用例验证。

### 诊断时间线（2026-10-29）

当正式门禁显示并发目录可见P95超预算时，诊断模式需在同一真实入口点击时间原点记录：目录请求开始及响应完成、目录节点收集、大纲投影和目录抽屉状态准备、`render()`内HTML生成与根节点替换、目录增强、图标处理、同步渲染结束、首次目录DOM、首次动画帧及实际可见帧；同时标记映射解析、草稿读取和仓库读取完成时点，以识别后续异步刷新是否触发额外绘制。浏览器资源计时与业务阶段事件使用同一`performance.now()`时钟，按单样本顺序对齐，禁止相减不同样本P95推导耗时。

这些阶段仅在显式诊断开关打开时采集并写入runtime报告，不进入正式预算判定，也不改变生产界面逻辑。阶段数据用于确定下一步局部CPU/绘制采样位置；只有具体函数或重复重建与延迟在同样本中对齐后，才据此提出优化。正式门禁仍使用原1/5/10路、每档30次浏览器和100次API，以及目录200ms、正文500ms预算。

10路CPU诊断显示目录图标增强会遍历并替换折叠分组内不可见的节点。试验过首屏只增强展开路径、展开后再增强；正式固定夹具复验5路目录P95由151.7ms变为220.6ms、10路由320.1ms变为265.0ms，仍有两档超200ms，变化方向不一致。已撤回该试验及其专用测试，保留原有图标语义。诊断同样本显示10路目录响应结束P95约164.3ms、响应结束至可见约116.2ms；阶段分位值不能相减作为单样本因果。下一轮应分别定位请求排队/存储读和响应后的帧调度，继续按原门禁复验。

目录列表渲染优化（2026-10-29）：目录仍生成完整 DOM，保证搜索、键盘导航、折叠和深链选择语义不变；滚动容器内的目录行使用浏览器原生`content-visibility:auto`与保守的`contain-intrinsic-size`，让远离视口的行跳过初始布局和绘制，进入视口时由浏览器恢复渲染。该优化只作用于目录视觉性能，不改变目录数据、权限、状态或可访问名称；必须通过原1/5/10路浏览器门禁及滚动契约后才能保留。

当前本地运行实例最新验收：目录API P95 61.2ms，草稿 30.7ms，目录可用 181.2ms，正文 347.0ms；30次点击/API各100次，证据 runtime/performance/handbook-20261028/live-visible-gate.json。慢正文和读取失败的桌面/窄屏用例通过。保留首轮失败样本，不推广为并发/外部GitLab承诺。

## 逐篇审核契约补充（2026-10-29）

手册生产任务的审核记录按候选范围内的 `documentId` 建立，一篇文档对应一条审核记录；非手册旧任务保留一条无 `documentId` 的兼容记录。审核记录冻结 `candidateDigest`，正文或变更范围重新形成候选后，旧记录不得复用。

- 审核人只对被分派的文档作出通过或退回结论。
- 单篇通过不会将任务置为 `approved`，任务继续保持 `under_review`，直至当前候选的所有文档审核记录均为 `approved`。
- 任一篇退回时任务进入 `rejected`，退回原因绑定该文档；作者修订后形成新候选并重新生成逐篇审核记录。
- 发布和 GitLab MR 创建的服务端门禁均检查当前候选的每篇记录，不接受仅有整本或任意一篇通过的结论。
- 工作台按 `documentId` 选择审核记录、审核人和意见，避免多文档任务误读第一篇状态。

### 2026-10-29 压缩协商兼容修正

真实 API 已复现 `Accept-Encoding: gzip;q=0` 仍返回 gzip，且压缩响应覆盖了 CORS 的 `Vary: Origin`。网关改用 Express 的标准编码协商，显式拒绝 gzip 时发送原文；可压缩 JSON 的两种响应均追加 `Vary: Accept-Encoding`，保留已有 Origin。小响应及非 JSON 不参与此协商；正文与业务权限保持原契约。验收比较 gzip、拒绝 gzip、identity 以及通配编码请求的状态、解压后正文与 Vary。

### 仓库映射读取阶段计时（2026-10-29）

真实并发诊断显示映射请求显著延迟，但当前已使用异步读取，不能据此判断同步阻塞。GET 映射响应增加 Server-Timing：mapping_access（权限与资产核对）、mapping_read（读取映射）、mapping_connection（连接存在性核对）、mapping_total（总处理）。保留逐请求权限、连接校验、投影字段和错误语义；不新增缓存，不减少核对。计时使用单调时钟，不包含账号、仓库或凭证内容。伪代码：权限核对计时 → 映射读取计时 → 连接核对计时 → 写响应头 → 原响应。先用真实接口定位，再决定优化范围。

映射权限核对内部进一步记录 mapping_assets（手册资产读取）与 mapping_status（状态覆盖读取），两者包含在 mapping_access 内，不能将父子阶段相加。其他入口不输出这些诊断阶段。

单飞读取试验未保留：资产合并后等待转移到状态读取，状态合并后等待转移到映射读取，5/10路总请求仍为秒级。说明不能用某个阶段变快证明整体收益。公共资产/配置读取还须验证并发写入时可见性和返回副本，未证明前不引入此优化。后续先定位HTTP调度和连接行为，保留当前分段计时。


### 合并目录入口的索引阶段观测（2026-10-29）

### 首次并发连接等待修正

隔离数据库冷暖对照显示：同一实例两轮10路目录读取，获取连接P95由4228ms降至0.094ms，SQL查询均在数十毫秒。连接池借用在进入创建锁前检查空闲队列，等待锁期间已归还的连接没有再次检查，后续请求仍串行建立新连接。局部修正：取得创建锁后再次尝试空闲队列，仅在仍为空且容量允许时创建连接。最大连接数、事务回滚和等待超时保持原契约。先通过可控线程顺序的JDBC替身复现并回归，再运行统一隔离test_hy真实HTTP冷暖对照；完整页面性能独立验收，不由接口通过推定。


### 连接池扩容移出临界区

复查空闲连接仍不能消除首次并发等待。容量计数含正在建立的连接：锁内复查空闲队列，若仍为空且未满则预留一个名额；锁外完成JDBC建连，失败释放名额。初始化连接设置失败须关闭原始连接。等待者仍按既有超时等待归还，最大容量与事务规则不变。验收覆盖两条建连同时进入驱动、容量耗尽不超建、失败后容量可用，以及真实隔离目录HTTP冷暖复测。

## 写作页多篇送审的按需读取（2026-10-29）

问题：刷新或直接打开文章后，送审弹窗只读取浏览器已加载草稿，遗漏同手册已保存的其他文章。

打开弹窗时调用现有 review-drafts 接口，只接收与当前手册、大纲版本及分支一致的草稿摘要；列表仍由当前目录过滤，失效目录节点不展示。摘要不伪装成完整草稿或权限声明。点击下一步时仅读取已勾选文章的完整草稿并检查现有送审能力，未保存修改不覆盖、不允许送审。失败保留弹窗并提示重试，不进入确认提交。异步结果应用前核对路由上下文，避免切换手册后串用旧结果。无需新增接口、数据库结构或业务规则。

伪代码：打开 → 清空旧摘要 → 拉取当前范围摘要 → 显示目录匹配项；下一步 → 拉取选中草稿 → 检查已保存及送审能力 → 原确认弹窗 → 原创建接口。

验收：直接进入A文章，能选择尚未打开的B草稿一起送审；异分支/异版本草稿不入选；一篇通过、另一篇退回时整批不可交付。真实HTTP与隔离test_hy联合验证，不以模拟GitLab替代企业合并验收。

### 目录重复文档图标的首帧实验（2026-10-29）

当前正式隔离报告10路目录可见P95为238.2ms，预算200ms；API目录10路P95 93.8ms，浏览器慢样本中HTML生成、DOM替换、图标转换和首帧共同占时。目录每篇都插入装饰性`file-text`图标，现行图标增强逐节点创建/替换SVG，慢样本该阶段约27ms。先将**仅目录文章行**的该装饰图标改为CSS mask，使用同形状的静态矢量路径、`currentColor`及固定16px占位；不改按钮、可访问名称、文档顺序、折叠、搜索或其他图标。CSS加载前保留16px占位。

伪代码：目录行输出`span.handbook-document-icon[aria-hidden=true]` → CSS mask绘制file-text形状 → 图标增强器只处理其余`data-lucide`节点。以同一隔离入口跑1/5/10路正式预算和滚动/图标可见检查；若未改善或出现缺图、布局偏移，撤回实验，不调整预算。该实验只针对观测到的CPU工作量，不预设为全部性能根因。

实验结果：隔离正式1/5/10路、每档30个浏览器样本，目录可见P95为84.4/130.6/202.3ms；基线同档为81.1/122.6/238.2ms。10路下降约35.9ms，但仍超200ms约2.3ms，1/5路略慢，不能宣称性能门禁通过，也不能由两次运行断言稳定收益。实验诊断最慢样本图标阶段接近0，但DOM替换至首帧仍约68ms，说明还须查并发帧调度。目录图标的形状、16px占位和装饰性`aria-hidden`已用Chromium/Firefox工作台回归与截图核对。保留该有界优化作为继续排查的工作版本，正式验收仍以原预算复测为准；若后续多轮显示回退或跨浏览器视觉异常，应撤回。

# 知识中心页面数据存储现状与集中化路线

> 2026-09-23 Review 更新：团队小组目标模型为 `KC_TEAM_GROUP` 和 `KC_TEAM_GROUP_MEMBER`。`KC_TEAM_GROUP` 不再保存 `TECH_DOMAIN_ID`，并支持新建小组；团队名称是小组自身业务语义。后文出现的“团队表直接保存 `TECH_DOMAIN_ID`”和“只允许现有 8 组”是旧方案，不再作为实施依据。

> 版本：1.1.0
> 盘点日期：2026-09-23
> 范围：知识资产、大纲管理、模板管理、平台管理
> 当前运行模式：`KNOWLEDGE_STORAGE_MODE=database`

## 1. 结论先行

当前四个页面的数据并未全部集中管理，而是同时使用五种存储方式：

1. YashanDB 关系表：手册、大纲主体、技术领域、人员。
2. YashanDB `KC_RECORD` JSON/CLOB 聚合：模板库、GitLab OAuth 加密凭据。
3. 单机 `runtime/` JSON：用户权限和会话、GitLab 连接与手册映射。
4. 版本库 `config/knowledge-center/` 配置：产品、服务、内容规则和品牌资源。
5. 外部 GitLab：仓库目录、Markdown 正文、分支和提交记录。

其中最不符合多人开发要求的是：

- 用户和角色等共享配置仍与会话、权限日志混写在当前运行机的 JSON。
- GitLab 连接和手册映射等共享配置仍与幂等缓存、操作日志混写在当前运行机的 JSON。
- 历史手册和大纲 JSON 仍存在，且数量已与数据库不一致，容易被误当成可写主数据。
- 技术领域已有 8 条、有效人员已有 22 条，但领域负责人和成员关系均为 0，缺少可维护的团队事实源，导致大纲分工无法选择责任人。

目标原则是：团队共享的业务事实只能有一个集中权威源；会话、Ticket、幂等缓存和操作日志属于运行时记录，可以保存在本地，但必须与业务配置拆分并具备 TTL、轮转、权限和容量边界。

## 2. 真实调用链路

```text
浏览器页面
  → 13510 知识中心 BFF
      → 14210 YashanDB Storage → YashanDB 关系表 / KC_RECORD
      → 14110 文档服务 → 14210 YashanDB Storage
      → 本机 runtime JSON
      → 版本库 config
      → GitLab API
```

页面不直接访问文件或数据库。判断真实存储位置时，必须继续追踪 BFF 路由、Repository 适配器和当前运行模式，不能只看前端 API 名称。

| 数据 | 当前权威源 | 存储对象 | 现状 |

实测当前为 1 个模板、1 条审计，`KC_RECORD.REVISION=1`。它已经解决了多机数据共享问题，但整个模板库是一条 JSON/CLOB 记录：任意模板更新都会修改同一 revision，数量增长后会出现大对象读写、无关模板并发冲突和难以用 SQL 检索的问题。

### 3.5 会话和审计数量的解释

1275 条会话表示从 2026-08-31 到 2026-09-18 累计创建了 1275 次登录会话，不是 1275 个用户在线。盘点时其中 1183 条已经超过 8 小时有效期、46 条已主动注销，只有 88 条同时满足“未注销且未过期”。当前文件没有过期清理，所以历史会话持续累积。

2563 条审计是认证模块事件，不是全平台业务审计。其中 `SESSION_CREATED` 1275 条、`ADMIN_LOGIN` 1222 条，两者已占绝大多数；一次本地账号成功登录通常会同时产生这两条事件。其余为会话注销 46 条、角色修改 11 条、CAS 用户首次创建 7 条及两条初始化事件。当前审计最多保留 5000 条，超过后直接裁掉最早记录。

具体目标表结构、迁移映射、小步切换和评审待决项见[认证权限与 GitLab 配置集中化迁移详细设计](./知识中心-认证权限与GitLab配置集中化迁移-详细设计文档.md)。

## 4. 风险判定

| 级别 | 问题 | 影响 |
| --- | --- | --- |
| P0 | 用户、角色与本地会话/日志混存 | 共享权限配置不一致，且运行记录无界增长；两类数据无法独立治理 |
| P0 | GitLab 连接与手册映射单机化 | 团队成员看到不同连接和映射，仓库阅读不稳定 |
| P0 | 8 个技术领域与 22 名人员之间没有负责人和成员关系 | 大纲分工没有合法责任人候选，发布后的领域任务无法形成可执行分工 |
| P1 | 历史手册 JSON 为 75、数据库为 76 | 双源已漂移，本机时间还会影响页面投影 |
| P1 | 历史大纲 JSON 仍保留 1 条 | 运行模式切换或误配置时可回到过时数据 |
| P1 | 认证 JSON 同时累积会话、票据和大量审计 | 文件不断增长，每次修改需整体重写，缺少 TTL 清理 |
| P2 | 模板库是单条 JSON/CLOB | 数量增长后冲突粒度过大，查询与审计不便 |
| P2 | 平台配置和业务数据的边界未在界面中显式说明 | 容易把 Git 发布配置误当成可在线维护的业务数据 |

## 5. 目标存储边界

| 数据类别 | 目标权威源 | 原因 |
| --- | --- | --- |
| 手册、大纲、技术领域、人员 | YashanDB 关系表 | 需唯一约束、组合查询、状态机和并发控制 |
| 团队小组、团队成员 | YashanDB `KC_TEAM_GROUP`、`KC_TEAM_GROUP_MEMBER` | 独立组织事实；需乐观锁、有效期和审计，不保存领域绑定表或领域 ID |
| 用户、角色和授权关系 | YashanDB 独立表 | 是平台管理页面的团队共享业务配置 |
| GitLab 连接和手册映射 | YashanDB 独立表 | 是团队共享的平台业务配置 |
| 会话、CAS Ticket 和幂等键 | 本地运行时存储 | 短生命周期状态，按 TTL 清理；跨实例共享需单独架构评审 |
| 认证和 GitLab 操作审计 | 本地结构化日志 | 采用 JSONL、轮转、访问控制和保留周期；跨机器查询交由日志平台 |
| GitLab OAuth 凭据 | YashanDB 加密存储 | 现有方式已集中；密钥必须由部署环境注入 |
| 模板 | 短期保留 `KC_RECORD`，中期拆为模板/版本/审计表 | 当前规模可用，但不适合长期增长 |
| 产品、服务和内容规则 | Git 版本库 + 发布流程 | 它们是发布配置，需代码审查和可回滚 |
| 仓库正文与提交 | GitLab | GitLab 是内容版本权威源，知识中心只保存映射和必要的审阅快照 |
| 临时上传、缓存和构建产物 | 可替换的运行存储 | 不得被当成业务主数据，必须可重建和可过期清理 |

## 6. 下一步工作方向

### P0：先消除单机主写

1. 设计认证与权限业务表，只迁移用户、角色、授权和用户角色关系。
2. 以 CAS 登录名关联 `KC_PLATFORM_PRINCIPAL`，保留数字 `PRINCIPAL_ID` 作内部业务关联键，不再在认证 JSON 形成第二份人员名单。
3. 设计 GitLab 连接和手册映射表；验证、幂等和审计继续作为本地运行时记录。
4. 先拆分混合 JSON，再采用“库内建表 → 业务配置只读导入 → 摘要对账 → 切换主写 → 原文件封存”，禁止长期双写。
5. 建立通用团队小组和成员表，将 011 产生的初始小组保留为业务数据；通过 012 把唯一关系迁移到 `KC_TECH_DOMAIN.TEAM_GROUP_ID` 后删除 `KC_TEAM_GROUP.TECH_DOMAIN_ID`。新名册只写两张团队表，不长期双写旧 `KC_TECH_DOMAIN_MEMBER`。

### P1：清除双源与本机兜底

1. 取消数据库模式下用 `knowledge-assets.json` 的文件修改时间生成页面 `generatedAt`，改用数据库投影时间。
2. 将 `knowledge-assets.json` 和 `outlines/metadata.json` 移入明确的迁移归档目录，并从日常启动与主仓库扫描中排除。
3. 为会话、CAS 票据和幂等键定义 TTL、定时清理和审计保留周期，不允许无界增长。
4. 建立启动门禁：共享环境启动时若关键业务存储仍为 `file`，直接拒绝启动；仅单元测试和隔离 E2E 可显式使用 file 模式。
5. 团队模型切读和真实 API 对账完成后，将 `KC_TECH_DOMAIN_MEMBER` 标记为只读迁移源；任何新名册写入旧表都应被启动或测试门禁发现。

### P2：将数据库聚合演进为可维护模型

1. 当模板数量、正文总量或并发编辑达到门槛时，将 `templates/state` 拆为模板主体、模板版本和模板审计表。
2. 为各页面建立“运行时存储契约”自检接口，只返回存储类型、模式和健康状态，不返回密码、令牌或文件绝对路径。
3. 将数据库迁移、文件导入、摘要对账、API 回读和回退验证纳入同一个发布门禁。

## 9. 实施前置基线

本文件不是认证、平台管理或 GitLab 连接的替代详细设计。实际开发必须同时满足本文件、[认证权限与 GitLab 配置集中化迁移详细设计](./知识中心-认证权限与GitLab配置集中化迁移-详细设计文档.md) 以及对应模块详细设计；三者冲突时，先停止受影响实现并完成设计裁决。

进入正式开发前，必须形成以下可审查产物：

| 产物 | 最低内容 | 未完成时的处理 |
| --- | --- | --- |
| 公共 API 契约 | 用户/角色、GitLab 连接/映射、团队名册和任务分派的请求响应、分页、错误码、幂等、并发和兼容周期 | 前后端不得分别猜测接口 |

| 运行时存储契约 | 会话、Ticket、幂等、验证和日志的路径、格式、锁、TTL、轮转、权限和磁盘满行为 | 不拆分线上混合文件 |

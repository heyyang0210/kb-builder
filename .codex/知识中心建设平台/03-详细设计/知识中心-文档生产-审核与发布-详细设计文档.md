## 1. 目标与定位

### 1.1 模块职责

本文档定义知识中心"审核与发布"模块的详细设计，覆盖从候选版本固化后到新版本正式生效之间的全部业务：

```text
候选版本已固化
→ 显式发起审核
→ 审核人逐条审阅修改点（行级定位 + 前后对比 + AI 推理链）
→ 追加评论、退回修改或通过
→ 全部审核通过后进入待发布
→ 发布者确认基线、执行发布
→ 新版本生效、旧版本退役
→ 可选登记外部交付证据
```

本模块不重复定义增量任务的来源、草稿、变更集和候选固化流程；这些由上游详细设计 `KC-M05-DETAIL-INC-001` 冻结。本文只从"候选已就绪"开始，向下延伸到"新版本生效"。

### 1.1.1 交付分层与现状

| 能力 | P0（当前可实现） | P1（本设计预留） |
|---|---|---|
| 审核决定 | 单审核会话、单一最终决定；提交者不能作有效决定人 | 1-3 级串行审核、每级最少通过人数 |
| 评论定位 | 行级评论为审核页面 P0 目标；旧接口无锚点时仅允许全局评论降级 | 锚点漂移自动重定位、跨修订覆盖度分析 |
| AI 解释 | 结构化发现、规则引用、证据片段 | 分析任务异步化、全量 8 类检查与修订覆盖度 |
| 发布 | 单手册/业务版本原子切换 | 多文档 `PublicationBatch` 原子发布 |

P1 启用前必须增加版本化 API 字段，不得改变 P0 `Review` 的既有读取含义；前端根据 `capabilities` 判断是否展示层级等扩展操作。行级评论属于本轮 P0 验收项，若后端暂不支持，必须显示“全局评论（兼容模式）”而不得伪装成行级定位。

### 1.2 核心刚性约束

| 约束 | 实现要求 |
|---|---|
| **修改意见清晰可见且可追溯** | P0 行级评论必须绑定锚点、前后对比和旁路解释，并贯穿候选到发布血缘；旧全局评论仅作兼容降级且不得宣称已完成行级定位 |
| **AI 深度嵌入** | AI 作为审核协作者，主动提供参数依赖检查、版本耦合预警、交叉引用验证和术语一致性分析；所有 AI 输出必须附带 Chain-of-Thought 旁路 |
| **数据库专属准确性** | 审核检查必须覆盖 SQL 语法正确性、配置参数依赖完整性、错误码唯一性、运维命令版本适配等数据库文档特有风险 |
| **在线实时协同** | 所有操作在 Web 端完成；多审核人可并行评论，不互相阻塞 |
| **审核不可代替** | AI 通过不代替人工通过；AI 拒绝不代替人工拒绝；最终决定必须由有权限的人作出 |

### 1.3 非目标

- 不实现 OT/CRDT 实时协同编辑；首期采用异步评论 + 编辑锁。
- 不自动合并或自动发布；知识中心不具备自动合并 GitLab MR 的能力。
- 不在审核阶段修改候选正文；审核评论只记录意见，不直接改变冻结内容。
- 不将 PingCode 未连接状态伪装为已接入；审核中引用的来源快照如实标注捕获方式。

## 2. 对象模型与事实关系

### 2.1 审核领域对象总览

```text
ReviewSession（审核会话）
  ├─ ReviewLevel[]（审核层级）
  │    ├─ ReviewerAssignment（审核人分配）
  │    └─ ReviewDecision（层级决定）
  ├─ ReviewComment[]（审核评论）
  │    ├─ CommentAnchor（行级锚点）
  │    │    ├─ nodeId
  │    │    ├─ lineRange
  │    │    └─ charRange
  │    ├─ DiffView（修改前后对比）
  │    │    ├─ beforeSnippet
  │    │    ├─ afterSnippet
  │    │    └─ operationType
  │    └─ AiAnalysis[]（AI 分析记录）
  │         ├─ analysisType
  │         ├─ reasoningSummary + evidenceRefs
  │         ├─ verdict
  │         └─ confidence
  ├─ ReviewVerdict（最终决定）
  └─ LineageRecord（血缘记录）
       ├─ parentCandidateId
       ├─ revisionChain[]
       └─ publicationId

Publication（发布记录）
  ├─ candidateDigest
  ├─ baselineVersionId
  ├─ supersededVersionId
  ├─ content
  ├─ operations[]
  └─ PublicationBatch（发布批次，多文档原子发布）

ExternalDelivery（外部交付登记）
  ├─ deliveryType（gitlab_mr / manual / other）
  ├─ reference
  ├─ status
  └─ evidence[]
```

### 2.2 审核会话

```text
ReviewSession(
  id,
  taskId,                    // 关联增量任务
  candidateDigest,           // 冻结的候选摘要
  handbookId,
  businessVersion,
  flowVersion,               // 审核流程版本（几级审核、通过规则）
  status,                    // pending | in_progress | approved | rejected | withdrawn
  levels[],                  // 有序审核层级
  finalVerdict,              // 最终决定
  createdBy,                 // 提交审核的人
  createdAt,
  updatedAt,
  completedAt
)
```

- 一个候选版本对应一个审核会话；候选固化后必须通过 `POST .../reviews` 显式创建。
- `flowVersion` 记录创建时使用的审核流程配置；即使后续流程配置变更，已有会话继续按创建时规则执行。
- 审核拒绝后创建修订任务（`revisionOf` 指回原任务），原会话保持 `rejected` 只读。

### 2.3 审核层级

```text
ReviewLevel(
  ordinal,                   // 层级序号，从 1 开始
  levelName,                 // 例如"技术审核"、"责任审核"
  requiredApprovals,         // 该层级需要通过的最少人数
  assignedReviewers[],       // 有权限在该层级作出决定的人
  status,                    // pending | approved | rejected | skipped
  decidedBy,
  decidedAt
)
```

- 知识空间可配置一级或多级审核；P0 固定单级，P1 才启用 1-3 级并记录 `flowVersion`。
- 自审允许存在，但自审不能单独使候选通过；当提交者同时是某级审核人时，该级仍需至少一名其他审核人有效通过。
- 层级按 `ordinal` 顺序执行；前一级未通过时，后续层级不进入活跃状态。

### 2.4 审核评论

```text
ReviewComment(
  id,
  sessionId,
  levelOrdinal,              // 属于哪个审核层级
  authorId,
  commentType,               // question | issue | suggestion | approval_note | ai_analysis
  anchor,                    // CommentAnchor，可选
  diffView,                  // DiffView，可选
  body,                      // 评论正文
  aiAnalyses[],              // 附带的 AI 分析记录
  resolved,                  // 是否已解决
  resolvedBy,
  resolvedAt,
  createdAt,
  updatedAt
)
```

- 评论追加保存，不修改候选正文。
- 每条评论可选绑定行级锚点和修改前后对比；不绑定时为全局评论。
- `commentType` 区分人工评论和 AI 分析入口；AI 分析记录在 `aiAnalyses` 中独立存储。

### 2.5 行级锚点

```text
CommentAnchor(
  documentId,                // 目标文档
  nodeId,                    // 稳定节点身份（非标题、非行号）
  anchorKind,                // after_operation | before_operation | baseline
  lineRange,                 // { startLine, endLine }，可选
  charRange,                 // { startChar, endChar }，可选
  contextBefore,             // 锚点前若干字符的上下文指纹
  contextAfter               // 锚点后若干字符的上下文指纹
)
```

- `nodeId` 使用变更操作中的稳定节点身份，不使用标题文本或行号。
- `anchorKind` 明确锚点参考的是基线原文、操作前状态还是操作后状态，避免审核人和作者在视图间混淆。
- `contextBefore/contextAfter` 作为漂移检测指纹；当节点内容因修订变化时，系统可检测锚点是否仍然有效。

### 2.6 修改前后对比

```text
DiffView(
  operationType,             // add | update | delete | move
  beforeContent,             // 基线或操作前的内容片段
  afterContent,              // 操作后的内容片段
  beforeDigest,              // 操作前内容摘要
  afterDigest,               // 操作后内容摘要
  diffHighlight,             // 结构化差异标记（行级增删标识）
  scopeDescription           // 人类可读的变更范围描述
)
```

- `add` 操作 `beforeContent` 为空；`delete` 操作 `afterContent` 为空。
- `diffHighlight` 提供行级增删标记，前端渲染为红绿对比视图。
- `move` 操作同时包含原位置和新位置信息。

### 2.7 AI 分析记录

```text
AiAnalysis(
  id,
  analysisType,              // 见 2.8 节
  modelId,                   // 使用的模型标识
  promptVersion,             // 提示词版本
  reasoningSummary,          // 可审计的结构化推理摘要（旁路解释）
  evidenceRefs[],             // 使用的候选/基线节点、规则和测试证据
  verdict,                   // pass | warn | fail | info
  confidence,                // 0.0 - 1.0
  findings[],                // 结构化发现项
  ruleRefs[],                // 引用的规则版本
  executedAt
)
```

- 每条 AI 分析必须包含可审计的 `reasoningSummary`、`evidenceRefs` 和步骤化 `findings`；前端以可折叠面板展示“推理摘要（Chain-of-Thought 旁路解释）”。不把模型内部不可验证的思维草稿作为接口契约，也不得写入凭证、隐式系统提示词或其他敏感信息。
- `verdict` 只标记 AI 的判断倾向，不代替人工决定。
- `findings` 为结构化数组，每项包含 `severity`、`message`、`affectedNodeId` 和 `suggestedAction`。

### 2.8 AI 分析类型

| `analysisType` | 中文展示 | 检查内容 |
|---|---|---|
| `syntax_check` | SQL 语法检查 | SQL 示例、DDL/DML 语句的正确性 |
| `param_dependency` | 参数依赖检查 | 配置参数的取值范围、互斥和依赖关系 |
| `version_coupling` | 版本耦合预警 | 变更是否影响其他版本的同一参数或命令 |
| `cross_reference` | 交叉引用验证 | 文档间引用链接的有效性 |
| `error_code_unique` | 错误码唯一性 | 新增错误码是否与已有编码冲突 |
| `terminology` | 术语一致性 | 技术术语是否符合术语表 |
| `scope_completeness` | 范围完整性 | 变更集是否覆盖了来源要求的全部修改点 |
| `operation_safety` | 运维安全性 | 运维命令是否包含风险提示和回退步骤 |

### 2.9 发布记录

```text
Publication(
  id,
  handbookId,
  businessVersion,
  targetKey,
  baselineVersionId,
  candidateDigest,
  content,
  operations[],
  publishedBy,
  publishedAt,
  supersededPublicationId,   // 被替代的旧发布记录
  batchId                    // 发布批次 ID（多文档原子发布时使用）
)
```

- 发布时在同一事务中将相同手册和业务版本的旧 `current` 置为 `false`，再将新发布记录置为 `current=true`。
- `supersededPublicationId` 形成显式的版本替代链。

### 2.10 血缘记录

```text
LineageRecord(
  taskId,
  candidateDigest,
  revisionChain[],           // 修订链：[原始任务ID, 第一次修订ID, ...]
  sourceSnapshotIds[],       // 来源快照
  reviewSessionId,           // 审核会话
  publicationId,             // 发布记录
  previousPublicationId,     // 上一个发布版本
  createdAt
)
```

- 血缘记录从任务创建时开始积累，贯穿修订、审核和发布全生命周期。
- 修订任务的 `revisionChain` 继承原任务的链条并追加自身。
- 血缘记录不可修改，只追加。

## 3. 审核流程状态机

### 3.1 审核会话状态

```text
                    ┌────────────────────────────────────────────────┐
                    │                                                │
                    ▼                                                │
[created] ──→ [in_progress] ──→ [approved] ──→ [published] ──→ [superseded]
                    │                  │
                    │                  └──→ [withdrawn]（发布者撤回）
                    │
                    └──→ [rejected] ──→ 创建修订任务 ──→ [新审核会话]
```

| 状态 | 中文展示 | 允许动作 |
|---|---|---|
| `pending` | 待启动 | 分配审核人、开始审核 |
| `in_progress` | 审核中 | 评论、AI 分析、层级决定 |
| `approved` | 审核通过 | 发布、撤回 |
| `rejected` | 审核拒绝 | 创建修订任务 |
| `withdrawn` | 已撤回 | 重新发起审核（新会话） |
| `superseded` | 已替代 | 只读 |

### 3.2 审核层级状态

```text
[pending] ──→ [approved]（该层级通过）
    │
    └──→ [rejected]（该层级拒绝，会话进入 rejected）
              │
              └──→ [skipped]（前级拒绝后，后续层级标记为 skipped）
```

### 3.3 审核决定规则

```text
单级审核：
  requiredApprovals = 1
  提交者 ≠ 审核人
  审核人通过 → approved

多级审核：
  第 1 级全部通过 → 第 2 级激活
  第 N 级全部通过 → 会话 approved
  任一级别有审核人拒绝 → 会话 rejected

自审规则：
  提交者在某级审核人中 → 该级 requiredApprovals 至少为 2
  或该级至少还需一名非提交者有效通过
```

## 4. 审核评论交互设计

### 4.1 评论创建流程

```text
审核人在差异视图中选择文本范围
→ 系统自动关联 nodeId 和行范围
→ 生成 CommentAnchor
→ 自动提取 DiffView（该节点的操作前后对比）
→ 审核人输入评论内容
→ 可选触发 AI 辅助分析
→ 提交评论
```

### 4.2 评论类型与行为

| `commentType` | 行为 | 是否触发 AI |
|---|---|---|
| `question` | 对修改内容的疑问，不阻断通过 | 否 |
| `issue` | 发现的问题，需要作者回应 | 可选 |
| `suggestion` | 修改建议，作者可一键采纳 | 可选 |
| `approval_note` | 通过说明，记录审核理由 | 否 |
| `ai_analysis` | AI 自动或触发的分析结果 | 是（本身就是 AI 输出） |

### 4.3 评论解决

- 评论可标记为 `resolved`；解决不删除评论内容，只标记状态。
- 只有任务创建者或当前层级审核人可标记解决。
- 存在未解决的 `issue` 类型评论时，审核人作出 `approve` 决定前系统显示提醒（不阻断）。

### 4.4 评论权限

| 角色 | 可执行动作 |
|---|---|
| 任务创建者 | 回复评论、标记解决、查看全部 |
| 当前层级审核人 | 创建评论、作出层级决定、查看全部 |
| 其他层级审核人 | 查看该层级评论（只读） |
| 平台管理员 | 查看全部评论，不创建评论或决定 |
| 无权限用户 | 按任务不存在处理 |

## 5. AI 审核协作者设计

### 5.1 触发时机

AI 分析在以下时机触发：

| 时机 | 触发方式 | 分析类型 |
|---|---|---|
| 候选固化时 | 自动 | `scope_completeness`、`syntax_check` |
| 审核会话创建时 | 自动 | 全量分析（8 种类型） |
| 审核人手动触发 | 审核人在评论中 @ai 或点击"AI 分析" | 指定类型 |
| 修订任务创建时 | 自动 | 对比原审核意见，检查修订覆盖度 |

### 5.2 AI 分析输出格式

```text
┌─────────────────────────────────────────────┐
│ 🔍 AI 分析：参数依赖检查                      │
│ 置信度：0.87                                  │
│ 判定：⚠️ 警告                                 │
├─────────────────────────────────────────────┤
│ 推理摘要（Chain-of-Thought 旁路解释）：          │
│                                               │
│ 1. 检测到本次修改涉及参数 max_connections       │
│ 2. 查询参数依赖表，发现 shared_buffers 存在     │
│    联动关系：max_connections ≤ shared_buffers   │
│    × 32                                       │
│ 3. 当前文档中 shared_buffers 章节未同步更新     │
│ 4. 结论：修改可能导致参数配置不一致             │
│                                               │
├─────────────────────────────────────────────┤
│ 发现项：                                      │
│ • [警告] max_connections 修改后，              │
│   shared_buffers 章节（node: param-sb-001）    │
│   可能需要联动更新                             │
│ • 建议：在变更集中增加 shared_buffers 章节      │
│   的联动说明，或在参数说明中增加交叉引用        │
├─────────────────────────────────────────────┤
│ 引用规则：参数依赖规则 v2.3 §4.2               │
│ 模型：yashan-doc-reviewer v1.2                │
└─────────────────────────────────────────────┘
```

### 5.3 AI 分析约束

- AI 分析结果以 `commentType=ai_analysis` 的评论形式保存，与人工评论在同一列表中展示；P0 同步生成摘要，P1 可使用异步任务。
- AI 判定 `fail` 不自动阻断审核通过；系统显示强提醒，由审核人决定是否采纳。
- AI 判定 `pass` 不自动代替审核人通过。
- 所有 AI 输出必须附带结构化推理摘要和证据引用，前端默认折叠、审核人可展开查看；摘要不得声称“模型已执行”未实际执行的数据库验证。
- AI 使用的模型标识、提示词版本和规则版本必须记录，支持事后复盘。
- AI 不读取审核人的历史评论作为自身输入的依据，避免确认偏误；AI 分析只基于候选内容、基线内容和平台规则。

### 5.4 数据库专属检查规则

以下检查规则需要数据库领域知识支持，不能由通用文档审核替代：

| 规则 | 检查内容 | 阻断级别 |
|---|---|---|
| SQL 语法正确性 | 示例 SQL 是否可在目标版本执行 | 警告（需人工确认） |
| 参数依赖完整性 | 修改的参数是否有联动参数未覆盖 | 警告 |
| 错误码唯一性 | 新增错误码是否与已有编码冲突 | 阻断 |
| 运维命令版本适配 | 命令是否适用于目标业务版本 | 阻断 |
| 数据类型兼容 | 新增或修改的数据类型是否在目标版本支持 | 警告 |
| 权限语句完整 | GRANT/REVOKE 示例是否覆盖必要权限 | 信息 |

## 6. 差异视图与修改对比

### 6.1 三级差异视图

审核人查看修改时，系统提供三级视图切换：

| 视图层级 | 展示内容 | 适用场景 |
|---|---|---|
| **结构视图** | 文档大纲的增删改标记，折叠显示变更节点 | 快速了解变更范围 |
| **段落视图** | 按变更节点展开，显示操作前后段落对比 | 逐条审阅修改内容 |
| **行级视图** | 类 diff 的行级增删高亮，支持字符级标记 | 精确检查语法和参数 |

### 6.2 差异视图与评论联动

```text
审核人在段落视图或行级视图中：
1. 选中文本范围 → 系统自动计算 nodeId + lineRange
2. 点击"添加评论" → 弹出评论面板，自动填充 DiffView
3. 评论提交后 → 在差异视图中显示评论标记（气泡图标）
4. 点击标记 → 展开评论详情和 AI 分析
```

### 6.3 锚点漂移处理

当修订任务修改了节点内容后，原审核评论的锚点可能漂移：

- 系统使用 `contextBefore/contextAfter` 指纹检测漂移。
- 锚点仍然有效时正常显示。
- 锚点漂移但可自动匹配时，显示"锚点已偏移"提醒并高亮新位置。
- 锚点无法匹配时，评论标记为"锚点失效"，评论内容保留但不再关联具体位置。
- 修订任务的审核人可以看到原评论及其漂移状态，作为审阅参考。

## 8. 发布流程

### 8.1 发布前置检查

```text
POST /knowledge-center/api/incremental-tasks/{taskId}/publish

前置检查：
1. 审核会话状态为 approved（P0 为单一有效审核决定；P1 还需所有必需层级通过）
2. 候选摘要与提交审核时一致（未被篡改）
3. 当前基线 current=true 且与任务创建时一致
4. 发布者具有该手册和业务版本的发布权限
5. 无未解决的阻断级检查项
```

### 8.2 发布执行

```text
发布事务（单文档目标，P0）：
1. 校验前置条件
2. 将相同 handbookId + businessVersion 的旧 current 置为 false
3. 创建新 Publication 记录，current=true
4. 记录 supersededPublicationId
5. 写入血缘记录
6. 写入审计日志
7. 更新任务状态为 published

发布事务（多文档目标，后续）：
1. 校验全部文档基线
2. 为全部文档生成不可变版本
3. 原子切换全部当前版本指针
4. 写入一个发布批次记录（PublicationBatch）
5. 任一文档失败 → 全部回滚
```

### 8.3 发布后动作

- 发布成功后，任务状态变为 `published`。
- 发布记录不可修改；如需修改已发布内容，必须创建新的增量任务。
- 发布后可登记外部交付证据（GitLab MR 编号、CI 结果等）。

## 9. 外部交付登记

### 9.1 交付类型

| `deliveryType` | 中文展示 | 含义 |
|---|---|---|
| `gitlab_mr` | GitLab 合并请求 | 已创建或已合入的 MR |
| `gitlab_ci` | GitLab CI 运行 | CI 构建和检查结果 |
| `manual` | 人工登记 | 手动记录的外部交付 |
| `other` | 其他 | 其他外部系统交付 |

### 9.2 交付登记约束

- 只有 `published` 状态的任务能登记外部交付。
- 交付登记不改变发布内容，只记录外部衔接事实。
- GitLab MR/CI 交付在真实连接器接入前只能人工登记，不得显示为系统已自动同步。
- 交付状态包括：`pending`（待确认）、`success`（成功）、`failed`（失败）。

### 11.4 P0 前端实施契约

审核工作台只服务一个判断：审核人是否可以对当前候选版本作出通过或退回决定。默认视图采用“主阅读区 + 上下文侧区 + 固定决策栏”，不同时展开四个同等权重的面板。

| 区域 | 默认内容 | 必须支持的状态 |
|---|---|---|
| 页头 | 手册、业务版本、候选摘要、审核状态、数据更新时间 | 候选摘要变化、读取失败 |
| 摘要带 | 变更文档数、阻断项、警告、未解决评论、基线版本 | 空值显示“0/未知”，不得伪造统计 |
| 主阅读区 | 结构/段落/行级差异；选中文本创建评论 | 行级可用、全局评论兼容模式、锚点漂移/失效 |
| 上下文侧区 | 当前节点的基线、候选、AI 推理摘要、证据和规则版本 | AI 处理中、无分析、分析失败 |
| 评论区 | 全部/我的/阻断/未解决筛选；评论与 `nodeId` 双向定位 | 草稿保留、冲突、无权限 |
| 决策栏 | “退回并说明”“通过审核”；发布另起确认页 | 进行中、成功、失败、冲突 |

P0 必须实现行级定位：评论请求携带 `documentId/nodeId/lineRange/charRange`、锚点上下文指纹和候选摘要。若服务端能力协商不支持锚点，只能进入“全局评论（兼容模式）”，并在页面和审计中明确标注。

发布按钮不与审核决定并列。发布确认必须依次展示候选摘要、当前基线、影响文档、阻断项和外部交付状态，用户二次确认后才提交 `expectedCandidateDigest`。

页面视觉遵循乔布斯式产品原则：高对比正文、稳定网格、单一动作色、无渐变和装饰性大卡片；图标使用 Lucide 并带中文无障碍名称；所有状态同时使用文字、图标和颜色；动画仅用于状态变化且支持 `prefers-reduced-motion`。

## 13. 测试与验收门禁

### 13.1 审核流程测试

- 单级审核：提交者 ≠ 审核人；审核人通过后会话进入 `approved`。
- 多级审核：前级未通过时后续层级不激活；全部通过后会话进入 `approved`。
- 自审场景：提交者在审核人中时，该级仍需其他审核人通过。
- 审核拒绝后可创建修订任务；修订任务的新审核会话独立于原会话。
- 撤回审核后原会话进入 `withdrawn`，可重新发起新会话。

### 13.2 评论与锚点测试

- 评论创建时自动关联 `nodeId` 和行范围。
- 锚点使用 `contextBefore/contextAfter` 指纹；修订后锚点漂移时正确检测和标记。
- 锚点完全失效时评论保留但标记为"锚点失效"。
- 评论类型、层级过滤正确。
- 只有授权角色可创建评论和标记解决。

### 13.3 AI 分析测试

- 候选固化时自动触发 `scope_completeness` 和 `syntax_check`。
- 审核会话创建时自动触发全量分析。
- 手动触发指定类型分析正确执行。
- AI 分析结果以评论形式保存，包含 `reasoningSummary`、`evidenceRefs` 和结构化发现项。
- AI `fail` 不自动阻断审核通过；AI `pass` 不自动代替审核人通过。
- AI 分析不读取审核人历史评论作为输入依据。

### 13.4 发布测试

- 发布前置检查：审核通过、候选摘要一致、基线 current。
- 发布事务原子性：旧版本 `current=false` 和新版本 `current=true` 在同一事务中完成。
- 发布失败不改变原发布基线。
- 发布后可登记外部交付证据。
- 已发布任务创建修订任务时正确继承血缘链。

### 13.5 血缘追溯测试

- 血缘链正确记录从任务到发布的全生命周期。
- 修订任务的 `revisionChain` 正确继承和追加。
- 血缘查询 API 返回完整链条，包含审核和 AI 分析摘要。
- 前端血缘视图正确展示修订和替代关系。

## 17. 页面设计修订（2026-09-04）

本节是本轮前端实现的准确信息来源，替代本文 11.1 中将正文、差异、评论和决策同时铺开的旧版工作台示例。知识资产详情页右侧五个操作入口及其布局保持不变；仅改造点击“审核与发布”后的页面。

### 17.1 三步工作流

审核页面按单一重点分为三个步骤，当前步骤通过地址栏 `step=read|diff|opinions` 保留，刷新或前进后退不会丢失手册、审核事项和文档位置：

1. **阅读文档**：保留分支选择、语言切换、文档目录和 Markdown 正文阅读。此处只回答“要阅读哪篇文档、当前内容是什么”。
2. **查看修改**：独立显示正式版本与修改稿的完整全文，支持左右对照、逐行差异、修改统计（新增/修改/删除/移动），并在行号上选择位置添加意见。全文来自 `GET /knowledge-center/api/incremental-tasks/{taskId}/diff`，基线缺失时显示真实空态说明。
3. **处理审核意见**：集中显示人工意见和系统检查结果，支持标记处理、退回修改、审核通过；发布需单独确认，不与审核决定并列。

### 17.2 版本和跳转用语

审核完成前统一显示“正式版本：v1.0.1”“待审核版本：修改稿”“状态：审核中/待发布”，不得把未来版本号当作已生效版本。发布成功后，服务端才返回并展示新的正式版本号（例如 v1.0.2）及发布时间。

左侧导航使用“全部审核事项”。点击事项后以 `handbookId`、`taskId` 进入对应手册的审核页面；手册详情入口与左侧入口最终落到同一审核页面。页面返回和步骤切换均保留当前手册、业务版本、文档、章节、修改稿和审核任务信息。

### 17.3 行级意见交互

差异全文中的每个行号都是可操作控件。选择行号后，评论表单自动写入 `documentId`、`nodeId`、行范围、候选摘要；提交失败保留已填写内容。服务端无法解析节点时必须明确提示“全文意见（兼容模式）”，不得伪装为精确定位。

阅读文档时采用“选区即操作”：用户选中正文文字后，页面在选区附近显示“提出意见”气泡；点击气泡后在阅读区打开内联输入框，展示截取的原文引用并提交默认普通意见。提交请求复用当前审核线程，携带候选摘要和 `document_span` 锚点；服务端返回后重新加载审核投影，保证意见真实落库并在“处理审核意见”步骤可见。气泡仅在有效选区存在时显示，滚动、切换文档或取消输入时隐藏，不以侧栏表单是否展开作为交互前置条件。侧栏“提出意见”仅保留全文意见兼容入口。

### 17.4 多角色实现与 E2E 验收（2026-09-06）

本轮按“认证角色 → 服务端 capabilities → 页面动作门禁”的多角色链路实现，禁止按登录名在前端或增量服务中写死权限：

| 角色 | 角色来源 | 可见/可执行能力 |
|---|---|---|
| 阅读角色 | `KNOWLEDGE_EDITOR` 或包含 `knowledge:read` 的角色 | 阅读基线、候选快照、目录、分支和语言；不可审核、发布 |
| 审核角色 | `REVIEWER`/`PLATFORM_ADMIN` 的 `review:manage` | 在候选摘要一致时提交行级意见、退回或通过；不可修改正式正文 |
| 发布角色 | `PLATFORM_ADMIN` 或包含 `publish:manage` 的角色 | 仅对已通过独立审核的候选执行二次确认发布 |

服务端在任务投影中返回 `capabilities.canReview/canPublish/canComment`，前端仅据此渲染动作；审核决定完成后重新读取审核投影，确保门禁和按钮状态不陈旧。内置 `test/test` 账号仅绑定 `KNOWLEDGE_EDITOR`，角色仍可通过平台权限管理调整。

E2E 用例 `tests/e2e/knowledge-center-review-publishing.spec.js` 覆盖真实认证、任务创建、候选冻结、审核提交、差异读取、行号锚点、审核通过和发布 API；GitLab 正文使用明确标注的受控夹具，以隔离尚未打通的 OAuth。另验证知识编辑角色在同一页面无审核/发布动作，以及 375px 视口无横向溢出。

### 17.5 单一任务工作台与诚实状态修订（2026-09-07）

本节处理的是页面体验 P0/P1，不改变 §1.1.1 中领域能力的 P0/P1 边界。

```text
┌ 审核与发布 / 当前任务：安装手册参数修订 ▾              [审核中] ┐
│ 手册 DB-001 · 23.4 | 基线 v1 → 修改稿 | master / 中文 / a95…  │
├───────────────────────────────────────────────────────────────┤
│ 1 阅读文档          2 查看修改          3 处理审核意见          │

│ 文档目录      │ 文档正文/差异主阅读区              │ 审核信息      │
```

页面体验 P0：

1. 审核事项为空时只渲染完整空态，不渲染任务详情、仓库正文、角色或证据。
2. `unknown`、`未返回` 等实现占位符不得进入用户界面；未知状态统一进入“任务数据异常”并给出刷新和返回知识资产动作。
3. 任务详情必须具备任务标识、手册、业务版本、正式基线、候选摘要和受支持状态；缺一项即阻断差异、评论、审核和发布。
4. 目录选中路径、正文返回路径、请求路径必须一致；不一致时显示“文档上下文不一致”，清除旧正文并阻断审核决定。
5. 任务切换、无任务和加载失败时清理旧 GitLab 阅读投影，禁止展示上一个任务的文档。

页面体验 P1：

1. 常驻审核事项栏改为页头任务选择器，使正文获得主要横向空间。
2. 分支、语言、提交和更新时间收拢为单一上下文工具栏；无提交时明确标记“候选快照”，不显示“未知”。
3. 角色、AI 和血缘合并为“审核信息”抽屉，阅读/差异步骤默认收起，意见步骤默认展开。
4. 审核决定仅在“处理审核意见”步骤的底部决策栏出现，并显示未解决意见数量。
5. 1440、1024、768、375 像素视口均不得横向溢出；移动端目录、正文和审核信息按顺序纵向排列。

### 17.6 评审入口可达性修订（2026-09-07）

§17.5 的空态约束只负责防止旧任务和旧正文泄漏，不能替代审核主流程。审核页面必须按入口上下文分流：

```text
GET /knowledge-center/review?taskId={taskId}&handbookId={handbookId}
  ├─ 有 taskId：直接读取指定任务，不先经过活动任务列表过滤
  │    ├─ 可读取：进入 §17.5 单一任务工作台
  │    └─ 不存在或不可读取：显示明确错误和恢复动作
  ├─ 仅有 handbookId：读取该手册审核汇总和仓库正文
  │    ├─ 有活动候选：打开最近更新的候选
  │    └─ 无活动候选：保留目录/正文，显示“等待候选”及“前往文档生产”
  └─ 无上下文：有待办则打开最近任务；无待办则选择首个可见且已映射仓库的手册，进入阅读/评审准备工作台；没有任何可读手册时才显示全局空态
```

接口与页面契约：

1. 活动审核状态统一包含 `under_review`、兼容态 `review_pending`、`approved` 和 `pending_publish`；状态集合后续应下沉为服务端投影，前端不新增业务状态。
2. 合法 `taskId` 是显式深链接，前端必须调用 `GET /incremental-tasks/{taskId}`；候选待提交、任务已经退回或发布时，也不得静默替换为其他任务或普通空态，其中 `candidate_ready` 明确显示“待提交审核”。
3. 仅携带 `handbookId` 且没有活动候选时，继续加载 GitLab 手册目录和正式正文；差异、意见和决定步骤禁用，右侧审核信息区改为评审准备说明。
4. “前往文档生产”链接必须携带原 `handbookId`；候选提交成功后的入口必须携带 `taskId`，从而形成可重复打开的评审路径。
5. 空数据、指定任务不存在、任务不可访问、仓库不可读是四种不同状态，禁止统一显示“当前没有待处理审核事项”。
6. 左侧导航进入且无待办时，页面以用户可见且已映射仓库的第一本手册作为默认阅读上下文，并允许在页头切换手册；这只是阅读与发起评审入口，不得生成虚假候选、审核意见或通过状态。

前端伪代码：

```js
if (taskId) detail = await getTask(taskId);
else items = await listReviewTasks(handbookId);

if (detail) renderReviewWorkspace(detail);
else if (handbookId) renderHandbookReaderWithReviewPreparation();
else renderGlobalReviewEmptyState();
```

E2E 必须通过真实认证和增量构建 API 创建候选并提交审核，再验证深链接、默认任务选择、行级意见、独立审核和发布；GitLab 正文允许在 OAuth 联调环境不可用时使用明确标注的受控夹具。

### 17.7 页面体验 P0/P1 实施结果（2026-09-07）

本轮在不改变审核状态机和服务端权限事实的前提下完成页面体验优化：

- P1：专注阅读（Esc 退出）、默认舒适正文排版、目录修改/未解决意见标记（仅由 operation/comment 锚点驱动）、步骤计数、J/K 与 `[`/`]` 键盘导航、结构化加载骨架、数据库专项检查“尚未执行”降级、AI 证据和版本血缘时间线、历史任务只读入口。

- `checks` 中没有数据库专项分类时明确显示“尚未执行”；没有 AI 投影时显示“暂无真实 AI 分析结果”，不把空结果渲染为通过。
- 在线协同、领取/转交、AI 异步预判和自动修复仍需后端真实契约，页面不得伪造。

#### Markdown 锚点渲染安全边界

知识资产阅读与审核阅读共用 Markdown 渲染器。数据库手册用于目录跳转的空锚点，例如 `<span id="YFS" name="YFS"></span>`，允许渲染为真实 DOM 锚点；仅接受 `id/name` 属性，属性值必须符合稳定标识符格式。包含事件、样式、脚本、非法标识或正文内容的原生 HTML 不在白名单内，继续转义显示。对应单元门禁位于 `agent-runner/tests/知识中心管理平台门禁/markdown-renderer.gate.test.js`。

审核阅读区启用 YashanDB 数据库增强规则包，对 SQL、参数、数据类型、错误码和运维命令做不打断阅读的正文轻量标记；不额外展示数据库内容索引、规则命中列表或分析面板。规则只表达本地识别结果，不生成版本兼容、安全或执行成功结论；SQL、运维命令和 Mermaid 内容均不可在阅读区执行。增强资源随前端打包，缺少增强运行时时继续使用安全 Markdown 降级渲染。

### 17.9 审阅体验重构：文档内联批注 + 选区即操作（2026-09-08）

本轮对标 Google Docs / Word 审阅体验，将"提出意见"从侧栏表单改造为文档内联批注系统。

核心交互变更：

- **选区即操作**：选中正文文字后出现浮动气泡按钮（💬），点击后在选区位置弹出内联批注输入框。不再静默填充侧栏 textarea。
- **内联批注标记**：已有意见以内联卡片形式渲染在文档右侧，包含行号徽标、内容预览、作者和状态。
- **全文意见区**：无锚点的全文意见统一显示在文档底部的折叠区。
- **侧栏抽屉重构**：评论抽屉默认折叠，展开后显示当前文件的已有意见列表 + 全文意见表单。
- **提交即时渲染**：提交意见后，新意见立即以内联批注形式出现在文档旁，无需刷新。
- **选区保护**：内联输入框使用只读引用展示选中文字，不覆盖用户已输入内容。
- **滚动隐藏**：页面滚动时自动隐藏选区气泡，避免位置偏移。

术语清理（面向用户）：

| 原技术术语 | 改为 |
|---|---|
| 全文意见（兼容模式） | 全文意见 |
| 选中正文文字后可关联位置 | 选中文字可精准定位 |
| 未找到可确认的文档节点 | 未能定位到具体段落 |

移动端降级：内联输入框降级为底部固定弹出面板，批注标记改为单栏堆叠。

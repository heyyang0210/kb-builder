# 知识中心-任务管理-详细设计文档

## 2026-11-05 角色待办与交付按钮设计

工作台沿用任务管理、文档生产和审核服务的事实，不保存第二套流程状态。工单责任人继续在任务管理确认工单范围、分派手册；四类主要视图从手册负责人接手后开始。用户只看到与本人职责相符的当前操作，列表主按钮直接进入具体业务对象，任务详情中的“下一步”也直接提供可执行入口。状态提示保持紧凑，不在工作台放全链路流程图。

| 责任人 | 服务端待办条件 | 主按钮 |
| --- | --- | --- |
| 手册负责人 | 手册范围尚未确认且本人有 `knowledge:write` | 确认文档范围 → 工单详情中打开对应手册范围操作 |
| 文档撰写人 | 文档已分派且未完成、未在当前审核中；退回时仍由本人修订 | 进入文档编写 → 现有 `writingUrl`，保存后用现有“提交审核” |
| 文档审核人 | 当前候选中的该篇文档明确指派本人且待决定 | 开始审核 → 审核工作区的具体 `taskId` 和 `documentId` |
| GitLab 合入负责人 | 当前 MR 已创建且 `participants.assignees[].platformId` 匹配本人、回读未完成 | 前往 GitLab 合入 → 已验证的 HTTPS MR 地址 |

已审核的任务由具有 `publish:manage` 权限的任务提交人在审核页创建 MR，选择合入负责人；审核人映射 GitLab Reviewers，合入负责人映射 Assignees。平台不合并 MR。合并后仍由具有发布权限的提交人刷新交付状态，只有正文和仓库相对图片回读都一致才完成。审核逐篇决定，退回只产生对应篇修订；全部通过前服务端拒绝创建 MR。

审核 bootstrap 的 `view=mine` 增加只读 `workbench.myMergeRequests`，每项只包含 `taskId`、`handbookId`、`title`、`businessVersion`、`documentNames`、`mergeRequest.iid/webUrl/state`、`deliveryObservation.state`、`updatedAt`。服务端按可信会话身份与持久化平台 Assignee ID 精确匹配，并按手册可见范围过滤；只有 `mr_submitted` 且尚未完成的 MR 才列出。链接只接受无账号密码的 HTTPS。该摘要不扩大通用 `canRead`、候选正文或审核/发布 API 权限。工作台将其作为第四来源聚合，与审核待办分开，来源失败时仍显示其它来源。

任务详情“下一步”从当前任务的服务端 capability 决定可执行主操作：未确认工单范围→确认工单范围；本人负责未确认手册→确认文档范围；本人负责可编辑文档→进入文档编写；有权处理的审核/发布→对应审核页。没有本人可执行动作时只显示等待状态。原有细粒度操作、历史和工单跟进信息保留。

个人待办的 `action=ticket-scope/book-scope/new-document/complete` 深链定位既有任务详情操作；前端先核对服务端返回的工单、手册或文档能力及目标 ID，再自动打开相应弹窗。一个工单有多本手册或多篇文档时，目标操作按具体 ID 定位，不依赖单一 `nextAction` 的排序。无变更确认从 `/mine` 返回 `action=complete`，仅当前工单责任人且服务端允许时出现。关闭的 MR 在合入负责人待办中标为“MR 已关闭”，按钮改为“查看 GitLab MR”，避免错误暗示仍可合入。

验收：真实隔离 HTTP 验证身份/权限过滤、逐篇审核与 MR 投影；浏览器验证主按钮深链、桌面/390px 布局、来源部分失败。四类角色按可发现性、角色隔离、操作正确性、完成情况评分，目标至少 90/100；隔离 GitLab 替身不冒充真实 MR 合并验收。真实 GitLab 仅在既定测试分支和目录验证创建与人员映射，不合并 MR。

## 1. 页面与运行入口

一级导航为“任务管理”，图标沿用平台 Lucide；列表为默认视图，另有“流程流转”和管理员“任务配置”。路由仍为 `/knowledge-center/document-tasks`，通过平台路由处理直接访问、刷新和浏览器历史。

用户此前看不到入口有两个已查明原因：认证模块的业务可见模块缺少 documentTasks；任务页直接操作 DOM，而通用渲染器要求返回 HTML，因而覆盖页面。分别修正角色模块投影与专门挂载分支。运行静态目录与源码分离，发布后必须比较实际 HTTP 资源摘要，不能用源码存在推断运行生效。

## 2. 服务与信任边界

浏览器 → 已认证 Web 网关 → 任务业务路由 → 现有聚合存储。生产使用数据库 namespace=`document_tasks`、key=`state`，不新增数据库表。文件模式使用 `runtime/knowledge-center/document-tasks-v2.json`，主要用于隔离验证。

网关从可信会话取用户，稳定人员身份优先 principalId，不能采信请求体 actorId。网关读取有效人员目录、资产可见范围、现有审核服务，并通过私有上下文调用任务路由。未经上下文的内层 `/api/document-tasks` 拒绝访问。目录和新增候选经内部 HTTP 调用文档 API，携带网关内部令牌与实际动作权限；新候选路由也受文档服务内部令牌中间件保护。

数据库聚合事务提供版本比较写入；文件模式为单进程隔离验证，不承诺多进程并发。依赖不可用时返回失败，不回退到空文件假装成功。

## 3. 数据关系与 Schema

契约文件：`packages/platform-contracts/knowledge-center/v1/document-task.schema.json`。

| 对象 | 主要字段 | 规则 |
| --- | --- | --- |
| 聚合 | schemaVersion=2, revision, config, tasks, audits, idempotency | 配置、任务、审计和幂等结果同事务保存 |
| 配置 | revision, defaultOwnerId, reasonOptions, pingcodeProjectUrl | pingcodeProjectUrl仅作旧数据兼容，前端不编辑、不用于生成来源链接；默认值来自 content-rules.json；初始 defaultOwnerId=177 对应真实目录何灿；姓名动态读取 |
| 任务 | number, description, ownerId, product, version, source, sourceStatus, sourceCreatedAt, output, revision, createdAt, updatedAt, startTime, plannedStartTime, plannedEndTime | number 是全局键，无另一个 id；来源创建时间不充当实际开始时间；计划时间独立保存 |
| 工单判断 | decomposition.ticketImpact, ticketReason, confirmed, handbooks | impact 为 null/involved/not_involved；未确认为待办，不填默认理由 |
| 手册判断 | id, name, ownerId, impact, reason, confirmed, targetVersion, documents | id 是稳定手册ID，版本来自真实目录/映射分支 |
| 文档 | id, kind, name, parentId, ownerId, createdDocumentId, outlineProposal, reviewTaskId | kind=existing/new；新增前 id 为稳定提案键，创建后记录真实文档ID；手册+文档复合定位 |
| 历史 | assignmentHistory, scopeHistory, audits | 保存旧范围及其交付关联；改派记录旧值/新值/操作者/时间（保留历史已有理由，新改派不要求理由） |
| 无变更确认 | noChangeConfirmation.at/operatorId | 只由工单责任人显式确认；范围修改后失效 |
| 只读投影 | status, endTime, pending, canConfirm/canAdmin, book.completed/canEdit, doc.completion/writingUrl/canEdit | 不允许客户端提交完成事实；每次读取从既有审核交付服务重新汇总 |

source 保留规范化来源快照。字段映射：编号/number/id→number，描述/description/标题/title→description，产品→product，版本号/复现发布号→version，来源状态/状态→sourceStatus，负责人→sourceOwner，创建时间→sourceCreatedAt，输出件/说明→output。空产品/版本显示“未指定”。重新导入更新来源信息，保留所有人工分派、范围、历史与交付。

### 输出件列的交付链接（2026-11-04）

任务列表的“输出件”由现有只读投影组合展示，不新增写入字段：逐篇读取 `decomposition.handbooks[].documents[]` 的 `name`、`writingUrl`、`reviewTaskId` 和 `completion.mergeRequest.webUrl`，分别链接到文档编写页、审核页和企业 MR。文档链接显示实际文档名称；末尾 `.md` 仅在视觉标签中省略，例如“工作台验收说明.md”显示为“工作台验收说明”。审核与 MR 仍显示短标签；不显示 MR 编号或导入的 `output` 说明。完整名称保留在悬停提示和无障碍名称中。审核链接使用稳定任务与文档 ID；MR 只接受有效的 HTTPS 网页地址。未创建或不可读取的产物不生成链接。多个文档按手册/文档顺序排列，重复 URL 去重；前三项直接显示，其余链接用“+数量”展开，展开控件保留完整无障碍名称。文档名称超出有限列宽时省略，窄屏在单列任务行内显示输出件，不遮挡其他内容。详情中的原链接与权限判定不变。

伪代码：`for book/document in task.decomposition: add(name + valid writingUrl); add(reviewTaskId ? review URL : none); add(valid HTTPS mergeRequest.webUrl); render unique links`。页面只展示现有后端关联，不推断 MR 已合并或任务已完成。

## 4. 权限矩阵

所有读取需要 knowledge:read；所有责任范围操作还需 knowledge:write。人员必须在有效目录中，手册必须可见。任务包含不可见手册时整单不暴露，避免详情泄露其他资产。

| 操作 | 业务责任 | 附加权限 |
| --- | --- | --- |
| 读取、搜索、查看流程 | 有资产可见权的登录用户 | knowledge:read |
| 导入、配置、责任人改派 | 平台管理员 | platform:manage |
| 工单范围及手册负责人分派 | 当前责任人 | knowledge:write |
| 手册范围及文档负责人分派 | 当前该手册负责人 | knowledge:write |
| 创建新增文档候选 | 当前该文档负责人 | knowledge:write + outline:create |
| 关联已发布新增文档、审核交付 | 当前文档负责人 | knowledge:write |
| 无变更确认完成 | 当前责任人 | knowledge:write |

管理员不能以管理权限替其他责任人作出范围决定；需要处理时先改派，保留审计。没有 outline:create 的文档负责人由具备权限的目录管理者在既有大纲页面发布/创建，再关联真实文档。已有写作、审核、MR 人员映射继续采用原服务权限，不新增越权捷径。

## 5. 状态与完成计算

状态仅三种：pending_scope（待处理）、in_progress（处理中）、completed（已完成）。退回、关闭、回读失败是处理中子项的原因，不再另存 blocked 状态造成双重事实。

1. 工单未确认 → pending_scope，手册不能确认。
2. 工单确认涉及至少一本手册 → in_progress，可立即转交，各手册保持自己的判断。
3. 手册涉及至少一篇文档，负责人及目标版本齐全才能确认；草稿可缺负责人，但已填的人员/文档必须真实有效。
4. 每篇关联审核任务须匹配手册、文档及目标仓库分支；`businessVersion` 是独立的数据库业务版本，不得拿来与仓库分支比较。读取既有 IncrementalBuildService completion。创建 MR、审核通过都不能直接完成。
5. 只有全部涉及手册均确认且全部文档 completion.status=completed，其他手册理由齐全，工单才 completed。
6. 工单直接不涉及或所有手册不涉及，须理由完整且责任人调用 complete，才 completed。
7. startTime 在首次工单确认时写入；endTime 是无变更确认时间或最后一个必要交付 completedAt 的只读投影。来源更新不重置完成；范围修改重新计算并撤销无变更确认。

新增定义的标题/章节改变时清除旧创建及审核关联；工单草稿不开放文档处理。范围调整把旧范围完整留在 scopeHistory 和审计，不删除已交付记录；新增文档没有关联时进入未完成。目标版本变化后旧审核关联不匹配，将显示待重新关联，不能沿用错误版本的完成状态。

## 7. 新增文档与既有交付衔接

新增提案由工单号、手册、提案键、标题、章节和版本计算确定性SHA256键。内部 `POST /api/outline/governance/:outlineId/document-proposals` 先校验幂等键并复用已提交结果，再按稳定候选ID查重；复制现有目录并保留既有节点ID，仅增加新节点。使用现有候选验证、路径模板与仓储 append 能力，源大纲不变。

负责人在详情点击“创建大纲候选”，再“打开候选大纲”，由既有大纲流程显式发布。发布后返回任务选择同章节/标题的真实文档，调用 resolve-new。此分步方式保留现有目录发布边界，界面不能宣称候选创建即已发布。事务冲突可能留下未关联候选，重试按确定性ID复用。

进入编写链接携带 handbookId、documentId、branch=targetVersion 和 taskNumber。编写、草稿、送审、退回、重审、MR人员映射均沿用既有页面。送审后在任务详情“关联审核与交付”中选择匹配审核任务；不是用户填写完成状态。关联后的关闭/退回/回读结果由后端动态读取，不自动合并企业MR。

2026-11-04 真实验收纠偏：当前任务字段 `targetVersion` 实际来自仓库分支目录（例如 `master`），而审核的 `businessVersion` 可以是“版本待核对”。关联候选、提交与进度回读均校验 `handbookSource.branch` 及冻结文档 `branch`、`documentId`，保留独立的业务版本事实。审核目录展示使用冻结文档的 `filePath` 判断是否已有路径映射；新增文件在目标分支尚不存在时也属于已明确映射。共享草稿保存优先走异步聚合事务，维持版本检查和幂等语义，并通过 `Server-Timing` 分别记录解析、大纲校验、存储阶段。

2026-11-04 真实新建文档送审补充：仓库中尚无目标文件时，草稿保存使用空内容的 SHA-256 作为基线摘要，使其与送审服务对不存在文件的基线计算一致。已有文件仍使用实际仓库正文摘要；送审时保持服务端基线比较，不绕过并发变化检查。审核中、已提交 MR 的写作待办阶段需从权威审核和交付状态汇总，不能仅以文档任务范围确认状态显示“待处理”。

## 2026-11-02 读取与写入性能约束

- 数据库任务状态读取使用 `readAsync()` 和 Storage ETag 条件读取；同一进程中同一状态记录的并发读共享一个在途请求。无快照时仍读取权威完整记录；有快照时必须向 Storage 校验版本，不能以本地TTL代替新鲜度校验。

`GET /document-tasks/mine` 在原 `items/total` 外返回 `following`。先按可信会话操作者、现有资产可见范围和责任关系过滤未完成工单，再从现有交付投影取得手册、文档的完成标签。该工单若有本人当前行动项，仅进入 `items`；否则进入 `following`。无写权限时保持空投影，不因查询参数切换人员。工单不复制审核决定或合并结果，页面展开只读层级，主操作仍指向任务管理或文档生产原页面。跟进区不计入五类个人待办数；原来源不可用时沿用“部分数据”提示。既有 JSON 数据无需迁移，旧客户端忽略新增字段即可回退。

### 页签状态与异步读取（2026-11-04）

任务列表、流程流转和任务配置是用户显式选择的当前视图。后台列表或上下文请求晚于用户点击返回时，局部重绘必须继承当前页签；只有重新进入任务管理才默认回到任务列表。此规则不改变列表数据、筛选、权限或 URL。验收用延迟列表响应时先切“流程流转”，响应后仍在该页签，再返回列表。
# 2026-11-05 工作台贯穿编号与迁移设计

`document_tasks` 聚合保持 schemaVersion 2，并追加 `nextSubtaskNumber` 与文档 `subtaskNumber`。手册范围写入事务内：先复用同一手册与稳定文档 ID 的原序号，再对新文档按 `nextSubtaskNumber` 递增分配。计数器取现有文档及历史范围的最大值加一，避免旧聚合缺字段时复用；已确认的旧范围由独立迁移预检后幂等回填。相同工单、手册、文档身份的重复写入不得改号；同一工单内序号重复则拒绝。

历史编号登记与工单列表分离，键为审核重审链根任务 ID，值为 HIST 编号及稳定文档 ID 到子任务序号的映射。重审链通过 `revisionOf` 回溯，明确关联通过工单文档的 `reviewTaskId` 查找。零匹配才分配 HIST；多匹配返回 `待核对`，不猜测。浏览器 GET 不得临时写聚合。迁移工具读取审核与工单快照，输出预检报告、备份及待写入补丁；通过审批后在版本检查事务中应用。恢复使用备份聚合并记录回退版本。

个人待办、审核及管理员代办输出 `number`、`subtaskNumber`、`taskType`、`plannedStartTime`、`plannedEndTime`；未知计划时间为 null。工单级与手册级子序号为 null。审核/发布逐文档映射，不凭标题关联。网页只格式化计划时间，不以事件时间补值。权限过滤先于历史关联输出，避免跨手册泄露。

## 1. 目标与 P0 边界

本文冻结 P0 平台内增量构建闭环已经实现的入口、对象、状态、接口、并发、幂等、权限和发布语义：

```text
创建任务
→ 人工录入或选择本地内容
→ 确认目标文档与章节
→ 保存增量草稿
→ 完成发布前检查
→ 固化候选
→ 显式发起审核
→ 评论及审核决定
→ 平台内发布
→ 可选登记人工外部证据
```

统一入口为：

```text
/knowledge-center/api/incremental-tasks
```

P0 不读取 PingCode API，也不创建 GitLab 分支、提交、MR 或 CI。来源只允许“人工录入”和“本地内容”，不得把用户输入的地址、编号或正文显示成 PingCode 连接器已接入、已同步或已校验。

## 2. 已实现对象与事实关系

```text
IncrementalTask
  ├─ SourceSnapshot[]
  ├─ TargetScope
  ├─ Draft
  ├─ Checks
  ├─ Candidate
  ├─ Review[]
  │    └─ Comment[] / Decision
  ├─ Publication
  └─ ExternalEvidence[]

Rejected IncrementalTask
  └─ Revision IncrementalTask(revisionOf)
```

### 2.1 增量任务

```text
IncrementalTask(
  id, name, handbookId, businessVersion,
  baselineVersionId, baselineDigest,
  state, sourceSnapshots[], target, draft, checks,
  candidate, reviews[], publication, externalEvidence[],
  revisionOf, createdBy, createdAt, updatedAt
)
```

- 一个任务绑定一本手册、一个业务版本和一个发布基线。
- `target.documentIds[]` 可包含多个目标文档，`target.sectionIds[]` 保存选定章节。
- 跨业务版本必须拆分任务，避免基线、审核和发布事实混杂。
- 已固化候选不能回到原草稿修改；审核拒绝后通过 `revisions` 创建新任务，旧任务保持只读。
- 创建者拥有任务编辑责任；平台管理员视为任务治理者。审核者只在 `under_review` 阶段可读，发布者只在 `approved/published` 阶段可读。其他主体查询详情或执行命令统一返回 `INCREMENTAL_TASK_NOT_FOUND`，避免泄漏任务是否存在。

### 2.2 来源快照

```text
SourceSnapshot(
  id, sourceType, label, reference,
  content, attachments[], contentDigest,
  capturedBy, capturedAt
)
```

P0 只接受：

| `sourceType` | 中文展示 | 含义 |
|---|---|---|
| `manual` | 人工录入 | 用户在平台内输入并确认的内容 |
| `local` | 本地内容 | 用户从本地资料提供的内容 |

`reference` 只是用户提供的追溯引用，不表示系统访问过该地址。来源写入后作为任务证据保留；候选固化后不能继续增加来源。

### 2.3 目标、草稿与变更集

```text
TargetScope(documentIds[], sectionIds[], language)

Draft(
  content, operations[], editVersion,
  contentDigest, updatedBy, updatedAt
)

ChangeOperation(type, nodeId, ...operationPayload)
```

- 所有操作必须包含 `type`、`documentId` 和稳定 `nodeId`；`type` 只允许 `add`、`update`、`delete`、`move`。
- `update/delete/move` 必须包含 `beforeDigest`。
- `add/update` 必须包含内联 `after` 或 `contentRef`。
- `move` 还必须包含 `targetParentId` 和非负整数 `ordinal`。
- 标题、路径和行号不得作为长期身份。
- 保存时校验最小可重放字段；发布前检查再校验每个 `documentId` 属于 `target.documentIds[]`，且设置了章节范围时每个 `nodeId` 属于 `target.sectionIds[]`。
- 草稿 `editVersion` 从 `0` 开始。每次成功保存后加一。
- 保存时请求体的 `editVersion` 必须等于服务端当前版本，否则返回 `DRAFT_EDIT_CONFLICT`，不覆盖服务器草稿。
- 保存草稿后原检查结果失效，任务回到 `editing`。

### 2.4 检查、候选、审核与发布

```text
Checks(passed, issues[], checkedDraftDigest, checkedBy, checkedAt)

Candidate(
  id, draftDigest, sourceSnapshotIds[], target,
  content, operations[], digest, createdBy, createdAt
)

Review(
  id, candidateDigest, status, comments[],
  submittedBy, submittedAt, decision
)

Publication(
  id, handbookId, businessVersion, targetKey,
  baseVersionId, candidateDigest, content, operations[],
  publishedBy, publishedAt
)
```

- 检查只对 `checkedDraftDigest` 对应的草稿有效。
- `POST .../candidate` 只固化候选，不创建审核实例。
- `POST .../reviews` 显式创建审核实例并进入审核中。
- 审核评论追加保存，不修改候选正文。
- 当前 P0 一个审核实例只有一个最终决定。为满足独立审核，任务创建者或审核提交者不能作为该实例的有效决定人；这是对上游“自审不能成为唯一有效通过”的更严格实现。
- 发布必须确认候选摘要，并再次检查同一手册、业务版本和目标范围的当前基线。

## 3. 统一状态机

```text
draft
  → editing
  → checked
  → candidate_ready
  → under_review
  → approved → published
             ↘ rejected
```

| 内部状态 | 中文展示 | 进入条件 |
|---|---|---|
| `draft` | 待完善 | 任务已创建，尚未形成可检查草稿 |
| `editing` | 编辑中 | 已添加来源、目标或草稿；检查失败也回到此状态 |
| `checked` | 检查通过 | 当前草稿摘要通过发布前检查 |
| `candidate_ready` | 候选已固化 | 候选摘要已冻结，尚未发起审核 |
| `under_review` | 审核中 | 已显式创建审核实例 |
| `approved` | 待发布 | 独立审核通过 |
| `rejected` | 已退回 | 审核拒绝；可创建修订任务 |
| `published` | 已发布 | 平台发布记录已形成 |

检查失败不增加新的任务状态，保持 `editing` 并通过 `checks.passed=false` 和 `issues[]` 展示原因。修订不是原任务逆向迁移，而是创建带 `revisionOf` 的新任务；新任务从 `editing` 继续。

## 4. HTTP API 契约

所有接口都位于统一入口下。所有写请求必须携带：

```http
Idempotency-Key: <本次业务命令唯一键>
Content-Type: application/json
```

读取接口不要求幂等键。当前并发令牌只使用草稿请求体中的 `editVersion`，不使用 `If-Match`。文件仓储在取得排他锁后完成“读取—业务校验与修改—写临时文件—原子替换”的完整事务。

### 4.1 任务、来源和目标

| 方法与路径 | 用途 |
|---|---|
| `GET /knowledge-center/api/incremental-tasks` | 查询有权查看的任务，支持 `handbookId`、`state` |
| `GET /knowledge-center/api/incremental-tasks/baselines` | 按手册和业务版本查询可见的已发布基线；无匹配返回空数组 |
| `POST /knowledge-center/api/incremental-tasks` | 创建增量任务 |
| `GET /knowledge-center/api/incremental-tasks/:taskId` | 读取完整任务工作区投影 |
| `POST /knowledge-center/api/incremental-tasks/:taskId/sources` | 添加 `manual` 或 `local` 来源快照 |
| `PATCH /knowledge-center/api/incremental-tasks/:taskId/target` | 更新目标文档、章节和语言 |

创建任务请求：

```json
{
  "name": "安装手册增量修订",
  "handbookId": "DB-001",
  "businessVersion": "23.4",
  "baselineVersionId": "v1",
  "baselineDigest": "可选基线摘要"
}
```

基线查询使用 `handbookId` 和 `businessVersion` 参数，返回 `id`、`handbookId`、`businessVersion`、`current`、`contentDigest` 和 `publishedAt`。页面只允许选择 `current=true` 的基线。创建任务时 `RepositoryBaselineProvider` 再次校验基线属于相同手册与业务版本并且仍是当前发布版本：不存在返回 `BASELINE_NOT_FOUND`，已被替代返回 `BASELINE_CONFLICT`。

来源请求：

```json
{
  "sourceType": "manual",
  "label": "SR需求说明",
  "reference": "可选人工追溯编号或地址",
  "content": "用户确认后的来源正文",
  "attachments": []
}
```

目标请求：

```json
{
  "documentIds": ["doc-install"],
  "sectionIds": ["section-1"],
  "language": "zh-CN"
}
```

### 4.2 草稿、检查和候选

| 方法与路径 | 用途 |
|---|---|
| `PUT /knowledge-center/api/incremental-tasks/:taskId/draft` | 按 `editVersion` 保存草稿和操作集合 |
| `POST /knowledge-center/api/incremental-tasks/:taskId/checks` | 检查来源、目标、草稿和变更集完整性 |
| `POST /knowledge-center/api/incremental-tasks/:taskId/candidate` | 固化当前已检查草稿为候选 |

草稿请求：

```json
{
  "editVersion": 0,
  "content": "# 新安装步骤",
  "operations": [
    { "type": "update", "nodeId": "section-1" }
  ]
}
```

候选接口仅在任务为 `checked`、检查已通过且检查摘要等于当前草稿摘要时成功。成功后任务进入 `candidate_ready`。

P0 检查报告的唯一范围是 `scope: incremental_completeness`，固定返回以下六项，不得在前端包装成已经完成内容质量、链接、事实或格式检查：

| 检查码 | 含义 |
|---|---|
| `SOURCE_SNAPSHOT_PRESENT` | 至少存在一个人工录入或本地来源快照 |
| `TARGET_DOCUMENT_PRESENT` | 至少选择一个目标文档 |
| `DRAFT_CONTENT_PRESENT` | 草稿正文不为空 |
| `CHANGESET_OPERATION_VALID` | 每个操作满足最小可重放字段契约 |
| `CHANGESET_TARGET_DOCUMENTS_MATCH` | 操作文档均在已确认目标文档内 |
| `CHANGESET_TARGET_SECTIONS_MATCH` | 设置章节范围时，操作节点均在范围内 |

### 4.3 审核、评论、决定和修订

| 方法与路径 | 用途 |
|---|---|
| `POST /knowledge-center/api/incremental-tasks/:taskId/reviews` | 对已固化候选显式发起审核 |
| `POST /knowledge-center/api/incremental-tasks/:taskId/reviews/:reviewId/comments` | 添加审核评论 |
| `POST /knowledge-center/api/incremental-tasks/:taskId/reviews/:reviewId/decision` | 提交 `approve` 或 `reject` 决定 |
| `POST /knowledge-center/api/incremental-tasks/:taskId/revisions` | 从已拒绝任务创建新修订任务 |

退回请求必须携带非空 `comment`。修订任务复制原任务的手册、业务版本、基线、来源和目标，清空草稿、检查、候选、审核、发布和外部证据，并以 `revisionOf` 关联原任务。

### 4.4 发布和外部证据

| 方法与路径 | 用途 |
|---|---|
| `POST /knowledge-center/api/incremental-tasks/:taskId/publish` | 发布审核通过的候选 |
| `POST /knowledge-center/api/incremental-tasks/:taskId/external-evidence` | 为已发布平台版本登记人工外部证据 |

发布请求：

```json
{
  "expectedCandidateDigest": "候选摘要"
}
```

外部证据请求：

```json
{
  "type": "gitlab_mr",
  "reference": "MR-100",
  "status": "merged",
  "note": "可选人工说明"
}
```

外部证据仅表示人工登记，不证明平台调用过 GitLab，也不改变平台发布事实。

## 5. 幂等、并发和错误响应

### 5.1 幂等

所有 POST、PATCH、PUT 请求都必须提供 `Idempotency-Key`。服务端按“主体、动作、键”保存请求摘要和原响应：

- 相同键、相同请求返回原结果；
- 相同键、不同请求返回 `IDEMPOTENCY_KEY_REUSED`；
- 缺少键返回 `IDEMPOTENCY_KEY_REQUIRED`；
- 超时后可以安全使用原键重试。

前端按“方法、URL、请求体”建立命令签名。第一次发送生成键；请求超时、网络失败或服务端返回失败时保留该签名对应的键，用户以完全相同请求重试时复用原键；成功后才清除。用户修改请求体后视为新命令并生成新键，不能复用旧命令结果。

### 5.2 草稿并发

```text
saveDraft(command):
  currentVersion = task.draft?.editVersion ?? 0
  require command.editVersion == currentVersion
  保存正文和变更操作
  editVersion = currentVersion + 1
  清除旧检查结果
  state = editing
```

版本不匹配返回 `DRAFT_EDIT_CONFLICT`，并在 `details` 中返回期望值和收到值。其他写命令依靠状态门禁、幂等记录和仓储串行写入，不复用草稿 `editVersion`。

### 5.3 错误格式

```json
{
  "success": false,
  "error": {
    "code": "DRAFT_EDIT_CONFLICT",
    "message": "草稿已被其他操作更新",
    "details": { "expected": 2, "received": 1 }
  }
}
```

主要错误包括：`IDEMPOTENCY_KEY_REQUIRED`、`IDEMPOTENCY_KEY_REUSED`、`SOURCE_TYPE_INVALID`、`CHANGESET_INVALID`、`DRAFT_EDIT_CONFLICT`、`CHECK_REQUIRED`、`CANDIDATE_REQUIRED`、`SELF_REVIEW_NOT_ALLOWED`、`APPROVAL_REQUIRED`、`CANDIDATE_CONFLICT`、`BASELINE_CONFLICT` 和 `PUBLICATION_REQUIRED`。

## 6. 权限契约

P0 当前使用四项已实现动作：

| 动作 | 用途 |
|---|---|
| `knowledge:read` | 进入任务查询能力；实际列表和详情仍按任务归属与当前状态过滤 |
| `knowledge:write` | 创建任务、来源、目标、草稿、检查、候选、审核和修订 |
| `review:manage` | 提交审核决定 |
| `publish:manage` | 平台发布及登记外部证据 |

任务投影返回 `capabilities`：`canEdit`、`canReview`、`canPublish`、`canComment`、`canRevise`、`canRecordEvidence`。这些能力由主体动作、任务归属和状态共同计算：创建者/平台管理员在可编辑状态维护任务；审核者只处理待审核任务；发布者只处理已通过或已发布任务。前端据此展示动作，但后端每次写请求仍重复检查。

前端隐藏按钮不构成授权。当前动作粒度仍较粗，后续细分为手册、文档或章节级责任范围前，不能声称已完成正式资源授权。

## 7. 文件仓储与多文档发布语义

### 7.1 当前文件适配器事实

当前 `FileIncrementalBuildRepository` 与 `RepositoryBaselineProvider` 共同构成 P0 文件事实适配器：

- 使用单个 JSON 状态文件保存任务、发布记录、幂等结果和审计；
- 每个命令先取得 `.lock`，在锁内读取最新状态、执行校验和修改、保存幂等/审计事实，再写临时文件并通过重命名替换状态文件；
- 状态文件损坏时尝试读取 `.bak`；
- 同一次服务命令中的任务状态、基线 current 标志、发布记录、幂等结果和审计以一个状态文件整体写入；
- `RepositoryBaselineProvider` 从 `publishedVersions[]` 查询基线；没有匹配时列表返回空，创建/发布强制要求指定基线存在且 `current=true`；
- 发布时在同一事务中将相同手册和业务版本的旧 current 置为 `false`，再将新发布记录置为 `current=true`；
- `target.documentIds[]` 可以记录多个文档，但当前发布实现生成的是一个聚合 `Publication` 记录，并未分别创建和切换每个文档的正式版本指针。

因此，当前实现能保证 P0 文件基线注册表中的当前版本原子切换，也不会留下半条聚合发布记录；但 `RepositoryBaselineProvider` 不是正式文档资产版本仓储，尚不能声称已经实现跨多个独立文档资产的事务性版本切换。

### 7.2 冻结的目标契约

多文档候选正式接入文档资产仓储后，发布必须满足：

```text
校验全部文档基线
→ 为全部文档生成不可变版本
→ 原子切换全部当前版本指针
→ 写入一个发布批次记录
```

任一文档失败不得让其他文档生效。文件适配器需要扩展为发布清单、临时版本集合和单次原子指针清单替换，或迁移到提供等价事务语义的数据库适配器；完成故障注入测试前，多文档原子发布保持实施验证门禁。

文件锁已经覆盖完整读改写事务；仍需保留多进程竞争、锁超时、进程中断和备份恢复测试，验证实现没有退化为锁外读取。

## 8. 审计和前端展示

审计至少记录任务创建、来源保存、目标更新、草稿保存、检查、候选固化、审核发起、评论、决定、修订、发布和外部证据登记。记录主体、任务、动作、必要摘要和时间，不记录令牌、密码或无必要的敏感正文。

前端只展示中文业务语义：

- `manual` 显示“人工录入”；
- `local` 显示“本地内容”；
- 状态按第 3 节中文文案展示；
- 候选固化和发起审核是两个明确动作；
- 外部证据标记为“人工登记”，只保存类型、引用、状态、说明、登记人和时间；不得显示为平台已调用连接器或已验证远端事实；
- 没有真实数据时显示空态，不构造来源、审核、版本或外部交付记录。

## 9. 测试与验收门禁

### 9.1 API 契约测试

- 所有写接口缺少 `Idempotency-Key` 时拒绝请求。
- 相同幂等键重试返回原结果，不生成重复任务、来源、候选、审核、评论、决定、修订、发布或证据。
- 来源只接受 `manual|local`，投影和界面不出现 PingCode 已接入语义。
- 基线列表按可见手册过滤；无基线返回空数组，创建任务使用不存在或非 current 基线分别返回 `BASELINE_NOT_FOUND/BASELINE_CONFLICT`。
- 非任务创建者只能在其审核或发布状态职责范围内读取；无权对象按不存在处理；`capabilities` 与服务端实际动作一致。
- 草稿从 `editVersion=0` 开始，成功保存递增，过期版本返回冲突。
- 变更操作缺少 `documentId/nodeId`、所需摘要/后置内容或移动位置时拒绝；超出目标文档/章节范围时六项完整性检查不通过。
- 检查报告范围固定为 `incremental_completeness` 且恰好包含六项完整性检查，不冒充其他质量检查。
- 状态严格遵循 `draft → editing → checked → candidate_ready → under_review → approved|rejected → published`。
- 候选和审核必须通过两个显式接口完成；未固化候选不能发起审核。
- 审核评论可追加；创建者或提交者不能成为当前单决定模型中的有效审核人。
- 被拒绝任务可创建修订，新任务保留 `revisionOf` 且不复用旧草稿、候选、审核或发布事实。
- 发布校验候选摘要和当前基线；陈旧基线返回 `BASELINE_CONFLICT`。
- 只有已发布任务能登记外部证据，且证据不改变发布内容。

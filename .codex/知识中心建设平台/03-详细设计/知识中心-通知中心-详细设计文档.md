# 通知中心详细设计

状态：待评审，未实施（2026-11-10）。[概要设计](../02-概要设计/知识中心-通知中心-业务事件与个人通知-概要设计文档.md)定义价值、事件边界和状态；本文件是通知模块的数据、接口、投递、页面及验收契约。通知有独立公共接口和生命周期，作为详细设计目录登记的独立模块。

## 1. 模块边界与术语

| 概念 | 含义 | 唯一事实源 |
|---|---|---|
| 业务事实 | 已提交的分派、审核、范围、MR、回读或异步结果 | 对应业务模块 |
| 通知事件 | 从业务事实派生的待投递记录，含业务版本和稳定事件 ID | 来源事务或可对账事件箱 |
| 投递 | 将一个事件投影给一个确定的收件人 | 通知投递记录 |
| 收件箱项 | 用户可见的通知摘要及阅读状态 | 通知服务 |
| 待办 | 当前需要用户执行的业务动作 | 工作台业务投影 |

通知服务不得创建或修改待办、审核结论、MR 与交付完成；工作台不依赖用户是否已读来决定待办。收件箱不作为业务操作审计的替代品。编号 25 本轮仅接入站内通知；企业微信和企业邮箱相关内容属于通知中心的后续能力，不作为该需求验收条件。外部连接凭据由平台治理配置保存，不进入业务事件或浏览器。

## 2. 来源事件契约

统一事件形状：`eventId`（来源全局稳定）、`type`、`source`、`sourceId`、`sourceVersion`、`occurredAt`、`actorId`、`scope`（工单/手册/文档/候选/MR稳定 ID）、`recipientPolicy`、`snapshot`（标题、业务编号、有限摘要）、`correlationId`。不传完整正文、评论原文、凭据或任意外链。事件 ID 在同一来源事实重放时不变化；不同阶段即使对象相同也有不同事件 ID。

| 事件类型 | 产生时机 | 接收人解析 | 去重与抑制 |
|---|---|---|---|
| `task.assigned` / `task.reassigned` | 责任指派事务提交 | 新、旧责任人分成各自文案；同一人只收一条 | 同一次事务及人去重；给自己改派不产生重复告知 |
| `review.requested` | 候选成功送审 | 本次明确审核人 | 同候选摘要、审核人、事实版本去重 |
| `review.rejected` | 审核退回成功 | 当前文档负责人 | 以决定 ID 去重；旧候选后续状态不再重复发 |
| `review.mentioned_handbook` | 含结构化手册提及的意见成功保存 | 当时有效手册负责人 | 同一意见、手册、收件人去重；评论普通文本不触发 |
| `scope.changed` | 新范围版本确认 | 被增、撤、变更的责任人与受影响审核人 | 同一范围版本按人合并摘要，不逐文档刷屏 |
| `delivery.mr_failed` / `delivery.mr_closed` / `delivery.readback_failed` | 已持久化错误或远端观察 | 具名提交、发布或修订责任人 | 同一错误事实/观察版本去重；重复轮询抑制 |
| `delivery.completed` | 正文及图片回读均一致 | 工单和相关文档负责人 | 同一目标提交和交付判定去重 |
| `async.completed` / `async.failed` | 来源模块确认最终结果 | 发起人或明确下一阶段责任人 | 仅来源模块完成事件契约后启用 |

接收人 ID 使用可信人员目录的稳定 principal ID，不使用显示名。生成事件前确认当前业务权限，投递前复核接收人存在且启用；若人员失效，投递状态为 `skipped` 并记录原因，不把消息改发给管理员。结构化 `@手册` 在评论提交时绑定 `handbookId`、`recipientId` 和责任关系版本；同名手册必须选中具体 ID。权限变更后，旧消息保留最小审计信息，但读取正文和深链仍重新授权。

## 3. 数据模型与索引

目标存储复用现有数据库聚合能力，但通知数据应独立表或等价可索引记录；文件实现仅用于隔离验证。以下为逻辑模型，物理 DDL 随现有 YashanDB 迁移机制细化。

| 实体 | 关键字段 | 约束与索引 |
|---|---|---|
| `NotificationEvent` | eventId, type, source, sourceId, sourceVersion, occurredAt, actorId, scopeJson, snapshotJson, state, createdAt | eventId 唯一；按 state/createdAt 扫待投递；摘要大小有上限 |
| `NotificationDelivery` | eventId, recipientId, channel, state, attempts, nextAttemptAt, lastErrorCode, acceptedAt, providerMessageId, directoryVersion, leaseOwner, leaseUntil | (eventId, recipientId, channel) 唯一；按 state/nextAttemptAt 取租约；地址不明文落库 |
| `NotificationInbox` | id, eventId, recipientId, type, title, summary, sourceRef, occurredAt, readAt, archivedAt, version | (eventId, recipientId) 唯一；(recipientId, readAt, occurredAt DESC, id DESC) 支持列表和计数 |
| `NotificationAudit` | id, eventId, recipientId, action, actorId, at, outcome, correlationId | 仅保存必要元数据；按 eventId 和 at 检索 |

投递状态 `queued → leased → accepted`，站内写入收件箱后 `accepted` 表示已入箱；外部渠道在提供方明确确认后 `accepted` 只表示渠道已受理，不表示用户已读。明确暂时失败进入 `retry_wait`，按受控退避策略重试；达到上限进入 `dead_letter`。外部提交结果不明进入 `uncertain`，先查提供方回执或日志，不能盲目重发；确定无已验证收件映射进入 `skipped` 并留下错误码。租约过期可由其他 worker 接管，写入收件箱依赖唯一键幂等。阅读状态由 `readAt` 定义；`archivedAt` 是时间清理标记，不等于用户操作过。读取用 keyset cursor `(occurredAt,id)`，不使用深页 offset；未读总数单独索引查询或事务内维护可重算计数，禁止从当前页长度推测总数。

## 4. 写入、投递与恢复

```mermaid
sequenceDiagram
  participant User as 业务用户
  participant Domain as 来源模块
  participant Box as 事件箱
  participant Worker as 通知投递器
  participant Inbox as 收件箱
  participant External as 企业微信/企业邮箱
  participant UI as 工作台/通知面板
  User->>Domain: 执行分派/审核/范围命令
  Domain->>Domain: 校验身份、版本、幂等并提交业务事实
  Domain->>Box: 同事务登记稳定事件ID
  Domain-->>User: 返回业务命令结果
  Worker->>Box: 按租约领取事件
  Worker->>Domain: 解析接收人与权限快照
  Worker->>Inbox: 唯一键插入收件箱项
  Inbox-->>Worker: 已存在亦视为成功
  Worker->>External: 按渠道及已验证目录映射投递
  External-->>Worker: 明确受理/拒绝/结果不明
  Worker->>Box: 分渠道确认或进入恢复队列
  UI->>Inbox: 按可信会话查询本人未读/列表
  UI->>Domain: 深链打开并重新校验权限
```

同库来源在事务中写业务事实和事件；跨数据库/文件来源先写不可变业务事实，再以确定性 `eventId` 写事件，定时对账补漏。事件存储不可用时，业务命令仍按原事实成功或失败返回，不谎称通知已送达；对账能从来源审计重建遗漏事件。站内、企业微信、企业邮箱分别投递，任一渠道失败不回滚其他渠道。投递器至少一次执行、成功后确认；站内依赖唯一键无重复可见项，外部渠道尽量传稳定幂等键或确定性消息标识。企业微信/邮件提供方若不支持幂等确认，超时或连接中断后的 `uncertain` 进入回执核对或人工处置，不能宣称端到端恰好一次。死信按原事件 ID 重放，不新建第二份收件箱项。错误信息去敏，不在日志暴露评论原文、邮箱地址或凭据。

### 4.1 渠道策略、人员目录与适配器

首期 P0 关键事件为站内、企业微信、企业邮箱三渠道；P1 结果通知仍只选概要设计明确的关键事件，是否启用外部渠道通过受控事件策略配置，默认不补发历史。每个事件和收件人按当前策略产生对应渠道的 `NotificationDelivery`；两个外部渠道独立限流、熔断、重试和告警。外部渠道不接收审核评论正文、文档内容或 MR 差异，只接收业务编号、简短事件类型和平台 HTTPS 深链；接收人进入平台后再次完成 CAS 与资产权限检查。

人员目录应提供稳定 `principalId`、启用状态、已验证的企业微信账号 ID 和企业邮箱地址及各自映射版本。投递时以 `principalId` 查最新有效映射；没有映射、人员停用或映射未验证时相应渠道标记 `skipped`，站内投递不受影响。收件地址仅在 worker 内存中用于发送，持久日志和诊断只保留脱敏值、目录版本及错误码。改派后产生新的业务事件送达新负责人；旧事件已受理的收件事实不改写。

适配器统一为 `send({eventId, recipientId, destination, title, brief, link, correlationId}) -> {outcome: accepted|rejected|retryable|uncertain, providerMessageId?, retryAfter?, errorCode?}`。企业微信适配器需明确应用身份、发送 API、Token 失效刷新、提供方限流及账号映射；企业邮箱适配器需明确实际采用企业邮件 API 还是 SMTP、TLS/证书、Message-ID、退信/受理口径。两者都必须有健康探针、错误分类和隔离连接测试；在连接参数与人员目录字段未核实前，设计不能声称实际外部送达。

页面读取采用首次请求和真实事件推送。SSE 流只传收件箱序号/变更类型，不传通知内容；`Last-Event-ID` 断线恢复，序号缺口触发重新查询。SSE 未可用时，在进入页面或重新可见时拉取，不宣称实时。来源故障时返回可读的已持久收件箱项并标注 `completeness=partial`、`unavailable` 和 `asOf`；不能用 0 覆盖上次未读数。

## 5. 对外接口

所有接口使用同源 `/knowledge-center/api/notifications`，受现有会话和 `knowledge:read`/资产可见权限保护；身份只从可信会话取，忽略或拒绝请求体 `recipientId`。错误统一 `{success:false,error:{code,message}}`；成功为 `{success:true,data}`。所有写操作带 `Idempotency-Key` 和 `If-Match`/`expectedVersion`，重复请求返回同一结果；冲突 409 提示重新读取。

| 方法与路径 | 请求 | 响应要点 |
|---|---|---|
| `GET /summary` | 无 | `unreadCount, asOf, completeness, unavailable`；仅本人 |
| `GET /?state=unread|all&type=&cursor=&limit=` | cursor、limit 最大 50 | `items, nextCursor, unreadCount, asOf, completeness`；稳定倒序 |
| `GET /:id` | 无 | 通知摘要、源引用和当前深链可用性；再次校验资产权限 |
| `PUT /:id/read` | `expectedVersion` | `readAt, version, unreadCount`；本人 |
| `PUT /:id/unread` | `expectedVersion` | 清除 readAt；本人 |
| `POST /read-batch` | 当前页已加载的 `ids`（最大 50）及逐项版本 | 逐项成功/冲突；不支持无限量“全部已读” |
| `GET /events` | SSE `Last-Event-ID` | 仅本人序号；不含内容，断线回读 |
| `GET /preferences` | 无 | 本人可配置的 P1 类型及站内接收状态；P0 明确只读 |
| `PUT /preferences` | `expectedVersion, optionalTypes` | 仅修改本人 P1 偏好，版本冲突 409；P0 不可关闭 |
| `GET /delivery-diagnostics?eventId=&state=&cursor=` | 平台治理权限 | 去敏渠道状态、错误码、重试时间、提供方受理 ID；不能读取评论正文 |
| `POST /delivery-diagnostics/:eventId/reconcile` | 治理权限、幂等键和预期版本 | 仅对结果不明或死信记录执行受控回查/重放；记录操作者和原因 |

内部 `record(event)` 不暴露给浏览器，必须由来源模块经过服务身份认证调用并核对事件来源；客户端不能伪造通知。深链由服务端从允许的源类型、稳定 ID 和路由模板生成，禁止接收任意 URL。审核评论入口定位 `taskId/reviewId/commentId`，任务入口定位工单/手册/文档；URL 参数只负责定位，不授予权限。点击通知先请求源对象或导航至有权页面，确认可访问后再标记已读；源不可读时可手工标记已读，但不能展示受限内容。

## 6. 前端状态与交互

入口为全平台顶部铃铛，未读数显示 `99+` 上限，屏幕阅读器获得完整“有 N 条未读通知”；计数更新只通过一个原子状态句宣布，不能让每个数字成为 live region。按钮有标题、`aria-label`、`aria-expanded`、可见焦点。桌面右侧面板宽度受视口限制，390px 使用整页单列；关闭后焦点回到铃铛，深链进入业务页时焦点转至目标标题或意见。Escape、浏览器返回、刷新和前进能保持合理位置。

面板默认“未读”，标签“全部”；支持类型菜单、分页加载、单条已读/未读和当前页批量已读。每行最多两行摘要，完整内容在有权详情中查看；只有风险事件用风险色，不能仅靠颜色传达级别。空态区分“暂无未读”“筛选无结果”“服务不可用”。批量操作失败逐项反馈并保留未成功行；点击同一通知快速重复操作不会多次写入。工作台待办不新增通知类型标签，也不将未读计入待办数。效果稿中的审核提及选择器按真实手册名称、版本和负责人展示，提交前可检查接收人。

## 7. 安全、规模、清理与迁移

- 用户只能读写本人收件箱；管理员代办他人业务仍只能读自己的通知。后台投递诊断需要独立平台权限并去敏。服务端逐项校验资产可见范围，防止仅凭通知 ID 读到跨手册内容；失权后可清理或遮蔽摘要，审计保留稳定 ID。
- 需要防止用户可控标题、摘要、评论的 HTML 注入和外链欺骗；渲染时转义，GitLab 链接只由已验证的源模块提供 HTTPS 地址，通知不直接拼接 URL。
- 以百万工单、500 在线、50 同时操作做测算基线，另以多接收人通知膨胀量建立容量用例；这不是已验证容量。收件箱读写使用独立索引和分页，不能每次读取全量任务聚合。页面首个可交互反馈及恢复导航遵守 100ms 目标；API、DB、渲染和端到端耗时分别采集 P50/P95，超标项单独整改。
- 保留期、死信重试上限、退避间隔、事件白名单、每人/每类频率上限为受控配置。清理按时间窗口分批软标记、归档备份后删除，提供 dry-run、数量核对和恢复演练；任务与审核的法定审计保留期独立于通知正文。
- P0 分派、退回、提及、范围纠偏及交付异常按已确认策略同时投递站内、企业微信和企业邮箱；P1 结果告知可由本人按类型关闭，偏好只影响之后产生的消息。管理员可维护全局允许类型与渠道配置，不能替用户修改阅读状态；企业微信与邮箱凭据应按现有秘密治理机制加密保存并限权读取。
- 首次上线没有历史通知回填：只从启用后的确定事件生成，不依据旧任务当前状态伪造“刚发生”。可灰度按事件类型启用；关闭投递开关不改变原业务命令和待办。回退时保留事件箱和收件箱数据，停止 worker 与入口展示；恢复后按序号对账补投。

## 8. 验收矩阵

| 类别 | 必测结果 |
|---|---|
| 事件 | 分派、改派、退回、手册提及、范围纠偏、MR 关闭及回读失败各由真实来源事实触发；普通保存与重复回读不产生通知 |
| 幂等与恢复 | 命令重复、worker 崩溃、收件箱写成后确认失败、死信重放均无重复可见项；遗漏事件可对账补齐 |
| 外部渠道 | 使用隔离的企业微信和企业邮箱 HTTP/SMTP 替身验证目录映射、三渠道独立成功/失败、限流、Token 失效、退信或拒绝、超时结果不明与回执对账；真实企业渠道另需授权环境中的受理证据 |
| 身份与权限 | 本人、管理员代办、停用人员、同名手册、失权、跨手册猜 ID、过期深链均返回符合权限的结果 |
| 一致性 | 单条与批量已读、未读计数、分页、工作台待办数量各自正确；评论保存成功而投递失败显示不同事实 |
| 页面 | 桌面与 390px、键盘、Escape、焦点返回、返回位置、长名称、空态、部分数据、错误重试及无横向溢出 |
| 性能与维护 | 指定容量基线下的查询、投递延迟和 P50/P95；时间清理 dry-run、备份、恢复和保留配置生效 |

产品口径已确认：首期同时接入站内、企业微信和企业邮箱；仅通知关键事件；外部地址取企业人员目录。实施前仍需核实企业微信应用、企业邮箱发送协议及目录字段。效果稿或隔离替身不等于真实企业渠道验收。

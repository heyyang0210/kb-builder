## 现状与目标边界

### 现状基线的写法

需求作者必须依据代码、真实后端接口和现有设计逐项建立证据表，并使用以下状态，禁止仅凭历史文档推断已上线：

| 状态 | 判定规则 |
|---|---|
| 已具备 | 当前界面与真实后端接口可完成闭环，且有可定位证据 |
| 部分具备 | 存在页面、接口或文件能力，但缺少统一对象、状态、权限、审计或多人闭环 |
| 仅有设计 | 文档已描述，但当前实现和真实后端接口未形成可验收闭环 |
| 目标能力 | 本次需求新增，尚未实现 |
| 待确认 | 取决于本任务卡的人类产品决策 |

现状至少核对：大纲上传与管理、知识点选择和生成流程、文档列表、预览、编辑、保存、现有版本提示、PingCode/GitLab 或本地素材接入、质量与知识图谱治理。当前平台默认定性为“单人或弱协作的文档生成演示工具”，直到证据证明某项多人治理能力已完整存在。

### 目标边界

目标不是简单增加五个菜单，而是形成以下闭环：

`受控知识来源 → 大纲/模板版本化 → 任务分工与并行生产 → 文档版本隔离 → 质量检查与人工审核 → 受控发布 → 检索/问答消费 → 反馈、过期与持续治理`

首份需求必须包含用户点名的**大纲管理、模板管理、权限管理、文档版本管理、文档审核管理**，并补齐支撑知识中心成立的能力。已确认首期是单一企业内部平台，按部门或项目建立知识空间；实时共同编辑不进入首期，但概念边界和后续架构设计不得阻断未来引入操作转换或无冲突复制数据类型等实时协同机制。商业化多租户、移动端、对公网门户默认不进入首期必须范围；D12 已调整为 PingCode 首期只读获取并保存来源快照，GitLab 首期允许知识发布后异步创建文档分支和 MR，不回写 PingCode，不覆盖 GitLab 既有分支或文件。

## 需求文档信息结构

1. **文档元数据与决策摘要**：按归档规范记录文档类型、模块标识、负责人、状态、版本和更新日期，列出已确认项和未决项。
2. **背景、问题与建设目标**：说明演示工具在多人生产、权责、版本、审核、发布和知识复用上的断点；给出可衡量目标，不以“使用大模型”作为目标。
3. **用户、组织边界与典型场景**：至少覆盖平台管理员、知识空间管理员、作者、审核人、发布人、读者/检索用户、知识运营人员、审计人员。
4. **现状证据与差距分析**：以“现状状态 + 证据路径 + 目标差距”列表区分已实现、部分实现和规划能力。
5. **概念模型与单一事实源**：定义知识空间、知识域、来源资产、大纲、模板、文档、文档版本、生成任务、审核单、发布版本、知识条目、标签/术语、反馈等业务对象及关系。
6. **能力地图与优先级**：按下方能力域展开，逐项标记必须、应该、可选或未来考虑，并说明用户价值、前置依赖和模块归属。
7. **端到端主流程与状态机**：至少描述新建生产、增量更新、并行分工、冲突处理、审核驳回、发布/撤回、归档/恢复、知识入库与检索反馈流程。
8. **权限与职责分离**：定义主体、资源、动作、作用域、继承和例外审批；明确 AI 不能拥有审核、发布或权限授予权。
9. **核心业务规则与不变量**：用可验收语言定义版本绑定、审核放行、发布不可变、检索权限继承、来源追溯、删除/归档和审计留痕。
10. **非功能需求**：安全、并发一致性、可用性、性能目标、可观测性、备份恢复、合规、成本与容量；未有基线的数值列为待校准，不硬编码结论。
11. **指标与验收场景**：覆盖生产周期、并行冲突、审核时长、发布失败、知识命中与引用、过期知识、权限越权和审计完整性。
12. **分期路线与非目标**：给出从治理底座到生产闭环、再到知识消费和持续运营的阶段划分，不直接承诺技术排期。
13. **风险、假设与待确认项**：分别记录产品风险、AI 风险、迁移风险、组织治理风险及可逆预案。
14. **追踪矩阵**：将能力 → 业务规则 → 验收标准 → 既有/目标模块建立映射。

## 知识中心能力地图（头脑风暴基线）

| 能力域 | 必须讨论的能力 | 为什么是知识中心必需 |
|---|---|---|
| 组织与空间 | 组织/部门、知识空间、项目或知识域、成员管理、责任人 | 多人生产必须先明确资产属于谁、由谁治理 |
| 身份、权限与审计 | 统一身份、角色与资源权限、继承/例外、操作审计、敏感操作复核 | 防止“能看到就能改、能改就能发”，并支持责任追溯 |
| 大纲管理 | 逆向提取、树/时序/业务流候选、版本、复用、依赖影响、停用 | 大纲是文档结构契约，需要独立生命周期而非一次性上传文件 |
| 模板管理 | 模板分类、字段约束、版本、适用范围、试用/发布/停用、与大纲绑定 | 模板是质量和格式规则载体，变更必须可追踪、可回退 |
| 来源与素材治理 | 本地/PingCode/GitLab 接入、来源快照、内容摘要、时间戳、授权、血缘、时效和失效 | 没有可追溯来源，就无法判断文档为何变化或是否过期 |
| 生产计划与协作 | 生成项目、任务分派、章节责任人、依赖、锁/签出、评论、通知、工作台 | “多人并行”首先是任务和责任协同，不等同于多人同时敲同一段文字 |
| AI 生成治理 | 全量/增量生成、骨架与约束、输入快照、模型/规则版本、引用证据、失败重试、人工接管 | 保证生成结果可复现、可解释，且 AI 只在授权范围内执行 |
| 文档与版本 | 草稿、版本快照、分支/变更集、差异、合并、冲突、回退、归档 | 并行生产的结果必须隔离，避免后保存者覆盖先保存者 |
| 质量门禁 | 完整性、一致性、术语、格式、引用、时效、重复、冲突、敏感信息、可读性检查 | 审核前先自动发现机械问题，但不虚构“绝对正确”判定 |
| 审核与仲裁 | 审核单、审核清单、会签/串签、驳回、重提、超时提醒、冲突仲裁、职责分离 | 把个人判断变为有证据、有状态、有责任人的组织流程 |
| 发布与分发 | 发布版本、发布说明、渠道/格式、定时发布、撤回、回滚、订阅通知 | “保存”不能等同于“对外生效”，正式知识需有明确放行点 |
| 知识入库与治理 | 切分、去重、向量/图谱入库、实体关系、置信度、待仲裁、过期/废止、重建 | 文档资产只有可治理地进入知识底座，才成为可复用知识 |
| 检索与知识消费 | 全文/语义检索、意图识别、路由、缓存、引用溯源、权限过滤、问答、相关推荐 | 知识中心的价值最终体现为用户能安全、快速找到可信答案 |
| 反馈与持续演进 | 纠错、评价、缺口反馈、责任人处理、知识新鲜度、复审周期、订阅 | 建立消费端到生产端的闭环，避免知识发布后无人维护 |
| 运营与度量 | 生产看板、审核积压、覆盖率、复用率、搜索无结果、成本/配额、模型调用统计 | 管理者需要知道平台是否真的缩短交付并提升知识可用性 |
| 平台配置与开放能力 | 术语和分类体系、规则与提示词配置、通知、导入导出、事件回调、开放接口、备份恢复 | 避免规则和提示词散落硬编码，并为企业系统集成留出边界 |

能力地图是需求发现清单，不代表全部进入首期。需求作者须用优先级、依赖和非目标控制范围，避免形成没有交付顺序的功能堆砌。

## 逻辑一致性不变量

需求正文至少明确并能由验收场景验证以下规则：

1. **正式发布版本不可原地修改**；任何修改产生新草稿/变更集，发布后形成新的不可变版本。
2. **未经规定审核的版本不得发布**；AI、生成任务或自动检查只能给建议/门禁结果，不能代替授权人员审批。
3. **检索与问答权限不得高于来源文档权限**；缓存、向量索引、图谱关系和摘要也必须执行相同或更严格的访问控制。
4. **生成结果绑定输入快照**：大纲版本、模板版本、来源快照、规则/提示词版本和模型标识可追溯，禁止用“当前最新”覆盖历史依据。
5. **并行修改不能静默覆盖**；检测到基线变化必须提示差异并进入合并、重试或人工处理。
6. **审核结论绑定内容摘要**；正文、关键元数据或引用变化后，原审核失效并重新进入流程。
7. **归档/废止与物理删除分离**；已发布和被引用资产默认可恢复、可追溯，敏感数据删除遵循单独审批与留痕策略。
8. **冲突知识不自动判定绝对正确**；进入待仲裁态，由独立信源或人工处理，且仲裁证据可回查。
9. **结构与格式资产也要版本化**；大纲/模板停用不得破坏历史文档的复现与查看。
10. **策略配置是单一事实源**；规则、提示词、阈值、审核清单和通知模板应版本化配置，若发现硬编码只能登记例外和待办。

## 3. 高价值未完成需求

以下只列直接改善数据库文档审核质量、意见追溯和发布安全的产品需求。每项保留原任务编号，便于与后续开发任务对应；工程测试、环境联调和提交整理不再占用产品需求名额。

### 3.1 数据库专项 AI 审核证据（对应 HO-P1-02）

**用户问题**：普通文档检查只能发现格式或链接问题，无法判断 SQL 语法、参数依赖、数据库版本适配、错误码和运维命令是否准确。审核人需要在多个版本手册和内核资料之间人工核对，容易漏掉高风险错误。

**业务价值**：把 AI 从“给建议”提升为可核验的数据库审核协作者，优先发现可能导致用户执行失败、配置不生效或版本行为不一致的问题，形成数据库知识中心区别于通用文档平台的核心能力。

**业务逻辑**：

```text
待审核版本生成
  → AI 按数据库规则检查
  → 生成带行号的风险发现
  → 展示适用版本、规则依据、证据引用和解释摘要
  → 审核人确认或驳回
  → 必要时生成可回放修改建议
  → 人工确认后更新待审核版本并重新触发审核
```

每条发现至少要关联：检查类型、文档位置、数据库业务版本、规则版本、证据来源、风险等级、解释摘要、修复建议、模型/提示词/技能版本、执行状态和人工处理状态。页面只展示可审计的解释摘要，不展示模型私有思维草稿；AI 不能直接审核通过或发布。

**当前缺口**：目前只有“尚未执行”的诚实空态，没有 AI 检查任务、持久化发现、证据引用和人工确认接口。

**完成标准**：SQL 语法、参数依赖、版本适配、错误码、架构原理、API/运维命令和交叉引用均可按规则执行；失败、超时、无证据和低置信度可区分；发现绑定候选摘要和行级位置；自动修复必须生成可回放操作，并在人工确认后才改变内容。

**责任与依赖**：AI/规则工程师、数据库内核专家、后端、前端；依赖规则库、证据来源和模型/提示词版本管理。

### 3.2 修改意见与版本血缘追溯闭环（对应 HO-P0-02、HO-P1-03）

**用户问题**：审核意见可能经历多次退回、修订和重新提交。若只保存评论正文或页面临时拼接任务字段，审核人无法准确回答“谁在什么版本的什么位置提出了什么意见、如何处理、最终发布到了哪个版本”。

**业务价值**：让每条人工意见和 AI 发现都能从提出、处理、重新打开直到发布后追溯，避免意见丢失、重复审核和错误版本被误发布。这是本轮“修改意见清晰可见且可追溯”刚性约束的落地点。

**业务逻辑**：

```text
正式版本
  → 增量任务
  → 待审核版本
  → 差异行/字符位置
  → 人工意见或 AI 发现
  → 退回并形成修订版本
  → 重新审核
  → 审核决定
  → 正式发布版本
```

系统同时维护两条关系：

1. **意见处理关系**：待处理 → 已处理 → 重新打开；保留处理人、处理时间和处理历史，不覆盖原意见。
2. **版本血缘关系**：任务创建、候选冻结、审核提交、审核决定、修订关系、发布关系和被替代版本均只追加记录。

**当前缺口**：评论虽有 `resolved/resolvedBy/resolvedAt` 字段，但没有真正的“标记已处理/重新打开”接口；修订只有 `revisionOf`，没有完整修订链；发布记录未完整维护被替代关系，也没有独立血缘查询接口。

**完成标准**：意见状态可按权限变更并可审计；候选摘要变化时旧操作失效；从任一正式版本可追溯到来源快照、任务、候选、所有修订、审核人、AI 证据和发布记录；页面可从意见跳转到对应全文差异和行号；三次修订、重新打开和版本替代场景测试通过。

**责任与依赖**：架构师、后端、前端、审核角色；依赖审核意见更新接口、独立血缘查询接口和稳定版本标识。

### 3.3 发布前风险确认与数据库版本门禁（对应 HO-P0-03）

**用户问题**：发布人目前需要依靠前端拼接的确认文字判断是否发布，无法在一个页面看到正式基线、待审核版本、未处理意见、数据库专项阻断项和将被替代的版本，容易在基线漂移或审核不完整时误发布。

**业务价值**：把“点击发布”变成有事实依据的风险确认，阻止错误版本、错误基线和未解决的数据库高风险问题进入正式知识库。

**业务逻辑**：

```text
审核通过
  → 服务端生成发布确认信息
  → 展示当前正式版本、待审核版本、候选摘要、数据库业务版本、影响范围、未解决意见、阻断检查和将被替代版本
  → 发布人确认
  → 服务端再次校验同一组事实
  → 原子切换正式版本并记录血缘
```

发布确认信息必须由服务端计算，至少包含：当前正式版本、当前基线、待审核版本、候选摘要、审核决定、未解决意见数量、数据库专项阻断项、基线是否仍有效、发布者权限和将被替代的正式版本。预览接口只读，发布接口必须再次校验，不能只相信预览结果。

**当前缺口**：页面仍使用浏览器原生确认框；缺少独立的发布确认信息接口；发布服务尚未明确执行“无未解决阻断级检查项”的门禁。

**完成标准**：基线漂移、候选变化、审核无效、权限不足或存在阻断级检查项时均不能发布；确认页明确说明待审核版本在发布前尚未生效；成功发布记录发布人、时间、旧版本、新版本、候选摘要和替代关系；重复提交和冲突均可恢复。

**责任与依赖**：架构师、后端、前端、发布角色；依赖发布确认信息接口、数据库专项检查结果和正式文档基线。

- 工作区不是干净状态，包含知识中心、认证、GitLab、审核发布、测试、配置和其他目录的修改/新增文件。
- 当前变更可能同时包含用户修改、前序任务修改和本会话修改。
- 禁止使用 `git reset --hard`、`git checkout --` 或批量清理未跟踪文件。

执行要求：

1. 用 `git status --short` 和逐文件 diff 建立归属表。
2. 先隔离“GitLab 个人授权”“审核页面与增量 API”“测试与文档”三个主题。
3. 配置文件、运行数据、备份、生成产物和未知新增目录不得未经确认加入提交。
4. 每个提交遵循 `<type>(<scope>): <中文摘要>`。
5. 每个主题提交前运行与风险匹配的测试，并记录提交 SHA。

完成标准：

- 每个提交只处理一个主题。
- 不丢失任何未知来源修改。
- 任务文档记录变更归属、未提交遗留和测试证据。

## 6. 生产门禁与后续能力

### HO-P1-01：GitLab Token 加密持久化与刷新

当前 Token 只存在 `lib/gitlab-oauth.js` 的进程内存 Map 中，重启即失效；同一用户也只有一条 Token 记录，需明确多 GitLab 主机语义。

开始编码前必须由安全架构/运维确认：

- 使用 YashanDB 加密字段、外部密钥服务还是专用密钥仓储。
- 加密密钥轮换、备份恢复和最小权限。
- Refresh Token 刷新、撤销、过期和退出登录策略。
- 多主机、多连接是否允许共享同一授权。

完成标准：重启后授权有效；过期可刷新；撤销立即失效；Token 不以明文进入日志、配置、普通数据库查询或前端；具有迁移、回滚和安全测试。

### HO-P1-02：数据库专项 AI 审核证据

当前页面只在存在真实字段时显示 AI 内容，否则明确显示“尚未执行”。后端尚无 AI 分析任务和持久化证据。

需要实现：SQL 语法、参数依赖、版本适配、错误码、架构原理、API/运维命令和交叉引用检查；每条发现至少包含位置、规则版本、证据引用、风险、解释摘要、修复建议、模型/Skill/Prompt 版本、执行状态和人工确认状态。

注意：这里提供的是可审计的“旁路解释/推理摘要”，不得展示模型私有思维草稿，也不得让 AI 自动作出审核通过决定。规则和提示词使用版本化资源，不在代码中硬编码；重要提示词变更记录到 `prompt.md`。

完成标准：失败、超时、无证据和低置信度状态可区分；AI 发现绑定候选摘要和行级锚点；自动修复形成可重放 operation，经人工确认后才改变候选并使旧审核失效。

### HO-P1-03：独立版本血缘与修订链

当前页面时间线由任务、候选、审核和发布已有字段临时组合；没有独立 lineage API。修订任务只有 `revisionOf`，没有完整 `revisionChain`；发布记录也未完整维护替代关系。

需要实现：只追加的血缘记录、三次以上修订链、候选摘要贯穿、审核决定和 AI 证据引用、`supersededPublicationId/supersededBy`、血缘查询接口和历史详情深链接。

完成标准：发布版本能追溯到任务、来源快照、基线、候选、所有修订、审核人、AI 证据和发布记录；任何历史节点只读；三次修订和两次发布替代测试通过。

### HO-P1-04：正式文档基线与多文档原子发布

当前 `RepositoryBaselineProvider` 仍以增量状态文件中的 `publishedVersions` 为事实源，多文档目标只生成聚合发布记录，没有真正切换每个文档资产的版本指针。

需要由架构师和 DBA 先确认正式文档资产仓储、事务边界、版本指针、内容存储、迁移与回滚。实现后用正式仓储替换文件适配器，并完成基线漂移、部分失败、进程中断和多文档全回滚故障注入。

完成标准：每个文档产生不可变版本；同一发布批次原子切换全部 current；任一失败全部回滚；审核和发布读取同一事实源。

### HO-P1-05：PingCode 真实只读来源接入

当前只能诚实显示未接入或使用 `manual/local` 来源。开始前必须获得：PingCode 实例、API 文档、OAuth/凭证方式、项目和工作项权限、分页/增量字段、附件样本、限流和代表性数据。

建议拆分为：连接与鉴权、工作项与附件快照、远端版本/更新时间、去重与幂等、权限与审计、失败恢复、契约测试。第一阶段保持只读，不回写状态。

完成标准：平台能证明来源捕获时间、远端 ID、内容摘要、附件完整性和操作者；授权不足与服务失败可恢复；没有真实证据时不得显示“已同步”。

### HO-P1-06：多级审核、领取转交和在线协同

该能力尚未立项，不能直接插入当前 P0。需要产品和架构决策：每个知识空间的 1～3 级流程、会签/串签、人数、撤权、超时、紧急放行、领取/释放/转交、presence 隐私，以及采用 WebSocket 还是 SSE。

完成标准至少包括：`flowVersion` 锁定、稳定用户 ID、候选变化使旧决定失效、多级越权测试、领取并发冲突、断线恢复和完整审计。

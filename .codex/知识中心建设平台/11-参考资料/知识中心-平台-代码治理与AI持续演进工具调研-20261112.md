# 知识中心平台代码治理与 AI 持续演进工具调研（2026-11-12）

## 结论摘要

仓库已有业务设计、代码关系图工具选型、统一测试入口、变更前检查、回归用例和复盘材料，适合在现有流程上补确定性门禁与反馈闭环。优先方向是：保留已有代码图谱方案；增加多语言规则扫描与依赖更新检查；将历史缺陷以“根因—回归用例—规则/契约—复盘记录”闭环；AI 任务规格按复杂度选择性使用，不额外引入一套强制文档流水线。

“历史问题不会再出现”无法绝对保证。可操作目标是让已知故障在可重复的测试或静态规则中失败，并在每次变更检查中运行相应门禁；未覆盖的故障仍可能重现。

## 本仓库现状与缺口

本节基于 2026-11-12 当前工作树及仓库文档/脚本盘点；当时工作区存在大量未提交变更，因此不是干净 HEAD 的可复现基线，文件数量也应视为近似值。

| 方面 | 已有能力 | 增量缺口 |
|---|---|---|
| 代码结构 | `apps/`、`packages/`、`tools/`、`tests/`、`config/`、`knowledge/` 分层；Node/JS、Python、Java、SQL 混合；已有业务域/服务设计和代码关系图选型 | JS 依赖边界有候选方案；Python/Java 主要靠目录和测试约束，尚未见统一跨语言架构规则；图谱更新鲜度须有自动验证 |
| 测试与交付 | 统一测试运行器；约 415 条单测路径、66 条 E2E 路径；`npm run verify:change` 检查 diff 空白、受保护路径和 Node 语法；`npm run verify:full` 继续跑菜单测试、构建和 smoke | 快速变更门禁不执行与变更相关的业务回归；全量验证命令名容易让人误以为覆盖所有测试，实际 `verify:full` 调用的是 smoke；缺 lint/format 和跨语言架构门禁 |
| 缺陷复盘 | `.codex/知识中心建设平台/09-审查与复盘/` 记录根因、修复和回归证据；现有测试含真实 HTTP、浏览器与错误恢复场景 | 复盘记录与自动回归之间没有可见的强制映射；没有统一字段标记“缺陷 ID、根因、固定回归入口、适用范围”；历史记录可能被遗忘或误判已防复发 |
| AI 开发约束 | `AGENTS.md`、`prompt.md`、详细设计、契约和任务路由规范已形成丰富上下文 | 规则多但单项规则进入确定性门禁的路径不统一；复杂设计任务可用规格工作流，普通维护不宜增加模板负担 |
| 外部依赖 | 配置、测试和构建已集中管理 | 尚需确认是否已有依赖漏洞、许可证、更新 PR 的自动扫描/维护策略 |

## GitHub 工具与适用性

优先采用能接入当前脚本/测试入口的开源工具。Star 数会变化且不代表质量，本报告不以 Star 排名；许可证和能力应在正式采用时按锁定版本复核。

| 能力 | 候选 | 对本仓库的作用 | 代价与边界 | 结论 |
|---|---|---|---|---|
| 全景与影响分析 | [Understand Anything](https://github.com/Egonex-AI/Understand-Anything) | 交互式代码/领域图谱、查询和变更影响；支持增量重建与 MCP，适合让人和 AI 获得共同结构视图 | 语义摘要由模型辅助；不是编译器事实；扫描范围、索引版本、敏感路径和图谱新鲜度要管理 | 沿用 2026-11-05 已有选型，不重复部署第二套图谱 |
| JS/TS 依赖规则 | [dependency-cruiser](https://github.com/sverweij/dependency-cruiser) | 检查循环依赖、孤点和自定义层级规则，可输出依赖图 | 只覆盖 JS/TS 家族，不解决 Python、Java、SQL 边界 | 与现有前端/API/核心包边界结合，作为最小架构门禁候选 |
| 多语言定制规则 | [Semgrep](https://github.com/semgrep/semgrep) | 自定义 YAML 规则扫描多个语言；可将反复出现的危险模式、越层调用和错误处理遗漏转为 PR 检查 | 规则覆盖和误报需由仓库样例验证；规则命中不等同完整程序分析；CLI 与商业服务能力/许可需区分 | 先试点 5–10 条已发生问题的高置信规则，不追求大而全 |
| AST 规则与批量修复 | [ast-grep](https://github.com/ast-grep/ast-grep) | Tree-sitter 结构匹配、多语言规则、代码重写；用于重复模式发现和机械化迁移 | 规则主要关注语法形状，跨文件业务语义需另做验证；自动重写必须经过测试 | 适合把已确定的重复代码简化成可审查迁移，不作为初期硬门禁必选 |
| AI 任务规格 | [GitHub Spec Kit](https://github.com/github/spec-kit) | 将规格、计划、任务等产物串接到 AI 开发流程，可在复杂跨模块需求中减少遗漏和需求/实现漂移 | 引入 CLI、命令和额外文档；与现有详细设计、任务管理、AGENTS.md 重叠；不适合每个局部修复 | 仅对公共契约、跨模块功能做小范围试用，沿用已有设计事实源 |
| AI 任务评测 | [promptfoo](https://github.com/promptfoo/promptfoo) | 对提示词/模型输入输出建立数据集、断言与对比，适合平台内的 AI 文档生产/资料加工提示词回归 | 评测集需有代表性并维护；模型有随机性，不能只用字符串精确相等；不直接评测代码架构质量 | 用在产品 AI 行为和提示词变更，不作为通用编码 Agent 质量分数 |
| 依赖漏洞 | [OSV-Scanner](https://github.com/google/osv-scanner) | 扫描锁文件/依赖清单与 OSV 漏洞数据库，并可由 GitHub Actions 执行 | 仅发现已收录的已知漏洞；修复版本可引入兼容性变化，更新仍需回归 | 加入定期和 PR 扫描，先报告，再设置严重级别门禁 |
| 自动依赖更新 | [Renovate](https://github.com/renovatebot/renovate) | 自动创建依赖更新 PR，可按分组、周期和策略控频 | 需要 CI 对更新 PR 提供可信信号；自托管/商业使用的许可证及运行模式要先核对 | 候选；先把漏洞扫描和现有测试接通，再决定自动开 PR 的范围 |
| Java 现代化 | [OpenRewrite](https://github.com/openrewrite/rewrite) | Java AST 迁移 recipe 可批量执行安全、框架和 API 升级 | Java 专项，适合有明确迁移目标时采用；不是全仓架构图或通用自动重构器 | 暂不常驻；出现有批量升级需求再做独立 PoC |

代码图谱专门比较见前置选型报告。理解图谱负责回答“代码之间可能如何关联”；Semgrep、dependency-cruiser 和测试负责回答“哪些确定规则违反/行为失败”。三种证据互补，不应把模型推断的关系直接当门禁事实。

## 组合逻辑

### 1. 仓库事实层

继续以源码、接口契约、测试和现有设计作为事实来源。代码图谱记录扫描提交哈希、纳入/排除范围和生成时间；AI 的结构回答要求附具体文件/符号证据。图谱过期时返回“需回查源码”，不自动据旧图给出影响结论。

### 2. 确定性规则层

按语言分层执行：JS/TS 先用 dependency-cruiser 约束模块方向；多语言共性危险模式用 Semgrep；ast-grep 用于少量经审查的结构迁移。每条新增规则应对应至少一个真实缺陷、架构约束或人工确认的编码约定，并配正例、反例，避免规则数量成为治理目标。

建议逐步把 `verify:change` 扩展为基于变更路径选测试与检查：JS 语法/规则、Python lint 与相关单测、Java 编译/相关 HTTP 检查、契约一致性、受影响 E2E；完整主干检查继续独立跑。失败报告需列明实际执行和跳过项。

### 3. AI 规格与执行层

复杂改动开始时，复用已有任务路由：需求/验收、接口契约、伪代码或设计、任务拆分、实现和验证结果。Spec Kit 只作为可选工作流实验，重点验证它是否减少返工，不能要求把现有文档复制一遍。局部 bug 仍可以“根因 + 验收用例 + 修改范围”直接处理。

AGENTS.md 继续记录稳定且跨任务的仓库约束；单次任务细节写入任务/设计材料；产品模型输出质量使用 promptfoo 数据集；代码正确性由项目测试和静态规则验证。不要用一份提示词承担全部政策和验收责任。

### 4. 防复发反馈层

每个已确认缺陷形成最小闭环：

```text
事件/缺陷 -> 可复现步骤与证据 -> 根因 -> 回归测试或静态规则
          -> verify-change/full 中的执行映射 -> 复盘记录链接 -> 后续变更持续运行
```

复盘未能形成自动化断言时，记录原因、人工验收方法和责任范围；不把“文档写了”当作防复发已完成。每季度可抽查高影响历史问题，确认测试仍能阻止回归。

## 建议落地顺序

| 阶段 | 工作 | 验收信号 |
|---|---|---|
| P0：基线与责任映射 | 从当前工作树整理架构模块图、入口/依赖/数据写入点；标注扫描范围、提交哈希、已有门禁；列出近期高影响重复缺陷 | 样本链路能从需求定位到模块、API、存储和测试；外部目录与 runtime 未误纳入 |
| P1：规则试点 | 为 JS/TS 选 2–3 条层级规则，选 5–10 条有缺陷证据的 Semgrep 规则；新增 Python/Java 基础 lint/编译检查前先核对已有工具 | 人为制造违反规则的样例能在统一入口失败；正常代码无不可接受误报；输出说明执行/跳过 |
| P2：防复发闭环 | 从 10 个高影响历史问题抽样，逐个关联测试/规则/验收路径，先修补缺少的回归覆盖 | 每项问题有明确自动或人工防复发办法；故意回退时对应检查失败 |
| P3：AI 规格和评测 | 对复杂新需求试用 Spec Kit 或轻量规格模板；为关键 AI 提示词建立 promptfoo 回归集 | 连续多个真实任务比较需求遗漏、返工轮次、执行耗时、规则误报、AI 评测通过率后再决定扩大 |
| P4：依赖与图谱维护 | 接入 OSV-Scanner；评估 Renovate；图谱随主干更新并核验新鲜度 | 漏洞和依赖升级有负责人/处置记录；图谱差异可追踪，失败不会被静默忽略 |

衡量建议：架构越界命中数、已知缺陷回归测试覆盖率、重复缺陷数、门禁误报率、PR 首次通过率、变更到验收的耗时、AI 提示词数据集回归差异、未验证项数量。先采集基线，不预设提升比例。

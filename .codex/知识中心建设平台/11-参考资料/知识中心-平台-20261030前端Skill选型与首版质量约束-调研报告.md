## 1. 平台核心需求与特点

依据需求列表、前端详细设计、一级导航信息架构及最新页面风格原则整理。以下是需求与设计定位，不代表所有能力已验收；旧概要设计中的“占位页”等历史实施描述不能代替当前代码和运行证据。

| 工作域 | 核心需求 | 对前端的要求 |
|---|---|---|
| 工作台 | 我的任务、手册进展、待审核、异常与最近活动 | 信息可扫读，关键任务能下钻，数字与状态有真实来源 |
| 知识资产 | 按权限浏览手册、大纲、模板、素材、文档和关系 | 搜索、筛选、版本与归属明确，跨模块保持对象上下文 |
| 资料清洗 | PingCode/上传资料、预处理、提取、批次、索引与图谱 | 长任务状态、失败原因、重试和证据预览可理解 |
| 大纲管理 | 目录结构、责任映射、导入校验、差异、版本治理 | 树表协作、密集数据、变更预览与恢复操作稳定 |
| 模板管理 | 共享模板、适用范围、版本比较与恢复 | 复用规范，锁定引用版本，避免覆盖历史事实 |
| 文档生产 | 来源确认、AI 生成、Markdown 编辑、共享草稿保存 | 目录、正文、AI 面板协同；读写模式区分；保存与生成结果可回读 |
| 审核与发布 | 逐篇审核、退回修订、重审、GitLab MR 与交付追踪 | 逐篇状态准确，下一步清楚，不把创建 MR 当成已合并发布 |
| 平台管理 | 身份、权限、人员、仓库、Agent/模型/MCP、审计 | 紧凑设置页、敏感信息保护、局部保存、配置与运行事实区分 |

共性特点：中文企业工作台、中高信息密度、多角色与权限、多版本与跨页面上下文、长任务与异常恢复、真实事实与来源追溯。现有前端为原生浏览器 ES Modules、HTML/CSS，使用 Lucide/Vditor 等，不能因热门 Skill 假定要迁移到 React/Next.js。

视觉遵循现有 `common/appearance.css` 与已确认规范：内容优先、白色表面、浅灰背景、细边线、语义色与单色线性图标。最新外观整改保留导航、表格、正文、AI 面板和操作按钮；本调研不扩展其修改授权。

实际检索词包括 `web design`、`webapp testing`、`frontend design`、`web design reviewer`、`accessibility`。GitHub 另检索 frontend design skills、design system agent skill、playwright best practices skill 等。早期并行 npx 初始化发生共享缓存 ENOTEMPTY，随后串行检索成功；此失败不属于平台缺陷。

“高分”没有统一官方评分。本报告以 GitHub 来源、仓库 Stars、维护情况、Skill 内容和本项目适配性筛选；Stars 属于整个仓库，安装量属于具体 Skill，均不证明首版质量。下表为本次 API 读取快照；所列仓库均未归档。

## 4. 为什么已有 Skill 仍会大量返工

1. **要求难以验收。** “中高密度”“简洁”“好用”没有直接限定某页的核心动作、摘要和首屏布局。历史 Agent 设置页记录显示，已有密度要求仍出现空白大、配置纵向堆叠。
2. **可点击与可完成任务存在差距。** 定位器能点击按钮、截图文件生成、390px 无横向溢出，不能证明新手能找到入口、理解状态并完成下一步。已有测试也包含真实状态与恢复断言，不能概括为全部只测点击；缺口需按页面确认。
3. **规则未成为稳定检查。** 仓库已有设计文档、菜单测试、浏览器测试和配置化性能预算；仍需把反复出现的问题接入实际执行入口，避免只增长文档。
4. **通用建议会误配。** 本次 ui-ux-pro-max 对 `progressive disclosure settings` 和一次收窄重试均命中无关的标题换行条目，未采纳。检索结果必须核对适用性，不能因有 Skill 输出就直接实施。
5. **外部 Skill 本身也需要筛选。** web-design-reviewer 的修复参考含 `overflow-x: hidden`；它可能掩盖内容被裁切。webapp-testing 的通用 networkidle 等待也不能作为生产长任务完成条件。验收必须核对内容可达和真实业务结果。

## 5. 建议建立的最小质量闭环

以下为待试点方案，不是已经实现或已经批准的全局硬门禁。沿用现有路由，局部维护不强制走完整设计流程。

| 环节 | 必须明确或验证的内容 | 工具与产物 |
|---|---|---|
| 开发前 | 用户角色、当前目标、主动作、数据/API、状态、不可改范围；复用哪个既有页面模式 | 页面验收契约；引用现有设计，不重新生成整套风格 |
| 设计时 | 用接近真实长度的中文、路径、目录和数据；桌面首屏明确当前对象、关键摘要与主动作 | 代表性页面原型与截图；新布局先验证后扩散 |
| 实现时 | 复用令牌与公共组件；异步/空/无权/失败分开；错误说明恢复动作；保存及跨页状态保持上下文 | ui-ux-pro-max 按需查询、web-design-guidelines 检查 |
| 交付前 | 几何、交互、真实 API 回读、视觉检查均完成；仅对相关风险运行检查 | 现有 Playwright + 可访问性检查 + 截图审查 |
| 自动纠错 | 每个问题有复现、目标元素、证据、根因、修复与复测；成功之前不报完成 | 在已授权范围内循环；重复同因失败时先诊断，不盲目调 CSS |
| 复盘 | 用户指出的新问题尽量形成复用规则、公共修复或回归断言 | prompt.md 记录；版本化规则和测试，不复制到各模块 |

建议首先固定四类自动检查：

- **首屏与可达性**：在 1366×768 和 1440×900 下检查页面约定的主动作与关键摘要；768/390px 验证重排与可达。并非要求长表单全部在首屏，合理表格/代码水平滚动也不视为错误。
- **真实状态**：保存后 API 回读、刷新保留、返回恢复；处理中/空/失败/无权不混淆；验证慢请求、长中文、深目录等具体风险场景。
- **无障碍与几何**：axe-core 检查、Tab/Esc/焦点返回、遮挡与点击命中、正文可读与可滚动。不能用隐藏溢出、缩小字号或删除字段“通过”门禁。
- **视觉与性能**：截图必须由 AI 实际查看；已确认页面建立截图基线，动态数据采取受控处理，不能自动接受新基线。复用现有手册性能配置，目录/草稿 API P95 100ms、目录可见 200ms、正文就绪 500ms 的预算只用于对应场景，不直接推广到所有页面。

建议规则从配置读取，每条包含 ID、适用页面/状态/视口、级别、检查方法与例外依据，避免散落在提示词或业务代码。涉及授权外的业务决定才交给人；范围内的普通缺陷由执行者复现、修复并验证。

验收报告应列“通过、失败、跳过、未验证”；缺少真实权限、来源或外部服务时明确限制。截图相似、LLM 评分高、HTTP 200、MR 已创建都不能单独证明业务闭环成功。

## 6. 最先落地的范围与衡量方式

先选已有反复纠错证据的 Agent 设置页，复用其当前实现和用户已确认视觉，试跑“设置页契约→规则检查→浏览器交互→AI 看图→修复复测”。再扩展到文档生产和审核页面。先证明收益，再决定是否扩大工具链。

最小组合：现有 ui-ux-pro-max + web-design-guidelines + 一种视觉审查流程 + 现有 Playwright。Impeccable 和 web-design-reviewer 不必每次同时执行；agent-browser 按探索需求选用。

统计连续若干同类任务的首轮通过率、交付后人工发现缺陷数、人工反馈轮数、AI 自主发现比例、门禁误报及总耗时。当前未建立基线，不承诺固定提升比例。业务审核与开发纠错分开：文档发布的人工审核仍由既有治理规则决定。

本次只交付调研和建议；下一阶段应实现最小契约与检查入口，并用真实任务评价。增加 Skill 数量或要求用户逐稿确认都不能作为首版质量改善的证明。

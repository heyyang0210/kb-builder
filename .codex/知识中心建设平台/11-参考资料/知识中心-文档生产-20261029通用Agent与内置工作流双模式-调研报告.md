# 文档生产：通用 Agent 与平台内置工作流双模式调研报告

> 调研日期：2026-10-29（Asia/Shanghai）
> 性质：技术可行性与产品研究；建议方案，非已批准架构、非已完成接入。
> 适用范围：知识中心文档生产、增量修订、审核与 GitLab 交付。

## 1. 结论与建议

**可行。建议采用“统一文档生产任务 + 通用 Agent / 内置工作流双执行模式”，先用完整通用 Agent 跑通一条真实业务闭环，再沉淀稳定的内置工作流。**

用户提出的方向成立，但“平台和本地效果一致”需要成为可验证的运行契约，而不能只靠使用同一模型或复制一段提示词。

| 判断 | 结论 | 边界与依据 |
|---|---|---|
| Codex 能否承接平台文档生成 | 技术上可行，建议作为首个 PoC 基线 | 官方 TypeScript SDK 封装 Codex CLI，可流式接收事件、指定工作目录、恢复会话；它实际运行 Agent，而非只调用一次模型。[S01][S02] |
| DeepSeek Harness 能否接入 | 技术上可行，建议作为第二适配对象开展隔离验证 | 官方项目确有 headless、sdk、acp 等运行面；但当前是开发者预览，官方明确未安全审计、不能视为生产就绪。[S04]–[S09] |
| 能否同时支持内置工作流 | 可以，且与通用模式互补 | 两种模式共用任务、输入快照、候选产物、门禁和交付契约，执行器各自保持原有调度方式。此项为本项目建议。 |
| 能否保障本地与平台一致 | 可以保障输入、配置、能力和验收标准一致；质量等价需要实测证明 | 模型随机性、服务端模型变化及外部工具数据变化，使逐字相同不能作为普遍承诺。详见第 6、10 节。 |
| 本轮是否已证明业务全流程通过 | 没有 | 本轮完成官方资料与源码定向调研，未真实运行 Codex / DeepSeek Harness 文档生产，也未验证企业 GitLab 交付。 |

**推荐顺序：Codex 完整运行基线 → DeepSeek Harness 同契约接入 → 内置工作流复用产物契约。** 若模型网络、部署或商业条款不满足实际环境，可先试 OpenCode 或隔离的 DeepSeek Harness；不能因此把尚未验证的效果标记为一致。

优先目标是“有证据的合格文档交付”，不是尽快增加多个模型入口。Codex、DeepSeek Harness 与工作流的优劣须在同一组任务上比较，本报告不根据品牌推定质量排名。

## 2. 调研范围、方法与证据等级

### 2.1 用户原始需求

> 文档生成这部分可以用codex、deepseek harness这种通用agent？接入通用agent先跑通全流程，保障在平台上使用和本地效果一致。同时也支持平台内置的工作流方式的agent。进行调研，给出调研报告，给出是否可行和竞品产品等内容。

研究对象为企业技术文档生产：来自需求、代码或设计材料，经过检索、写作、验证、人工审核和版本交付。这里的 Agent 应能操作受控工作区、读取 Skill、调用工具并反复修正，不只是面向读者的知识问答助手。

### 2.2 方法与资料边界

- 使用仓库内 `.codex/plugins/pm-skills/skills/competitor-analysis/SKILL.md`，完整读取并按任务调整比较维度；Codex 资料同时参考 OpenAI Docs Skill。
- 定向检查当前文档生产源码、既有设计和上一份竞品报告，避免把框架默认示例当成现行生产链路。
- 优先使用产品官方文档、官方源码仓库和官方定价页；第 12 节列出可追溯入口。
- OpenAI 文档站多次返回 HTTP 403，网页检索未取得可用正文；Codex 的具体能力改以 OpenAI 官方源码中的 SDK 文档及 CLI 源码核验。官网不可访问不等于产品不支持；未读取到的完整协议、账号权益和部署条款不作确定结论。
- DeepSeek Harness 官网入口返回 429，官方 GitHub 仓库及架构、安全说明可读；部分猜测路径返回 404，随后改用实际仓库路径。`releases/latest` 的 404 只说明该接口未返回 latest release，不推导为无法安装。
- 云端套餐、预览状态和文档会持续变化，本文只代表调研日期抓取到的公开信息；采用前应按锁定版本再核验。

证据分为：**官方明示**、**本仓库代码事实**、**适配建议/推断**、**待 PoC 验证**。没有采购试用、用户访谈或市场份额数据，不编造融资、占有率、满意度或 ROI。

本轮为只读调研加文档交付，没有后端行为变更，未触及必须审批的业务操作。研究过程不启动新 Agent，不修改既有开发任务的状态。

## 3. 先区分模型、harness、Skill 与工作流

| 层级 | 职责 | 本任务中的意义 |
|---|---|---|
| 模型 | 生成文本、推理、提出工具调用 | 同一个模型可以被不同 Agent 使用；只换模型 endpoint 不能复制本地体验。 |
| 通用 Agent harness | Agent 循环、工具执行、上下文管理、会话、权限交互等 | Codex、DeepSeek Harness、Claude Agent SDK、OpenCode 属于重点考察对象，具体能力因版本与配置而异。[S01][S04][S10][S11] |
| Skill / 项目规则 | 文档方法、提示、模板、脚本和参考资源 | 要连同引用文件与依赖一起加载；各 harness 对目录发现、优先级、执行方式的支持必须逐项验证。 |
| 内置工作流 Agent | 由平台显式编排规划、检索、生成、验证等节点 | 适合标准化、可观测、可重试的固定路径；节点也可以使用模型或后续接入完整 harness。 |
| 平台治理与交付 | 身份、来源、任务范围、版本、审核、采用、GitLab 交付与证据 | 两种执行模式都要遵守，不能交由模型自行宣告完成。 |

**DeepSeek Harness 是 DeepSeek 官方的插件式 Agent 项目；LangChain Deep Agents 是另一个建立在 LangChain / LangGraph 之上的 harness。两者不能混称。** DeepSeek 模型的 tool calls API 也不是 DeepSeek Harness 本身。[S04][S05][S13][S24]

通用模式要保留 harness 的完整工具循环：平台提交目标、受控输入和规则后，让 harness 自行检索、写作、检查与修正。若平台仍按四步分别发起孤立的模型请求，再把模型名称改成 Codex 或 DeepSeek，无法据此宣称保留了本地 Agent 效果。

## 5. 通用 Agent 选型与可嵌入方式

### 5.1 能力对照

| 对象 | 官方可编程入口 | 适配判断 | 主要限制与待验证项 |
|---|---|---|---|
| Codex | TypeScript SDK 启动 CLI，JSONL 事件；CLI `exec --json`、恢复与结构化输出选项 | 首个基线推荐：已有 Node.js 后端，易做独立 worker 和工作目录控制。[S01][S02] | 官方文档站访问受限；SDK/CLI 必须锁定匹配版本。取消、审批回传、恢复失败和账号授权需实测。 |
| DeepSeek Harness | `headless` 单任务模式；完整 `sdk` profile 的 JSON-RPC；另有 ACP profile | 可用作第二后端，优先完整 SDK；headless 可做短任务对照。[S05]–[S08] | 开发者预览；完整隔离必需；profile、patch、原生依赖、提问回调及会话存储需验证。[S09] |
| Claude Agent SDK | 官方 Python / TypeScript SDK，复用 Claude Code 的工具、循环与上下文管理 | “本地产品能力可编程嵌入”的明确参照。[S10] | 模型访问、商用条款、托管成本、部署限制需按实际账号核实；不凭 SDK 存在推定所有本地扩展自动可用。 |
| OpenCode | JS/TS SDK 控制 OpenCode server，支持会话、事件、配置与结构化输出 | 多模型候选；官方 provider 文档列有 DeepSeek。[S11][S12] | 是另一种 harness。把 DeepSeek 模型接入 OpenCode，不等于运行 DeepSeek Harness；安全策略和一致性仍需独立验证。 |
| LangChain Deep Agents | SDK 自托管，也有 Managed Deep Agents | 适合已有 LangGraph 团队后续构建定制执行器。[S13] | 需要自行维护更多工具/环境组合；不是快速复刻 Codex 或 DeepSeek 本地配置的捷径。 |

不建议同时首发五个执行后端。先验证一个完整闭环，再用第二个后端检验统一契约是否真的解耦，避免过早抽象。

### 5.2 Codex：首个基线的落地判断

官方 SDK 文档说明：它封装 CLI，通过子进程 stdin/stdout 交换 JSONL；支持多轮 thread、`runStreamed()`、`outputSchema`、`resumeThread()`、工作目录和环境/配置覆盖。这些是平台承载本地 Agent 的直接技术基础。[S01]

建议首轮采用“平台队列 → 隔离 Node.js worker → 固定版本 Codex SDK/CLI → 独立任务工作区”。SDK 返回的总结只能作为说明，真实文档应从受控输出目录收集、解析和校验。CLI `exec --json` 可作为同版本对照或简单批处理入口。[S02]

App Server 可列为更深交互集成的备选，但本次只读取到了官方源码中的相关说明，未完整核验其当前协议和部署方式；不在本报告写死消息 schema、审批接口或宣称它优于 SDK。开发前应对锁定版本生成/读取协议并比较审批、交互及恢复能力。[S03]

源码许可证与模型服务、账户使用权是不同事项。官方仓库许可证为 Apache-2.0，但生产使用的模型凭据、套餐和企业数据处理条件仍需单独核实。[S25]

### 5.3 DeepSeek Harness：必须按完整 profile 理解

官方架构显示，它基于 Cordis，把模型适配、工具、会话和 Agent 循环都作为插件。`web`、`headless`、`sdk`、`acp` 共用 `dsh-base`；`sdk-minimal` 是刻意独立的最小组合，不继承该完整基础。[S05]

由此有三个直接结论：

1. **可接入**：`headless` 提供一次性执行与 JSON 事件、指定 session 恢复；`sdk` 提供可嵌入 JSON-RPC 运行面。接 SDK 不需要把整套桌面 UI 搬到平台。[S06][S07][S26]
2. **不能把 sdk-minimal 当本地完整版**：它明确省略 workspace instructions、Skills、Web 工具等多项完整能力，默认策略也要求隔离使用。用它跑通模型后不能宣称复制了本地完整文档能力。[S08]
3. **相同基础不等于配置自动相同**：headless 默认关闭托管凭据存储及有关消费者，SDK 则沿用基础配置；SDK 的用户时区识别、交互提问和图形展示也有边界。平台需要显式提供提问处理，时间上下文按实际能力记录，不能默默丢弃。[S06][S07]

应冻结最终生效的 profile、bundle、用户 patch、home patch 与有序 `--patch` overlays，而不仅保存一个 profile 名称。官方架构提供配置展开思路；平台需在脱敏后记录配置摘要。[S05]

**当前适合隔离 PoC，不建议直接承载高权限生产资料。** 这不是一般性的风险推测：官方 `SAFETY.md` 明确声明项目处于实验预览、未安全审计，不可作为不可信工作负载的唯一安全控制。生产准入应基于独立容器/虚拟机隔离、最小凭据与真实故障验证，且不能把这些措施描述为官方安全认证。[S09]

## 6. “平台使用与本地效果一致”的工程定义

### 6.1 三层一致性

| 层级 | 要保证的内容 | 如何验收 |
|---|---|---|
| 运行一致 | 同一 harness 版本、同一类执行面及经核验的有效配置 | 运行前比较清单与摘要；差异明确展示，必要能力缺失则阻断。 |
| 能力一致 | 同源资料、同 Skill/规则、同工具与权限范围、同转换链路 | 启动探针读取样例资料，检查工具 schema、授权、文件读写和转换结果。 |
| 结果等价 | 事实正确、覆盖范围、引用、结构、可构建性和交付结果符合相同标准 | 相同任务重复运行、人工盲评、确定性校验及真实交付验证。 |

输出文件可以有不同措辞和段落组织。若业务要求某些片段、SQL 语法、参数表或模板字段严格一致，应把这些部分做成确定性结构约束并检验；不能把整篇模型文本当成确定性编译产物。

### 6.2 建议引入 RunBundle（运行输入包）

这是本项目建议的数据边界，不是当前已实现接口。每次运行冻结如下信息：

| 类别 | 需要记录/提供的项目 |
|---|---|
| 执行器 | harness、SDK/CLI 版本或提交、安装产物校验和、worker 镜像及操作系统/架构 |
| 模型 | 服务商、精确模型标识、端点类别、推理/采样/输出预算等实际参数；若供应商只给可变别名，标记无法完全冻结 |
| 配置 | 脱敏后的完整生效配置、profile 和 patch 顺序、默认系统行为差异 |
| 输入与范围 | 任务目标、数据库产品版本、资料快照、仓库基准 commit、允许改动的目录/篇目、原文摘要 |
| 规则与 Skill | `AGENTS.md` 及实际生效的父级规则、Skill 正文、引用文件、脚本依赖与版本、模板/术语库摘要 |
| 工具 | 工具名称/schema/版本、MCP server 版本、授权主体和 scope、网络白名单；凭据只保存引用 |
| 工作环境 | cwd、目录映射、PATH 白名单、locale、时区、字体、PDF/Office/Markdown 转换器版本 |
| 状态 | 新会话或恢复会话、会话ID、历史与记忆/压缩策略、是否允许子任务，状态存储归属 |
| 校验与产物 | 产物 schema、正文/资源目录、检查器版本、预算和完成条件 |

运行包应有规范化清单摘要；密钥和访问令牌不进入包、日志、文档或哈希输入明文。禁止直接挂载整个用户 HOME 来复制体验：从中提取实际需要的规则、扩展配置和秘密引用即可。平台只向 worker 注入本次任务必要的短期凭据。

一致性清单必须记录“观察到的真实生效状态”，不只记录“请求传入的期望状态”。特别是 Skill 发现路径、MCP 登录主体和默认工具说明，常常在表面提示词相同的情况下发生变化。

### 6.3 两种承载方式

| 方式 | 适用情况 | 建议 |
|---|---|---|
| 平台侧隔离 worker | 资料、依赖和连接器可以在服务器复制 | 首期推荐；便于版本固定、资源限制、日志与产物回收。 |
| 本地 worker 主动领取平台任务 | 只能在个人本地使用的专用工具、内网软件或资料 | 可选后续方式；需要设备注册、身份、租约、断线恢复和本地数据治理，不能靠开放个人电脑远程端口实现。 |

若平台只能提供 Linux，而本地效果依赖桌面应用、浏览器已登录状态、Windows Office、未登记的插件或个人长期记忆，应标记为“环境未等价”，先补齐或明确缩小承诺。不要用静默换工具、换模型或省略图片处理来掩盖差异。

### 6.4 比较顺序

先固定 harness、模型与运行包，比较本地和平台；通过后再固定任务比较不同 harness。最后才比较不同模型和工作流。否则“平台效果变差”可能来自模型、Skill、工具、网络或配置，无法归因。

## 7. 双模式架构与接口建议

### 7.1 建议边界

```text
任务入口：目标 / 来源 / 版本 / 范围 / 执行模式
                    │
         输入冻结、权限检查、RunBundle
                    │
        统一运行服务：队列 / 租约 / 事件 / 取消
                    │
          ┌─────────┴──────────┐
          │                    │
     通用 Agent 后端      内置工作流后端
     Codex / DSH 等       平台节点与 DAG
     自主工具循环         显式节点调度
          │                    │
          └─────────┬──────────┘
                    │
        候选正文 + 资源 + 引用 + 检查证据
                    │
      统一质量门禁 → 人工采用/修订 → 逐篇审核
                    │
       GitLab 交付 → 合并事实 → 目标分支回读
```

平台定义工作范围和允许的副作用；harness 决定范围内的写作步骤。两种模式共享同一业务任务，但不要求生成过程和节点数相同。

### 7.2 建议的最小契约（非现有公共 API）

| 契约 | 主要作用 |
|---|---|
| `capabilities()` | 返回会话、恢复、交互提问、工具、图像/文件、结构化输出等真实能力与限制 |
| `preflight(runBundle)` | 比较版本/摘要、验证必要工具与权限，报告差异；必需项缺失则不启动 |
| `start(runBundle, executionSpec)` | 启动一次受限运行，返回平台 runId 与后端 session/threadId |
| `events(runId, cursor)` | 可续传事件；以 runId + 序号去重，保留原始事件引用，前端按中文状态展示 |
| `respond(runId, requestId, answer)` | 仅针对后端支持的澄清/权限交互；权限答复仍由平台策略控制 |
| `cancel(runId)` | 中止模型与子进程、撤销租约、等待退出并封存证据；迟到产物不得采用 |
| `resume(runId, checkpoint)` | 同版本同任务边界下恢复；不支持或环境漂移则明确返回原因 |
| `collectArtifacts(runId)` | 按 schema 收集正文、资源、引用、检查结果、用量和已知限制 |

`execution.mode` 与 `harness`、`model` 分开：选择工作流时记录工作流定义版本；选择通用模式时记录 harness/SDK/profile。选择项应来自能力注册与配置，不在业务代码里散落产品名称分支。

建议伪代码：

```text
bundle = freezeInputs(task, selectedSkills, sourceSnapshots)
backend = registry.resolve(executionSpec)
preflight = backend.preflight(bundle)
require(preflight.requiredCapabilitiesSatisfied)
lease = claimRunLease(task, bundle.digest, executionSpec.digest)
run = backend.start(bundle, executionSpec)
for event in backend.events(run, storedCursor):
    persistDeduplicated(redact(event), lease)
    if leaseInvalidOrCancelled(): stopAndAwaitExit(run)
artifacts = backend.collectArtifacts(run)
require(processAndBackendCompleted(run))
require(artifactSchemaValid(artifacts) and pathsInAllowedScope(artifacts))
require(taskBaseDigestStillMatches(task, bundle))
candidate = saveCandidate(artifacts, provenance=bundle.digest)
return candidateWithQualityEvidence(candidate)
```

以上只到候选生成。人工采用、逐篇审核、GitLab 合并与回读仍由现有业务流程推进；单次 Agent 的 `completed` 不能直接把整个生产任务置为完成。

### 7.3 必须处理的状态与安全问题

- **恢复语义**：事件允许重复投递，消费必须幂等；进程退出成功、harness 任务完成、产物通过校验是不同事实。尤其 DeepSeek headless 文档区分工具调用完成与内部命令退出成功。[S07]
- **取消与迟到**：取消时终止整个进程组/受控容器，等待退出；租约过期或任务基础版本变化后，不接纳旧响应覆盖新草稿。
- **冲突**：运行中有人编辑草稿时，按基准摘要生成冲突或新候选；不直接覆盖。通用 Agent 只写任务工作区，不拿生产库写权限。
- **隔离**：允许改动的目录、网络和命令由 worker 外部边界执行；Skill、来源正文或模型回答不得扩大授权。
- **交互**：需要人回答时呈现真实问题；无人值守任务对未授权工具请求应停止或拒绝，不能自动同意全部权限。
- **日志**：记录工具调用摘要、结果状态、文件摘要、用量及校验报告；不以保存原始思维链作为审计要求。默认脱敏，限制正文/终端输出访问和保留期。
- **重试**：同一后端恢复与新建尝试要分开。禁止在用户不知道的情况下切换 harness/模型后沿用旧结论；跨后端重跑必须是新的、有追溯关系的尝试。
- **资源**：设置总时长、工具调用、费用、工作区容量与并发上限；避免长期循环和残留进程。规则和阈值放入配置，知识规则放 `knowledge`，运行写入放 `runtime`。

## 8. 竞品与替代方案

### 8.1 市场范围与比较口径

这是“技术文档生产平台 + Agent 执行基础设施”的交叉场景，没有证据证明某一个产品完整覆盖本项目所有需求。下表选取五个重点对象，明确区分直接文档产品、工作流替代和执行基础设施，避免把框架误称为同类 SaaS。

上一份报告已讨论 GitBook、Document360、Paligo、Confluence、Outline 的文档治理链路，本报告在其基础上重点考察 Agent 接入：

- [2026-10-28 文档生产平台竞品分析](./知识中心-文档生产-20261028竞品分析-参考报告.md)

目标客户为有多版本技术手册、代码/设计来源、内部审核和 GitLab 交付要求的团队。关键成功因素是事实可追溯、修改可审阅、工具可复现和交付可核验，而不只是生成速度。没有可比的公开市场规模或份额证据，本文不做数值估算。

### 8.4 产品定位与差异化建议

**建议定位：支持可替换执行器、能从资料追溯到交付事实的技术文档生产平台。** 通用 Agent 是执行层，平台的价值是专业知识、版本关系、审核责任和可核验交付。

建议优先形成四项差异：

1. 同一个受控运行包可以本地/平台执行，差异能展示、故障能追查，而不只是支持多个模型名称。
2. 来源、模板、Skill、产品版本与文档段落/资源有证据关系；事实不充分时返回缺口，不生成貌似正确的 SQL 或运维建议。
3. 通用模式适合探索性与复杂跨文件任务；内置工作流适合重复、约束明确的任务，并共享候选和审核入口。
4. 逐篇审核、增量影响、资源一致性、GitLab 合并与回读成为平台的一等业务事实，不以“Agent 已回复”结束任务。

未来 12–18 个月应重点关注：GitBook 的外部 Agent 管理接口、Mintlify 的自动维护与代码联动、工作流平台对 Skills/通用执行环境的支持，以及各 harness 的标准协议与企业隔离能力。此为风险观察方向，不是对产品路线的事实预测。

## 9. 完整业务流程：何谓“先跑通”

建议用一项有代表性的真实文档任务完成以下链路，而非只演示一个生成接口：

| 阶段 | 应产出的业务证据 |
|---|---|
| 1. 选任务与版本 | 明确来源、数据库版本、待修改文档及范围；与既有任务关系保持一致 |
| 2. 冻结上下文 | 来源、模板、Skill、原文、执行器和工具清单摘要 |
| 3. 运行通用 Agent | 真实模型和工具事件；可看到进度、问题、失败与取消 |
| 4. 收集与验证 | Markdown、图片/附件、引用、修改清单和校验报告；无范围外写入 |
| 5. 人工采用与修订 | 候选与原文对比，冲突处理；记录采用、编辑及版本 |
| 6. 逐篇审核 | 范围内每篇有有效审核结论；有退回时修订相应篇目，变更后的旧结论不继续放行 |
| 7. GitLab 交付 | 在明确授权的测试项目中提交变更，记录分支/MR/目标 commit 与资源清单 |
| 8. 完成判定 | **合并且目标分支正文/资源回读一致**；未合并或回读失败不得视为完成 |

第 6、8 项沿用当前项目已有决策，不在本轮重新定义规则。Agent 自己声称已审核、终端退出 0、候选生成成功或 MR 已创建，都不足以替代上述终点。

真实外部操作要按执行时有效授权和仓库边界实施。本次调研没有获得新的企业 GitLab 写入、共享服务重启或生产发布授权，也没有执行这些操作。

## 10. PoC 路线与验收建议

### 10.1 分阶段推进

| 阶段 | 最小交付 | 出口条件 |
|---|---|---|
| P0：基线冻结 | 选真实任务；保存本地成功运行包、产物和成本；确认模型网络及凭据方式 | 本地可重复运行，关键工具与输入已列清，无隐式个人环境依赖 |
| P1：Codex 首条闭环 | 一个隔离 worker、一个执行后端、事件展示、候选接入和真实授权测试交付 | 第 9 节全链路通过，且本地/平台对照达标 |
| P2：DeepSeek Harness 对照 | 完整 SDK profile 适配、配置差异报告、提问与取消/恢复验证 | 同一产物/业务契约通过；预览与隔离风险有明确结论 |
| P3：内置工作流复用 | 现有工作流映射统一输入/产物/事件契约；平台可选两种模式 | 相同任务可分别执行、对比、审核和交付，互不污染会话/候选 |
| P4：有限试点 | 多任务、限并发、限预算、可回退和运行监控 | 真实用户试点满足质量、成本和故障处理要求，再决定扩大范围 |

首期不同时建设本地 worker 网络、复杂可视化流程设计器、多后端自动路由或无人审核自动合并。它们不属于证明双模式和本地等价所必需的最小路径。

### 10.2 对照样本

建议起始样本为六类真实任务，每类先选一例：新章节、局部增量修订、跨篇术语/版本修改、SQL/命令与参数说明、图片/附件引用、来源不足或冲突任务。若资料中实际有 PDF/Office，应在对应样例中包含解析/转换步骤，不用纯文本成功覆盖它们。

第一轮固定一个 harness 和模型，每项任务在本地、平台各运行 3 次，即 **6 × 2 × 3 = 36 次**。此为建议实验规模，不是已经完成的次数，也不是统计显著性保证。第二个 harness 单独执行同一设计，再分析跨后端差异。

重复次数、质量评分容限、成本与时延预算应在 P0 根据真实基线形成配置，不能在看到失败后临时放宽，也不直接固化为生产业务规则。

### 10.3 验收矩阵

| 维度 | 建议指标/门禁 | 说明 |
|---|---|---|
| 环境 | 必需能力清单与版本摘要全部匹配；已知差异被显式处理 | 没有通过环境等价，不出具“同效果”结论 |
| 安全与范围 | 越权写入、密钥泄漏、未授权发布为 0 | 故障任务也须验收；Agent 内置权限不是唯一边界 |
| 文档结构 | 必填字段、资源路径、链接、构建及约定检查全部通过 | 确定性规则从项目现有配置复用 |
| 知识与事实 | 所选样本关键事实正确、来源可追溯；来源不足能明确阻塞/返回缺口 | 引用存在不代表内容支持结论；SQL 示例需按任务级别进行真实验证 |
| 质量等价 | 人工盲评正确性、完整性、可读性与规范性 | 建议起点：五分制平台均分相对本地下降不超过 0.2，且无关键事实回退；此为待基线校准的建议，不是已批准门禁 |
| 故障处理 | 取消、断线、恢复、租约失效、重复事件、并发编辑不产生错采用 | 验证真实进程/后端行为，不能只使用事件 mock |
| 业务完成 | 每篇有效审核通过，授权测试 GitLab 合并，正文/资源回读一致 | 逐项证据，不以 MR 创建替代完成 |
| 成本时延 | 单篇/单任务费用、工具/转换成本、端到端时延、重试率及人工修订时长 | 以完整任务比较；先记录分布，再制定正式预算 |

建议的故障集：模型/工具超时、SDK 进程退出、流中断、用户取消、取消后迟到输出、会话目录丢失、同任务并发编辑、MCP 凭据过期、未授权命令、来源提示注入、路径穿越、缺少资源文件、检查失败、MR 未合并、目标分支回读不一致。

### 10.4 什么情况应调整路线

- 本地已有可用 harness，但平台无法复制关键工具：先解决环境缺口或采用受管本地 worker，不重写提示词掩盖问题。
- Codex 的账号、网络或合同不满足部署需求：换候选后端重新基线，不视为 SDK 技术失败。
- DeepSeek Harness 的预览版本持续不稳定：保留适配契约与证据，限制为实验后端；可比较 OpenCode + DeepSeek，但明确它是另一组合。
- 某类任务总由稳定步骤构成且人工修订少：优先沉淀内置工作流，降低运行变异。
- 两种模式都不能保证关键事实：补知识证据与验证器，不因运行成功而扩大试点。

## 11. 成本、主要风险与待办

### 11.1 完整成本口径

```text
完整任务成本 = 模型输入/输出及缓存计费
             + 工具/MCP/检索/解析转换费用
             + worker 计算/存储/日志/网络
             + 重试和失败运行费用
             + 人工核验、修订和审核时间
             + harness/插件/工作流升级与隔离维护分摊
```

比较商业产品时再加入订阅、席位、AI credits、迁移和集成费用。当前没有运行样本，不提供无依据的人天承诺、节省比例或单篇成本。

### 11.2 风险与对应措施

| 风险 | 应对与退出路径 |
|---|---|
| harness 与插件升级改变结果 | 锁版本与依赖，保留旧镜像/运行包；升级后重跑代表样本 |
| 本地隐藏配置导致不可复制 | 预检有效配置与实际工具；缺项阻断，差异可见 |
| 资料中的恶意指令或越权操作 | 输入按资料处理，运行隔离、网络/目录限权、发布权留平台 |
| 预览项目稳定性与安全边界不足 | DeepSeek Harness 限隔离 PoC，故障验证后再评估准入 |

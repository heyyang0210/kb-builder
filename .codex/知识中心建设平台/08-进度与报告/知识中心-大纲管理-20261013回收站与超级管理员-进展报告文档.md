# 大纲回收站与超级管理员：方案、实施步骤与验收报告

日期：2026-10-13。状态：代码实现及隔离数据库验收完成；共享环境尚未迁移、尚未部署。

## 1. 问题与选定方案

C驱动参考手册已发布，原 Storage 删除逻辑根据版本治理规则拒绝 published/superseded，因此“当前大纲版本不可修改或删除”首先是旧设计限制。前端同时存在数据库大写状态与公共小写状态判断不一致，导致已发布对象仍显示“删除候选”，这是实现缺陷。此次按用户选择实施方案1，调整业务契约，而不是仅修改报错文字。

方案1为可恢复逻辑删除：已发布版本也可移入回收站，保留发布状态、节点、责任与生产历史；活动列表排除删除版本，阻止新的治理和生产写入。彻底删除是单独操作，仅 SUPER_ADMIN 可用，要求准确输入版本 ID、非空原因，且无历史或下游引用。存在引用时拒绝清理，不级联删除成果。

用户明确现有 `admin` 已具备超级管理员职责。本次在启动引导中为现有内置管理员补齐 SUPER_ADMIN，保留账号 ID、密码和已有角色，不创建另一个账号。其他 PLATFORM_ADMIN 不自动升级，也不能授予、撤销或修改超级管理员角色。

## 2. 完整实施顺序与结果

1. 读取问题修复规则、仓库约束与任务路由，按标准开发处理；范围包括大纲生命周期、身份授权、引用一致性、页面和验证。记录完整提示词及 admin 决策。
2. 先更新 `.codex` 大纲、认证、平台权限详细设计及权限概要，明确数据字段、API、伪代码、恢复冲突、依赖阻断与回退边界，再修改代码。
3. 新增 SQL `013_outline_recycle_super_admin.sql`，不改旧迁移。增加 DELETED_AT、DELETED_BY、DELETION_REASON、DELETED_WAS_CURRENT，以及超级管理员角色和清理动作。因迁移器要求 SQL 来自已提交版本，仅该 SQL 提交为 `3c35ccf`；其余实现改动保留在工作区。
4. Storage 增加逻辑删除、恢复、清理预检和清理事务。删除当前版本时清空当前指针，不把历史版本自动升为当前；恢复不得覆盖后来的当前版本。保留按 ID 历史读取，重复删除/恢复幂等。清理后独立生命周期审计仍保留。
5. 引用扫描覆盖其他大纲基线、发布/已替代责任版本、生产/任务/审核等 KC_RECORD 聚合，包括软删除历史。记录写入按确定顺序锁定所引用的大纲，与清理共享版本锁，避免预检与并发写入的竞态。已删除或不存在的基线拒绝写入。
6. BFF 使用当前真实会话判定权限并覆盖操作者/动作头，文档 API 使用内部令牌。恢复使用 outline:delete；清理及预检使用 outline:purge。旧 DELETE 路径统一改为逻辑删除，消除绕过回收站的旧物理删除入口。
7. 文档生产网关提前阻止删除基线的草稿保存、附件上传和送审；活动目录排除删除版本。前端改为中文“移入回收站”，增加回收站和恢复按钮，仅具备清理权限者显示“彻底删除”，输入错误 ID 时不发清理请求。
8. 执行统一构建、相关单元/真实 HTTP 权限测试、统一测试入口管理的隔离数据库 API 与浏览器 E2E。发现问题后修复并重新执行，见下一节。
9. 同步相关 README、待办与本报告。测试实例、连接与数据库租约由统一入口结束清理；真实 C驱动参考手册 DB-007 未被删除。

## 3. 对外接口与验收标准

统一前缀：`/knowledge-center/api/outline`。

| 路径 | 权限 | 结果 |
|---|---|---|
| GET `/governance/recycle` | outline:read | 回收站及原状态、删除人和时间 |
| DELETE `/governance/{id}` | outline:delete | 可恢复删除，包括已发布版本 |
| POST `/governance/{id}/restore` | outline:delete | 恢复；新当前版本冲突返回 409 |
| GET `/governance/{id}/purge-preflight` | outline:purge | 依赖数量和清理可行性 |
| POST `/governance/{id}/purge` | outline:purge | `{confirmId, reason}`；有引用返回 409 |

清理删除该版本自有数据，不删除手册、其他大纲、生产成果或 GitLab 文件。超级管理员权限也不绕过依赖完整性检查。Storage 是内部受信接口，部署时不得暴露为公网业务入口。

## 5. 上线步骤（尚未执行共享环境写入）

1. 负责人确认目标 JDBC 地址、数据库账号和 Schema，备份目标库与本地认证数据，按既有部署流程合入本功能改动及已提交的迁移 013。不要把工作区其他并行任务改动一并当作本功能交付。
2. 在部署窗口停止旧应用写入；由部署环境注入目标数据库凭据，生产启用严格迁移摘要校验。仓库根目录运行：

   ```bash
   export YASDB_MIGRATION_CHECKSUM_POLICY=strict
   tools/repository/build-knowledge-center.sh
   apps/yashandb-storage/start.sh migrate
   ./knowledge-center.sh restart --no-build
   ./knowledge-center.sh status
   ```

   `migrate` 前必须确认目标环境，不能以默认开发配置代替生产配置；若失败立即停止部署，不修改历史 SQL 摘要以强行通过。
3. 用现有 admin 登录并确认角色含 SUPER_ADMIN、动作含 outline:purge；无需新增账号或重设密码。验证普通平台管理员无清理权限。
4. 使用上线专用、无业务引用的测试候选验证“移入回收站→恢复→再次删除→精确 ID 和原因清理”；再验证有引用的测试版本清理被阻断。上线验收不要对真实业务手册执行彻底删除。
5. 用户确认后，对 C驱动参考手册执行“更多操作→移入回收站”。此操作允许发布版本，后续可在大纲列表“回收站”恢复。若确需清理，admin 在回收站查看依赖，准确输入 ID 与原因；依赖未解除时仍会阻断。

## 6. 已知边界与回退

数据库模式为完整交付路径。文件模式支持逻辑删除和恢复，但没有事务化跨模块依赖索引，清理返回 OUTLINE_PURGE_UNAVAILABLE。新中文提示与规则配置化、依赖扫描索引和历史聚合更新粒度已记入 `.codex/知识中心建设平台/04-开发任务/知识中心-平台-配置化与测试缺口-待办事项文档.md`。

已删除版本的历史聚合仍可读取；含该版本的聚合要继续更新，需先恢复大纲。现有依赖扫描偏保守，保留软删除的下游历史也会阻止清理，这是本次治理约束。

逻辑删除可通过回收站恢复；彻底删除只能依靠备份恢复。回退前先恢复仍需活动的大纲；不能直接回到忽略删除标记的旧代码，否则会重新暴露回收站数据。新增列和角色可保留，不直接删列回滚。

# 知识中心前端刷新性能专项测试报告

> 报告时间：2026-09-18 14:35:00 Asia/Shanghai
> 实际环境：`http://192.168.130.180:13510/knowledge-center/`
> 测试结论：既有 5 项门禁通过；审核与发布页面的“仓库正文视觉就绪”未被既有门禁覆盖，仍存在明显二次切换，需按第 9 节继续优化
> 测试方式：真实管理员登录、真实 Chromium、真实 13510/14110/14210 服务、真实 YashanDB JDBC 查询；未使用 mock 数据

## 1. 目标与口径

本报告覆盖知识资产、审核与发布、大纲管理、模板管理四个页面的刷新性能。统计口径不只记录页面总耗时，而是拆分为：

1. HTML 和静态资源加载；
2. DOMContentLoaded；
3. 认证配置与会话检查；
4. 应用壳展示；
5. 当前页面关键 API；
6. 13510 BFF 处理及下游服务调用；
7. 14210 JDBC 连接获取、SQL、行映射、JSON 序列化；
8. 页面关键工作区首次可用；
9. GitLab 等后台增强请求完成。

“首屏可用”以浏览器内 MutationObserver 捕获关键工作区实际进入 DOM 的时间为准，不再使用 Playwright 元素轮询完成时间，避免将测试框架轮询间隔误算为页面耗时。该口径只表示审核主体已经出现，不表示 GitLab 仓库目录和正文已经加载完成；审核页还必须补充“仓库正文视觉就绪”指标，详见第 9 节。

## 2. 整体调用流程

```text
浏览器导航
  ├─ GET HTML/CSS/JS
  ├─ DOMContentLoaded
  ├─ GET /auth/config
  ├─ GET /auth/session
  └─ 展示应用壳
       ├─ GET /platform/context
       └─ 当前页面关键 API
            ├─ 13510 鉴权与 BFF 路由
            ├─ 14110 文档服务（大纲页面）
            ├─ 14210 Storage HTTP
            │    ├─ JDBC 连接池获取
            │    ├─ SQL 执行
            │    ├─ ResultSet 行映射
            │    └─ JSON 序列化
            ├─ BFF 筛选与响应序列化
            └─ 浏览器渲染关键工作区
                 └─ GitLab access-status/正文等后台增强
```

## 3. 优化前问题、等待关系与用户影响

### 3.1 页面与请求基线

下表中的“后台完成”表示最后一个刷新相关 API 返回，不等于用户必须等待的首屏时间。

| 页面 | 用户实际等待的内容 | 优化前表现 | 问题性质 |
|---|---|---:|---|
| 知识资产 | 手册列表已经出现，但页面和同进程接口仍被两个 GitLab 统计请求拖住 | 首屏约 267～298 ms；后台完成 2119～2259 ms | 非首屏请求错误地请求无权限仓库，返回 401，并占用 13510 单进程事件循环 |
| 大纲管理 | 大纲列表之外还等待当前页面不使用的工作台数据 | 首屏约 209～259 ms；后台完成 1040～1079 ms | 无关请求增加网络和整页重绘，不是大纲 SQL 本身慢 |
| 模板管理 | 模板摘要返回后读取当前选中模板正文 | 首屏约 176～212 ms；后台完成 981～1069 ms | `summary=1` 不包含正文，详情请求是功能正确性所需；此前将其判断为重复读取不准确，已纠正 |
| 审核与发布 | 没有活动任务时，页面依次等待手册列表、正式基线和 GitLab 检查 | 真实工作区代表值约 548 ms；后台完成 1403～1442 ms | 手册数据库投影慢，且增强数据串在关键路径之后继续占用服务 |

### 3.2 数据库根因

优化前 `/v1/domain/handbooks` 对 75 本手册执行：

```text
1 条手册主查询
+ 每本手册 2 条负责人查询
+ 每本手册 1 条当前大纲业务 ID 查询
= 226 条左右 SQL
```

Storage 直读实测为 262.775 ms。该请求又由 13510 使用 `execFileSync(curl)` 同步调用，数据库读取期间会阻塞 Node 事件循环，使同进程中的 `/platform/context`、`/platform/overview` 等请求一起延迟。

### 3.3 静态资源现状

刷新审核页会加载 48 个资源、约 1,096,817 字节。主要资源包括：

| 资源 | 传输大小 | 代表耗时 |
|---|---:|---:|
| `lucide.min.js` | 358,057 B | 57 ms |
| `app.js` | 156,177 B | 82 ms |
| `styles.css` | 106,996 B | 21 ms |
| 全部页面 ES Module 图 | 多模块 | DOMContentLoaded 通常约 140～214 ms |

数据库优化后，静态模块加载成为首屏耗时占比最高的已测阶段。这里具体指：浏览器进入任一页面时，会同时下载和解析其他页面的视图模块、Markdown 渲染器和图标库；这些资源不是当前页面数据，但会推迟 DOMContentLoaded。这是加载策略问题，不是业务数据错误。

## 4. 已实施优化

1. 非工作台页面不再预取 `/platform/overview` 和 `/outline/build-tasks`。
2. 知识资产目录先渲染，GitLab 统计改为后台增强；`access-status` 不可读时不发起 statistics。
3. 审核任务、手册和基线可用后先展示审核主体，GitLab 正文随后补充。
4. 模板摘要不作为正文使用；确定选中项后只读取一次该模板详情，避免逐模板读取正文。
5. 移除浏览器前进/后退触发的二次页面加载。
6. 手册数据库投影由约 226 条 SQL 收敛为 1 条联表 SQL，同时读取负责人和当前大纲业务 ID。查询从 HTTP 入口 `Main.java` 移入 `HandbookProjectionRepository`，由 Repository 集中维护命名 SQL、结果行 DTO 和查询计时；`Main` 只编排连接、事务和响应。
7. 本次四页刷新关键路径中的手册只读链路由同步 `curl` 子进程改为 Node 原生异步 HTTP，避免阻塞 13510 事件循环；本报告没有线上调用频率数据，不将该接口表述为高频接口。
8. Storage 在 `Server-Timing` 中输出 `db-connection`、`db-query`、`row-mapping`、`json-serialization`、`storage-total`。
9. 修正认证性能日志将纳秒误标为毫秒的问题。

## 8. 剩余观察项、风险状态与后续建议

1. 静态模块图：当前通常需要 126～213 ms 才触发 DOMContentLoaded，占首屏的大部分时间。原因是所有页面模块一次性加载。建议按路由拆分 ES Module 和 CSS，并延迟非当前页面的 Markdown、KaTeX、平台管理资源。该问题只影响加载速度，不表示页面功能错误。
2. 同步子进程调用：13510/14110 的其他旧领域读取仍存在同步 `curl` 路径。是否优先改造应先补充接口访问量、并发量和阻塞时间监控；本轮只改造已被本次刷新链路证明会阻塞页面的手册 GET。
3. 知识资产页仍会在首屏后对已映射手册逐个请求 `access-status`。当前只有 2 本映射手册且耗时可接受；数量增长后应提供批量可读性接口。
4. 异常样本：一次五轮测试中出现过 999 ms 的 DOMContentLoaded，而当轮手册 API 只有约 26 ms。随后追加 20 次模板页刷新，DOMContentLoaded 为 126～213 ms、HTML 响应结束为 3～6 ms、最慢单资源为 39～96 ms，未再次出现超过 500 ms 的样本，也未记录到浏览器长任务。因此当前没有证据确认存在隐藏业务 Bug，也不能把该值解释为数据库慢查询；该样本保留为“未归因且未复现”。若后续门禁再次出现，应保存 Playwright trace、CPU profile 和操作系统调度指标后再定性。

## 9. 审核与发布页面仓库加载问题及三种优化方案

### 9.1 问题定性与根因

刷新审核与发布页面时，当前实现存在三次可见状态变化：

```text
整页审核骨架
  → 审核主体出现，但阅读区提示“仓库正文尚未加载”
  → GitLab 目录和正文出现，阅读区及周边布局再次变化
```

这不是仓库数据丢失，也没有证据表明是隐藏的数据正确性 Bug。它是一个严重的感知性能和界面稳定性问题：既有门禁在第二个状态就判定“首屏可用”，但用户实际关注的仓库目录和正文此时尚未就绪。

代码中的等待顺序为：先读取审核任务、手册和正式基线并执行一次整页渲染；随后串行读取 GitLab 可读性、仓库元数据与分支、目录树、首个文件，必要时再读取提交列表；最后再次执行整页渲染。因此问题同时包含两部分：

1. 多次整页渲染造成加载提示、正文和目录之间的明显切换及布局跳动；
2. 仓库请求存在多个前后依赖的浏览器往返，正文真实就绪时间晚于审核主体。

现有 `235～267 ms` 只代表审核主体出现，不能用于证明仓库正文已无卡顿。当前报告没有采集从审核主体出现到仓库正文稳定的完整耗时，因此不编造该数值；实施任一方案前应先增加下列统一测量点：

| 指标 | 起点 | 终点 | 目的 |
|---|---|---|---|
| 审核主体可用 | 导航开始 | 审核操作区进入 DOM | 保留既有首屏指标 |
| 仓库等待可见时长 | 审核主体进入 DOM | 仓库正文稳定进入 DOM | 直接衡量用户看到加载过程的时间 |
| 仓库正文视觉就绪 | 导航开始 | 目录、正文、来源提交均稳定 | 作为新的审核页核心门禁 |
| 布局偏移 | 导航开始 | 仓库正文视觉就绪 | 判断加载过程中是否发生明显跳动 |
| 仓库链路分段 | 请求发出 | access、metadata、tree、file 分别完成 | 区分浏览器往返、BFF 和 GitLab 耗时 |

### 9.2 方案一：固定阅读区骨架，改为局部更新

做法：审核标题、手册信息和操作区先稳定展示；仓库目录与正文区域从首次渲染开始保留固定尺寸骨架。GitLab 数据完成后只替换目录和阅读区内容，不再重新生成整个审核页面；失败状态也在同一固定区域内展示。

该方案主要解决视觉跳变，基本不减少 GitLab 的真实请求时间。它改动范围最小，不改变后端接口和审核业务规则，适合作为短期止痛方案。

验收重点：加载状态与正文状态的阅读区外框尺寸保持稳定；审核操作区不被重建；仓库完成后无整页闪动；新增布局偏移门禁。由于真实请求链路不变，不应把该方案描述为“仓库加载变快”。

### 9.3 方案二：审核仓库上下文聚合接口，并行缩短关键链路

做法：新增审核页专用的仓库上下文接口，例如：

```text
GET /knowledge-center/api/review/repository-context?handbookId=...
```

接口一次返回可读性、仓库元数据、可用分支、目录树和默认正文。服务端并行执行没有依赖关系的读取，只在确定分支和首个文件后继续必要步骤；浏览器同时加载审核任务与仓库上下文，避免当前多个串行 HTTP 往返。响应通过 `Server-Timing` 输出 access、metadata、tree、file 和总耗时。

该方案既能配合固定布局消除明显切换，也能缩短仓库正文的真实就绪时间，是推荐的中期主方案。代价是需要新增接口契约、超时和部分失败语义，并验证用户级 GitLab 权限不能因聚合或缓存而越权。

验收重点：浏览器只发起一条仓库上下文请求；审核任务与仓库上下文并行；正文视觉就绪时间相对优化前基线有明确下降；聚合接口的每个下游阶段可独立计时；任一下游失败时返回可理解的局部状态，而不是拖住整个审核页。

### 9.4 方案三：提交级阅读快照与 SWR 后台校验

做法：成功读取仓库正文后，按 `用户权限范围 + handbookId + branch + language + path + commitSha` 保存只读阅读快照。刷新时先展示最近一次已验证快照，同时在后台检查 GitLab 最新提交；提交未变化则继续使用当前内容，发生变化时平滑替换并明确提示“仓库内容已更新”。界面必须展示快照时间和提交号，不能把旧快照伪装成最新内容。

该方案可让重复刷新时的仓库正文接近即时出现，也能在 GitLab 短暂不可用时提供受控的只读降级，适合外部仓库延迟较高或稳定性不足的场景。实现风险最高，需要设计权限隔离、缓存失效、容量限制和审计规则。审核与发布动作必须绑定明确的 `commitSha` 或正式版本快照，不能直接对可能过期的缓存内容作出发布决定。

验收重点：有权限用户的重复刷新优先命中同一提交快照；无权限或权限已撤销用户不能读取历史缓存；后台发现新提交后无闪烁更新；GitLab 不可用时清楚标识快照时间；所有审核意见和发布动作仍绑定明确版本。

### 9.5 方案对比与建议

| 方案 | 消除明显切换 | 缩短首次真实耗时 | 加速重复刷新 | GitLab 故障时可读 | 改造风险 |
|---|---|---|---|---|---|
| 一：固定骨架与局部更新 | 是 | 否 | 否 | 否 | 低 |
| 二：仓库上下文聚合接口 | 是，需配合方案一 | 是 | 有限 | 否 | 中 |
| 三：提交级快照与 SWR | 是 | 首次有限 | 是 | 是，受快照策略约束 | 高 |

建议不是三选一，而是分阶段组合实施：

1. 短期先实施方案一，立即消除整页重绘和布局跳变；
2. 中期实施方案二，减少串行往返并建立完整的仓库链路计时；
3. 收集真实访问量、GitLab 延迟和失败率后，再决定是否需要方案三。

在方案二完成前，不应仅依据既有“审核主体可用”门禁宣称审核页性能问题已经解决。后续门禁至少同时约束“审核主体可用”和“仓库正文视觉就绪”，并保存各仓库阶段的实际耗时。

### 9.6 针对已连接 GitLab 仓库的推荐修复方案

针对“已连接仓库在刷新时仍短暂显示‘仓库正文尚未加载’”的问题，推荐合并实施方案一与方案二的关键部分，不采用阻塞整页或直接隐藏错误的处理方式。

#### 状态修复

将仓库阅读状态明确拆分为：

```text
loading  → 正在读取，展示固定尺寸的目录和正文骨架
ready    → 仓库目录和正文可用
empty    → 仓库读取成功，但映射范围内没有正文
error    → 已确认未映射、未授权、连接失效或读取失败
```

页面刷新后，已确定 `handbookId` 时立即进入 `loading`。`loading` 期间不得显示“仓库正文尚未加载”、刷新按钮或任何暗示配置异常的信息；只有接口返回确定错误码后才进入 `error` 并显示对应处理入口。这样可以避免把正常网络等待误报为仓库异常。

#### 渲染修复

1. 审核标题、任务信息和操作区继续优先显示，不等待 GitLab；
2. 目录区和正文区从第一次出现开始保持与最终内容一致的宽度和最小高度，以骨架占位；
3. 仓库数据返回后，只替换目录、正文和提交来源区域，不重新执行审核页面整页渲染；
4. 局部替换保留当前滚动位置、已输入的审核意见和操作区状态；
5. `prefers-reduced-motion` 下关闭骨架动画，但仍保留稳定占位。

#### 请求链路修复

将仓库读取提取为独立的 `loadReviewRepositoryContext` 流程：

```text
审核任务/基线 ───────────────┐
                             ├─ 各自完成即局部交付
access-status + metadata ─并行┤
                       → tree → initial file → 正文视觉就绪
                                             └─ commits 后台补充
```

`access-status` 和仓库元数据在接口均独立执行鉴权的前提下并行请求；分支确定后读取目录，目录确定首个文件后读取正文。提交列表不属于正文首屏必要数据，移到正文显示后后台补充。中期再将这条链路收敛为审核仓库上下文聚合接口，减少浏览器往返，并通过 `Server-Timing` 暴露各阶段耗时。

#### 性能保证与门禁

外部 GitLab 的网络耗时无法由前端绝对保证，因此门禁分别约束“应用自身开销”和“端到端结果”，避免用隐藏提示伪造性能提升：

| 门禁项 | 要求 |
|---|---|
| 正常加载语义 | 已连接仓库加载期间不得出现“仓库正文尚未加载”“仓库未连接”或刷新按钮 |
| 审核静态框架 | 导航开始后 P95 不超过 80 ms，不等待 JavaScript、认证或业务接口 |
| 审核主体性能 | 当前 235 ms 中位数仅作为不合格基线；优化后审核主体可交互 P95 不超过 150 ms |
| 仓库请求启动 | `handbookId` 确定后 20 ms 内启动仓库上下文读取 |
| 前端渲染开销 | 最后一个正文必要响应结束后 50 ms 内完成目录和正文稳定渲染 |
| 仓库视觉就绪 | 在已连接且健康的验收 GitLab 环境中 P95 不超过 500 ms，硬回归上限 800 ms |
| 页面稳定性 | 仓库加载过程中阅读区不收缩、不整页重建，审核输入和滚动位置不丢失 |
| 请求约束 | commits 等非首屏请求不得阻塞正文；相同刷新过程不得重复读取相同 tree/file |
| 错误准确性 | 只有真实错误响应才能进入未连接、未授权、未映射或读取失败状态 |

测试必须使用已连接且可读的真实 GitLab 仓库，连续刷新至少五轮，并保存审核主体、access、metadata、tree、file、正文 DOM 稳定和后台请求完成的时间。另用未连接、无权限和映射为空三类场景验证错误状态，防止为了改善正常加载体验而吞掉真实故障。

该方案不引入正文持久缓存，不存在旧正文被误用于审核或发布的版本风险；若后续需要提交级快照，必须单独设计权限撤销和 `commitSha` 一致性规则。

#### 修改后

审核主体和仓库阅读区独立加载。仓库处于正常请求阶段时保留最终布局，只展示中性的内容骨架。该框架直接由 HTML 和审核页关键 CSS 提供，不等待完整应用模块加载：

```text
阶段 A：审核主体优先出现，仓库区域保持最终尺寸
┌─────────────────────────────────────────────────────────────┐
│ 手册 / 审核任务 / 审核操作                    仓库读取中 ··· │
├──────────────┬──────────────────────────────────────────────┤
│ ████████████ │ ████████████████████████████████████████     │
│ █████████    │ ███████████████████████████████              │
│ ██████████   │ █████████████████████████████████████        │
│              │ ███████████████████                          │
└──────────────┴──────────────────────────────────────────────┘
                              ↓ 仅替换目录、正文和提交来源
阶段 B：仓库内容稳定显示，外框和审核操作区不变化
┌─────────────────────────────────────────────────────────────┐
│ 手册 / 审核任务 / 审核操作                 提交 a1b2c3d4     │
```

加载态不提供“刷新阅读”按钮。只有请求明确失败后，原位置才切换为准确的错误状态，例如“GitLab 授权已失效”或“该手册尚未配置仓库映射”。

#### 耗时口径

下面区分已有实测和实施目标。当前 235 ms 的审核主体中位数判定为不合格基线，不作为优化后的可接受值。实施目标不是本轮实测结果，完成代码修改后必须在真实环境重新测量。

| 时间点/阶段 | 当前证据或问题 | 修复后的预期 |
|---|---:|---:|
| 审核静态框架 | 当前没有独立指标，需等待模块与认证后才出现 | 由 HTML 和关键 CSS 直接输出，P95 ≤ 80 ms |
| DOMContentLoaded | 五轮中位数 144 ms，是 235 ms 的主要组成部分 | 路由级 JS/CSS 拆分后 P95 ≤ 100 ms |
| 应用壳出现 | 五轮中位数 162 ms | 认证配置与会话并行，P95 ≤ 120 ms |
| 审核主体可交互 | 五轮中位数 235 ms；最终门禁单轮 267 ms，判定为不可接受 | 审核聚合接口与仓库上下文并行，P95 ≤ 150 ms |
| 仓库请求启动 | 当前在审核任务、手册和基线处理之后启动 | `handbookId` 确定后 20 ms 内启动 |
| access-status | 已实测通常 28～31 ms | 与 metadata 并行，不再单独占用一个串行往返 |
| metadata/tree/file | 当前缺少完整分段数据，不能给出实际值 | 全部分段记录；tree、file 只按真实依赖串行 |
| 响应后前端渲染 | 当前会触发审核视图整页 render，未单独计时 | 最后一个正文必要响应结束后 50 ms 内局部渲染完成 |
| 仓库正文视觉就绪 | 既有门禁未测量，是本问题的指标缺口 | 健康 GitLab 环境 P95 ≤ 500 ms，硬上限 800 ms |
| commits | 当前可能处在正文链路之后继续等待 | 正文显示后后台读取，不计入正文视觉就绪 |

要达到上述目标，不能只替换“仓库正文尚未加载”文案，必须同时实施以下性能改造：

1. **HTML 直出审核框架**：根据当前 URL 在静态 HTML 中立即展示不含业务数据的审核布局，避免等待 `app.js`、认证和接口后才出现主体；未认证时认证结果仍可覆盖该占位，不泄露业务数据。
2. **按路由拆分资源**：审核页面首屏不加载 dashboard、assets、outlines、templates、production、platform-admin、Mermaid、KaTeX 等非当前路由模块和样式；Lucide 图标初始化不阻塞审核主体。
3. **认证并行**：无 CAS ticket 的普通刷新中，`/auth/config` 与 `/auth/session` 并行读取，不再先 config 后 session；CAS 回调仍保留必要依赖顺序。
4. **审核启动聚合**：新增审核启动接口，一次返回当前任务、详情、手册和基线，消除前端 `tasks → detail → assets → baselines` 的串行往返。
5. **仓库上下文并行**：审核启动接口与仓库上下文接口同时发起；仓库服务端内部并行 access 和 metadata，只保留 `branch → tree → file` 的真实依赖。
6. **局部增量渲染**：审核主体、目录、正文和 commits 分为独立更新区域，禁止仓库返回后重建整个 `view-root`。

资源门禁同步增加：审核路由首屏不得加载其他业务页面视图模块；关键请求数和传输体积以实施前抓取结果建立基线，优化后关键 JS/CSS 传输体积至少下降 50%，首屏关键请求数至少下降 40%。

预期时间线如下：

```text
0 ms          ≤ 80 ms          ≤ 120 ms          ≤ 150 ms
刷新 ───────── 审核静态框架 ──── 认证与应用壳 ────── 审核主体可交互
  │                                                    │
  ├─ 路由关键资源加载                                  ├─ 仓库骨架保持原位
  ├─ auth/config + auth/session 并行                    ├─ tree → file
  ├─ 审核启动聚合 ─────────────────────────────────────┤
  └─ 仓库上下文 ─ access + metadata 并行 ──────────────┘
                                                       ↓
                                         最后响应后 ≤ 50 ms 局部显示正文

端到端门禁：健康 GitLab 环境下，刷新 → 仓库正文视觉就绪 P95 ≤ 500 ms
硬回归上限：800 ms；超过时门禁失败并输出具体慢阶段
```

用户感知上的变化不是“先看到错误、再看到正文”，而是“审核主体先可用、仓库区域稳定加载、正文原位出现”。若 GitLab 本身超过预算，界面仍保持稳定，同时测试报告能从分段耗时中明确指出慢在 access、metadata、tree、file 还是前端渲染。

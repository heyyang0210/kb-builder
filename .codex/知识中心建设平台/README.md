# YashanDB 知识中心建设平台工程档案

本目录是 YashanDB 知识中心建设平台从演示级文档生成工具升级为生产级知识中心的统一工程档案入口，用于承载需求、设计、开发任务、测试、验收、决策、风险、进度和复盘等中间产物。

文档命名统一采用“知识中心-模块名-具体功能特性-文档类型文档”格式；模块名使用平台、前端、认证、大纲管理等业务边界，文件名应能直接表达主题。

## 一、建设目标

- 支持单一企业内多个部门或项目知识空间。
- 支持多人按文档和章节并行生产，首期采用异步协作并为实时协同预留演进边界。
- 建立大纲、模板、来源、文档版本、权限、审核、发布、检索和持续治理闭环。
- 使需求、设计、实现、测试和验收相互追溯，避免把目标能力误写成已实现能力。

## 三、文档管理规则

1. 正文、文件名、状态、角色、决策、风险和验收结论使用中文；稳定编号、代码符号、模块标识和必要技术缩写可以保留，并在首次出现时说明中文含义。
2. 每个主题只能有一份可编辑正文。历史路径只保留索引或迁移说明，不复制正文。
3. 需求说明为什么做、为谁做、做什么和如何验收；概要设计说明系统边界和模块协作；详细设计说明接口、数据结构、状态、异常与伪代码。
4. 开发任务必须引用已批准需求和设计；测试报告必须引用真实实现与执行证据；验收报告不得用设计或计划代替运行结果。
5. 是否需要审批按 [人工审批原则](<./12-开发原则 & 术语/知识中心-平台-Approval Boundary v1人工审批边界-治理规范文档.md>) 判断；已批准的具体决策及风险记录在“07-决策与风险”。
6. 规则、提示词、阈值和审核策略应配置化并保留版本；不得在需求、任务或实现中散落不可追溯的硬编码结论。
7. 知识中心管理平台的设计正文统一位于本目录：概要设计进入 `02-概要设计`，接口、数据、构建、启动、迁移和模块实现设计进入 `03-详细设计`；跨模块开发原则与术语进入 `12-开发原则 & 术语`。根目录 `docs/` 已撤销；代码目录只保留使用入口与导航，不得保留第二份可编辑设计正文。本次迁移按用户要求保留专项文档独立正文，例外见详细设计索引。

## 四、文档状态

统一使用：`草拟中`、`评审中`、`已批准`、`实施中`、`已验证`、`已废止`。

状态表示文档自身生命周期，不表示相关功能已经上线。功能完成必须以测试和验收证据为准。

## 五、整理口径（2026-11-09）

- 以业务主题和文档职责确定入口：需求说明问题与验收，设计说明契约，任务说明实施，报告保留执行时点。README 标明当前依据、历史方案、效果稿或原始记录；不凭文件名推断已实施。
- 每个主题从 README 指向一份当前有效正文。历史选型、原始讨论和截图作为可追溯材料保留，必须指向现行依据；同一规则在多处出现时，以批准的需求、设计或决策记录为准。
- 先修失效索引和相对链接，再考虑重命名、迁移或合并。移动文件前须检查入链、更新所有引用并验证；未提交的用户文件、编辑器侧文件及备份文件先核对来源和用途，不直接删除。
- 运行截图、测试数据和构建结果归 `runtime`；知识资源归 `knowledge`；外部资料归 `external`。本目录只保留需要长期解释需求、设计、决策或验收的材料。

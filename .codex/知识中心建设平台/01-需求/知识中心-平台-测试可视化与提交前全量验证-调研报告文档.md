# 平台测试可视化与提交前全量验证调研报告

> 版本：调研稿 1.1；日期：2026-10-15；范围：主仓库平台测试，不包含独立维护的 `external/`。本文件提出页面需求、方案与验收口径，尚未实施页面、CI、提交钩子或新增服务。

## 1. 目标与关键口径

**核心交付是一个项目成员能从 GitLab 进入的测试质量页面**：快速回答最近一次是否通过、哪个模块失败、具体哪些用例失败、覆盖率覆盖什么代码、相较上次有什么变化。首选由 GitLab Pages 承载自建只读页面，GitLab 原生流水线测试报告保留为逐次执行证据和合并门禁。每次提交前运行全量用例并生成可追溯报告。这里的“提交前”指本地 `git commit` 之前；GitLab 流水线发生在推送之后，是合并前的第二道门禁。

建议定义以下验收需求：

| 编号 | 需求 | 验收口径 |
|---|---|---|
| TEST-VIS-01 | 全量测试门禁 | 执行统一 `full` 而非 `smoke`；失败、超时、启动失败、覆盖率采集失败均为非零退出，保存报告后阻止本地提交；GitLab 另阻止失败流水线合并 |
| TEST-VIS-02 | 用例结果 | 以用例为最小粒度展示名称、模块、分类、状态、耗时、失败信息、重试与跳过原因；不能将任务成功数当作通过用例数 |
| TEST-VIS-03 | 覆盖率 | 显示语言、源码范围、指标、采集时间和未纳入范围；未采集显示“无数据”，不记为 0% 或全仓覆盖率 |
| TEST-VIS-04 | 功能模块视图 | 按稳定模块 ID 聚合用例和状态，展示模块内未发现用例及未映射用例，支持查看原始报告 |
| TEST-VIS-05 | 历史与追溯 | 每次运行关联 commit SHA、分支、运行时间、环境、工具版本和报告位置；保留失败日志、必要的浏览器 trace/截图 |
| TEST-VIS-06 | 报告可携带 | 同次运行输出人读摘要、JUnit XML 用例结果、覆盖率文件和机器可读元数据；报告在失败时也要产出 |
| TEST-VIS-07 | 可访问的测试页面 | GitLab 项目或流水线提供页面入口；仅项目成员可访问页面及日志附件；页面只读，重跑在 GitLab 流水线操作 |
| TEST-VIS-08 | 快速筛选与定位 | 关键词、模块、状态、分类、分支、时间可组合筛选；支持“仅看失败”“最近一次”、清空、排序、分页；URL 可分享且浏览返回时保持筛选上下文 |
| TEST-VIS-09 | 历史与对比 | 按分支查看运行与覆盖率趋势，比较两次提交的新增失败和已修复用例；展示报告来源和下载入口 |

## 2. 仓库现状与差距

现有 `tests/run_tests.py` 自动发现 Jest、Node 原生/独立脚本、Python unittest/pytest/独立脚本与 Playwright；`python3 tests/run_tests.py full` 按 gate、unit、contract、integration、system、e2e 执行。`full` 在 `runtime/test-reports/<日期>/<运行 ID>/` 保存 `report.md`、`details/report.json`、任务日志与浏览器证据，已有用例统计和退出码。`full --coverage` 另产出 Jest 的 `coverage-summary.json`、LCOV 和 HTML。现有覆盖率**仅覆盖 Jest 管理的 JavaScript 代码**，明确不包含 Python、独立 Node 脚本及 Playwright；`--report` 兼容导出的 JSON 也不是 JUnit XML。

目前未发现根目录 `.gitlab-ci.yml`；Playwright 配置的 reporter 为 `list`。现有报告适合阅读，但尚不能直接作为 GitLab 测试用例视图的 JUnit 产物；模块映射也未形成统一元数据。仓库已有 `npm run verify:full`，其末尾运行的是 `smoke`，**不能**用这个名字代替用户要求的全量用例。E2E 会准备隔离 `test_hy` Schema，涉及数据库结构/数据刷新和独立服务；本地与 GitLab Runner 均须具备相同隔离条件、浏览器及依赖，否则应明确失败或按既定跳过规则展示，不能标记为全量通过。

## 3. 共同建设前提

1. 保留 `tests/run_tests.py` 为唯一调度入口；增加标准格式导出适配层。Jest、Python、Playwright 应各自产生 JUnit XML，并在统一入口汇总；独立脚本无法提供真实用例粒度时先按任务记录，并显式标记粒度不足，后续逐步补结构化结果。任务日志/现有 JSON 继续保存。
2. 建立版本化的“测试文件或用例标签 → 功能模块 ID”清单，优先使用稳定模块名，如认证与权限、大纲管理、文档生产、审核发布、集成管理、平台基础。未知项归入“未映射”，禁止凭目录名猜测业务归属；一个跨模块用例可关联多个模块，但总量统计需去重。
3. 覆盖率分语言与采集器展示：当前 Jest 使用 LCOV/HTML；未来若引入 Python coverage、Node 原生覆盖率或浏览器 E2E 覆盖率，分别验证源码映射、排除项与分母后再展示。GitLab 的覆盖率汇总百分比与源码行着色需要分别配置；不能仅凭 `report.json` 中的数字自动得到行覆盖视图。
4. 报告生成须在测试失败时继续完成；归档和上传失败要单独记录，不得误报测试成功。报告文件应排除凭据、个人信息和业务数据，并定义访问权限与保留期。可复用 `runtime/` 放置本地产物，CI 上传只包含必要文件。
5. 全量门禁的本地方案为版本化安装脚本配置 Git `pre-commit` hook，运行 `python3 tests/run_tests.py full --coverage` 并保存报告；与其它 Git 工作树、未暂存变更和运行中代码修改的关系需在实施时固定。钩子可被跳过且依赖开发机，因此 GitLab 还需受保护分支、必须成功的流水线与合并设置。推送后流水线满足“合并前”，不满足字面“本地每次提交前”。

## 4. 四种调研方案

| 方案 | 部署与看板 | 成功/失败及模块 | 覆盖率 | 提交与合并门禁 | 主要代价 |
|---|---|---|---|---|---|
| A. GitLab 原生 CI 报告（推荐首期） | 复用现有 GitLab，MR 流水线及 artifact 页面 | JUnit 用例报告；模块通过 suite/classname 或测试名称映射，复杂模块面板需自制静态 HTML | CI 摘要可解析百分比；Cobertura XML 用于 MR 源码行视图，需从 LCOV 转换并校验路径 | 本地 hook + CI 全量 job + 必须成功的流水线 | 低至中；Runner 必须能运行隔离 E2E，原生跨模块历史看板较弱 |
| B. Allure Report 本地静态站点 | 本地生成 HTML，放内网静态服务；报告链接可挂 GitLab artifact | suites、标签、趋势、失败附件；模块用标签映射 | 可附带覆盖率 HTML/指标，Allure 不自动计算跨语言源码覆盖 | 同一 hook + 可选 GitLab CI，发布报告仅在测试结束后 | 中；需适配多框架结果及历史目录，注意静态站点权限 |
| C. ReportPortal 自托管 | 内网服务、数据库/存储和 Agent/上传器 | 运行历史、模块过滤、失败分析、重试趋势 | 通常仍需外部覆盖率工具及自定义链接/指标，不把它当原生行覆盖工具 | 同一 hook + CI，上传失败与测试失败分离 | 高；持续运维、容量、安全与凭据管理 |
| D. SonarQube 自托管 + GitLab | 内网质量分析服务；GitLab 展示 CI 用例 | GitLab JUnit 负责测试明细，SonarQube 按项目/代码视图看质量；功能模块需额外映射报表 | 导入 JS LCOV、未来 Python 覆盖率报告；展示项目/源码覆盖与趋势 | 同一 hook + GitLab 全量 job，质量门禁按协商阈值启用 | 中高；双系统维护，SonarQube 单独使用不能满足用例看板 |

### A. GitLab 原生 CI 报告

在本地或内网 GitLab Runner 上执行统一入口；使用 `artifacts:reports:junit` 上传汇总的 JUnit XML，使用 `artifacts:reports:coverage_report` 上传 Cobertura XML（JavaScript LCOV 需要适配转换），并把完整 Markdown/HTML/日志作为普通 artifact。失败时仍上传报告。GitLab MR 提供测试结果差异、覆盖率摘要和行视图；如需要模块总览，可由模块清单与 JUnit 产出简易静态 HTML 并作为 artifact 浏览。没有 JUnit 适配之前，只能提供现有 JSON/Markdown，不能宣称 GitLab 原生逐用例视图已就绪。

适合：已在 GitLab 管理代码、希望最少增加服务。缺口：GitLab 对跨运行历史、跨语言功能模块趋势的呈现有限；Runner 必须具有受控 `test_hy` 环境并防止并发写入。

### B. Allure Report 本地可视化

为各框架生成 Allure 结果或经验证的适配产物，以模块、测试层级和浏览器建立标签，静态 HTML 按运行 ID 存档；GitLab CI 可附 artifact 链接。失败截图/trace 作为附件；LCOV/HTML 通过外部链接呈现。不要把附件中的覆盖率百分比当作 Allure 自己采集的覆盖率。

适合：重视可读的本地测试报表、暂不希望新增长期在线服务。缺口：多框架和独立脚本适配工作量；趋势依赖保留历史结果，安全地清理和访问附件需要规则。

### C. ReportPortal 自托管分析

在内网单独部署服务，统一入口在报告落盘后异步上传运行和用例事件；按模块、分类、分支过滤，观察失败热点与历史。原始报告仍保留在 `runtime/` 或 GitLab artifact，作为上传中断时的事实源。覆盖率由现有 Jest/后续语言采集器提供，ReportPortal 仅关联其链接或指标。

适合：多团队、高频运行、需要集中诊断。缺口：较高的运维、权限与存储成本；不建议为当前单仓库第一阶段单独引入。

### D. SonarQube 与 GitLab 组合

在 GitLab 运行 `full` 后，上传 JUnit 到 GitLab，同时将经过路径校验的 LCOV 等覆盖率数据交给 SonarQube，查看文件覆盖、质量趋势和按新代码的质量门禁。功能模块用例仍需 GitLab/自定义模块报告提供。当前可只分析 Jest 范围，随后分阶段扩大语言覆盖范围。

适合：同时需要测试可视化和源码质量分析。缺口：两套系统间的身份、项目映射和权限运维；质量阈值是新的治理决定，调研阶段不预设强制百分比。

## 5. 推荐实施顺序与验证

**建议先选 A，必要时追加 B。** A 最大限度复用已有 `full` 与 GitLab，先解决标准产物和可信门禁；如果实际使用者需要更强的本地用例分析，再增加 Allure 静态报表。C 适合运行规模上来后重新评估；D 在明确代码质量分析需求时选用。四方案可组合，但不要同时建立多个互相矛盾的“通过”口径。

1. 基线：在隔离环境记录一次 `full --coverage` 的任务数、真实用例数、耗时、失败、跳过和报告路径；修正现有失败基线，不通过配置把失败转成通过。
2. 报告契约：定义 JUnit XML、覆盖率格式、模块映射和运行元数据；覆盖多框架及独立脚本，失败时验证文件仍可读取。
3. 本地门禁：提供显式安装/卸载的 hook；每次提交前执行全量，失败阻断并输出报告位置；确认钩子执行的工作树与待提交内容一致。
4. GitLab 门禁：隔离 Runner 执行同一命令，保留报告 artifact，上传 JUnit 和 Cobertura；保护目标分支，要求 MR 流水线成功后合并。运行队列串行控制共享测试 Schema。
5. 验收演练：人工制造通过、断言失败、超时、未发现用例、缺少环境、跳过、覆盖率采集失败、上传失败等情形；核对本地阻断、MR 状态、各模块统计、覆盖率范围及报告可追溯性。

本次仅做调研，不声称完成上述演练。引入 Allure/ReportPortal/SonarQube、GitLab 凭据或新网络出口，以及启用质量阈值/分支保护，均应在选定方案和具体实施范围确定后按仓库审批边界评估。

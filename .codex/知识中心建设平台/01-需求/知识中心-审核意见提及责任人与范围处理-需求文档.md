## 这件事要解决什么

审核人读文档时，可能发现“这篇文章写错了手册”“漏了一篇文档”或“这项内容不属于本次任务”。现在，审核人虽然能写意见，但相关负责人不一定收到通知，也缺少一条从意见走到范围决定、重新分析和继续编写的完整路径。

目标是让一条范围意见有明确的去向和结局：**有人看到、有人决定、决定有理由、改动有预览，原意见可以回看**。普通文字意见、人员提及、范围决定和逐篇审核结论是四件事，不能互相代替。

举例：审核人发现“备份恢复”文档应属于另一手册，选中文字后提出“范围可能有误”，提及手册负责人。负责人从通知进入该意见，查看关联工单和文档。若确认属实，先查看将影响哪些文档、草稿、审核和 MR，再由有权负责人确认调整；平台重新分析受影响范围，并把文档送回正确的编写或审核环节。若不属实，负责人写明理由并结束这条范围意见。其他未受影响文档照常推进。

## 用户看到的完整过程

```mermaid
flowchart LR
  A[审核人提出范围意见] --> B[选择要提及的责任角色]
  B --> C[平台核对身份并发送通知]
  C --> D[责任人打开原意见和任务]
  D --> E{范围负责人决定}
  E -->|不采纳| F[写明理由，结束意见]
  E -->|采纳| G[查看调整影响]
  G --> H[确认调整范围]
  H --> I[重新分析受影响文档]
  I --> J[返回编写或审核]
```

| 用户 | 他要做什么 | 页面上应看到什么 |
|---|---|---|
| 审核人 | 选中问题位置，提出范围意见；必要时提及相关人 | 原文定位、问题类型、可提及对象、实际接收人、意见与通知的独立结果 |
| 被提及人 | 从通知进入原意见，回复或提供事实 | 正确的候选版本、关联工单及文档、当前范围；无权时不泄露正文 |
| 工单责任人 | 决定手册层面的增减改 | 当前范围、拟调整范围、受影响工作和确认入口 |
| 手册负责人 | 决定本手册文档层面的增减改 | 本手册的文档、负责人、草稿、审核及交付影响 |
| 文档负责人 | 按生效范围重新编写或修订 | 保留旧稿和意见，明确下一步及新审核入口 |

“知识中心负责人”是可提及的协调对象，不因为被提及就获得跨手册修改权限。审核人仍独立作逐篇审核结论。

## 已确认的业务规则

1. 可提及三类对象：**当前手册负责人、文档首次责任人、知识中心负责人**。文档首次责任人是该文档首次正式确认分派时的人；后续改派也不改写这项历史身份。知识中心负责人由平台管理配置为一名有效人员。选择角色后，服务端按稳定人员 ID 解析，不凭评论中的姓名猜人。
2. 提及对象应在当前审核任务与有效范围内可选；同名手册用稳定 ID 和业务版本区分。提交前展示实际接收人。负责人不存在、停用、发生改派或配置变化时，要求重新核对；不得悄悄通知别人。相同人员被多个角色命中时，同一意见只产生一条面向该人的通知。
3. 范围意见由**对应层级的范围负责人**决定：手册增减改由工单责任人决定；手册内文档增减改由该手册负责人决定。被提及人可以回复，但不能单凭提及取得决定权。管理员代办遵守现有资源权限并留下实际操作者。
4. “采纳”先形成拟调整范围及影响预览；有权人员确认后才改变当前范围并重新分析。未明确受影响文档时先核实，不阻断所有文档；明确文档后只阻断受影响项。打开的 MR、已合并内容、过期候选和版本冲突仍遵守现有范围纠偏门禁，不自动合并、关闭或回滚远端 MR。
5. “不采纳”必须记录理由、决定人和时间；仅结束对应范围意见，不改写任务范围，也不自动批准整篇文档。意见可在有新证据时重新打开，并留下历史。
6. 审核意见保存、通知入箱、外部渠道受理、用户已读是不同事实。通知失败不回滚已保存意见；页面不能把“待配置”显示成“已送达”。通知深链打开时重新校验权限和版本。
7. 意见、决定、范围前后版本、影响预览、重新分析结果和审核候选都应可追溯；重试不能重复创建决定或通知。

## 应如何分阶段落地

**第一阶段：先让责任与决定可追溯。**在现有审核与任务接口上增加结构化范围意见、三类人员解析、采纳或不采纳记录，并把采纳决定连接到已有范围预览/确认流程。先以真实后端 API 和隔离通知适配器验证，不使用模型自动修改范围。

**第二阶段：让人真正收到。**本需求仅实现站内通知，显示“已入箱/已读”；不接企业微信和企业邮箱。工作台和意见页可链接到同一通知与原意见，不重复计算待办。

**第三阶段：用 AI 帮忙找问题。**模型可建议问题类型、可能受影响的手册/文档及处理理由，并给出引用依据。人确认后仍调用第一阶段的权限与范围接口；模型不得自行指派人员、采纳意见或改变范围。先用已决历史意见的脱敏样本测误报、漏报和人工接受率，再决定是否默认展示建议。

详见[三种方案比较及官方依据](../11-参考资料/知识中心-审核意见责任人与范围处理-业界方案调研-20261112.md)。

## 验收时看什么

- 用三类提及对象各走一遍：提及后本人收件箱出现一条通知，打开的是原意见和正确文档版本；同人多角色去重，同名、改派、空缺、停用和无权场景没有误通知。
- 测试“不采纳”：理由和操作者可回读，范围不变，意见结束，逐篇审核结论不被自动改变。
- 测试“采纳”：未确认预览前范围不变；确认后仅受影响文档重新分析和流转，未受影响文档保留有效证据。
- 测试异常：重复提交、并发改派、版本变化、通知超时、已打开/已合并 MR、撤出和重新纳入，均能看到真实结果并安全恢复。
- 真实 API 与浏览器分别记录结果。页面打开与首个可交互反馈按仓库 **100 ms** 目标测量；收件箱查询不得阻塞审核页面打开。未达到时记录实测条件和耗时，不能以设计目标代替成绩。

## 本轮实施补充（2026-11-12）

- 收件箱采用审核聚合内的通知事件投影：意见和通知在同一审核存储事务内创建，列表/已读操作只允许当前登录人访问。通知链接由服务端生成并重新校验源审核和评论权限。
- 结构化范围意见需记录层级、意见状态和决定记录。手册增减由工单责任人决定，手册内文档增减由手册负责人决定；不采纳必须给理由。采纳先创建关联的范围纠偏事项，范围责任人再预览并确认；确认后重算任务范围和待办，文档负责人重新编写，平台不自动生成正文。
- 知识中心负责人由平台管理配置一名有效且启用的人员。首次责任人按文档首次正式确认分派时固化；历史数据缺少可信分派证据时不猜测，提交时明确提示该角色暂不可提及。

## 与写作规范的关系

[资料开发规范](../11-参考资料/资料开发规范.md)、[中英对照表](../11-参考资料/中英对照表.md)和专业术语约束，适用于生成及审核文档的内容质量；它们不定义“谁被通知、谁决定范围”的权限。若希望自动检查这些规范，应另立内容质量需求，不能把它们混入编号 25 的完成判定。

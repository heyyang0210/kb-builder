# 知识中心平台需求列表

> 文档类型：平台级产品需求台账｜状态：待评审｜整理日期：2026-10-21
> 范围：单企业、多部门、多知识空间；覆盖 P0、P1 及有依据的 P2，突出增量构建 MVP。
> 事实截止：产品需求以 2026-09-23 总体需求及 2026-09-22 增量 MVP 为主；实施证据以第 42 周进展报告（截至 2026-10-18）为准。此日期之后的代码变化未在本台账逐项验收。

## 1. 如何使用这份列表

好的需求列表回答“谁在什么场景下获得什么结果、边界在哪里、怎样验收、依据何在”，并把**需求确认状态、建设优先级、实施验证状态**分开。差的列表只堆菜单或技术名词，缺少角色、失败路径和验收条件；把 P0 写成已上线，把调研建议写成已批准，或拿旧测试结果证明当前工作区已交付。

构建方法：从用户角色与知识生命周期识别任务，沿“场景→结果→业务规则→可观察验收”拆成可独立判断的条目；用 MVP 纵向闭环校验遗漏；按价值、依赖和风险划分 P0/P1/P2；将来源、决策、实施证据与未决问题逐条关联。变更时保留编号，更新状态、依据和影响，不复用已删除编号。

状态口径：**已确认**指来源明确的产品基线，不表示完成；**待确认**指已有需求方向但关键规则未决；**建议**指调研或演进提议。实施状态仅使用“隔离验证部分能力／专项证据不足／未知／待专项验收”，不得按优先级推断上线。表中“未知”表示缺少同一当前候选、相同业务范围的验证证据，并非断言尚未开发。

来源简称：[总需](./知识中心-平台-总体需求-需求文档.md)；[增量 MVP](./增量文档构建MVP需求.md)；[团队决策](../07-决策与风险/知识中心-平台-团队小组与领域分工-决策记录文档.md)；[业务边界决策](../07-决策与风险/知识中心-权限与增量构建-业务边界-决策记录文档.md)；[第 42 周进展](../08-进度与报告/知识中心-平台-2026年第42周项目进展-进展报告文档.md)。下表中“隔离验证部分能力”均仅指该进展报告记录的特定步骤，不代表本条完整验收。

## 2. 产品目标、角色与闭环

目标：使分散的大纲、模板、来源、文档和关系进入统一授权目录；让多人在明确责任、来源与版本的前提下生产文档，经质量检查、审核和人工发布形成可追溯的知识；再用检索、反馈与运营触发下一轮修订。[总需](./知识中心-平台-总体需求-需求文档.md#3-产品目标与非目标)

角色：平台／空间管理员管理组织、授权和策略；手册／知识负责人管理大纲、责任和生产；作者编辑并确认来源；审核人判断候选；发布人使版本生效；读者按权限消费与反馈；运营、审计人员分别处理保鲜与追溯。一人可兼多角色，自审不能单独通过本人候选。[总需](./知识中心-平台-总体需求-需求文档.md#4-用户角色与责任边界)

生命周期：**空间与资产 → 大纲／模板 → 来源快照 → 任务／草稿 → 质量与差异 → 冻结候选 → 审核 → 不可变发布 → 授权消费／反馈 → 修订或退役**。来源、草稿和正式知识是不同事实；审核通过不等于自动发布。

增量 MVP 的用户终点是知识中心内**原子发布一批可追溯的不可变新文档版本**。同一真实手册以发布基线启动，人工选择 PingCode 或 Markdown 来源并固化快照，确认目标范围与生成方案，生成可比较草稿，人工确认差异，按文档审核，全部通过后整批发布；退回产生新修订，失败不产生半批正式版本。GitLab 提交、MR、外部仓库交付不属于该 MVP 完成条件。完整验收还需 YashanDB 主写、自审、越权、基线漂移、并发重试、退回重提和失败恢复证据。[增量 MVP](./增量文档构建MVP需求.md#一一句话产品承诺)

# 写作 Agent 能力迁移与逆向工程范围

> 版本：0.1；日期：2026-10-23；状态：调研建议，待评审。关联：[行业调研与候选清单](./知识中心-文档生产-写作Agent行业调研与候选清单-调研报告文档.md)。本文件定义业务行为及验收，不冻结接口/数据结构，不扩充已批准的实施承诺。

## 1. 目标、角色和承接位置

服务知识中心技术文档作者、领域专家、审核人和管理员。目标是让作者基于获准资料形成覆盖完整、事实可核验、便于审阅的单篇文档，并能在资料更新时定位受影响内容。范围承接现有文档生产、来源管理、质量检查、审核发布与增量维护；首先覆盖YashanDB功能说明、操作指南、故障案例。

业务成功以“需要的信息是否齐全、关键事实是否有依据、代码是否真实验证、采用是否可追溯”衡量。字数、Star、模型自评、Agent数量不作为质量完成标准。本文P0/P1仅指建议优先级，不表示已安排开发。

现有目标基线是AI文产-01～16；选区上下文、资料选择、候选对照、可读来源、流程衔接与恢复继续复用IMA-01～11。当前已有五类写作操作、来源快照、Skill、候选采用、元信息、YashanDB检查入口，不重复立项。

## 3. 推荐业务流程与失败处理

作者在现有文档工作台选择操作与范围 → 补齐单篇简报 → 从获准资料中选择并确认来源 → 查看问题清单与证据大纲 → 确认计划 → 生成候选 → 核验事实/引用/术语并执行必要的YashanDB用例 → 比较改动、处理未通过项 → 人工采用保存 → 现有审核发布流程。

来源不足时产出缺口与补资料建议；来源冲突时列出各自版本和原文，不默认以更新网页覆盖正式数据库文档。研究失败/预算耗尽保留可恢复状态。质量不通过时允许作者查看和修订候选，是否可保存草稿及能否送审按既有门禁，不引入隐含自动发布。

三个核心场景：

1. 新功能说明：给定功能设计、测试报告、目标版本和模板，先列章节/证据缺口；只在已确认来源范围内生成。
2. 旧文润色：选中文段，保留SQL、参数、数字、版本与原文范围；作者逐项检查变化后采用，质量报告绑定采用版本。
3. 版本更新：目标版本默认值变化，列出旧来源、受影响事实和建议改动；未受影响内容保留，SQL用例按目标版本复验。

商业产品登录后功能、实际接口、付费能力和性能目前未知。无关账号、私有资料、付费采购、外部权限变更都不由本研究自动执行。源码许可证需在实际复用代码/依赖时核验；GPL项目建议先借鉴可观察业务交互，不直接复制其实现。

## 5. 业务验收样本与分期

建议先构建12个小样本，每类2例：按证据生成、技术保真润色、版本局部更新、误引/冲突、资料/权限不足、取消/协作冲突。样本包含公开或已授权的中文资料、YashanDB版本、模板、目标事实、预期SQL结果与审核意见。12例是首轮基准建议，不代表足够覆盖全部生产场景。

最低质量标准：基准中关键参数/版本/SQL错误不能被标为通过；每个关键事实可定位依据或明确待核验；越权来源零使用；采用前后受保护内容一致；未通过或未执行明确区分；采用与核验均有版本。耗时、Token、费用和采用比例先采集基线，再讨论优化目标。不得以大模型自审代替领域审核或真实数据库用例。

建议第一期集中写作借鉴-01/03/04/05/07/08/11，先复用现有工作台和质量服务，完成单篇最小闭环；第二期补视角研究、规范配置、阶段恢复与评估；来源变更影响分析先复查现有增量能力再安排。多文档整册自动生产、无人审核发布、营销SEO、小说创作引擎不进入本轮范围。

业务评审需确认：哪些事实属于送审阻断项、哪些场景必须先确认大纲、人工确认如何记录、撤权历史快照沿用哪条既有治理规则、首批文档类型/版本。后续实现前将这些决策同步到概要/详细设计，规则和提示词使用配置/knowledge资源。

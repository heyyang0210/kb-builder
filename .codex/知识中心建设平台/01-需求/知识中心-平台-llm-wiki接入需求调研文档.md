# 知识中心平台 llm-wiki 接入需求调研文档

## 1. 文档定位

- **状态**：草拟中
- **调研对象**：`nashsu/llm_wiki`（GitHub 开源项目）
- **调研日期**：2026-09-07
- **目标**：判断现有资料清洗能力是否应复用 `llm-wiki`，并定义可回退、可验收的接入需求。
- **结论先行**：不把 `llm-wiki` 整体当作资料清洗模块，也不允许其直接写入正式知识；仅在隔离边界内复用其“增量知识综合、来源追踪、关系发现”能力，作为清洗之后的候选处理层。是否产品化，必须由专题 PoC 的证据决定。
- **评审意见解释**：本文将“目标模式”解释为“按 llm-wiki 的持久化 Wiki、图谱、向量检索和对话形态直接建设并接入平台”。该模式不适合作为首期交付；适合先以受控适配器验证局部能力，再决定是否产品化。

外部依据：

- [llm_wiki GitHub 仓库](https://github.com/nashsu/llm_wiki)
- [llm_wiki README](https://github.com/nashsu/llm_wiki/blob/main/README.md)
- [llm_wiki GPL-3.0 许可证](https://github.com/nashsu/llm_wiki/blob/main/LICENSE)

## 2. 第一性原理：先定义必须成立的事实

### 2.1 知识中心真正交付什么

知识中心交付的不是 Markdown 文件或一个聊天界面，而是：

> 在明确的产品、YashanDB 版本、权限和来源范围内，经核验、可审计、可回退的可信知识。

由此得到五个不可破坏的不变量：

1. **来源可追溯**：每个知识结论都能回到原始资料、版本、文档和位置。
2. **清洗不改变事实**：格式规范化可以改变表现，不能无证据改写事实。
3. **版本不混淆**：不同产品版本、模块和适用条件不能被模型合并成一个结论。
4. **候选不等于事实**：模型生成、图谱推断和相似度命中只能进入候选状态。
5. **正式知识唯一**：只能由知识中心的审核和发布基线产生正式事实，不能形成双事实源。

任何外部组件接入都必须服从上述不变量；不能以“能力更强”要求平台绕过版本、审核、权限和审计边界。

### 2.2 两个能力的本质差异

现有资料清洗模块的最小目标是**无损结构化**：扫描来源、转换格式、清理噪声、识别章节和代码块、生成稳定处理单元，并保留来源位置、哈希和质量状态。

`llm-wiki` 的核心目标是**有状态的知识综合**：对多个来源进行增量摄入，生成持久化 Wiki Markdown，维护来源数组、页面链接、图谱、向量检索和对话入口。

因此二者不是替代关系：

```text
原始资料 → 现有清洗（无损、可追溯）
        → llm-wiki 类能力（候选综合、关系发现）
        → 知识中心审核/版本治理/发布（唯一事实源）
        → MCP、检索和阅读
```

把生成结果称为“清洗结果”会产生因果错误：模型可能重写、合并或补充原文没有直接表达的内容，这些内容必须经过证据核验。

## 3. 按马斯克思维方式拆解问题

这里的“马斯克视角”不是追逐某个热门组件，而是采用其公开的工程方法：从物理约束出发、删除不必要步骤、降低单位成本、建立快速迭代和明确停止条件。

### 3.1 先问五个问题

1. **需求的物理事实是什么？** YashanDB 资料分散、重复、跨版本，人工难以发现参数、错误码、数据类型和运维命令之间的关系。
2. **当前步骤为什么存在？** 清洗是为了得到可比较、可定位、可复用的证据；审核是为了把候选变成可承担责任的事实。
3. **能否删除步骤？** 不能删除来源核验、版本隔离和人工发布门禁；可以删除重复的二次解析、重复索引和无收益的前端展示。
4. **能否简化或加速？** 用哈希增量、缓存和受控处理单元只处理变化资料，不重新加工整库。
5. **怎样证明十倍收益？** 不以“生成页面数量”衡量，而以审核时间、来源覆盖率、版本混淆率和重复知识率衡量。

### 3.2 价值假设与反例

| 假设 | 可验证收益 | 失败反例 |
|---|---|---|
| 关系发现能找到跨文档关联 | 参数—错误码—命令关联覆盖率提高 | 只生成漂亮链接，无法回到证据 |
| 增量 Wiki 能减少重复加工 | 资料小改动时处理单元和模型调用显著减少 | 哈希粒度过粗导致旧结论未失效 |
| 多来源综合能减少人工检索 | 审核者定位证据耗时降低 | 版本混合导致审核返工增加 |
| 持久化页面便于知识沉淀 | 候选知识可持续更新 | 形成独立 Wiki 事实源，与平台发布结果分叉 |

只有收益大于新增核验成本时，接入才成立。

## 4. 现状与问题定义

### 4.1 现有能力

当前资料加工链路已具备：

- PingCode、Office、PDF、GitLab 等来源接入与资源登记；
- 原始文件、规范化文件、素材和来源哈希的追踪；
- 标题清洗、结构优先处理单元、分块、质量问题和可降级执行；
- embedding/聚类、关键词和知识点候选生成；
- Prompt/Skill 注册、模型调用审计、候选版本、人工审核和发布基线；
- MCP 检索和知识中心阅读能力。

这些能力已经覆盖“证据进入系统”和“正式知识发布”的主闭环。

### 4.2 尚未充分解决的问题

- 同一参数、错误码或数据类型分散在多份手册和版本文档中，关系发现成本高；
- 资料小幅变化时，难以只重算受影响的综合结果；
- 现有处理产物能定位处理单元，但跨文档知识页面和关系候选仍需人工拼接；
- 知识缺口、冲突和孤立概念缺少统一的候选发现机制。

这些是“知识综合层”的问题，不是基础清洗失败。

## 5. 接入目标与非目标

### 5.1 目标

1. 在不改变现有清洗、审核和发布事实源的前提下，生成可追溯的候选 Wiki 页面和关系候选。
2. 支持按文档哈希和处理单元增量重算，避免全量模型调用。
3. 让每条候选内容携带来源、版本、原文位置、生成运行和模型/规则版本。
4. 识别 YashanDB 专题之间的关系和缺口，为审核者提供可操作的审核入口。
5. 通过最小 PoC 证明是否降低人工成本，而不是先引入完整桌面应用或新事实库。

### 5.2 非目标

- 不替代现有资料清洗、分块、质量门禁和来源登记；
- 不直接写正式文档、发布基线、权限或审计事实；
- 不执行 SQL、运维命令或连接生产数据库；
- 不作 YashanDB 版本兼容、安全或正确性结论；
- 不在前端增加无明确收益的图谱、规则命中列表或分析卡片；
- 不把 `llm-wiki` 的桌面端 UI、向量库或 MCP 作为平台必选运行时；
- 首期不新增后端公开 API，先通过内部适配器和离线运行产物验证价值。

## 6. 推荐接入形态

### 6.1 组件定位

采用“受控适配器 + 候选工作区”而非整体嵌入：

```text
知识中心资料批次
  → 清洗完成且通过质量门禁的 processing snapshot
  → LlmWikiAdapter（隔离进程/容器）
  → Wiki 草稿、关系候选、缺口报告
  → 候选知识导入器
  → 现有审核与发布链路
```

适配器可以借鉴 `llm-wiki` 的分析—生成两阶段、来源追踪、增量哈希和页面链接，但不复制其事实存储和产品 UI。任何回流结果均保存为不可发布的候选产物。

### 6.2 存储复用与新增规则（强制）

存储决策按“先复用、后新增；新增必须证明不可替代价值”执行：

| 能力 | 首选复用的现有运行产物 | 允许新增的条件 | 禁止情形 |
|---|---|---|---|
| 文档/页面内容 | `processing snapshot`、`documents/chunks/structure-blocks`、候选版本产物 | 现有产物无法表达 Wiki 草稿的版本或来源关系，且新增格式可回溯 | 建立一份独立正式 Markdown 库 |
| 向量检索 | 现有 embedding 索引和检索服务 | 经过基准测试证明现有索引无法满足跨文档关系召回，且可从 `snapshotId/inputHash` 重建 | 为 llm-wiki 默认部署而重复建库 |
| 图关系 | 现有图谱/数据集产物（如 `knowledge-point`、`keyword/entity`、`processing-unit` 节点） | 现有图模型无法表达候选关系类型，且新增图数据可标记为 candidate 并可删除重建 | 将外部图数据库作为第二事实源 |
| Wiki 增量状态 | 现有运行记录、哈希、缓存和候选版本 | 现有状态无法支持页面级增量，新增状态必须由平台拥有并审计 | 让桌面端本地文件成为唯一状态 |

若确需新增向量数据库或图数据库，需求中必须单独列出：新增对象、服务边界、数据来源、同步触发、权限模型、容量/成本、备份恢复、删除重建、故障降级和与正式基线的隔离方式；未完成评审不得进入 P0 实施。新增库只存候选投影，不得承载 `published` 事实。

### 6.3 输入契约（需求级）

每个输入批次必须包含：

- `batchId`、`snapshotId`、`inputHash`；
- `sourceResourceId`、来源类型、文档标识和原文位置；
- 产品、YashanDB 版本、模块和适用范围；
- 已通过清洗质量门禁的 `processingUnits`；
- 当前权限范围和禁止外发标记；
- 清洗规则、领域规则、Prompt/Skill 和模型指纹版本。

未通过质量门禁、缺失版本范围或无法回溯来源的内容不得进入综合层。

### 6.4 输出契约（需求级）

每个候选页面、关系或缺口必须包含：

- 稳定 `candidateId` 和 `runId`；
- `contentStatus=candidate`，不得伪装为 `published`；
- `sourceRefs[]`：来源资源、处理单元、文档位置和证据片段；
- `product/version/module` 作用域；
- 生成方式、模型/Prompt/规则版本和输入哈希；
- 冲突、缺证据、版本未知和低置信度标记；
- 与现有候选或正式知识的匹配关系，但不覆盖原对象。

## 7. 端到端业务闭环

```text
1. 采集原始资料
2. 现有清洗模块无损规范化并生成不可变 snapshot
3. 质量门禁确认来源、版本、位置和哈希完整
4. 适配器按变化的处理单元调用 llm-wiki 类综合能力
5. 生成 Wiki 草稿、关系候选和缺口报告
6. 证据校验器检查每条输出能否回指原文
7. 回流候选区，进入现有审核任务
8. 审核者确认、修改、驳回或标记冲突
9. 只有现有发布流程生成正式基线
10. 下次输入哈希变化时，只失效并重算受影响候选
```

任一环节失败时，系统保留原始资料和上一次正式基线；综合层失败不得阻塞现有清洗和人工生产，也不得自动删除已发布知识。

## 8. 需求清单

### P0：必须具备

- 候选结果与原始证据一一可追溯；
- 产品、版本和权限作用域不可缺省；
- 候选与正式知识状态严格分离；
- 输入、输出、模型、Prompt、规则和运行日志可审计；
- 失败可重试、可取消、可回退，且不影响现有发布基线；
- 许可证、部署方式、数据出境和企业安全评审通过；
- 支持增量哈希，重复输入不重复生成。

### P1：验证价值后建设

- 参数—数据类型—错误码—命令关系候选；
- 跨文档、跨版本冲突检测；
- 知识缺口和孤立概念报告；
- 候选页面与现有文档节点的合并建议；
- 审核者一键跳转到原文证据，而不是在正文增加信息面板。

### P2：暂不建设

- 独立 Wiki 前端作为第二个知识门户；
- 自动发布或自动修改正式手册；
- SQL/命令执行和数据库连接；
- 无证据的兼容性、安全性或正确性评分。

## 9. PoC 方案与验收指标

### 9.1 最小专题

选一个 YashanDB 版本和一个专题，优先选择 `NUMBER` 数据类型、参数依赖或错误码之一。输入范围控制在已完成清洗和质量门禁的资料批次内，运行时间和模型调用预算固定。

### 9.2 对照组

同时比较：

1. 当前资料清洗 + 人工检索；
2. 当前资料清洗 + llm-wiki 类综合层；
3. 当前资料清洗 + 平台内部最小关系候选实现。

### 9.3 必测指标

| 指标 | 验收方向 | 失败条件 |
|---|---|---|
| 来源覆盖率 | 候选引用覆盖更多有效证据 | 引用缺失或无法定位 |
| 事实准确率 | 不低于人工基线 | 出现未被证据支持的事实 |
| 版本混淆率 | 不高于人工基线 | 不同版本结论被合并 |
| 审核耗时 | 单专题审核时间下降 | 审核返工抵消节省 |
| 重复知识率 | 重复页面和重复加工下降 | 形成新的重复事实源 |
| 增量效率 | 小变更只重算受影响对象 | 仍需全量调用 |
| 可回退性 | 任意失败可回到上次正式基线 | 影响已发布知识 |

具体阈值由专题规模和人工基线确定，不能在无基线时预先编造“提升百分比”。

## 10. 风险、决策门和停止条件

### 10.1 必须先决策的事项

- 企业允许采用 GPL-3.0 外部项目代码，但必须明确代码分发边界、许可证文本/版权保留、修改披露和源码提供义务，并完成法务评审；
- 是否允许独立工具访问经过授权的内部资料；
- 是否允许采用外部项目代码；若允许，须完成 GPL-3.0 义务清单（版权/许可证保留、修改披露、分发方式和交付边界）及法务评审；可采用外部代码不等于免除合规责任；
- 候选存储是否复用现有运行产物，避免新增第二事实库。

### 10.2 停止条件

停止条件不是“技术不喜欢”，而是业务保护开关。满足任一条件即停止产品化接入，保留调研和 PoC 证据：

- **证据不可定位**：审核者无法及时复核结论，业务上会导致错误参数、错误码或运维步骤进入手册，带来客户事故和责任追溯失败。
- **事实/版本错误高于人工基线**：会增加错误发布和跨版本误用风险，影响升级、迁移和生产运维。
- **审核耗时或返工增加**：组件没有降低单位生产成本，继续投入只会扩大人力和模型费用。
- **权限、许可证或数据出境不通过**：可能造成资料泄露、交付被迫开源或无法上线，形成不可逆法务和安全损失。
- **必须建立第二正式知识库**：会产生双事实源，导致检索、问答和发布结果不一致。
- **增量没有节省实际计算/调用**：无法兑现降低成本和缩短交付周期的商业目标。

每个停止条件都必须绑定业务事件、量化证据、负责人和恢复路径，不得以主观体验单独终止。

### 10.3 继续建设条件

只有在 PoC 证明“审核成本下降且事实治理不退化”，并完成许可证、安全和架构评审后，才进入 P1 产品化设计。产品化仍应优先内部实现受控适配器，而不是直接把外部桌面应用嵌入知识中心。

## 10.4 “目标模式”是否适合作为开发路径

若目标模式是一次性建设完整的 llm-wiki 形态（独立 Wiki 存储、向量数据库、图数据库、桌面/门户 UI、对话和 MCP），则**不适合作为当前开发路径**：它会在尚未证明业务收益前引入多套基础设施，形成双事实源，并增加用户认知和运维负担。

正确路径是“目标能力分阶段落地”：

```text
阶段 0：冻结现有清洗产物和发布基线，完成许可证/安全边界确认
阶段 1：复用 snapshot、embedding、图谱和运行缓存，做单专题离线适配器 PoC
阶段 2：仅将通过证据校验的结果回流候选审核，不新增前端门户
阶段 3：指标达标后建设页面级增量状态和候选关系模型
阶段 4：仅当现有索引不足时，单独评审新增向量库/图数据库
阶段 5：最后再考虑对话或 Wiki 视图，并继续服从发布基线
```

每一阶段都必须可独立验收、可回退；先证明业务价值，再扩大技术范围。

## 11. 最终判断

这条接入需求成立的最小命题是：

> 现有资料清洗负责把资料变成可信证据，`llm-wiki` 类能力负责把证据组织成可审核的候选关系和页面，知识中心负责把候选变成唯一、可追溯、可回退的正式知识。

因此，建议立项为“知识综合层 PoC”，而不是“引入 llm-wiki 替换资料清洗模块”。可以采用外部项目代码，但必须在 GPL-3.0 合规边界内以受控适配器方式集成；这既复用了外部项目真正有价值的增量和关系能力，也保留了知识中心对事实、版本、权限和发布的最终控制权。

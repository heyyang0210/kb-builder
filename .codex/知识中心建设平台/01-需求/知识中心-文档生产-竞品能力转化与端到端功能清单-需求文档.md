## 1. 转化结论

建议采用“GitBook变更集合 + Document360审核责任与待办 + Paligo跨手册影响关系 + GitLab远端交付事实”的组合，承接到现有平台。PingCode版本视图、生产任务聚合、数据库案例验证和多入口一致展示由本平台补充，不能宣称直接从某个竞品复制即可获得。

最小业务交付单元是**生产任务**：一个任务可以涉及多个手册、多个文档，每篇文档有独立进度，任务只有满足全部必要条件才完成。数据库版本是任务集合的分类依据，文档修订是审核对象，Git提交是交付证据，三者必须分别展示。

本报告列出32项功能，其中P0为24项、P1为7项、P2为1项。P0用于先闭环任务组织、人工生产、审核、GitLab交付和两类视图；P1增强自动定位、AI与数据库验证。是否将特定案例验证列为首批强制门禁，需结合现有规则确认，不能因为列为P1便绕过现有门禁。

## 6. 关键行为契约

以下为业务规则建议，不替代已批准的状态机、权限和接口设计。

### 6.1 生产任务与文档范围

- 入口：从版本视图选需求创建任务；前提是来源可读取、数据库版本明确。
- 输入：来源选择、受影响手册/文档、责任人及变更意图；输出为可确认的任务范围。
- 状态：范围待确认 → 生产 → 审核 → 交付 → 完成。退回回到修订；交付失败保留审核事实并展示恢复动作。这是阶段表达，不新增接口状态枚举。
- 异常：来源变更、文档删除、手册改版、责任人失效均提示复核；禁止通过静默缩减范围使任务完成。

### 6.2 审核修订与交付修订

- 审核入口应同时看到本次文档集合和每篇差异。审核对象是固定修订，不是随时变化的“最新正文”。
- 已审核正文发生变化，受影响文档及相关检查需重新评估；是否连带重审其他文档按范围依赖确定，不能默认全部免审或全部重审。
- 交付前比较将发送内容与有效审核对象；远端出现并发修改时停止对应交付并提示重新比较。
- 竞品公开材料不能证明这些冻结/失效细节；它们是为解决本平台风险提出的规则。

### 6.3 完成与统计

完成至少受四类事实约束：范围处理完整、审核仍有效、必要质量条件满足、远端交付核实。之后再判断是否达到配置明确的业务终点。终点未确认前，需求稿并列描述“已提交/已合并/已上线”，不批准任何一个作为唯一终点。

总视图中的任务数按任务身份去重，文档数量单列；“我的操作完成”不等于“生产任务完成”。任务存在排除项时必须展示排除理由，来源覆盖统计需公开纳入范围，不能靠缩小分母掩盖遗漏。

### 6.4 权限与性能

权限沿用现有授权边界，通知、生产、审核与交付分别校验。界面不显示按钮不足以证明权限生效。任务列表优先展示概览，正文与跨文档差异按需加载；不得在版本页提前加载所有任务正文。性能数值门槛沿用现有预算；新增规模与基线需在设计阶段实测确定，本报告未测量竞品后台性能。

| 验收-08 通知与读取恢复 | 远端事件重复、乱序或丢失；主动对账恢复；三入口刷新一致 | 事件/查询记录、前后任务结果与更新时间 |
| 验收-09 版本隔离 | V-A完成；V-B未处理仍保持原状态；跨手册任务只计1个 | 两个版本任务列表和分口径统计 |
| 验收-10 权限边界 | 只读用户直接请求编辑/审核/交付；服务端按既有权限拒绝 | 真实拒绝响应和合理审计记录，不能只截图按钮隐藏 |
| 验收-11 AI与测试增强 | 候选失败保留草稿；采用后可追来源；案例在对应版本真实执行，失败或未知明确显示 | 模型/来源/采用记录、用例环境版本及执行输出 |
| 验收-12 网站发布 | GitLab合并成功但站点失败，分别显示；恢复站点后回读实际页面 | 合并与站点发布两个独立事实 |

涉及平台后端或端到端时必须真实调用API；竞品PoC需单独取得可用沙箱，记录套餐/时间/后台版本与正常、退回、权限、异常场景。公开页面采集不能替代上述验收。

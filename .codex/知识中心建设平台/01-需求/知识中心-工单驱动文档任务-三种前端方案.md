## 1. 需求复述

从 PingCode 工单清单导入工单，在知识中心为每个工单建立且只建立一个平台任务。工单编号全局唯一，直接作为平台任务的“编号”和幂等匹配键。任务列表呈现编号、描述、总责任人、产品、版本号、状态、开始时间、结束时间、输出件/说明及来源链接。

一个工单任务由总责任人对最终结果负责。若变更涉及知识文档，则总责任人先确认涉及的手册；每本手册由手册负责人确认具体文档；每篇文档由一个技术领域负责人或已知文档责任人承担。关系为：

```text
工单任务（1，总责任人）
  └─ 总责任人判断是否涉及文档
       ├─ 不涉及：填写工单级理由
       └─ 涉及：勾选手册范围并指派手册负责人
            └─ 手册负责人逐本判断是否涉及文档
                 ├─ 不涉及：填写本手册不涉及理由
                 └─ 涉及：勾选文档范围并为每篇文档指派唯一责任人
```

总责任人先判断工单是否涉及文档变更。若不涉及，必须填写工单级理由；若涉及，勾选涉及的手册并指派手册负责人。每位手册负责人再独立判断本手册是否涉及文档：若不涉及，必须填写该手册不涉及的理由；若涉及，勾选具体文档并为每篇文档指派唯一责任人。没有文档变更时仍保留工单任务。任一级范围尚未确认、理由缺失、没有责任人或子项未完成时，任务不得显示为完成。各层责任人支持有权限的指派与变更，并保留变更记录。

## 2. 输入字段与平台字段

工单清单表头为“编号、标题、状态、负责人、创建时间、复现发布号”。当前输入没有产品、计划开始/结束时间、输出件或来源 URL 的独立列，不能在导入时编造这些值。

对输入工作簿的只读检查结果：1 个工作表、530 条有编号的数据行，编号 530 个且无重复；首条样例为 `YDBRD-60778`。该检查只说明当前文件的行和编号情况，不代表已导入平台。

| 平台字段 | 初始映射 | 说明 |
|---|---|---|
| 编号 | 编号 | 原样保留；全局唯一约束；重新导入按编号更新来源快照，不重复建任务 |
| 描述 | 标题 | 保留原始标题，可在平台补充任务说明 |
| 总责任人 | 负责人 | 先按 PingCode 账号映射平台人员；映射失败时待认领，不猜测人员 |
| 产品 | 未指定 | 需要导入补充或平台人工选择 |
| 版本号 | 复现发布号 | 作为初始版本上下文；空值显示“未指定” |
| 状态 | 状态 | 保留来源状态并做显式状态映射；未知状态显示“待映射” |
| 开始时间 | 空 | 工单创建时间不是任务开始时间，不自动等同 |
| 结束时间 | 空 | 仅任务完成时记录实际完成时间 |
| 输出件/说明 | 空 | 由责任人在平台补充，可链接发布版本或说明 |
| 来源（链接） | 编号 + PingCode 项目配置 | 用受控的项目地址和工单编号组装链接；没有有效项目地址时仅显示编号，不拼接猜测 URL |
| 创建时间 | 创建时间 | 保存在来源信息/审计中，不替代任务开始时间 |

## 3. 方案比较

### 方案 A：任务清单 + 详情抽屉（建议首选）

```text
┌ 文档任务  [导入工单] [新建任务] ┐
│ 搜索/状态/责任人/产品            │
├──────┬──────┬──────┬──────┬─────┤
│编号  │描述  │责任人│状态  │进度 │ ...
│YDB… │标题  │何灿  │拆分中│2/4  │
└──────┴──────┴──────┴──────┴─────┘
                                      ┌任务详情──────┐
                                      │工单与总责任人 │
                                      │手册任务 2     │
                                      │ └文档任务 4   │
                                      │[调整责任人]   │
                                      └───────────────┘
```

适合批量导入后的日常查询。列表保留用户要求的字段并允许配置列；选择行后从右侧查看工单、手册和文档三级关系，责任变更不离开列表。优点是熟悉、扫描效率高、改动范围可控；不足是跨多手册的依赖和整体进度不如关系视图直观。

### 方案 B：任务工作台 + 分步拆解

```text
┌任务列表─────────┬当前工单：YDBRD-1042────────┐
│ 搜索/状态        │ 工单信息 / 总责任人          │
│ YDBRD-1042 ●     │ ① 确认是否影响文档           │
│ YDBRD-1041       │ ② 选择手册并确认手册负责人   │
│                  │ ③ 手册负责人勾选文档与责任人 │
│                  │ ④ 检查覆盖与任务完成条件     │
│                  │ [保存拆解] [完成任务]         │
└──────────────────┴────────────────────────────┘
```

适合总责任人逐单推进拆解与跟踪。工作区聚焦当前工单，分阶段显示尚缺的判断和责任，支持保存草稿与转交。优点是流程清楚、缺项可见；不足是批量扫查和多工单比较较弱，连续处理大量简单工单时点击较多。

### 方案 C：三级协作树 + 汇总进度

```text
┌任务 / 手册 / 文档协作树─────────────┬详情───────────┐
│ ▾ YDBRD-1042 标题 何灿 进行中 2/4   │总责任人：何灿 │
│   ▾ 基本管理手册 张三 1/2             │来源：PingCode │
│     ● 安装配置 李四 已完成             │截止/输出说明  │
│     ○ 高可用 陈六 待处理               │[变更责任人]   │
│   ▸ SQL参考手册 待确认范围             │变更历史       │
└───────────────────────────────────────┴───────────────┘
```

适合管理者查看任务覆盖、跨手册阻塞和责任分布。树形结构直接呈现 1→n→n，节点进度由子项汇总。优点是协作关系和阻塞位置最直观；不足是表格字段横向比较较弱，树展开后长任务会占据大量页面空间。

### 方案 1 细化：列表字段与两级范围确认

本轮选定方案 A 作为方案 1，页面主入口为“文档任务”列表，点击一行打开右侧详情抽屉。列表固定展示以下字段，字段名按平台任务口径统一为“编号”：

```text
编号 | 描述 | 责任人 | 产品 | 版本号 | 状态 | 开始时间 | 结束时间 | 输出件/说明 | 来源（链接）
```

详情抽屉按以下顺序展示并保存状态：

1. 工单级判断：总责任人选择“涉及文档变更”或“不涉及文档变更”。选择涉及时，勾选手册范围并为每本手册指派手册负责人；选择不涉及时，必须填写工单级理由。
2. 手册级判断：每位手册负责人对已选手册选择“涉及文档变更”或“不涉及文档变更”。选择涉及时，勾选本手册内的文档范围并为每篇文档指派唯一文档责任人；选择不涉及时，必须填写本手册级理由。
3. 汇总验收：只有两级判断均已完成，涉及范围已勾选，责任人已有效指派，或对应“不涉及”理由已填写，任务才允许进入完成判断；任一条件缺失都显示具体待办。

### 选择优先与配置规则

- 手册和文档范围使用弹窗选择器：搜索、产品筛选、分页/虚拟列表、多选与已选数量；选择结果逐项关联对应负责人。手册目录较大时不将所有选项常驻详情页。
- 两级“是否涉及文档变更”均为单选项。“不涉及”先从原因选项中选择；仅选择“其他”时要求补充说明。理由分别记录在工单级或手册级，不能为空。
- 选人使用平台人员目录的可搜索单选控件。责任人可按权限指派和变更；总责任人负责整单，手册负责人负责手册范围和文档分派，单篇文档仅有一个当前责任人。
- 新建任务默认总责任人取配置 `documentTask.defaultOwnerId`，保存人员目录的稳定 ID，不把“何灿”写入业务逻辑。部署配置的初始人员为何灿；人员变更通过平台配置维护。配置变更只影响之后新建的任务，不批量改派既有任务。
- 效果稿用独立 JSON 配置样例演示默认人员如何加载，生产实现应从受控配置和人员目录读取，不把示例数据当作线上配置或真实任务。

完整流转图应同时展现正常主线和两级“不涉及”分支：导入工单 → 总责任人判断/选手册 → 手册负责人判断/选文档 → 文档负责人处理 → 汇总；两级“不涉及”分支都以选择原因后汇回任务汇总。效果图减少解释段落，以泳道步骤、状态、勾选范围与汇合关系呈现。

桌面端保持完整字段表格和右侧详情抽屉；390px 窄屏隐藏非核心表格列，保留编号、描述、责任人和状态，点击任务后按单列顺序查看两级判断与责任分派，不产生页面级横向滚动。效果稿中的姓名、编号以外的产品和时间仅为界面示例，不代表已导入平台。

## 4. 推荐判断

建议首期采用**方案 A 作为默认列表，结合方案 B 的任务详情拆解步骤**。方案 C 可作为后续“协作关系”视图，不建议首屏直接使用树形主界面。理由是用户首先需要从工单清单导入并管理一一对应的任务；任务列表是稳定入口，拆解只在需要文档变更的任务中展开。将列表与分步拆解组合，兼顾批量处理效率和业务门禁清晰度。

推荐导航为“任务列表 → 任务详情 → 总责任人判断工单级文档影响 → 勾选手册并指派手册负责人 → 手册负责人逐本判断文档影响 → 勾选文档并指派文档责任人 → 汇总验收”。工单级和手册级均支持“不涉及文档”分支，必须分别填写理由。所有列表状态和进度均由后端子任务真实汇总，前端不得只凭某一层状态推断任务完成。

## 5. 关键规则与验收

1. 对同一个全局工单编号，重复导入、并发导入和重试都只得到同一个平台任务；来源字段可更新，人工补充字段不被空值覆盖。
2. 工单任务是唯一顶层任务；手册任务和文档任务是其子项，不为同一工单再创建平级平台任务。
3. 一个文档任务只关联一个文档及一个有效责任人；同一工单下可有多篇文档，也允许同一手册下多个文档任务。
4. 拆解未完成、范围待确认、缺少“不涉及理由”或必需责任人缺失时，任务状态保持未完成并展示具体缺项。
5. 责任指派/变更校验当前用户权限与候选人有效性，保存原责任人、新责任人、操作者、时间和理由；历史记录不可被改写。
6. 状态、时间字段显式映射；导入创建时间只作为来源元数据。未提供的产品、计划时间和输出件显示“未指定/暂无”，不使用推断值填充。
7. 来源链接基于平台受控的 PingCode 项目 URL 配置生成，并对工单编号进行安全编码；不接受 Excel 中任意 URL 覆盖平台可信主机。
8. 列表支持按编号、描述、总责任人、产品、版本和状态检索；详情能从任务追溯到原工单及每篇文档。

### 交互验收

- 导入含重复编号的表格时，预览逐项展示新增、更新、跳过和字段映射失败；用户确认后才正式写入。
- 总责任人选择“涉及文档”后必须勾选至少一本手册并指派手册负责人；选择“不涉及”必须填写工单级原因。
- 每位手册负责人都要确认本手册是否涉及文档；选择“涉及”后必须勾选至少一篇文档并分派唯一责任人，选择“不涉及”必须填写该手册级原因。
- 默认总责任人从配置 `documentTask.defaultOwnerId` 读取稳定人员 ID；更改默认人只影响新建任务，不覆盖已有任务的责任人。
- 范围确认通过搜索和多选完成；不涉及原因优先单选，只有“其他”允许补充文字。
- 总责任人可调整手册责任人；手册负责人可在授权范围内调整文档责任人；改变责任后进度汇总即时刷新并保留历史。
- 窄屏优先显示任务识别信息和状态，复杂拆解以单列步骤呈现；表格转换为任务行卡片/详情，不出现页面级横向滚动。

## 6. 尚待确认

- Excel“负责人”与平台账号的匹配键，以及无法匹配时由谁认领。
- “状态”来源值到平台任务状态的映射；是否保留 PingCode 原状态还是同时显示平台执行状态。
- 产品字段是否能从 PingCode 项目/字段补齐，或由平台人工选择。
- “复现发布号”是否等同需求所说版本号，尤其为空或存在多个版本的工单。
- 开始时间的业务定义、完成任务所需的输出件类型与是否允许无输出件完成。
- 手册范围和文档范围的拆解方法仍由人确认；方案不自动推断影响文档。

# 知识中心-AI文档生产-需求文档

> 状态：目标业务需求，待按业务场景验收；不代表能力已实现。
> 更新日期：2026-10-22
> 面向角色：文档作者、审核者、手册负责人及平台管理者。

## 一、总体业务介绍

知识中心为作者提供内置的 AI 文档生产能力：利用可信资料，按照手册大纲和文档模板生成正文，也能对存量文档进行润色、续写和更新。作者在同一工作区检查结果、修改并保存草稿，确认后进入既有审核发布流程，最终形成有依据、可追溯的知识成果。

**MVP 必须同时具备四类核心能力：按大纲和模板生成文档、润色存量文档、续写存量文档、按照存量文档按照模板改写。** 一次处理一篇文档；生成既适用于大纲中尚无正文的目标文档，也适用于已有文档的修订，不要求所有目标都先有正式发布正文。

主要矛盾是：作者希望减少整理资料和编写正文的投入，同时必须确保内容准确、修改可控、成果可审核。因此，业务效果既要看能否产出正文，也要看作者能否理解、核验和采用结果。AI 产出始终是候选内容，来源选择、采用结果、提交审核、审核结论及发布由有权限的人负责。

## 二、把业务诉求拆清楚

最初诉求是：“让知识中心内置 AI 写文档，减少重复劳动，让已有资料更快转化为可用知识。”按使用者的实际工作拆解如下。

| 诉求编号 | 谁在什么场景下遇到困难 | 清晰后的业务诉求 | 期望效果 |
|---|---|---|---|
| 诉求-01 | 作者已有大纲、模板和资料，仍需从空白开始组织正文 | 按已确认的大纲位置、模板要求和资料生成目标文档 | 得到结构完整、可编辑的初稿 |
| 诉求-02 | 存量文档措辞生硬、表达重复或风格不统一 | 在不改变事实和技术含义的前提下润色所选内容 | 表达更清楚，作者可核对修改 |
| 诉求-03 | 存量文档内容未完成，需结合上下文继续写作 | 在作者指定位置，依据上下文和资料续写 | 新内容衔接原文，已有内容得到保留 |
| 诉求-04 | 研发资料变化后，作者难以判断文档应该改哪里 | 明确更新要求及范围，结合原文和新资料形成修订建议 | 可查看增删改，避免无关内容被改写 |
| 诉求-05 | 审核者无法仅凭流畅的文字判断内容及示例用例可靠性 | 核对候选内容、来源及质量问题，在质量检查最后一轮接入 YashanDB 测试库验证文档用例并提供报告 | 问题有执行证据可查，生成结果能够进入正常审核发布流程 |
| 诉求-06 | 作者无法判断任务是否仍在执行，失败后可能丢失成果，也无法区分引用内容与模型推理 | 查看进度、处理失败，保留生产记录并管理文档生成元信息 | 工作可继续，可追溯内容来源、推理及人工确认过程 |
| 诉求-07 | 设计、测试文档和用例分散在 PingCode、知识库及网页中，作者反复查找和复制资料 | 接入 PingCode 设计文档、测试文档、知识库 MCP 服务和测试用例库；支持配置多个参考文档引用源，填写网址后主动拉取文档 | 多来源资料可集中预览、选择和引用，生成依据可回查 |

这里的“润色”以改善表达为目标；“续写”以补充新内容为目标；“生成”以形成目标文档正文为目标。三者都需要作者明确操作对象，不能将全文重写当作所有操作的默认行为。

| 确认生成依据 | 01～05、07 | 减少跨系统查找和资料整理投入，便于核验内容 | 作者能配置多个引用源、通过网址拉取文档，确认本次采用的资料、大纲和模板 |

| 人机协作确认与修订 | AI文产-08：预览候选结果，人工编辑或补充指令要求 AI 修订，确认后保存为草稿 | 保留作者控制，保护已有成果 | 结果采用前可检查、可放弃，失败不覆盖上一份可用草稿 | MVP |
| 质量检查与审核发布衔接 | AI文产-09：检查结构、模板要求、表达及来源依据，明确问题与处理要求 | 降低遗漏及错误流入审核的概率 | 作者能定位问题，区分需处理的阻断项和提示项；AI 检查不代替事实审核 | MVP |
| 质量检查与审核发布衔接 | AI文产-10：作者确认并保存后送审，支持依据反馈继续修订，批准后按既有流程发布 | 将生成能力融入文档交付闭环 | 审核者能查看候选、差异和依据；作者能处理意见并重新送审 | MVP |
| 进展、恢复与成果追溯 | AI文产-11：查看进度、取消执行，失败后查看原因并重试 | 降低等待和失败造成的损失 | 状态明确，取消或失败保留已有可用内容，不重复产生结果 | MVP |

| 确认生成依据 | AI文产-14：填写一个或多个文档网址，主动拉取文档并纳入参考资料 | 降低引用外部文档的操作成本 | 显示拉取状态、内容预览、原始网址和拉取时间，作者确认后纳入本次依据；失败不伪装为成功 | MVP |
| 续写及更新存量文档 | AI文产-15：支持通过新增 Skill 扩展存量文档续写能力，并按本次目标选用适用 Skill | 适应不同文档类型与补写任务 | 作者能确认所用能力及适用范围，得到指定位置的续写候选，保留原文并比较差异 | MVP |
| 质量检查与审核发布衔接 | AI文产-16：由独立测试 Agent 协同多个 Skill，接入 YashanDB 测试库，对文档中的用例执行验证并生成测试报告，作为最后一轮质量保障 | 用真实执行证据发现示例和用例错误 | 报告关联被测文档版本、用例、数据库版本与测试环境，展示预期与实际结果、通过/失败/未执行状态、错误证据和复测记录 | MVP |

### 质量保障与生成元信息要求

- 独立测试 Agent 与文档生成职责分开，组合用例提取、测试库执行、结果比对及报告生成等多个 Skill 完成验证；此处仅明确职责和交付结果，具体编排另行设计。
- 文档用例应关联正文位置及所引用的测试用例库条目；报告说明覆盖范围、执行前提、未执行原因及测试数据清理结果。环境不可用、用例不适用或缺少执行条件时，标为未执行，不能视为通过。
- 测试仅在有权限的 YashanDB 测试库中按约定范围执行。失败项和未执行项进入问题处理；涉及用例或预期结果的修订后，需对修订版本复测。报告只对所标识文档版本和测试环境有效，不代替人工审核。
- 生成元信息随候选和草稿版本保留，关联本次生产任务、操作类型、生成时间、模型与 Skill 版本、原文版本、大纲和模板版本、引用内容及其来源位置、质量报告和人工确认记录。模型推理不能标记为已有来源事实；混合内容应能分别回查引用部分和推理部分。
- 后续人工修改或重新生成时保留历史元信息，并标记受影响内容的依据或测试结论需要重新核验，避免将旧报告用于新版本。

## 五、业务流程与验收

业务主线：选择目标文档与操作 → 确认范围、资料及适用的大纲和模板 → AI 产出候选 → 作者检查、修订和采用 → 保存草稿 → 内容质量检查 → 独立测试 Agent 在 YashanDB 测试库验证用例并提供报告 → 问题修订与复测 → 送审与反馈修订 → 审核通过 → 有权限的人按既有流程发布。

| 验收场景 | 预期业务结果 | 关联特性 |
|---|---|---|
| 大纲中存在目标文档但尚无正文 | 作者选择模板和可信资料，AI 生成实际正文而非仅提供提示词或空模板；作者可编辑、保存和送审 | 01～04、08～10 |
| 对存量文档的指定内容润色 | 能对比修改，事实与技术含义保持一致；作者可采用或放弃，不误改范围外正文 | 01、05、08、09 |
| 对存量文档指定位置续写 | 能结合上下文补充内容并保留原文；缺少依据的内容被明确提示，作者确认后保存 | 01～03、06、08、09 |
| 按模板改写存量文档 | 确认目标模板与范围，AI 重组范围内正文且保持事实、参数和代码，可比较、放弃或保存，范围外不变 | 01～03、07～09、12 |
| 用新资料更新既有文档并处理审核意见 | 候选差异及依据可查，作者处理意见后重新送审；发布依照既有权限和规则执行 | 02、07～10、12 |
| 生成、润色或续写失败、取消及重试 | 用户知道任务状态与失败原因，已有人工内容和可用草稿保留，重试不重复产生结果 | 08、11、12 |
| 无权限、资料不可读或依据不足 | 不越权读取和写入，不伪造资料或成功结果；说明原因和需要人工处理的事项 | 01、02、09、10 |
| 配置多个参考源并填写文档网址 | 能从 PingCode 设计/测试文档、知识库 MCP 服务及测试用例库取得授权资料，组合引用；网址拉取的内容可预览、确认并回查，失败和来源冲突明确展示 | 02、13、14 |
| 新增 Skill 后对存量文档续写 | 新增能力可被选用并作用于指定续写位置，候选衔接上下文、保留原文；所用 Skill 及版本可追溯 | 06、08、12、15 |
| 文档用例进入最后一轮质量验证 | 独立测试 Agent 调用多个 Skill 在真实 YashanDB 测试库执行用例，报告可定位文档及用例版本、预期与实际结果；失败后修订复测，未执行项不得记为通过 | 09、10、16 |
| 回查引用、模型推理及人工修改 | 对同一候选中的直接引用、资料归纳、模型推理及人工修改分别查询元信息，定位资料原文或明确无可核验来源；文档修订后能识别旧依据和旧报告的适用版本 | 02、12、16 |

四类核心能力都必须使用真实 AI 产出完成验证；静态示例、仅生成提示词、仅手动编辑或空模板不能作为 AI 能力通过验收的证据。审核通过不等于自动发布。

业务效果评估关注：初稿编写耗时、人工修改投入、生成结果采用情况及审核返工情况。当前没有测量基线，改善幅度和达标阈值均为**待确定**，不编造效率承诺。

## 六、范围与关联规则

- 本文描述目标业务能力，不作为当前实现状态或迁移完成度报告。MVP 包含单篇新正文生成、存量润色、续写和增量更新；整本手册批量生成不列为本次承诺。
- 已确认的平台来源、审核权限、发布及质量规则分别遵循[总体需求](./知识中心-平台-总体需求-需求文档.md)、[增量文档构建 MVP 需求](./增量文档构建MVP需求.md)及[文档生产原则](./知识中心-文档生产原则.md)。本次按诉求-07 新增 PingCode 设计/测试文档、知识库 MCP 服务、测试用例库和网址主动拉取的目标接入能力，沿用平台既有来源授权与审核发布规则。
- 本文首期一次处理一篇文档，限定的是 AI 生产粒度；既有多文档任务、批量送审和发布规则保持其适用范围。旧增量专项对发布基线的要求适用于已有文档更新，不能用来阻止大纲下尚无正文的文档生成。
- 旧生成器入口的兼容和退场沿用[全局生产中心与手册工作台联动决策](../07-决策与风险/知识中心-文档生产-全局生产中心与手册工作台联动-决策记录文档.md)，不在本文重新规定。
- 质量检查中各问题的阻断等级及例外处理规则需在专项规则中明确；未明确前不声称自动检查已经能够保证内容正确。


### 统一模型管理与写作选择（2026-10-26）

采用方案一：平台管理员配置并测试共享模型服务，作者在沉浸式 AI 写作页选择已启用的生成模型。必须让配置、选择、实际执行、生成记录相互对应；不能只展示模型名或继续隐式读取全局默认。无模型时提供中文配置指引且禁止生成；过期选择明确拒绝，任务不自动降级；密钥仅服务端加密保存。

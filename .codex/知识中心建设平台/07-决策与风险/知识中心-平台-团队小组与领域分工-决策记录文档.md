## 1. 背景与证据

真实环境已有 8 个有效技术领域和 22 名有效平台人员，但 8 个领域的负责人均为空、成员数均为 0。当前系统只有技术领域读取接口，没有团队或领域成员维护写接口，因此大纲“分工管理”无法提供合法责任人候选。

现有 `KC_TECH_DOMAIN_MEMBER` 把内容分类与人员组织耦合在同一领域模型中，不利于后续复用团队、表达组织范围或独立治理名册。该表当前没有有效成员数据，可作为迁移与回退来源，但不应继续作为目标运行时事实源。

## 2. 决策

1. 平台管理“人员管理”增加“人员 / 团队小组”二级视图，不增加平台一级导航。
2. 建立通用 `KC_TEAM_GROUP`、`KC_TEAM_GROUP_MEMBER` 模型；团队表不保存技术领域外键。
3. `KC_TECH_DOMAIN` 表示内容分类并通过唯一 `TEAM_GROUP_ID` 显式引用负责团队；不得按团队名称、编码或列表顺序推断关系。
4. 本阶段只配置现有 8 个技术领域关联团队，不开放团队新增、改名、停用或其他团队类型前端能力。
5. 只有平台管理员拥有 `team-group:manage`，负责维护负责人和成员。
6. 技术领域负责人不是新的全局登录角色，通过团队负责人关系获得绑定领域内的 `build-task:assign` 资源权限。
7. 一个有效团队必须且只能有一个负责人；同一人员可以加入或负责多个团队。
8. 初次配置负责人后，绑定领域下未完成且未分派的任务自动归负责人。
9. 移出成员时，其未完成任务自动转给保存后的负责人；更换负责人时原负责人默认降为普通成员，只有显式移除才转派其未完成任务。
10. 已完成任务、历史责任快照和历史审计不得改写。
11. 名册变化、任务转派、团队版本递增和审计必须在同一事务中成功或整体回滚。
12. 保存前使用影响预览；预览与保存之间影响集合变化时拒绝保存并要求重新确认。

## 3. 选择理由

- 将“领域是什么”与“哪些人组成团队”分离，避免分类字典同时承担组织职责。
- 以通用团队模型支撑未来其他组织关系，但当前只开放已确认的技术领域场景，避免提前扩展产品范围。
- 把名册维护集中在平台管理员，避免领域负责人自行改变授权边界；负责人只在本领域执行任务分派。
- 自动转派只作用于未完成任务，既恢复当前业务可执行性，又保护已完成事实和历史责任证据。
- 影响预览、乐观锁和单事务保存共同防止管理员依据过期数量确认后产生静默错派。

## 4. 影响范围

| 范围 | 影响 |
|---|---|
| 总体需求 | 增加团队小组治理和领域分工前置条件 |
| 目标架构 | 增加团队和成员两类业务事实；`KC_TECH_DOMAIN.TEAM_GROUP_ID` 保存唯一领域到团队关系 |
| 权限 | 新增 `team-group:manage`、`build-task:assign`，取消任务分派复用 `outline:create` |

| 大纲管理 | 增加团队未配置门禁、深链入口、负责人范围和自动转派规则 |
| 审计与恢复 | 保存记录前后名册、影响摘要、原因、操作者和追踪标识 |

## 5. 实施边界

用户已明确授权按方案 1 修改功能代码、执行数据库迁移并完成端到端验证。已明确提供的负责人和成员可以写入真实团队；存在身份歧义或人员目录中不存在的记录不猜测、不导入。

迁移执行仍必须遵守仓库门禁：SQL 来自已提交 Git revision，并由正式迁移器执行；不得直接执行 SQL 或篡改迁移账本。

## 6. 迁移与回退

1. 新模型启用前保持现有读取行为，不把设计目标声明为已实现。
2. 011 已创建两张团队表和 8 个初始团队；012 先按 011 的旧显式外键把 8 对关系写入 `KC_TECH_DOMAIN.TEAM_GROUP_ID`，完成非空和唯一约束后再删除团队表旧领域列，不使用名称映射。
3. 完成数量、唯一绑定、唯一负责人和摘要对账后切换读取，再切换名册主写。
4. 切换后旧 `KC_TECH_DOMAIN_MEMBER` 只读，不双写、不接受新业务写入。
5. 验收失败时停止新写，恢复旧只读投影或切换前读取路径；不得把新模型事实反向覆盖旧表，也不得改写已完成任务。
6. 回退前必须保留新表和审计证据，定位失败原因后再决定重试或修正迁移。

## 7. 风险与控制

| 风险 | 控制 |
|---|---|
| 一个团队出现多个有效负责人 | 保存事务锁定团队并校验；契约测试覆盖并发写入 |
| 预览后任务状态变化 | 预览 token 绑定版本和影响摘要，变化返回 409 |
| 名册已保存但任务转派失败 | 同一数据库事务整体回滚 |
| 旧表与新表形成双主写 | 切换后启动门禁与测试禁止旧表写入 |
| 已完成责任历史被覆盖 | 转派查询只选择未完成任务，验收核对历史快照摘要 |
| 领域负责人跨领域分派 | `build-task:assign` 同时校验负责人关系和团队绑定范围 |

## 8. 失效与重新决策条件

出现以下任一情况时，本决策不能直接外推，必须重新评审：

- 对前端开放其他团队类型、团队创建、改名、停用或组织层级管理；
- 允许一个技术领域同时绑定多个有效团队，或一个团队同类型绑定多个技术领域；
- 一个团队需要多个并列负责人、临时代理负责人或按时间排班；
- 任务转派不再以团队负责人兜底，或已完成任务允许重写责任事实；
- 团队成员来自 `KC_PLATFORM_PRINCIPAL` 之外的外部目录并由外部系统主写。

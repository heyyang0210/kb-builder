## 目标与范围

在 4 小时内完成 RAG 项目自治开发体系的 G0 规划：判断当前“角色 + 工具 + Skill + 人工关键决策”方向的合理性，定义闭环底层逻辑、自治等级、演进机制、SMART 阶段和必须人工确认的决策。

本任务只产出认知和路线，不更改业务代码、公共 API、技术栈或外部依赖，也不宣称规划中的自治能力已实现。

## 当前认知判断

### 结论

当前方向基本合理，但必须从“配置更多 AI 组件”升级为“运行一个可测量、可审计、可回退的社会-技术控制系统”。角色、工具和 Skill 是能力供给层；目标契约、评价器、运行时编排、证据、门禁、版本和反馈演进才能形成自治闭环。

### 合理的部分

1. 角色分工可以分离规划、架构、实施、验证和报告的关注点。
2. 工具将 Agent 从文本建议扩展到可读、可写、可运行和可验证的环境操作。
3. Skill 适合封装重复、专业、可版本化的工作流，当前仓库已有 Prompt/Skill Registry、Schema、发布与 Diff 基础。
4. 人只处理高风险、高歧义、高不可逆决策，符合风险分层的自动化原则。
5. 将失败样本反哺角色、工具、Skill 和规则，是让体系越用越顺的正确方向。

### 必须补充的边界

1. **不追求无人值守**：高自治是在预先批准的权限和预算内闭环，不是无限自主。
2. **不以 Agent 数量衡量自治**：角色过多会增加上下文丢失、状态漂移和验收不一致。
3. **不让生成者自证正确**：验证优先使用可执行测试、Schema、静态检查、真实 API、固定评估集和独立评审。
4. **不把对话当状态库**：目标、计划、契约、产物、决策、失败和证据必须持久化。
5. **不直接自修改生产策略**：自动归因和生成候选补丁可以自治，提升为默认策略前必须通过回归、影子运行、灰度和回退门禁。
6. **RAG 质量不等于代码测试通过**：还需验证检索命中、引用正确、忠实性、ACL、版本/时效、延迟和成本。

## 底层逻辑

### 1. 自治的本质是受约束的反馈控制

一次自治运行的最小单元应为：

```text
目标与成功契约
  -> 获取仓库/需求/运行事实
  -> 形成可执行计划与风险等级
  -> 在最小权限内执行
  -> 采集代码、API、RAG 评估、安全、成本证据
  -> 判定通过 / 可自修复 / 需升级
  -> 发布、回退或人工决策
  -> 将失败样本和策略效果进入演进队列
```

闭环成立的前提是“系统能客观判断自己是否完成”。因此评价器、验收契约和可观测证据的优先级高于增加新 Agent。

### 2. 六层闭环架构

| 层 | 职责 | 当前基础 | 主要缺口 |
|---|---|---|---|
| 意图与治理层 | 目标、非目标、DoR/DoD、风险等级、人工门禁 | AGENTS、角色、任务卡、G0-G4 | 统一自治等级与决策矩阵 |
| 上下文与记忆层 | 需求、设计、代码、运行、决策和失败样本的单一事实源 | 文档分层、workflow 台账、审计产物 | 状态口径分散，缺运行/决策/学习统一 ID |
| 规划与编排层 | 依赖、文件归属、并行度、预算、超时、恢复和升级 | Planner/PM/Worker 角色 | 缺机器可执行任务契约和持久化状态机 |
| 能力层 | 角色、工具、Skill、Prompt、Provider 与模型 | 已有多角色、Skill/Prompt 版本基础 | 缺能力注册表、选择策略、健康度和权限声明 |
| 执行与证据层 | 最小变更、真实 API、测试、RAG eval、日志、成本、产物追溯 | 真实 API 约束、部分运行快照/证据链 | 缺统一 run manifest 和跨层评估仪表盘 |
| 学习与发布层 | 归因、候选改进、回放、影子运行、灰度、晋级、回退 | Prompt 发布/Diff、部分回归 | 缺组件级评估集、晋级标准和自动回退 |

### 3. 三个套嵌闭环

1. **任务内闭环（分钟至小时）**：规划 -> 实施 -> 测试 -> 修复 -> 验收；只解决当前任务。
2. **工程闭环（天至迭代）**：失败聚类 -> 缺口识别 -> 更新角色/工具/Skill/契约 -> 回放 -> 晋级；降低同类人工干预。
3. **产品闭环（周至月）**：用户任务 -> 线上 RAG 指标/反馈 -> 数据和检索改进 -> 离线/在线评估 -> 发布；确保“代码做对”转化为“用户问题解决”。

### 4. 自治等级建议

| 等级 | 系统权限 | 典型任务 |
|---|---|---|
| L0 建议 | 只读分析，人工执行 | 架构选型、安全策略 |
| L1 有界执行 | 在独占文件与预批准命令内变更，人工验收 | 单模块缺陷、文档同步 |
| L2 自主闭环 | 自主计划、执行、测试和有界重试，通过门禁后提交审批 | 契约明确、可回退的常规改动 |
| L3 受控发布 | 可自动影子/灰度发布并按阈值回退 | 低风险 Prompt/检索配置升级 |
| L4 策略自演进 | 根据长期证据生成并晋级策略 | 仅限成熟、可沙箱、可自动回退的组件 |

推荐初始目标为 **大部分开发任务 L2，Prompt/检索参数 L3，架构、公共 API、安全、外部依赖保持 L0/L1**。不建议一开始追求 L4。

## 组件演进逻辑

### 统一组件契约

每个角色、工具、Skill、Prompt 或评价器都应声明：

- `componentId/version/owner/status`；
- 适用场景、输入/输出 Schema 和不适用场景；
- 所需权限、工具、模型、数据和成本上限；
- 超时、重试、幂等、降级、人工升级和回退策略；
- 测试集、历史基线、通过阈值和已知限制；
- 变更原因、评估结果、晋级/废弃时间和回退点。

### 卡点到组件升级的闭环

```text
运行失败或人工接管
  -> 结构化分类（目标/上下文/计划/权限/工具/知识/生成/评价/基础设施）
  -> 归因到最小可替换组件
  -> 将真实失败脱敏后加入回归集
  -> 生成组件新版本候选
  -> 离线回放与对照评估
  -> 影子运行/灰度
  -> 指标达标后晋级，退化则自动回退
```

只有同时满足“更高成功率、不降低安全/质量下限、成本和延迟在预算内”才能晋级。单次任务成功不是更新 Skill 的足够证据。

## SMART 分阶段方案

### Phase 0：基线与决策冻结（1 周）

| 候选任务卡 | 1–4 小时产物 | 可量化验收 |
|---|---|---|
| `AUTONOMY-ARCH-01` | 自治等级、人机决策矩阵、非目标 | 覆盖架构/API/安全/性能/成本/数据写入等至少 8 类决策 |
| `AUTONOMY-AUD-01` | 当前角色/工具/Skill/工作流能力清单 | 每项有 owner、版本、权限、测试、缺口和重复度 |
| `AUTONOMY-METRIC-01` | 自治基线和 10–20 个代表任务样本 | 量出端到端成功率、首次通过率、人工介入时长、重开率、成本和周期 |

**里程碑 M0**：人类确认自治边界和成功指标，没有评估基线不进入平台实现。

### Phase 1：最小工程闭环（2 周）

| 候选任务卡 | 1–4 小时产物 | 可量化验收 |
|---|---|---|
| `AUTONOMY-DES-01` | Run/Task/Decision/Artifact/Evidence 契约、状态机和伪代码 | 正常、重试、取消、升级、恢复路径都可表达 |
| `AUTONOMY-EVAL-01` | 代码 + 真实 API + RAG eval 的分层验收契约 | 每类任务至少一个确定性判定器，无证据不能完成 |
| `AUTONOMY-ORCH-01` | 在既有编排上实现有界重试、预算和升级原型 | 选定 3 类低风险任务，完整保存运行证据 |
| `AUTONOMY-TST-01` | 故障注入与真实 API 验收 | 超时、无效输出、工具不可用、权限拒绝、进程中断均有确定终态 |

**里程碑 M1**：代表任务端到端完成率达到基线目标，且没有未记录的人工接管、无限重试或证据缺口。

### Phase 2：能力组件化与选择（2–3 周）

| 候选任务卡 | 1–4 小时产物 | 可量化验收 |
|---|---|---|
| `AUTONOMY-REG-01` | 统一组件 Manifest/Registry 设计 | 角色/工具/Skill/评价器的元数据、版本和权限可查 |
| `AUTONOMY-ROUTE-01` | 基于任务类型、风险、能力和历史效果的选择策略 | 固定评估集上无权调用数为 0，路由决策 100% 可追溯 |
| `AUTONOMY-GOV-01` | 组件权限、成本、超时、并发和降级政策 | 超限必停，不可在 Prompt 或代码中绕过 |
| `AUTONOMY-CANARY-01` | 组件新旧版本影子对比 | 同一输入产出差异、质量、成本和延迟报告 |

**里程碑 M2**：组件可替换但任务契约不漂移；组件新版本不能直接成为默认版本。

### Phase 3：持续演进闭环（3–4 周）

| 候选任务卡 | 1–4 小时产物 | 可量化验收 |
|---|---|---|
| `AUTONOMY-FAIL-01` | 卡点分类法、失败信封和人工接管反馈 | 人工介入 100% 关联 runId、原因、动作和受影响组件 |
| `AUTONOMY-REPLAY-01` | 脱敏失败样本库和可重放评估 | 新版本必须通过历史阻断样本且无关键回归 |
| `AUTONOMY-PROMOTE-01` | 候选 -> 影子 -> 灰度 -> 默认 -> 废弃状态机 | 晋级和回退均有阈值、证据、审批人和不可变记录 |
| `AUTONOMY-RPT-01` | 周期效果报告 | 每周统计自主完成率、人工介入原因 Top N、回归、成本和发布效果 |

**里程碑 M3**：连续两个迭代显示人工介入率下降，同时质量、安全、成本和交付周期不退化；否则不得声称自治性提升。

## 关键不确定项与推荐

| 决策 | 推荐选项 | 备选 | 为何需要确认 |
|---|---|---|---|
| 首期自治范围 | 仅开发/测试环境 L2；生产发布保持人审 | 直接覆盖生产 L3 | 决定权限、审批和回退架构 |
| 试点任务 | Prompt/Skill 文件发布 + 小范围后端缺陷 | 全链路功能需求 | 试点需可回放、可回退且验收客观 |
| 成功主指标 | “无人介入的验收通过率”，质量/安全/成本为护栏 | 以交付速度为主 | 单独优化速度会放大重开和风险 |
| 人工门禁 | 风险分级，只审批架构/API/依赖/安全/性能/生产写入 | 所有任务完成后审批 | 后者会让人成为吞吐瓶颈 |
| 学习数据 | 仅脱敏的失败输入、证据、人工修订和结果 | 保存完整 Prompt/模型响应 | 涉及凭据、隐私、内部数据和模型内容边界 |
| 平台实现 | 先扩展现有 workflow/runner 契约，证明瓶颈后再引入新平台 | 立即引入外部 Agent 平台 | 新依赖和技术栈需人审，且迁移成本高 |
| 模型策略 | 任务按质量/成本/延迟路由，先固定可重现基线 | 所有任务始终使用最强模型 | 决定成本、重现性和供应商风险 |
| 策略晋级权 | 系统自动候选/回放/回退，人审晋级为默认 | 全自动晋级 | 在无成熟评估集前全自动会导致静默退化 |

## 风险与反模式

| 风险/反模式 | 表现 | 约束 |
|---|---|---|
| 角色通胀 | 每个问题都新增 Agent | 先判断是否只需扩展现有角色契约；用职责冲突和产物边界决定新角色 |
| Skill 变成长 Prompt | 无 Schema、测试、错误和版本 | 不满足组件契约不得发布 |
| 自己生成自己打分 | 模型声称完成但无可执行证据 | 确定性检查优先；LLM judge 只补充语义评估并定期人审校准 |
| 文档驱动假闭环 | 看板齐全但不能从运行证据重建状态 | 以 run manifest 和产物为事实源，报告仅为投影 |
| 无限重试 | 消耗 Token/时间仍不升级 | 每类错误固定重试上限、预算和终态 |
| 过早平台化 | 尚未知道真实卡点就重建编排平台 | 先用代表任务量基线，只为高频且可归因缺口建组件 |
| 指标被游戏化 | 为提高通过率而降低难度或跳过测试 | 主指标 + 质量/安全/成本/重开护栏联合判定 |
| 评估集污染 | 针对公开用例过拟合 | 保留隐藏集、时间切分集和新鲜失败集 |
| 上下文污染 | 将未验证结论或敏感数据写入长期记忆 | 仅将有来源、有状态、可过期、可撤销的事实晋级为记忆 |
| 并发写冲突 | 多 Worker 修改同文件或共享产物 | 计划阶段锁定文件归属，冲突文件串行，补丁前重读 |
| 把开发完成当 RAG 完成 | 单测绿但检索/引用/权限退化 | 真实 API + 固定检索集 + 引用与 ACL 断言 + 性能/成本基线 |

# 成熟 RAG 知识库任务切分与开发提示词

## 1. 使用边界

本文件不要求模型输出隐含的逐步思考链。模型应输出可审计的结论、依据、假设、变更文件、测试结果和未决风险。不得把“模型认为正确”当作事实证据。

任务切分遵循以下边界：

| 能力 | 适合由模型完成 | 必须由代码/规则完成 |
|---|---|---|
| 文本理解 | 主题、实体、关系、别名候选、摘要候选 | Schema 校验、ID 分配、证据绑定、失败隔离 |
| 语义判断 | 规则无法确定的候选分类和关系类型 | 发布状态、权限、版本、门禁、重试和幂等 |
| 检索辅助 | 查询改写、同义词候选、重排建议 | ACL 过滤、top-k、去重、超时、上下文预算 |
| 答案生成 | 基于给定证据生成回答草稿 | 引用映射、无证据拒答、敏感信息过滤 |
| 质量分析 | 对失败样本给出解释候选 | 指标计算、阈值判断、回归比较和发布阻断 |

模型输入必须包含 `sourceSnapshotId`、`chunkId`、证据文本和适用版本；模型输出必须是结构化 JSON，所有实体和关系都必须带证据片段或明确 `uncertain` 状态。

## 2. 分解逻辑

1. 先做状态和安全边界：错误发布或数据泄露的损失高于召回不足。
2. 再冻结 lineage 和 Schema：没有稳定 ID，模型输出无法复现和合并。
3. 再做最小语义抽取：模型只产生候选，代码负责校验、归一化和落库。
4. 再做混合检索和引用闭环：检索必须能回到稳定证据，不能直接依赖模型记忆。
5. 再做评测和发布门禁：以固定问题集决定是否可发布，而不是以任务是否结束决定。
6. 最后做增量、性能、多模态和在线反馈：这些能力建立在 P0 闭环稳定之后。

## 3. 角色开发提示词

### 3.1 Planner

```text
你是本仓库的 Planner。基于 REQ-KGO-33 和 TASK-RAG-KG-ROADMAP-01，把目标拆成 1~4 小时的 SMART 原子任务。
每个任务必须写清：目标、输入、输出文件、依赖、不可修改范围、验收指标、需确认的架构决策。
不要把模型调用、外部数据库或公共 API 视为已获批；未确认的内容标为 deferred。
输出任务卡和关键路径，不输出隐藏思考链，只输出结论和依据。
```

### 3.2 Architect

```text
你是资深架构师。为当前 RAG 子任务给出最小可行设计，优先复用现有文件产物、Repository 和 API。
请按“现状事实 -> 约束 -> 方案 -> 取舍 -> 接口/Schema -> 伪代码 -> 验收 -> 风险”输出。
明确哪些判断由规则完成、哪些判断可交给模型、模型失败如何降级。
禁止擅自引入 Neo4j、Milvus、pgvector、Elasticsearch、新模型或改变公共 API；如确有必要，列为待确认 ADR。
```

### 3.3 Backend：状态与发布门禁

```text
你是 Backend Worker。实现状态/lineage/release 子任务。
要求：keyword_analysis、formal_knowledge、index、evaluated、published 状态不可混淆；状态迁移必须有服务端守卫、结构化阻断原因、幂等和审计事件。
关键词图谱不能被标记为正式 RAG 知识库；knowledge/entity/relation/index 缺失时必须返回明确状态。
先读取目标文件和设计文档，再提交接口、伪代码、实现和测试；不得修改无关文件。
验收需覆盖非法状态迁移、重复请求、发布阻断、回滚和错误分类。
```

### 3.4 Backend：Ontology 与模型抽取适配

```text
你是 Backend Worker，负责 ontology 和模型抽取适配。
模型只输出实体/关系/别名候选，不允许直接写正式图谱；每条记录必须绑定 sourceResourceId、chunkId、evidenceText、offset、schemaVersion 和 confidence。
代码必须完成 canonical ID、Schema 校验、关系两端存在性、证据完整性、版本范围和失败隔离。
单条失败写入质量问题并继续批次；清单不可验证或产物准入失败才终止批次。
模型超时、非 JSON、Schema 错误和低置信结果要分别分类，不能统一显示为模型服务错误。
```

### 3.5 Backend：混合检索与引用

```text
你是 Backend Worker，负责检索垂直闭环。
先定义统一的 sparse、dense、rerank、context assembly、citation 和 abstention 接口，再实现适配器。
所有召回结果必须经过 ACL、数据集、版本和有效期过滤；候选合并、去重、top-k、超时和上下文预算由代码控制。
模型可以提供 query rewrite 或重排建议，但不能绕过过滤和证据校验。
每次查询记录 queryId、graphVersionId、indexVersionId、embeddingVersion、过滤条件和证据 ID；普通日志不得写入完整敏感正文。
没有足够证据时返回结构化 abstain，不生成无来源答案。
```

### 3.6 Test Engineer：评测与故障注入

```text
你是 Test Engineer。为 RAG 子任务建立真实后端 API 验收和离线回归。
先构造隔离数据集，不修改目标生产批次；至少覆盖关键词回退图、正式知识、空知识、单 chunk 失败、模型非 JSON、ACL 越权、版本失效和无答案。
评测报告必须包含 Recall@K、MRR/NDCG、context precision/recall、citation correctness、faithfulness/groundedness 和 abstention。
每个失败样本必须能下钻到 resourceId/chunkId/evidence 或明确说明为什么缺失。
不要只测 HTTP 200；验证状态、产物、统计不变量、审计事件、幂等和回滚结果。
```

### 3.7 Frontend Worker：状态和证据体验

```text
你是 Frontend Worker。实现中文的加工状态、发布门禁、检索结果和证据下钻界面。
明确区分“关键词分析完成”“正式知识未构建”“索引未就绪”“评测阻断”“已发布”。
错误提示必须来自后端错误分类，不把所有失败显示为模型不可用。
证据展示只使用后端返回的稳定 ID、片段和定位；stale、missing、unlinked 必须显式显示，不按名称猜测来源。
保持现有页面交互和响应式布局，先写接口契约和状态矩阵，再修改组件并运行生产构建。
```

### 3.8 Reviewer：安全、质量和可维护性审查

```text
你是代码审查者。只基于当前分支与设计文档审查变更，按安全、正确性、竞态、可维护性和测试稳定性分类。
优先查：状态越级发布、ACL 绕过、证据漂移、模型输出未经 Schema 校验直接落库、失败被统计成空知识、敏感正文进入日志、重试重复写入。
每个发现给出文件/行号、复现条件、影响、修复建议和是否阻断发布；没有证据的猜测标为待核验，不当作缺陷结论。
```

## 4. 模型调用通用约束

- Prompt、规则、阈值和模型参数使用 Registry/配置文件，不散落在业务代码中。
- 输出采用严格 JSON Schema；解析失败不得自动修复后静默落库。
- 模型结果必须保留 `modelVersion`、`promptVersion`、`inputHash`、`outputHash` 和调用状态。
- 不把模型的解释文字当作证据；证据只能来自源文档和稳定偏移。
- 不允许模型决定权限、发布、删除、回滚、批次终止或最终质量门禁。
- 生产大批次默认只读，写入型验收使用隔离数据集。

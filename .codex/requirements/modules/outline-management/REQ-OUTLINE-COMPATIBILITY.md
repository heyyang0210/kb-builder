# REQ-OUTLINE-COMPATIBILITY：管理员手册大纲兼容需求

> documentType: requirement
> moduleId: outline-management
> owner: Product Manager
> 需求编号：REQ-OUTLINE-COMPATIBILITY
> 所属模块：大纲管理（outline-management）
> 状态：已规划，待分阶段实施
> 需求负责人：Product Manager
> 创建日期：2026-08-17

## 1. 为什么做

数据库管理员希望把已有的管理员手册知识点大纲上传到 YashanDB 知识库文档生成器，并尽快进入知识文档生成。但当前样本采用 `# / ## / ###` 标题树，现有上传解析仅识别特定列表格式，可能出现“上传成功但知识点为 0”的假成功。用户既不知道哪里不符合要求，也无法判断自动转换是否误解了领域层级。

该需求要把一次性的人工改稿问题转化为可复用的产品能力：先让当前文件安全可用，再逐步提供统一解析、可定位诊断、落库前预检、差异确认、评分和修改建议。

## 2. 用户与价值

| 用户 | 当前困难 | 期望结果 | 业务价值 |
|---|---|---|---|
| 数据库管理员 | 手册标题树无法直接上传，报错或假成功后难以修复 | 获得不覆盖原文的合规副本和明确修改清单 | 缩短从现有手册到知识文档的准备时间 |
| 知识库运营人员 | 无法在落库前判断结构是否完整 | 预检时看到格式、计数、阻断项和结构差异 | 降低无效大纲进入生成链路的概率 |
| 规则维护者 | 同类问题反复人工判断，规则变更难回归 | 规则、诊断和评分均带版本及证据 | 支持可审计升级、回归和回退 |

## 3. 需求范围

### 3.1 必须提供

- 保持原始管理员手册大纲只读，生成独立的规范副本、映射报告和未决项清单。
- 识别标准 Markdown 与 `# / ## / ###` 标题树方言，并归一化为统一的大纲结构。
- 对空树、0 知识点、重复 ID 和必填字段缺失给出结构化阻断诊断。
- 诊断包含稳定错误码、中文说明、原文行号或字段路径、证据和修改动作。
- 对歧义节点显式列入 `unresolvedMappings`，不得静默丢弃、提升或虚构领域内容。
- 在正式落库前提供无副作用预检、转换差异和用户确认；确认内容变化或规则版本变化后，旧确认失效。
- 按版本化规则输出评分和修改建议；建议必须有证据和可测验收条件。
- 使用真实后端 API 验证上传结果、失败无残留和预览树与落库树一致。

### 3.2 本次不提供

- PDF、Word、图片或任意纯文本直接转换为知识点大纲。
- 自动补写未经用户确认的 YashanDB 领域事实，或替代专业事实审核。
- 修改知识点正文生成模板、生成模型、检索链路或 PingCode 素材上传链路。
- 一次覆盖所有 Markdown 方言；新方言需按版本化规则单独准入。

## 4. 用户主流程

1. 用户选择现有大纲文件，系统识别输入方言并执行预检。
2. 系统展示解析计数、阻断项、行级诊断、转换差异和未决映射。
3. 可自动处理的问题生成规范结构；歧义内容等待用户确认或修订。
4. 系统按规格评分并给出有证据的中文修改建议。
5. 只有无阻断项、满足准入阈值且用户确认的版本才能正式上传。
6. 正式上传后，用户看到的知识点树必须与确认版本一致。

P1 阶段先以离线规范副本实现步骤 2 至 4 的最小闭环；后续阶段逐步纳入产品界面。

## 5. 验收标准

| 编号 | 验收条件 |
|---|---|
| AC-01 | 原始 `outlines/yashan数据库管理员手册知识点大纲.md` 未被修改，转换产物可追溯到源行和源路径 |
| AC-02 | 每个源标题进入标准树或未决映射，静默丢失节点数为 0 |
| AC-03 | 合规副本真实上传后 `kp_count > 0`，列表、详情和转换树一致 |
| AC-04 | 原样本不再出现 `success=true` 且 `kp_count=0`；失败不产生正式文件或 metadata 半成品 |
| AC-05 | 标准 Markdown、标题树及既有 JSON/CSV 合格样本通过真实 API 回归 |
| AC-06 | 每个阻断项均有错误码、中文说明、行号或字段路径、证据和修改动作 |
| AC-07 | 未确认、有阻断项、内容摘要变化或规则版本变化时不能正式落库 |
| AC-08 | 同一输入和同一规则版本的解析、评分结果稳定，规则可回归和回退 |
| AC-09 | 无阻断项、格式与可解析性 20/20、总分不低于 80，才可进入批量生成 |

## 6. 业务指标

| 指标 | 目标 |
|---|---|
| 0 知识点误成功数 | 0 |
| 静默丢失节点数 | 0 |
| 诊断可定位率 | 100% |
| 方言识别准确率 | 标注样本中不低于 95% |
| 评分稳定率 | 同输入、同规则版本达到 100% |
| 合格大纲结构类生成失败率 | 低于 1% |

预检闭环成功率和人工修订率在 P4 建立基线，P5 起按 `specVersion`、`ruleVersion` 和方言持续观察。

## 7. 产品与工程约束

- 服务端是解析、诊断和放行的单一事实源，前端不得维护另一套判定规则。
- 解析规则、阈值、文案键、评分权重和建议模板必须版本化配置；硬编码例外需登记待办。
- 校验必须发生在正式文件和 metadata 写入之前。
- 前端展示使用中文，稳定错误码与中文文案解耦。
- 设计先于实现；新增模块、公共 API 变更、外部依赖及安全/性能变更需按门禁审批。
- 测试必须启动真实后端并调用 API，纯函数测试不能替代端到端验收。

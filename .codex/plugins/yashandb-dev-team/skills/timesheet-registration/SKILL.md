# 工时登记

把用户确认的实际工作整理成可核验的工时记录，并在确认后登记到指定人员名下。工时属于责任记录；提交内容必须来自用户提供的信息或可核实的工作证据。

## 流程

1. 明确登记人员、日期范围和目标系统。按用户时区计算“本周”等相对日期，并在草稿中写出具体日期。
2. 收集工作事项和时长。可查看当前工作目录中的提示词/工作日志、提交记录、任务记录，以及系统现有工时；提交或时间戳只能证明活动，不证明实际投入时长。
3. 读取系统中的人员、项目、工时字段配置、标签选项和目标人员在该日期范围内的既有记录。优先使用受支持的只读 API；没有筛选 API 时，在本地过滤结果，输出和保存时只保留目标人员及所需字段。
4. 将内容整理为逐条草稿，至少包括人员、日期、项目、工时、工作描述；系统要求的工时类型、人力类别、标签、关联任务也列明。区分已知事实和待确认项。
5. 在草稿中检查日期、总时长和记录粒度。只有用户明确给出标准工作日总时长或剩余时长时，才计算“其余时间”；不能默认每天为 8 小时。不同项目的工作分别归属到对应项目，不将讨论会默认为主开发项目。
6. 把完整草稿和未决字段展示给用户，等待用户确认具体记录。宽泛的“登记本周工时”不授权编造时长、项目或标签；若用户已确认此前展示的完整草稿，可按该草稿执行，不重复确认。
7. 确认后再次读取目标日期的现有记录，防止草稿展示后出现重复。若存在相同记录，先报告并等待用户选择跳过或修改；不自行覆盖、删除或重复创建。
8. 通过系统支持的写入方式提交确认的记录。遵守 UI 和 API 的必填契约；必填选项缺失、项目无法匹配、用户身份不确定或 API 行为与 UI 冲突时，停止写入并说明阻塞，不用虚构值或未经确认的 API 绕过。
9. 每条写入后检查 HTTP/API 结果；随后重新读取目标人员和日期范围的记录，核实日期、项目、工时、标签和描述。任何部分失败都报告已成功和未成功的记录，不对失败请求盲目重试。
10. 汇报总条数、总工时、记录 ID、项目归属、验证结果及尚存限制。

## 记录原则

- “本周”按当前日期、用户时区解释；默认周一至周日。只登记用户请求覆盖的日期，不把未来日期或未说明的休息日补成工时。
- 小时数只采纳用户提供的实际值，或系统中明确存在且用户确认的工时记录。不能根据 commit 数、对话数、工作跨度或通常工作日推算投入。
- 描述用简洁、可追溯的工作结果；会议和讨论如有独立项目，应记录到对应项目。多项工作合并时，在描述中标明各事项及其小时分配。
- 发现已有记录时检查人员、日期、项目、工时和描述。不能只以“同一天”认定重复，也不能因查询无结果就跳过写后回读。
- 不将其他用户的工时明细带入回答。处理未过滤的列表响应时只在本地筛选目标用户和日期。
- 写入只覆盖用户确认的人员、记录内容和系统字段。确认登记不等于授权修改已有记录或清理历史数据。

## 当前工时系统参考

用户提供了项目管理与工时系统的 `/my-workbench` 页面。使用时从用户给出的主机读取前端和 API 行为，不假设地址、字段或配置在其他实例上相同。已观察到该实例包含 `GET /api/users`、`GET /api/projects`、`GET /api/timelog-configs`、`GET /api/tags`、`GET /api/timelogs` 与 `POST /api/timelogs`；实际请求前仍需核对当前实例的契约。

该实例的登记表单要求人员、日期、工时和标签，工时范围为 0.5 至 24 小时；可见的人力划分、性能类型、工单及自定义字段由项目配置决定。项目“知识中心管理平台”曾无专属工时配置和可用标签；此事实不能推广到其他项目或时点。遇到这种情况，先说明选项缺失并确认允许的登记方式。

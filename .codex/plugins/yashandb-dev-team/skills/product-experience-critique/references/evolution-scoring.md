# 历史运行评分与 Skill 演进

## 何时启用

仅在用户要求评价 Skill 是否需要演进、根据历史运行记录评分或演进后复评时启用。本规范不改变普通页面评审不输出综合分数的默认行为。

## 证据盘点顺序

按以下顺序建立样本清单，并记录缺失项：

1. `prompt.md` 中完整的产品体验评审和 Skill 自演进记录。
2. `runtime/skill-evolution/product-experience-critique/runs/` 下的截图、录屏、运行摘要和失败产物。
3. `runtime/test-results/` 下与评审页面对应的 API、E2E、响应式和错误恢复结果。
4. Skill `evals/` 的语料、基线和外部运行结果。
5. 当前 Skill、references、Memory 和脚本的变更历史。

历史记录只能证明记录中实际出现的行为。没有结果文件、截图或真实 API/E2E 证据时，结论降级为“未验证”，不得按设计目标补齐。

## 评分口径

使用 100 分制，但分别报告方法能力和真实运行结果：

| 维度 | 权重 | 评分问题 |
|---|---:|---|
| 触发与边界 | 15 | 是否正确触发、退出和保持 `implementationAuthorized: false`？ |
| 设计与事实路由 | 15 | 是否查到当前有效设计，并区分设计目标、实现和运行事实？ |
| 证据纪律 | 15 | 是否按截图、代码、API、E2E 的能力边界下结论？ |
| 产品聚焦与优先级 | 15 | 是否提炼一个核心矛盾，最多三个核心问题，并做删除/简化/强化取舍？ |
| 整改可执行性 | 15 | 是否给出对象、收益、代价、风险和验收，结构性问题有前后界面对照？ |
| 运行闭环 | 15 | 是否覆盖加载、空态、失败、恢复、权限、移动端和真实 API/E2E 结果？ |
| 学习与演进 | 10 | 是否记录观察、候选经验、验证结果，且不把单案例直接升级为通用规则？ |

每个维度按 0、0.5、1 三档计分：`权重 × 档位`。分数表示 Skill 在对应历史样本上表现出的能力，不表示页面本身质量。

- “演进前方法分”与“演进后方法分”可在同一评分表下对比。
- “历史运行基线”只表示既有样本对旧版 Skill 的支持程度，不能重命名为“演进后真实运行分”。
- 没有新的独立真实评审和整改复测时，“演进后真实运行分”必须写为“待验证（N/A）”，不得用历史分数、惩罚分或估算分代替。
- 任何总分必须等于各维度得分之和；不一致时报告无效，不得用于演进结论。

另报“实际运行证据覆盖率”：已被真实截图/API/E2E/用户反馈支持的评分维度权重之和 / 100。覆盖率低于 70% 时，综合分数必须标记为低置信度。

## 演进判定

- 只修复重复出现的缺口，或单案例但涉及权限、安全、错误事实、不可恢复操作的高影响缺口。
- 演进前后使用同一评分表；新增维度不得为了抬高分数而改变历史分母。
- 演进后若只有静态 Eval 通过，报告“方法分提升、运行分待验证（N/A）”；至少一次独立真实评审和一次复测后，才可报告演进后运行分及其变化。
- 新增候选经验写入 `runtime/skill-evolution/product-experience-critique/candidates/`，包含适用条件、不适用条件、反例和效果证据；正式 Memory 仍需 Eval 和人工确认。
- 评分报告写入 `runtime/skill-evolution/product-experience-critique/evaluations/`，不要把动态分数放进正式参考文档。

## 输出最小结构

```text
样本范围与证据限制
评分表（演进前）
重复缺口与演进决策
修改文件与回归证据
评分表（演进后方法能力）
演进后真实运行分（有新独立评审与复测时填分，否则填 N/A）
真实运行仍待验证项
```

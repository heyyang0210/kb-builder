# 设计上下文路由

评审前把 `.codex/知识中心建设平台/` 作为所有模块前置设计的统一发现入口，而不是为某个页面维护固定文档映射。设计提供目标和约束，当前代码与运行证据提供实现事实；不得把设计目标写成已实现能力。

## 动态发现流程

1. 读取 `.codex/知识中心建设平台/README.md`，确认工程档案边界。
2. 从当前页面、代码和运行证据提取检索词：页面名称、用户角色、业务对象、导航名称、路由、接口、状态和稳定业务术语。
3. 使用这些词及其业务同义词，在整个 `.codex/知识中心建设平台/` 中搜索候选文档；先看目录 README 和文档标题，再按需查看正文命中位置。
4. 根据相关性选择最小必要上下文：直接定义当前业务的设计优先，跨模块约束再补充平台、前端、认证、权限、数据或外部集成设计。
5. 文档冲突时，以目录索引登记的当前正文、文档状态和更明确的业务边界判断；无法消解时标记待确认，不自行选取方便的结论。
6. 测试和验收报告只用于确认已验证行为，不替代设计；开发任务和进度报告只提供时点信息，不作为稳定产品规则。

不要因为以前评审过某个模块，就默认复用上次的文档集合。页面能力、设计目录或业务边界变化后必须重新发现。

## 三个通用维度

三个维度分别借鉴任务导向产品设计、领域建模和可靠性治理的通用做法，适用于所有页面，不为特定模块定制检查表。

### 1. 用户决策

回答“谁在什么场景下，为了什么结果使用页面”：

- 主要角色、触发场景、核心任务和成功结果；
- 用户需要做出的判断、选择或承诺；
- 任务频率、风险和时间压力；
- 页面术语是否使用角色熟悉且稳定的业务语言。

### 2. 领域事实

回答“页面依靠什么事实做出正确表达”：

- 核心业务对象、关系、状态机和模块边界；
- 权威事实源、稳定标识、数据时效和一致性要求；
- 权限、业务规则、前置条件和操作后果；
- 目标设计、当前实现和运行证据之间的差异。

### 3. 运行闭环

回答“正常、异常和变化发生后，用户能否完成闭环”：

- 加载、就绪、空数据、失败、无权、过期和部分成功是否可区分；
- 异常是否说明影响、证据、责任和恢复动作；
- 操作是否可确认、可追踪、可重试、可恢复和可验收；
- 是否具备与风险相匹配的审计、反馈和端到端验证。

找不到有效设计时，在证据限制中明确说明，并基于当前代码、真实页面和通用产品原则降低结论强度。

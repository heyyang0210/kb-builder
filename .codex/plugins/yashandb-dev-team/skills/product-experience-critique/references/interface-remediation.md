# 前端整改与简图

整改方案应让开发者看得出页面从当前形态如何演进到建议形态，而不只写“增强层级”“优化体验”。简图用于比较结构、关系或状态变化，不用于装饰报告。

## 何时必须提供简图

满足任一条件时提供一组最小必要的“当前界面 / 建议界面”对照简图：

- 页面信息架构或模块顺序需要重组；
- 两个以上区域的主次关系发生变化；
- 核心流程、状态切换或异常恢复需要调整；
- 用户明确要求界面整改、布局方案或示意图。

局部文案、单个控件、颜色或间距问题通常不画图。

## 整改表达

重要整改按以下顺序表达：

1. 整改目标：改变哪个用户判断或任务结果。
2. 当前界面简图：基于真实页面、截图或代码，压缩表达当前区域顺序、主次和关键操作；证据看不到的部分不得补画成事实。
3. 建议界面简图：在相同粒度下表达保留、删除、合并、移动和新增的区域，以及主操作和异常恢复入口。
4. 变化说明：逐项说明结构、交互、状态和术语发生了什么变化。
5. 优化后的优点：说明每项变化如何降低认知负担、缩短任务路径、减少错误判断或增强业务闭环，不能只写“更美观”。
6. 移动端原则：说明内容优先级和重排，不机械缩小桌面布局。
7. 不建议改动：保护已经有效的结构，防止整改范围失控。
8. 验收：以可观察行为证明改善成立。

## 简图规则

- 使用紧凑 ASCII 线框、流程或状态图，选择最能解释问题的一种，并保持当前图和建议图的抽象粒度一致。
- 当前图用于揭示问题结构，建议图用于表达整改结果；两者必须与核心问题和建议逐项对应。
- 标出主结论、主任务、风险信息和关键操作；不追求像素级尺寸。
- 一般只提供一组桌面对照图；只有状态流无法在线框中表达时，再增加一组当前/建议状态流。
- 不虚构当前不存在的业务能力；拟议能力标注为建议。

示例：

```text
当前界面
┌ 页面标题                              ┐
│ 多个同权重摘要                         │
├──────────────────────────────────────┤
│ 信息列表，主任务和风险入口不突出       │
└──────────────────────────────────────┘

建议界面
┌ 页面标题                    [主操作]  ┐
│ 核心结论 / 首要任务 / 风险             │
├────────────────┬─────────────────────┤
│ 主任务区        │ 证据、详情与恢复入口 │
├────────────────┴─────────────────────┤
│ 次要信息 / 历史记录                   │
└──────────────────────────────────────┘
```

对照图后必须用文字解释建议界面的优点，以及这些优点分别解决了哪个已观察问题。

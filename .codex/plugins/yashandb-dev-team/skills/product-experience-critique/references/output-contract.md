# 评审输出契约

根据问题复杂度压缩内容，但保留以下信息。

## 一句话判断

说明页面当前是否支持核心任务，以及它更像什么、还缺什么。

紧接着给出“核心矛盾”：用一句话说明当前体验最主要的冲突。明确推荐先做什么，以及在核心问题解决前不建议做什么。

## 评审前提

- 页面和主要角色；
- 核心任务；
- 证据等级和限制；
- 乔布斯视角默认启用；如用户明确关闭，说明关闭原因。

## 优点和核心问题

优点只写当前证据支持、值得保留的内容，通常不超过 3 项。

核心问题最多 3 个，只收录 P0/P1 或直接影响核心任务的问题，按用户影响而不是评审维度排序。每个核心问题包含：

```text
级别：P0/P1/P2/P3
观察：当前可见事实
影响：对哪个角色和任务造成什么影响
推断：可能原因，如果尚未证实则明确标记
建议：应如何处理
验收：如何证明改善成立
```

没有可靠推断时省略“推断”，不要机械填充。P2/P3 或不改变核心判断的问题进入“次要问题”紧凑表格，不与核心问题平铺。

## 前端整改方案

用户要求整改意见，或核心问题涉及信息架构、模块关系、流程和状态变化时，输出：

- 整改目标；
- 页面结构和关键交互调整；
- 状态与术语调整；
- 当前前端界面简图；
- 建议优化后的前端界面简图；
- 优化后界面的具体优点，以及它们分别解决的核心问题；
- 移动端重排原则；
- 不建议改动的有效部分。

简图要求见 [interface-remediation.md](interface-remediation.md)。局部问题不强制画图。

## 整改路线

只列实际建议执行的动作，按 P0 到 P3 排序，说明用户收益、实施成本、影响面和前置决策。默认用“删除 / 简化 / 强化”总结产品取舍，但不为了形式完整强行填满；用户明确关闭乔布斯视角时省略。

## 结论边界

```yaml
implementationAuthorized: false
evidenceLimits: []
unresolvedQuestions: []
```

这个 YAML 是沟通摘要，不代表要创建任务状态文件。

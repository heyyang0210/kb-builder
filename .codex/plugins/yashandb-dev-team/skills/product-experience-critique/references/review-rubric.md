# 产品体验评审维度

默认不生成综合百分制分数。每个维度使用“严重问题 / 重要问题 / 改善机会 / 已达预期”判断。

| 维度 | 核心问题 | 级别 |
|---|---|---|
| 用户与目标 | 页面为谁服务，首要任务是否清晰 | 最高 |
| 产品聚焦 | 核心任务是否被低频或无关内容干扰 | 最高 |
| 业务完整性 | 用户能否完成查询、操作、确认、恢复和结果查看 | 最高 |
| 信息层级 | 当前状态、主操作、关键数据和风险的顺序是否清晰 | 高 |
| 核心流程 | 步骤是否可预期、无重复录入、可返回和可恢复 | 高 |
| 状态反馈 | loading、ready、empty、error、permission-denied、success 是否准确互斥 | 高 |
| 端到端一致性 | 页面、URL、API、数据和业务术语是否表达同一事实 | 高 |
| 术语与认知负担 | 文案是否使用角色熟悉且稳定的业务术语，是否暴露内部键、技术缩写或增加不必要解释成本 | 高 |
| 感知性能 | 稳定框架、主任务就绪、局部更新和真实耗时是否合理 | 高 |
| 可访问性 | 键盘、焦点、对比度、标签、语义和错误通知是否可用 | 硬约束 |
| 视觉工艺 | 对齐、间距、密度、排版、图标和布局稳定性是否一致 | 中 |
| 实施价值 | 预期用户收益是否值得代码、契约、测试和维护代价 | 高 |

## 分级整改

- P0：阻断核心任务，产生错误事实、安全/权限风险或不可恢复后果。
- P1：核心流程、信息层级、状态反馈或业务完整性有明显缺口。
- P2：操作效率、感知性能、视觉一致性或可访问性改善。
- P3：不影响主任务的工艺打磨。

对每个 P0/P1 问题必须给出可观察验收方式。

## 术语检查

- 页面标题、导航、字段、状态和操作使用同一套业务概念。
- 优先使用项目设计和业务人员已经采用的中文名称，不为“专业感”引入新的近义词。
- 内部模块键、数据库字段、错误码和技术缩写只在能帮助定位或处置时展示，并给出用户可理解的解释。
- 操作文案表达用户结果，例如“重新验证连接”，不只表达技术动作，例如“重跑探针”。
- 状态文案必须能指导判断；“异常”“失败”之外说明影响和下一步，但避免长段解释挤占主任务。

# 知识中心产品体验评审

为当前知识中心项目输出有证据、有取舍、可验收的页面体验评审。默认只评审，不修改代码、设计文档或运行数据。

## 模式和边界

- 用户要求“评价页面”“分析优缺点”“UI/UX 评审”“给出整改意见”或“从产品角度审查”时使用本 Skill。
- 纯 CSS 局部修改、后端故障定位、数据库任务、用户已明确方案的实现任务不使用本 Skill，除非同时要求产品体验评审。
- 前端页面评审默认读取并应用 [references/jobs-lens.md](references/jobs-lens.md)，从产品聚焦、做减法、端到端一致性和细节可信度进行取舍。用户明确要求“常规评审”“不使用乔布斯视角”或仅做指定的合规检查时关闭该视角。
- 乔布斯视角是默认产品方法，不是名人语气模仿；不得使用名人口吻，也不得以“极简”为由牺牲业务完整性、权限、审计、风险和恢复能力。
- 评审不等于实施授权。用户只要求评审时，输出方案后停止；明确要求“按方案修改”时，将其视为新的开发任务，重新路由。

## 必要上下文

1. 先读取 [references/project-context.md](references/project-context.md)，确认页面所属模块、主要角色和核心任务。
2. 读取 [references/design-context-routing.md](references/design-context-routing.md)，在整个 `.codex/知识中心建设平台/` 中根据当前页面、业务对象、路由、接口和术语动态发现相关设计。不要把模块绑定到单一固定文档，也不要一次加载全量设计。
3. 根据页面类型读取 [references/review-rubric.md](references/review-rubric.md) 的对应部分。所有模块都从动态发现的有效设计中提取领域约束，不在 Skill 内维护逐模块规则百科。
4. 根据证据类型读取 [references/evidence-levels.md](references/evidence-levels.md)。
5. 查询 [memory/index.md](memory/index.md)，只读取与当前页面类型和现象相关的 Memory，不一次加载所有案例。
6. 当前页面、当前代码和有效设计始终优先于历史 Memory；冲突时标记待确认，不得猜测。
7. 用户要求“根据历史运行记录评分”“评估 Skill 是否需要演进”或“演进后复评”时，读取 [references/evolution-scoring.md](references/evolution-scoring.md)，盘点 `prompt.md`、`runtime/skill-evolution/product-experience-critique/`、测试结果和 Eval 证据；不得只按 Skill 文本自评。

## 评审流程

1. 明确评审对象、主要角色、使用场景、核心决策或任务、页面类型和证据等级。
2. 按“用户决策、领域事实、运行闭环”三个维度从有效设计提取会改变评审结论的约束；区分设计目标、当前实现和真实运行证据。
3. 默认使用乔布斯视角识别页面唯一核心价值，判断应删除、简化和强化什么；用户明确关闭时跳过这一取舍镜头。
4. 先归纳一个“核心矛盾”，再选出最多 3 个直接影响核心任务的关键问题。其余 P2/P3 问题进入紧凑清单，不与核心问题平铺。
5. 将每条内容标记为“观察”“推断”或“建议”。不得将推断写成已验证事实。
6. 按用户目标、产品聚焦、业务完整性、信息层级、核心流程、状态反馈、端到端一致性、术语认知、感知性能、可访问性和视觉工艺评审。
7. 优先指出影响核心任务的问题，不为了“显得严格”而强行给出大量修改建议。页面已达标时明确说明不建议大改。
8. 对每个重要建议说明修改对象、用户收益、实施代价、风险和验收方式。
9. 当整改涉及信息架构、模块关系、核心流程或关键状态变化时，读取 [references/interface-remediation.md](references/interface-remediation.md)，对照输出当前界面简图、建议界面简图及优化收益。
10. 使用 [references/output-contract.md](references/output-contract.md) 生成中文结果。默认不输出虚假精确的综合分数。
11. 评分模式下必须同时输出：历史样本范围、评分维度与权重、演进前方法分、由历史证据支持的演进决策、演进后方法分及尚未验证的部分。没有新的独立真实评审和复测时，演进后真实运行分必须记为“待验证”，不得填入数字，也不得把“新增规则”当作“真实运行改善”。

## 证据纪律

- 只有截图时，不评判真实性能、键盘操作、错误恢复或完整响应式行为。
- 只有代码时，不宣称真实页面、真实接口或用户流程已验证。
- 需要性能结论时必须有相同口径的实测数据；骨架、延迟显示或隐藏加载状态不等于性能改善。
- 证据不足不会阻止静态评审，但必须降低结论强度并显示证据限制。

## Memory 与自演进

- `memory/` 是经验证的项目经验，与 `references/` 平级；它不是 Codex 自动记忆机制，必须通过本文档路由。
- 修改案例只有在真实实施和验证后才能成为候选经验；抽象时必须包含适用条件、不适用条件和反例。
- 原始观察、候选经验和 Eval 运行结果写入 `runtime/skill-evolution/product-experience-critique/`，不直接写入正式 Memory。
- 正式 Memory 晋升需要通过 `evals/` 回归，生成变更提案，并由人类确认。不允许单个案例无门禁改写核心方法。
- 详细晋升规则见 [references/memory-governance.md](references/memory-governance.md)。
- 历史运行评分和 Skill 演进只能先写入 `runtime/skill-evolution/product-experience-critique/`；没有新的真实运行证据时，不晋升正式 Memory。

## 结果约束

- 中文展示，语气直接、专业、克制。
- 不用名人口吻、情绪化批评或无证据的绝对化判断。
- 可访问性、安全、权限和业务完整性是硬约束，不能为视觉简洁而牺牲。
- 最终明确 `implementationAuthorized: false`，除非用户在当前任务中明确授权实施。

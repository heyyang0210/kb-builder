##   [1. 总述](https://conf.yasdb.com/pages/viewpage.action?pageId=91780307#1-%E6%80%BB%E8%BF%B0)  

本特性需要支持，在一主多备自选举下，主库文件故障导致不可用时，触发failover，让备库升主，提升数据库高可用性。

###   [1.1 需求来源](https://conf.yasdb.com/pages/viewpage.action?pageId=91780307#11-%E9%9C%80%E6%B1%82%E6%9D%A5%E6%BA%90)  

当前YashanDB主备自动故障切换的条件为，备库与主库网络异常，心跳超时这一种情况。某些情况下，主库故障时，主备网络并不会异常，无法自动切换。

比如主库文件损坏，磁盘满等异常，这些情况下主库已经无法继续提供服务，目前只能人工介入，无法做到自动切换。

因此需要支持主库出现指定的非网络异常时，自动执行failover。

**部署形态为 主备(单机，分布式)**

##   [2. 接口](https://conf.yasdb.com/pages/viewpage.action?pageId=91780307#2-%E6%8E%A5%E5%8F%A3)  

|接口|接口表现|接口说明|是否涉及|
|:---|:---|:---|:---|
|配置参数|**FAILOVER_HEALTH_CONDITION**|立即生效，默认为空。可以设置为以下几个条件的组合：,- **CORRUPTED_CONTROLFILE**  ：表示主库写control文件失败后，自杀触发选举
- **INACCESSIBLE_LOGFILE**  ：表示主库写redo失败后，自杀触发选举
- **STUCK_ARCHIVER**  ：表示主库因磁盘满，归档失败后，自杀触发选举
- **DATAFILE_WRITE_ERRORS**  ：表示主库写脏页失败后，自杀触发选举
- **DATAFILE_NO_SPACE**  : 表示主库因磁盘满导致创建或写入数据文件失败
- ** SLICE_NO_SPACE**  : 表示主库因磁盘满导致创建或写入slice文件失败
,举例：,1. FAILOVER_HEALTH_CONDITION=INACCESSIBLE_LOGFILE,STUCK_ARCHIVER
1. FAILOVER_HEALTH_CONDITION=DATAFILE_WRITE_ERRORS
|是|
||**FAILOVER_ERROR_CONDITION**|立即生效，默认为空。最多可以设置16个错误码，当主库向客户端抛出指定的错误码时，自杀触发选举,某些错误码，可能会关联不同类型的系统错误码，比如写文件失败，如果系统错误码为28，表示磁盘空间不足。因此该参数中可以通过  *number1-number2*  的格式指定  **数据库错误码**  和  **系统错误码**  ，当抛出的数据库错误码和系统错误码都匹配时，才会触发自杀选举,举例：,1. FAILOVER_ERROR_CONDITION=2329,3232
1. FAILOVER_ERROR_CONDITION=311-28,311-22,897
|是|


##   [3. 规格与约束](https://conf.yasdb.com/pages/viewpage.action?pageId=91780307#3-%E8%A7%84%E6%A0%BC%E4%B8%8E%E7%BA%A6%E6%9D%9F)  

规格：

1. RTO：正常业务压力（备库接收延迟<1s，回放延迟<1s）下，RTO < 10s
1. 部署形态：仅支持单机/分布式一主多备，election选举下生效
1. 条件数量：FAILOVER_HEALTH_CONDITION 最多支持4个条件，FAILOVER_ERROR_CONDITION 最多支持16个错误码


约束：

1. 主备之间的FAILOVER_XXX_CONDITION 是独立的参数，不会自动同步
1. 在election选举下，FAILOVER_XXX_CONDITION 才会生效
1. 主库触发故障后，会尝试等待最多30s同步redo到某个备库
1. 集群暂不支持
1. 如果配置了monitor，并且monitor拉起数据库的间隔时间小于主备心跳超时时间，可能会在选举前将原主库拉起，参与选举并升主

- 主库在检测到condition failover对应的故障时，会设置一个故障状态，并将数据库设置为abnormal。该状态会通过心跳发送到可用的备机，备库可以感知到主库故障。

###   [4.2 ](https://conf.yasdb.com/pages/viewpage.action?pageId=91780307#42-%E7%89%B9%E6%80%A7%E5%8A%9F%E8%83%BD%E7%82%B92)    故障检测

#### 文件故障识别

```
/* 检测是否触发了failover条件，如果触发了，则进行redo发送等待和abort */
CodVoid checkFailoverHealthCond(AnkHanlder* handler, CondType type)

typedef struct StKernelAttr {
    ......
    CodBool   failoverHealth[4]; // 文件类故障failover使能参数
    CodUint32 failoverErrors[16]; // 错误码failover使能参数
} KernelAttr;
```

在dbwrFlushBlock，rdFlush，ctrlEndAtom中文件写失败后，调用checkFailoverHealthCond进行failover条件检查。

在归档线程失败，无法继续归档时，调用checkFailoverHealthCond进行failover条件检查。

#### 错误码识别

错误码有两种方案：

- 方案一，在codSetError里添加回调函数，通过回调函数判断，这个错误码是否会触发failover。这个可以覆盖所有错误码，但这个就必须要在ani_error里  **增加全局变量**  ，否则没有地方挂回调函数
- 方案二，在anrAckError里识别给客户端返回的错误码，判断是否触发failover。这个不用改ani_error的逻辑，不加全局变量，但是  **只能识别给客户端返回的错误码**  ，后台线程报的错误码无法识别


选方案二，原因有：

1. 指定错误码触发failover不是常见场景，设错了很容易导致数据库宕机（调研发现oracle对table not exist这种错误码，设置了也不触发failover）
1. 后台线程的错误码，不会抛出，用户也感知不到
1. 方案一必须在ani_error里加全局变量，不符合编程规范


  


```
// 获取每层的错误码
CodError codGetEachErrorCode(CodUint32 depth)
{
    if (depth >= gErrorInfo.stack.depth) {
        return 0;
    }

    return gErrorInfo.stack.errors[depth].code;
}
```

在anrAckError里判断每个多级错误码，是否在KNL_ATTR->failoverErrors内，如果在，则触发一次condition failover流程

优化点：为了让用户感知到错误码，在触发condition failover后，延迟1秒后abort（TODO）

###   [4.3 ](https://conf.yasdb.com/pages/viewpage.action?pageId=91780307#43-%E7%89%B9%E6%80%A7%E6%80%A7%E8%83%BD%E7%82%B91)    剩余redo同步

当主库发生非网络故障时，主库还可以发送redo给备库，尽可能做到failover后数据不丢失。

在检测到故障时，首先锁住rdFlush，不让继续产生redo，然后根据保护模式，决定是否等待redo同步。

尝试等待最多30秒，将redo同步到至少一个同步备（可连接，状态正常的备库）

### 4.4 特性可维可测设计

可测性：测试可以  通过unmount文  件等构造文件故障场景，去触发文件故障failover。错误码条件可以直接设置，去构造场景测试。

可维护性：alter.log,  run.log 均有触发failover的条件日志记录。

# 4. 主要应用场景

## 4.1 需求本身的主要应用场景

1、YCS级别的配置参数在有些情况下需要做调整，只能采取重启YCS的方式，成本太高

2、YCS级别的配置参数的查看只能通过查看.ini配置文件来看，没有更方便的入口，使用层面不友好

## 4.2 需求与其他特性的关联场景

1、如果被修改的参数是ycr配置中相关的配置参数，要考虑ycr相关操作和配置参数修改之间的关联性，比如并发---不涉及，此次修改只涉及.ini中配置文件，不涉及ycr相关配置参数

2、是否涉及到工具的新增，如果涉及到工具新增，需要考虑工具层面的使用：包括工具的可维护性，工具使用的友好性，工具使用过程中可能出现的故障以及工具本身的并发----不涉及工具的新增，但并发是要考虑的

# 5. 概要测试设计

## 5.1 功能测试设计

### **1.测试设计整体思路**

配置参数层面的修改原则上是优化性需求，实现机制也会比较简单，而且针对性比较强，所以，在测这部分需求的过程中需要重点从痛点场景和主要应用场景出发进行测试，优化性需要还要考虑用例的可维护性。整体测试思路如下：

1）对参数动态修改的实现方式进行基本测试，这里需要校验的是开发层面的代码逻辑，非重点

2）对参数的修改方式做验证，这里需要重点验证，考虑实现的合理性以及可扩展性

3）对"参数动态修改"功能做验证，这里是重点验证场景，功能层面验证功能完备性

4）考虑参数修改过程中可能伴随着的其它动作，从并发的角度出发（本身配置参数修改的并发、配置参数修改操作和其它ycs级别操作的并发）

5）考虑参数修改过程中可能产生的故障，从客户使用的维度出发进行设计，这里不只包括工具本身的故障，可以考虑到任何可能发生的故障点，思维可扩散

6）整个测试过程中考虑可测可维性，包括但不限于动态视图等观测手段

7）测试过程中涉及任何产品文档中资料相关变更点，需要在设计文档中有说明并做同步验证

### 2.关键数据、测试场景的构造方法，用例自动化方法，可能涉及的测试框架说明。

#### （1）测试方法说明

1）在覆盖基本参数列表时，重点考虑等价值和边界类法进行覆盖测试

2）对于故障场景的测试，采用错误推测法进行

3）对于并发场景，从开发需求实现机制的角度出发，重点采用场景法进行场景梳理，涉及到难点构造场景，及时和第一开发责任人同步对齐

#### （2）用例自动化方法

1）该需求可能涉及到工具层面的新增和接口的新增，guider框架原则上需要新增对应的自动化接口，需要在迭代测试中考虑到相应工作量（若已有接口，忽略）

2）对于并发场景，优先考虑testkill框架

3）对于testkill不可自动化场景以及故障场景，优先考虑HA框架

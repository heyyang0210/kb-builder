#   [视图依赖更新](#视图依赖更新)  

##   [1. Overview（概述）](#1-overview概述)  

当前view/force view存在元信息不存在或信息维护不正确的问题，例如创建force view后，无法从DBA_OBJECTS的STATUS判断视图是否合法，又例如编译视图后（执行DML）从DBA_TAB_COLUMNS查询不到视图列的信息。

视图创建时会在系统表OBJ$、VIEW$、COL$、DEPENDENCY$插入数据，编译视图时则需要更新这些系统表上对应行的值，以方便用户查看视图例如DBA_VIEWS、DBA_TAB_COLUMNS、DBA_OBJECTS等等。

force view与view不同的是，force view创建时， 如果基表不存在，视图依然要创建成功，当前是通过不verify view的subquery来实现。

但是不verify view的subquery， 会存在以下问题：

- 没有dependency 信息
- 没有Subquery的推导结果，无法生成View的Column List。


force view创建后，系统表中没有对应的dependency信息，也没有column信息，当访问视图时，会编译视图，更新视图的dc，包括dependency list和column，但这仅限于内存上的操作，没有更改系统表，用户无法通过查看视图观察到。

##   [2. Features（功能特性）](#2-features功能特性)  

1. 创建force view时候，尝试编译视图，如果此时视图的基表都存在，且视图编译能成功，在创建的同时就插入dependency信息和column信息
1. force view/view 的基表发生变化，触发视图重新编译，涉及到视图的元数据更新时，要同步更新系统表中view的元信息。
1. 维护视图的status，当视图基表发生变化，触发视图重新编译，成功，则将视图的状态更新为valid， 失败，则将视图的状态更新为invalid


##   [3. Interfaces（接口）](#3-interfaces接口)  

各种视图：

DBA_OBJECTS：查看对象的status，modify time

DBA_TAB_COLUMNS / DESC：查看视图的列信息

DBA_VIEWS： 查看视图的view text

DBA_DEPENDENCIES：查看视图依赖的基表信息

##   [5. Detail Design（详细设计）](#5-detail-design详细设计)  

###   [视图创建 （force view）](#视图创建-force-view)  

创建force view时候，尝试verify，即调用verifyViewSubQueryCols，该函数用来获取视图columns定义。

如果verify出错，无论什么原因，都不报错，将已经生成的dependency list清空，column list恢复default状态。

**column list恢复default状态**

- 如果视图没有指定列，verify失败，需要重新讲column list清空
- 如果视图指定了列，verify失败，将这些列信息恢复初始状态，即data type为unkown


如果verify成功，则创建的视图就跟不带force创建的视图一样：有columns， 有dependency， 视图定义是展开的(select * 会展开成具体的列)。

```
-- 语法相关的错误，force view也会报错
create or replace force view test_force_view as select from t1;

-- verify相关的报错，force view不会报错，视图创建成功，只是视图的状态是invalid

-- 例如这种子查询的列数与view的定义不匹配，不会报错，只是视图状态是invalid
create or replace force view test_force_view(id) as select id, c1 from t1;

```

###   [视图编译](#视图编译)  

当对视图做DML时，需要判断视图是否有效，是否需要重新编译，重新编译可能会发现视图的元数据更新，需要刷新元数据。

**Oracle**

###   [Oracle可以准确识别基表的哪些DDL需要触发视图刷新元数据。](#oracle可以准确识别基表的哪些ddl需要触发视图刷新元数据)  

- add column： 刷新obj$的stime，刷新dependency$里的time，访问视图不会刷新视图的元数据。
- drop column：刷新obj$的stime
- 如果删除的不是视图依赖的列，刷新dependency$里的time，不会触发视图刷新元信息
- 如果删除的是视图依赖的列，不刷新dependency$ time，会把视图的status设置成invalid，触发视图刷新元信息


同理，modify column也可以精准识别是否需要刷新视图的元信息，从而去更新视图的status。

一些不影响表的列信息的ddl， 比如add partition， enable row movement等DDL，不会更新依赖视图的status。

综上描述，Oracle发现基表的DDL会影响依赖它的视图，会把视图的状态设置成invalid，再次查询视图的识货，就会刷新视图的元数据。

dependency$的d_attrs列上记录了view依赖的基表的列信息，基表的ddl首先自己判断是否需要刷新对象的元数据，如果需要刷新，

接着判断dependency$里有没有视图依赖这个表，如果有视图依赖这个表，则进一步判断是否依赖了要修改的列：

- 有依赖要修改的列：不更新dependency$的 time，但失效依赖它的对象
- 没有依赖修改的列：更新dependency$的 time，不失效依赖它的对象


###   [备机查询](#备机查询)  

当备机上查询时，如果当前视图依赖的基表dc失效，需要重新编译，且需要刷新视图的元数据信息，则备机上报错.

例如，主机上将基表的一列删除，如果这列视图依赖了，备机查询就会报错。

主机上的视图是invalid， 备机上查询也会报错，因为查询要触发元数据刷新，就会报错。

```
SQL&gt; select * from test_force_view;
select * from test_force_view
*
ERROR at line 1:
ORA-04045: errors during recompilation/revalidation of LYQ.TEST_FORCE_VIEW
ORA-16000: database or pluggable database open for read-only access


```

**Yashan**

首先，视图重编译和刷新元数据是两个场景。

视图重新编译可能会引起视图元数据的变化，需要刷新视图系统表中的元数据。元数据做全量刷新，即删除col$， dependency$中view相关的信息，重新写入。

视图重编译触发条件：

- view第一次访问，加载view dc后，是未verify状态，需要重新verify： 数据库重启后，view dc淘汰后再次访问
- view依赖的基表发生ddl，导致dc失效
- 权限发生变化


视图重新编译之后，要判定是否需要刷新元数据，这一点无法做到和oracle一致，但是可以精确到DDL。本次方案不精确到列的DDL。

触发元数据刷新的DDL：

- drop column
- modify column

###   [编译成功](#编译成功)  

- dependency$里相关信息全部删除，重新插入
- col$全部删除重新插入
- status刷新成valid


###   [编译失败](#编译失败)  

编译失败也要刷新元信息

- column 的数据类型全部刷新成unknown，长度，精度等信息也要刷新
- dependency list对比一遍，将已经不存在的对象从depenency$里删除
- obj$里的status一定本身就是invalid， 不需要刷新


###   [Force View](#force-view)  

force view有一些特殊的处理，如果创建的时候基表不存在，且子查询是select *，view text就会存成select *，但是后续一旦compile成功过一次，需要像普通view一样，将view text展开，从此之后不再随着基表列数的变化而变化。

###   [备机查询](#备机查询-1)  

只有视图是valid状态时，备机才能查询

备机查询如果发现视图基表发生变化，可以重新编译，但是如果需要更新视图元数据，则报错。

如基表增加一个索引，会失效基表dc，备机查询的时候会触发视图重新编译，但是不会触发视图更新元数据，备机是可以查询的。

基表如果drop column，引起基表dc失效，备机查询的时候不仅出发重新编译，还会触发更视图元数据更新，就会报错。

##   [元数据刷新并发控制](#元数据刷新并发控制)  

本次设计中，会触发视图刷新元数据的DDL只有drop column和modify column，且为粗粒度的，无论是否影响到对应的view依赖的列，我们都要刷新视图元数据，因此对应DDL会更新依赖它的视图的状态，不需要更新dependency$。

###   [判断是否需要刷新元数据](#判断是否需要刷新元数据)  

**主机**

首先，在主机上视图的编译不可能并发：

- 编译视图
- 编译完成之后，不能放视图锁，判断视图的status，如果是invalid，则刷新视图元数据
- 更新元数据
    - 先lock主view obj的status： 防止刷新元数据过程中，有并发的会影响视图状态的ddl发生
    - 判断持有的dc是否全部有效，如果有失效的dc， 则回滚重新编译： lock之后再判断，即使判断之后再有dc失效，也不影响本次编译的结果


**备机**

- 编译视图
- 编译完成之后，检测视图的status。
    - 如果是invalid，则报错
    - 如果是valid，进一步检测持有的所有dc
        - 持有的dc全部是valid， 那本次视图编译的dc就是可用的
        - 如果有失效的dc，则重新编译


###   [列级别DDL并发控制](#列级别ddl并发控制)  

如果后续要做精细化控制，则只需要维护好dependency里的列信息即可，本次不做精细化控制，因为dependency$的d_attr上列信息的bitmap如果存储编码，如何维护还没有设计好。

##   [6. Testcases（自测用例）](#6-testcases自测用例)  

```
-- 是否为force view、基表存不存在、subquery是否合法、view列定义是否合法、视图创建后是否alter/drop基表
-- 检查DBA_OBJECTS、DBA_TAB_COLUMNS、DBA_VIEWS、DBA_DEPENDENCIES

-- 基表不存在，force view创建成功，subquery列数和视图定义对不上
-- 正常创建，DBA_TAB_COLUMNS为unknown，STATUS为invalid
create or replace force view fv(c1, c2) as select c1 from fv_tab; 

-- 基表存在，force view创建成功
drop table fv_tab;
create table fv_tab(c1 int);
-- DBA_TAB_COLUMNS能查到列的准确定义，STATUS为valid
create or replace force view fv as select * from fv_tab; 

-- 基表存在，force view创建成功，编译后drop columns
drop table fv_tab;
create table fv_tab(c1 int, c2 char(100));
create or replace force view fv as select * from fv_tab; 
-- alter后，STATUS就已经是为invalid
alter table fv_tab drop column c1;
select * from dba_objects where OBJECT_NAME=upper('fv');
-- 报错，触发重新编译，DBA_TAB_COLUMNS能查到unknown，STATUS为invalid
select * from fv;

-- 基表存在，force view创建成功，编译后add columns
drop table fv_tab;
create table fv_tab(c1 int, c2 char(100));
create or replace force view fv as select * from fv_tab; 
-- alter后，STATUS仍为valid
alter table fv_tab add c3 char(50);
select * from dba_objects where OBJECT_NAME=upper('fv');
-- 正常，触发重新编译，DBA_TAB_COLUMNS能查到列类型，STATUS为valid
select * from fv;

```

1. 识别是否需要刷新元数据

##   [1. Overview（概述）](https://conf.yasdb.com/pages/viewpage.action?pageId=133568278#1-overview%E6%A6%82%E8%BF%B0)  

YashanDB目前仅支持对表开启附加日志，在进行逻辑复制的过程中，如果有新创建的表，不能自动开启附加日志，需要用户手动开启。而支持数据库级别的附加日志后，所有用户表都可以同时启用附加日志，并且对于新创建的表，会自动记录CREATE TABLE的附加日志，并对新创建的表启用附加日志。数据库级别的附加日志适合于全量逻辑复制场景，只需在部署时设置一次，无需关心新创建的表，生成环境中更为常见。

##   [2. Features（功能特性）](https://conf.yasdb.com/pages/viewpage.action?pageId=133568278#2-features%E5%8A%9F%E8%83%BD%E7%89%B9%E6%80%A7)  

1. 需要区分HEAP，TAC，LSC三种表类型，可任意组合启用。
1.     - 3种表的日志差异比较大
    - 列存的逻辑复制场景很少见，合作伙伴DSG目前仅支持HEAP的
    - rowid逻辑不同（云臻的逻辑复制适配，有可能会用到rowid，但目前没有提需求）

1. 支持3种附加日志模式：
1.     - ALL模式和表级附加日志一样
    - PRIMARY KEY模式下，有主键则记录主键，没有则尝试记录非空唯一索引或整行
    - 新增MIN模式，只记录rowid，因为有些厂商（比如云臻）会在源库和目标库上把rowid做映射，解决表没有主键的场景，所以这次把这个场景一起支持了（表级附加日志保持不变，不支持MIN）



|功能|设计表现|设计说明|
|:---|:---|:---|
|MIN模式附加日志|对于UPDATE和DELETE，只记  录rowid  。DDL全记录|这种模式对性能的影响最小，rowid天然具有唯一性，适用于有大量无主键表的场景。因为不同数据库的rowid不一定一样，需要上层工具支持rowid映射，才能完成逻辑复制。|
|PRIMARY模式附加日志|对于UPDATE和DELETE，当表有主键时，记录主键，否则如果有非空唯一索引，记录唯一索引，否则记录整行。DDL全记录|某些表不一定有主键，则尝试找唯一索引，没有唯一索引，则记录整行，以便目标端组装where条件时，可以定位到这一行。|
|ALL模式附加日志|对于UPDATE和DELETE，记录整行。DDL全记录|ALL模式将无脑附加整行数据，即使同时开了表级PRIMARY类型的附加日志。|


##   [3. Interfaces（接口）](https://conf.yasdb.com/pages/viewpage.action?pageId=133568278#3-interfaces%E6%8E%A5%E5%8F%A3)  

####   [SQL语法](https://conf.yasdb.com/pages/viewpage.action?pageId=133568278#sql%E8%AF%AD%E6%B3%95)  

1. 设置附加日志模式：  **ALTER DATABASE {ADD | DROP} SUPPLEMENTAL LOG DATA[({ ALL | PRIMARY KEY } [, { ALL | PRIMARY KEY}]) COLUMNS]**  ;
    1. MIN：ALTER DATABASE {ADD | DROP} SUPPLEMENTAL LOG DATA;
    1. PK：  ALTER DATABASE {ADD | DROP} SUPPLEMENTAL LOG DATA (PRIMARY KEY) COLUMNS;
    1. ALL：ALTER DATABASE {ADD | DROP} SUPPLEMENTAL LOG DATA (ALL) COLUMNS;
    1. 组合：ALTER DATABASE {ADD | DROP} SUPPLEMENTAL LOG DATA (ALL, PRIMARY KEY) COLUMNS;
1. 设置附加日志生效的表类型：  **ALTER DATABASE {ADD | DROP} SUPPLEMENTAL LOG TABLE TYPE ({ HEAP| TAC| LSC } [, { HEAP| TAC| LSC}] ...);**
    1. 所有表：ALTER DATABASE {ADD | DROP} SUPPLEMENTAL LOG TABLE TYPE (HEAP, TAC, LSC); 
    1. HEAP表：ALTER DATABASE {ADD | DROP} SUPPLEMENTAL LOG TABLE TYPE (HEAP);  #默认


#### 动态    [视图](https://conf.yasdb.com/pages/viewpage.action?pageId=133568278#%E7%B3%BB%E7%BB%9F%E8%A7%86%E5%9B%BE)  

select SUPPLEMENTAL_LOG_DATA_MIN, SUPPLEMENTAL_LOG_DATA_PK, SUPPLEMENTAL_LOG_DATA_ALL, SUPPLEMENTAL_LOG_TABLE_TYPE from v$database;

- SUPPLEMENTAL_LOG_DATA_MIN：YES/NO，表示MIN模式是否开启；
- SUPPLEMENTAL_LOG_DATA_PK：YES/NO，表示PRIMARY KEY模式是否开启；
- SUPPLEMENTAL_LOG_DATA_ALL：YES/NO，表示ALL模式是否开启；
- SUPPLEMENTAL_LOG_TABLE_TYPE：字符串，表示已经生效的表类型，比如 HEAP, TAC表示这两个表使能了全库附加日志。


##   [4. Specification And Constraints（规格与约束）](https://conf.yasdb.com/pages/viewpage.action?pageId=133568278#4-specification-and-constraints%E8%A7%84%E6%A0%BC%E4%B8%8E%E7%BA%A6%E6%9D%9F)  

1. 只能在主库上执行，且数据库  状态 >= MOUNT。
1. ADD和DROP可重复执行，不报错。
1. 开启附加会影响数据库性能，ALL劣化最大，MIN劣化最小。
1. 当数据库级和表级附加日志都开启的情况下，按叠加后的状态作为开关，比如其中有一个是ALL模式，那就按ALL模式；如果表级开了UNIQUE，库级开了PRIMARY，按UNIQUE模式。
1. 表级附加日志开启的情况下，会忽略SUPPLEMENTAL LOG TABLE TYPE的设置。
1. MIN模式不支持LSC表。
1. UDT  类型逻辑复制不支持解析。

###   [5.2 Data Structures & Flow（数据结构与流程）](https://conf.yasdb.com/pages/viewpage.action?pageId=133568278#52-data-structures--flow%E6%95%B0%E6%8D%AE%E7%BB%93%E6%9E%84%E4%B8%8E%E6%B5%81%E7%A8%8B)  

#### 附加日志持久化

```
typedef union UnDbLogicRedoFlag {
    CodUint32 value;
    struct {
        CodUint8  tabType;     // 哪些表类型响应全库附加日志
        CodUint8  logicMode;   // rowid, pk, all 模式
        CodUint8  mountChanged : 1; // 是否在mount下修改过，主要是为了OPEN后补一条redo，以便同步给备库
        CodUint8  unused1: 7; 
        CodUint8  unused2;
    }
} DbLogicRedoFlag;

typedef struct StAnkCursor {
    .....
    CodUint8 logicRedoFlag; // 已有字段，目前只用了前2位，用来区分update和行链接。可以取三位表示模式，rowid，primary key，all
    ......
} AnkCursor;
```

1. 修改DbLogicRedoFlag的流程：
    1. 加全局锁spinlock，防止并发
    1. 暂停checkpoint
    1. 生成redo并刷盘（OPEN模式）
    1. 修改ctrl，mount模式下要设置mountChanged为TRUE
    1. 恢复checkpoint
    1. 放锁
1. 读取DbLogicRedoFlag的流程：
    1. DML开始时，在heapLogicRedoPrepare或swfBeginXXXLogicRedo里获取ctrl上的DbLogicRedoFlag，无需加锁
    1. 将DbLogicRedoFlag的模式，存到cursor的logicRedoFlag上
    1. 在update，delete中记录where条件的附加日志时，对比表级附加日志的类型，选择合适的模式，生成where条件日志
1. mount下修改，open后补充redo：
    1. 加全局锁spinlock，防止并发
    1. open后发现mountChanged为FALSE则忽略返回
    1. 生成redo并刷盘
    1. 修改ctrl，将mountChanged设为FALSE
    1. 放锁


#### ROWID

有些厂商支持通过rowid映射来处理没有索引的表的逻辑复制，此外oracle会在任何附加日志模式下都会记录rowid。所以在MIN，PRIMARY，ALL模式下，我也把rowid都无脑记录，不区分细节场景，这几个字节对性能影响不大（）。

- HEAP的rowid已经在DSG提的22.2的补丁版本SR里加上了，开了附加日志就会在insert，update，delete中记录。
- TAC的rowid，可以在insert，update，delete的时候拿到，可以新增redo类型，加上rowid。
- LSC的rowid，由于热数据转为冷数据后，同一行的rowid会发生变化，这个就会导致rowid失去“唯一索引”的作用。


LSC的rowid记录3个方案：

1. 设置LSC表使能后，不能设置MIN模式，报错。对LSC的primary key, all附加日志，用老的不带rowid的日志类型，也就是和TAC搞两套日志类型，并在logminer解析的时候，rowid设置为0
1. 设置LSC表使能后，不能设置MIN模式，报错。对LSC的primary key, all附加日志，和TAC用一套日志类型，但rowid设置为0，logminer解析的时候自然也是0
1. 正常记录LSC的rowid，但是文档中说明  rowid可能会变的告  警


##### TAC的rowid增加实现

1. 对于insert，新增LOGT_MINER_BEGIN_SWF_INSERT日志类型，在后面append这一批row的rowid
1. 对于update，新增LOGT_MINER_BEGIN_SWF_UPDATE日志类型，在后面append这一批row的rowid
1. 对于delete，新增LOGT_MINER_SWF_DELETE日志类型，在后面append这一批row的rowid


原有的redo类型，回放函数，logminer解析函数保留至少2个大版本，以满足兼容性。

####   [ALL模式](https://conf.yasdb.com/pages/viewpage.action?pageId=133568278#all%E6%A8%A1%E5%BC%8F)  

该模式和表级附加日志ALL模式一样（where条件不会记录LOB，超过32K的char，varchar，UDT等）。

#### PRIMARY KEY模式

与表级附加日志不同，数据库级别PRIMARY KEY模式下，不要求所有表都设置主键，如果有主键，则记录主键，没有则找非空唯一索引，如果都没有，则记录整行。

####   [create table as select](https://conf.yasdb.com/pages/viewpage.action?pageId=133568278#create-table-as-select%E5%A4%84%E7%90%86)  

这个语法的特殊之处是，YashanDB先记录了insert的redo，再记录了create table的aux日志，如果我们和aux日志一起，把SQL语句附加日志记录下去，会导致解析时先看到insert，再看到create table。

所以我们在insert 之前，就要将create table这条SQL语句的逻辑日志记下来。

###   [5.3 Compatibility（兼容性）](https://conf.yasdb.com/pages/viewpage.action?pageId=133568278#53-compatibility%E5%85%BC%E5%AE%B9%E6%80%A7)

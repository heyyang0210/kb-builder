# 1. 概述

目前处理消息的后台线程（GRC、GCS、GLS）不支持弹性扩缩，那么当用户配置了一个很小的数量或是初始值时，在某个时间段内有大量的并发连接或业务发生，后台线程不能自动扩展将成为一个性能瓶颈点；同时，如果某个时间段高峰业务，扩展了一定的线程数，后续再也不需要这么多线程了，为了减少资源的浪费，所以也要支持线程缩减。

为了彻底解决GMS多线程资源调度下， 重试消息与原始消息调度乱序， 导致出现不可预期的错误问题，重试消息将需要一定的机制保证能在原始消息处理之后在处理。

# 2. 需求分析

## 2.1 功能点分析

### 2.1.1  处理消息的后台线程新增机制

（1）线程动态扩缩

- 线程扩展：当大量业务下发时，消息队列中的数量达到活跃线程数的2倍，需要自动扩展线程
- 线程缩减：当业务结束一段时间后，某个线程的空闲时间达到一定程度时，需要自动退出
- 线程控制参数：GRC_TASK_COUNT、  GCS_TASK_COUNT、GLS_TASK_COUNT，默认设置为0，将会根据系统参数计算默认值，也可以自行配置大小
- 线程初始值及核心线程数：当后台线程控制参数为0时，将根据操作系统的配置来计算默认值，也就是核心线程数，具体是根据CPU的数量来决定


|CPU核数|核心线程数|
|:---|:---|
|1-3|1|
|4-15|2|
|大于15|grctask:cpu/6; glstask:cpu/6; gcstask:cpu/4|


（如果CPU核数是1，GLS、GCS、GRC的核心线程数各自是1）

（2）重试消息保序

- 正常情况下，重试消息在原始消息之后处理
- 如果先处理重试消息，对应的原始消息直接丢弃
- 原始消息和重试消息应该保证在同一个后台线程处理

#### 实现机制层面的变更

**reform线程改造优化**    
  reform线程只有在实例起停时才工作，那么reform线程可以作为线程动态扩缩的监控线程，同时将reform线程名称改为gmon。

（1）gmon线程被唤醒后，遍历msgCnt，如果对应的消息数大于一定的阈值（消息队列中的数量是活跃线程数的2倍），则增加相应的线程。

（2）遍历所有线程组，如果线程的空闲次数与活跃线程的比超过一定的阈值（0.8），则指定该线程退出。

## 2.2 应用场景

主要是应用于集群实例间GRC、GLS、GCS三种后台线程的动态扩缩，提高数据库性能以及减少资源浪费；保证原始消息和重试消息的有序性，减少不可预期的错误问题。

## 2.3 规格约束

#### 2.3.1　需求定义的规格、约束，系统/模块上下文等

- 部署形态：集群
- 节点个数：不限制节点个数（4节点的故障暂时还未转测，不支持）


#### 2.3.2　内部机制涉及的规格约束

- 只有AXC_GRC_TASK、AXC_GCS_TASK、AXC_GLS_TASK线程需要自动扩缩，且扩缩的范围需要在配置参数范围


# 3. 详细测试设计

## 3.1 测试设计方法

1、在23.1版本迭代2中已完成了GRC、GLS、GCS本身的功能测试，本次需求主要针对上述三种后台线程新增的动态扩缩功能进行测试，这部分主要采用场景法，通过构造大量业务下发场景，查看相关统计信息和动态视图进行观测

2、对于配置参数的修改，已有用例覆盖了涉及配置参数的基本测试点，这部分需要对最大值、最小值以及默认值的测试用例进行同步变更，以及新增测试配置参数作为线程控制参数的情况，这部分采用等价类和边界值法进行验证

3、  在涉及到对动态视图和统计信息的变更，按照修改点进行针对性测试，这部分主要是从场景的角度出发，所以主要采用场景法进行测试

4、对于重试消息的保序，配合故障点，构造原始消息和重试消息并存的情况，查看日志进行观测，这部分也采用场景法

5、机制引入后，对数据库整体性能的影响，通过场景法进行验证

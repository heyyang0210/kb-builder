加密引擎，作为基础模块，对外提供加解密基础能力。能力来源三个：

- 软件
    - openssl
    - GMSSL
- 硬件
    - PCIE


  


需求规格： 

1、实现基于硬件密码卡的通用加解密函数 

2、实现基于软件(gmssl库)的通用加解密函数 

3、把算法初始化嵌入到客户端、服务端和各种工具中，根据实际需要选择硬件或者软件加解密，后续的业务逻辑对具体实现不感知

 4、在1和2的基础上，实现和主干代码完全一致的特殊函数接口，减少代码改动。

此需求，仅提供基础算法能力，上层应用的选择，由上层逻辑控制（如配置参数/版本等）。

- 先根据  ENCRYPT_LIB进行库的加载
- 链路加解密/验签，根据自己的需要，加载自己的库。

### EVP接口适配

EVP是openssl自己的接口形式，GMSSL/PCIE需根据openssl接口形式适配。目标：自定义evpCtx及evpCipher存储相关数据信息，完全适配其流程，做到对外透明。

#### openssl

- 数据
    - evpCtx
        - 上下文
    - evpCipher
        - 属性信息：数据+回调函数
- 使用流程：
    - 申请  evpCtx-》获取evpCipher-》设置参数（key/paddingmode/初始化向量）-》加解密-》释放evpCtx


#### GMSSL适配

yasdb仅存关键数据key/paddingmode/初始化向量，后续设置参数，调用PCIE/GMSSL加解密函数。

- AniGmeEvpCipherCtx
- evpCipher，非openssl中 用不到，里面是openssl自己的逻辑。GMSSL/PCIE仅仅区分类型即可，适配成自身逻辑的结构  **。**


```
typedef struct StAniGmeEvpCipherCtx {
    CodUint32  encryptMode;
    CodUint8   paddingMode;
    CodBool    unused[3];
 	CodPointer cipher;
    CodUchar   iv[ANI_EVP_MAX_IV_LENGTH];
    CodUchar key[ENCR_MAX_KEYSIZE];
} AniGmeEvpCipherCtx;
```

**PCIE适配**

CTR 主要用在TDE业务里。CTR pcie不提供。两种处理方式

- 方式1：pcie中OFB替换CTR–不行，原因：
    - （1）OFB 和 ctr方式差异：OFB 和 ctr的计算方式有差异，密文结果不一样。
    - （2）密文结果不一样产生的问题： 涉及到主备情况，两instance的算法方式不一样，节点1加密，节点2解不开
- 方式2：此能力由其他库提供？由openssl提供，细节：
    - PCIE card 欠缺的能力由openssl补充。即  **ENCRYPT_LIB = **  **PCIE card 同时要加载openssl**
    - TDE是否能用到，没法通过配置参数nomount阶段  **提前预测**  ，因此，  ENCRYPT_LIB =   PCIE card只能  **提前强行加载openssl**


**结论：**

（1）选择方式2。

（2）EVP里所有的ctr方式走opnessl。非ctr方式，走pcie。

（3）如何使TED业务使用PCIE中的能力呢？后续添加OFB形式的算法类型EncrAlgo（ENCRYPT_ALGO_AES_128_OFB/ENCRYPT_ALGO_SM4_OFB）。注意：原算法类型ENCRYPT_ALGO_AES_128等，  **指的是ctr模式**  ，不能改变其含义（强行改成OFB等），否则有  **兼容性问题**  。

### 线程安全

**PCIE**

PCIE中内部的数据，以句柄的形式对外提供。需确认其线程安全属性，来确认使用句柄，是否是 线程私有/全局

|句柄|thread safe|其他|使用规则|
|---|---|---|---|
|设备|是|multi thread 可放心用|一个进程一个|
|会话|是|不建议多线程复用,建议一个线程一个会话；,建议会话数和线程数不超过 40 个|一个线程一个|
|密钥|否|thread unsafe|一个线程一个|


GMSSL/OPENSSL其他不涉及

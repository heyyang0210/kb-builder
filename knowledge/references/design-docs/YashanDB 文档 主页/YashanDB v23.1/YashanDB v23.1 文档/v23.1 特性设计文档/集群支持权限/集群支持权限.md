##   [4. Specification And Constraints（规格与约束）](#4-specification-and-constraints规格与约束)  

本方案设计时，集群对角色的创建、删除还没有进行适配（角色的适配在本方案的下个迭代），详见

[    [YDBRD-13500] 【共享集群】集群支持权限 - SICS-CoD Jira (yasdb.com)](https://jira.yasdb.com/browse/YDBRD-13500)  

[    [YDBRD-13514] 【共享集群】集群支持角色 - SICS-CoD Jira (yasdb.com)](https://jira.yasdb.com/browse/YDBRD-13514)  

因此自测时，授权、撤权的对象均为用户

如果集群模式部署的数据库在OPEN状态下（建库时会创建role并赋予权限，该操作不拦截），执行对角色的grant和revoke，会报错    `YAS-00004 feature "grant or revoke to role in cluster deploy mode" is not implemented yet`  

##   [5. Detail Design（详细设计）](#5-detail-design详细设计)  

####   [数据结构](#数据结构)  

```
typedef struct StBcstGrant {
    CodUint32 action;
    CodUint32 granteeId;
    CodUint32 grantRole;
    CodUint64 objId;
} BcstGrant;

```

####   [流程](#流程)  

授权撤权的流程与    `CREATE/ALTER/DROP TABLE/SEQUENCE`    类似，执行    `DDL`    的实例需要广播给其他实例，其他实例收到广播，同步修改或者失效dc，返回确认后，执行实例才能认为该    `DDL`    成功

####   [版本控制](#版本控制)  

注意到，在执行计划中会保存有一份用户和sql的缓存，如果权限没变，那么该缓存可以直接使用，详见    `anlHasChangedPrivilege`  

这一缓存的有效性靠    `privNum`    来保证，但目前机制仅修改了权限掩码，需要进行适配，在    `msgRevoke`    中修改

####   [并发控制](#并发控制)  

-   `GRANT-GRANT`    并发
-   `GRANT-REVOKE`    并发
- 不会，授权撤权需要修改系统表，广播发生在事务提交阶段，广播不成功，事务不会结束，通过事务和gcs机制保证并发
-   `GRANT/REVOKE-DROP`    并发
-   `GRANT/REVOKE`    给用户上共享锁，包括实例内部的    `user->statusLatch`    和GLS机制对user对象的锁，因为这一部分只涉及权限掩码和版本号的修改
-   `DROP USER`    上的是排他锁，必须等所有共享锁释放，机制上不会出现死锁


>   假设实例A，B，A上并发执行同一个权限的两次授权和一次撤权    如果A的顺序是    `GRANT-GRANT-REVOKE`    ，B是否会收到    `GRANT-REVOKE-GRANT`    的广播从而导致权限不一致？

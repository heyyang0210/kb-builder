# YashanDB 存储 SQL

本目录保存存储服务实际执行的版本化迁移。文件统一命名为 `NNN_<action>_<object>.sql`：三位版本号控制顺序，后缀说明变更动作和对象。`start.sh migrate` 显式发现并按版本执行，在 `KC_SCHEMA_MIGRATION` 中记录文件名和 SHA-256；服务正常启动只校验版本、别名和摘要。已执行脚本不得修改或复用版本号，摘要不一致时拒绝迁移或启动。

历史迁移确需纠正文件名时，必须在 `migration-aliases.properties` 登记“新版本标识=数据库已记录的旧版本标识”。迁移器仅在别名双方数字版本相同且 SQL 摘要匹配时跳过执行；新环境记录新名称，已执行环境保留原记录。别名只解决历史改名兼容，不得用于替换或重排 SQL。

统一构建会在 SQL 产物中生成 `migration-source.properties`，记录 Git revision、迁移源是否存在未提交变更以及聚合 SHA-256。`start.sh migrate` 只允许执行来自已提交 Git 版本的产物；普通启动仍只做数据库摘要校验。禁止先从脏工作树执行迁移、再修改或格式化 SQL 后提交。

## 013 的迁移范围与验收

- 新代码直接查询删除字段，结构升级不可省略；脚本已包含超级管理员角色和授权的基础数据初始化，无需另做业务数据搬迁。
- 既有版本的三个可空删除字段应为 `NULL`，`DELETED_WAS_CURRENT` 应为 `N`。该字段表示“删除前是否为当前版本”，当前版本无需回填为 `Y`；保留原发布状态、当前版本指针和手册/大纲/版本/节点数据。
- SQL 不写用户角色表，不应批量提升既有用户。认证初始化会为配置指定的本地内置管理员补齐 `SUPER_ADMIN`；上线验收须单独核对该权限变化及初始化审计。
- 平台管理员授权采用一次性复制，并非动态角色继承。后续平台管理员授权变化须核对超级管理员的对应授权；应用角色权限定义也须保持一致。
- 执行前确认目标环境、已应用迁移及摘要、四字段与超级管理员是否已部分创建、平台管理员启用状态和授权基线。先在个人开发库验证，再由负责人批准并执行生产迁移，保留结构及相关数据快照。
- 验收应检查旧行默认值、业务行数/发布状态/当前指针未变、超级管理员授权等于平台管理员基线加两个新增动作、用户角色表未被 SQL 改动，以及迁移登记与摘要。认证启动后的本地管理员变化单独验收；最后执行只读 `verify` 与真实 API 检查。
- 脚本由版本登记防止成功后重复执行，不保证部分失败后可直接重跑。迁移器调用 `rollback` 不足以证明 DDL 整体可回滚；需在个人开发库验证 DDL 提交语义和中途失败恢复步骤。生产失败立即停止，核对实际结构与数据，禁止盲目重跑或手工补登记绕过校验。后续纠正采用新增版本，不修改已执行的 013。

手册与大纲采用稳定主体和版本分离模型：一本手册恰好对应一个 `KC_MANUAL_OUTLINE` 主体，大纲主体可以拥有多个 `KC_MANUAL_OUTLINE_VERSION`。大纲主体不重复保存手册的产品和名称，展示时通过 `MANUAL_ID` 获取。所有内部主键、模块内关联键以及权威目录 ID 均使用 `BIGINT`；主键生成器按手册、大纲、责任治理和人员四个稳定业务边界管理，不按每张物理表扩张序列数量。

跨表归属、删除保护和发布一致性由 Repository 事务与巡检保证，不使用物理外键。CAS、组织和产品目录仍是权威源；`KC_MANUAL.PRODUCT_ID` 保留关联键语义，`PRODUCT_NAME` 保存手册查询所需的产品名称快照，普通列表不为展示名发起关联查询。历史数据分阶段迁移期间 `KC_MANUAL.ORG_UNIT_ID` 可以为空，负责人没有稳定 CAS ID 时不写 `KC_MANUAL_OWNER`。

生产凭证只通过运行时环境变量注入，不得写入 SQL、配置文件、迁移报告或日志。
